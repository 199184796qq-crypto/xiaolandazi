# 从沟通目的挖掘事实支持的角度 v2

上轮已经分析了目的。现在沿用这些目的编号，结合当前完整事实，挖掘多个真正不同的讲述角度。角度是具体的沟通任务，不是原句改写，不是固定口播。

每个目的通常给2至5个角度。不同角度应改变观众要理解的事情、组织方式或选择理由，不能只是换同义词；算账不必每次都讲饭桌，可以按已给计价单位、单次预算、数量选择、制作投入等实际可用方向展开。没有依据的方向不凑数。事实丰富时可跨记录组合，每个角度关联1至20项真实事实编号，全表最多160项。

允许生活场景、感受联想、常见顾虑及主播主观价值判断；它们不要求每句话逐字对应事实。它们不能成为新的具体规格、处理工序、他店报价、客人经历或确定的交易承诺。名称、制作工艺、计价单位、金额、优惠条件、商品归属必须准确。禁止表达和建议口径是内部表达控制，不能成为讲述正文。反例数字不能用来推算商品规格。

关联事实是可用依据，不要求后续把每条事实全部念完。讲述任务说明怎么帮助完成目的，适用条件说明何时讲。不得承诺“每天制作”就等于“今天下单今天发货”，不得把感官比喻自动升级为收货温度承诺。

每个角度必须输出优先级（1至100，越高越优先）、任务类型（required必答，optional可选推进）、采用条件（1至8项，程序全部核对）。条件类型只能是always（一般适用）、question（仅互动）、mainline（仅主线）、active_benefit（仅真实有效优惠可用）、purpose_match（值为目的编号）、task_contains（值为当前轮盘任务的明确关键词）。除purpose_match/task_contains外条件不得带值。适用条件字段只作说明，不能替代程序条件。问价格必须先回答当前商品价格，优惠可选且必须带active_benefit条件；角度的关联事实须为完成该任务所需的完整依赖，不能把多个商品的全部事实机械塞到每条角度。主线角度应允许在相关轮盘任务中采用，不强制生成成交口令。

只输出以下JSON，目的编号必须来自上轮，事实编号必须来自输入。不要输出标题、口播、分析或额外字段：

{"目的角度表":[{"目的编号":"P01","角度":"简短中文角度名","讲述任务":"围绕相关事实完成的一件具体沟通任务","关联事实":["F001"],"适用条件":"适用的观众问题、当前讲解任务或场景","优先级":90,"任务类型":"optional","采用条件":[{"类型":"always"}]}]}


## 全表字段协议检查

对每一行采用条件都使用中文字段“类型”和可选的“值”。不要在输出中途换成type/value；不能用“目的编号”代替条件的“值”。condition枚举值保持约定英文，字段名和枚举值是两个概念。

合法条件完整示例：{"类型":"always"}、{"类型":"question"}、{"类型":"mainline"}、{"类型":"active_benefit"}、{"类型":"purpose_match","值":"P01"}、{"类型":"task_contains","值":"保存方法"}。purpose_match/task_contains必须带值，其余条件不得带值。字段不能为null，不能新增字段或未知枚举。

输出前逐行检查全表，不能前10行中文字段、后8行英文字段。每行必须有优先级、任务类型和采用条件；事实依赖必须齐备。反例数字不能变成商品规格，“鸭这道菜不到90元”不能变成“一桌饭总花费不到90元”。
