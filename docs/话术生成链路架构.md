# 话术生成链路架构

更新时间：2026-10-14

> 本文档梳理直播伴侣系统「话术生成」的完整链路：从卖点×角度规划，到正文生成、改写、合规审核，最后送到 TTS 播出的全过程。基于代码实测（`management-service`），非设计文档，是当前实现的事实记录。

---

## 1. 核心结论

1. 一条主线话术从"卖点×角度"到"TTS"是一条**串行链路**，中间依次经过：角度规划 → 正文生成 → 同义改写 → P0 审核 → 最终内容复核 → 采纳 → TTS 合成。
2. 正常不违规的话术，**模型调用 4 次**：正文（mainline_text）、改写（mainline_text_rewrite）、最终复核（mainline_final_content_review）、TTS（mainline_tts）。踩到硬词才额外触发「局部重写」和「P0 语义复核」。
3. 事实、风格、P0、四层结构全在 **system 消息**里；卖点×角度、角度钩子工作卡、字数上限等在 **user 消息**里。
4. 事实按「商品」筛选（不按角度），一个商品的一堆事实作为一个 JSON 数组塞进一条 system。
5. 话术防重复靠 4 层机制（采样随机 + 程序轮换 + 近期避重 + 同义改写），**砍掉同义改写不会让话术逐字一样**，只会让高频短语复读风险回升。

---

## 2. 总体流程概览

```
规则层 → 行业层 → 当前直播方案 → 用户纠正/智能体记忆
  → 当前直播实时上下文 → 智能决策 → 文本生成 → TTS → 音频分发
```

主线话术生成的主循环是 `advanceAnchorCycle`（`anchor_style_cycle.go:680`），一次循环产出一段话术。

---

## 3. 主线话术生成流程（一次循环 = 一段话术）

### A. 前置检查（程序，无模型）
1. 加锁 + RunID/Revision 校验（防并发、防过期请求）
2. 状态检查：上一轮未确认（Uncertain）、已结束（ended）、被拦（blocked）
3. 风格 / 打分基准 / 卖点轮盘一致性校验

### B. 规划层
4. 安装 P0 词表母版（读文件，程序）
5. **宏观反馈**（若待回灌）→ `accepted_macro_feedback`【模型】—— 滑动窗口三项回灌
6. 渲染本段 prompt（程序）
7. **角度规划**（若开启）→ `mainline_angle_plan`【模型】—— 确定卖点×角度

### C. 生成层
8. **复用检查**（程序）—— 命中话术池直接拿旧话术，跳过下面所有模型调用
9. **正文生成** → `mainline_text`【模型】（若 P0 局部重写则走 JSON 协议）
10. **同义改写** → `mainline_text_rewrite`【模型】
11. 价格漂移检查（程序）

### D. 后处理层（程序，无模型）
12. 复读检测（和已播话术逐字比对，复读则换角度重试）
13. 风格打分 + 回灌 feedback
14. 标点修复（可选）

### E. 合规审核层
15. P0 字面扫描（程序，硬词表）
16. **P0 语义复核** → `mainline_p0_context`【模型·仅命中"需语境判断的词"】
17. 讲座审核（讲座模式才有）
18. **最终内容复核** → `mainline_final_content_review`【模型】

### F. 采纳层（程序）
19. AddCandidate 采纳进已接受列表
20. 记录审核事件、落库保存

## 4. 正文生成 Prompt 结构

正文生成入口：`completeCycleText`（`text_generation.go:258`），prompt 组装在 `renderCycleTextMessages`（`text_generation.go:102`）。

### 4.1 System 消息（本场稳定）

由「母版 + 四层结构内容」拼接：

```
system = 主线正文任务母版(mainline-text-task.md)
       + "不提"层（未知项正反不说）
       + "可说"层（纯事实列表）
       + "商品必要事实与使用边界"
       + "有效P0"（P0 词表规则）
       + "用户已确认的长期纠正规则"
       + "改写"层（禁说/安全改写）
       + "主播表达标尺"（风格禁用词/主力称呼池）
```

四层结构（母版 `mainline-text-task.md` 定义）：

| 层 | 内容 |
|---|---|
| 必说 | 本次任务（卖点×角度）是本段核心，围绕展开，不跑题不跳过 |
| 可说 | 本场有效事实是素材，可换场景/措辞，不要求逐条讲、不补写 |
| 不提 | 未确认项正反都不说，需要时说"这点帮您确认" |
| 改写 | 禁说→安全说法，不照念约束 |

硬约束（母版里）：主播表达标尺是硬约束（禁用词/禁用称呼绝不能出现，主力称呼/口头禅/算账习惯必须体现）；字数上限；换措辞避重（数字不变、动词换着来）；有效 P0 按条件理解，不是"最/第一"一律禁。

### 4.2 User 消息（本次任务，每次变）

```json
{
  "开头模式": "address_or_content | content_first",
  "本次任务": { "卖点": "...", "角度": "...", "观众顾虑": "...", "参考人群": "..." },
  "角度钩子工作卡": { "本段要完成的沟通任务": "..." },
  "讲述目的": "...",
  "程序计算的数值资料": [...],
  "环节": "opening | body | closing",
  "本次切入侧面": "...",
  "本段授权的商品称呼": ["1号链接"],
  "字数上限": 300,
  "近期正文（仅供避重）": "..."
}
```

### 4.3 卖点×角度是"拆开"给的

角度规划选好方向后，程序**故意不把整段范文塞给模型**（避免照念），拆成三个字段：

| 字段 | 值 | 作用 |
|---|---|---|
| `本次任务.卖点` | 卖点名称 | 必说的对象 |
| `角度钩子工作卡.本段要完成的沟通任务` | 角度规划出的"要讨论什么" | 本段要解决的问题 |
| `讲述目的` | plan.Goal | 为什么讲这段 |

## 5. 事实内容的组织

### 5.1 事实放在 system，且按「商品」筛选

- 事实不在 user，而在 system 的「可说」层，是一个 JSON 数组。
- 筛选函数 `HookFacts()`（`angle_hook.go:103`）：只保留「适用商品链接」命中当前商品的，**不按角度筛**——当前讲哪个商品，就把该商品的所有事实整包喂进去，模型靠「角度钩子工作卡」决定这次从哪几条切入。

### 5.2 事实在数据库的存储格式

一条事实底层存成带分隔符的字符串：

```
该商品开袋即食；禁说=不得宣传需要二次加工；安全改写=这款打开包装就能直接吃，很方便
```

程序在生成前拆成两块（`generationFactView` → `generationMaterialViews`）：

**「可说」层（纯事实）**：
```json
[ { "事实内容": "- [product/原料与月龄] 采用八个月土麻鸭。", "适用商品链接": ["1","2","3"] } ]
```

**「改写」层（禁说/安全改写指导）**：
```json
[ {
  "对应事实": "- [usage/食用方式限制] 该商品开袋即食。",
  "适用商品链接": ["1","2","3"],
  "负向约束及正向举例": [
    { "内容": "不得宣传需要二次加工。", "要求": "禁说" },
    { "内容": "这款打开包装就能直接吃，很方便。", "要求": "安全改写" }
  ]
} ]
```

## 6. 防重复 / 多样性机制（4 层）

| 层 | 机制 | 位置 |
|---|---|---|
| ① 模型采样随机 | qwen 生成 temperature 有随机性，同样 prompt 每次采样不同 | provider |
| ② 程序侧轮换 | 开头模式 / 表达展开建议 / 切入侧面，按段数轮换 | 生成前 |
| ③ 近期正文避重 | 把最近已播正文塞进 prompt，要求"换个说法" | 生成前 |
| ④ 同义改写 | 生成后程序侧再主动换一次措辞 | 生成后 |

关键结论：**砍掉④同义改写，同样卖点×角度也不会逐字一样**（②③轮换 + ①随机性还在）；④是"程序侧锁措辞"的兜底，专治"叮1分钟"这类高频短语复读。

## 8. 预览 vs 主线差异

「事实话术预览」（`fact_speech_preview.go`）走的是主线链路的**子集**：

| 环节 | 主线 | 事实预览 |
|---|---|---|
| 正文生成 + 同义改写 + P0 语义复核 | ✅ | ✅ |
| 角度规划 | ✅ | ✅ |
| 复用检查 / 复读检测 / 打分回灌 / 标点修复 | ✅ | ❌ 都没有 |
| 最终内容复核（mainline_final_content_review） | ✅ | ❌ 没有 |
| rejected 自动重试一轮 | ❌ | ✅ 预览特有 |

预览核心三步模型调用：正文 → 同义改写 → P0 语义复核（+ rejected 重试一轮）。

## 9. 互动话术 TTS 前缀

所有互动话术递交给 TTS 合成前，文本开头统一加 `****`（4 个星号）。

- 常量：`interactionTTSPrefix = "****"`（`decisionexecutor/worker.go`）
- 辅助函数：`interactionTTSText`（防重复叠加）
- 覆盖 3 个互动 TTS 入口：
  1. `synthesizeFAQAudio`（faq_cache.go，互动回答主路径 + FAQ 缓存）
  2. worker.go 纠正重合成路径
  3. return_bridge.go 互动回归 bridge
- 主线话术（mainline，走 `anchor_style_cycle_voice.go` journaledMainlineSynthesizer）**不受影响**。

## 11. 已知问题 / 待办

1. **删词兜底语义反转**：`坚决不卖隔夜货` 删"坚决不"后变 `卖隔夜货`（语义反转仍违规）。删词兜底应正向改写而非机械删词。
2. **局部重写 stage 名硬编码**：`text_generation.go:303` `beginModelExchange(ctx, "mainline_text", ...)` 没用 stage 变量，局部重写仍记成 `mainline_text` 而非 `mainline_text_repair`（只影响统计，不影响功能）。
3. **macro_feedback / p0_context 缓存 0%**：DashScope 前缀缓存有最小长度阈值（约 4096 token），这两个环节的稳定内容量不够阈值，缓存不了（硬约束，非 bug）。
4. **连续对话第 2、3 句豁免称呼**：同一观众连续追问第 2、3 句不重复点名——已记录需求，未落地（需 `decisionItem` 加 `user_id` 追踪）。
