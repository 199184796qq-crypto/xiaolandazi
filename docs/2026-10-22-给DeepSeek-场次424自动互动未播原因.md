## 四、底层不匹配：名为“追加”，实际使用待刷新替换

这一部分解释为什么“已经有A级切点”仍然不足以让自动互动工作。

1. `management-service/internal/httpapi/recording_stream.go:200`的`appendRecordingStreamTrack`每次只传一个新track，在232行调用的是`RefreshRoomProgram`；随后循环等待该刷新被应用，才开始下一段。
2. Core的`RefreshProgram`把新track暂存在`PendingRefresh`。`core-service/internal/coreaudio/program_refresh.go:160`在边界应用时执行`program.Tracks = refresh.Tracks`，属于替换轨道集合。
3. `core-service/internal/coreaudio/client.go:1517`构造未来主线窗口时，只枚举`program.Tracks`。待刷新区只暴露任务编号与代数，不把它的轨道加入未来窗口。
4. 每个流式短track只有一个整段语义单元、段尾一个A级切点。`interaction_preparation_window.go:54`明确要求切点前有内容、切点后也有可以接回的完整内容；段尾之后没有下一单元时，直接排除该候选。
5. 于是，下一段虽然已备好并等待刷新，却不在自动互动读取的窗口里；当前段又没有段内后续单元。**存在安全切点，不等于存在可用于自动互动的“准备窗口＋回归内容”。**

本场直播中窗口正好呈现这个状态：

```text
sequential = true
track_count = 1
当前track = recording-1-8-217
当前track时长 = 9704毫秒
timeline = 1个整段单元
safe_points = 1个A级段尾切点
future_window = 仅当前track
generation = 17
pending_generation = 18
pending_job_id = recording-192-18
```

这个快照采于人工互动期间，不能把其中零缓存或当时游标当作全场无缓存、全场停顿的证明。但“当前轨道单段、下一轨道仍在待刷新区、未来窗口缺少后续单元”与源码机制一致。普通任务在领取前就要求这一窗口，人工抢答跳过它，正是两条链路表现不同的关键。

还有一个叠加关系：该自动问题保持在普通队列后，欢迎切点请求的代码还会因为存在非暖场排队任务而暂缓请求。它可能进一步延长自动欢迎的等待；不能仅提高欢迎权重就认为问题已解除。

**这不是JSON格式坏了。** JSON可解析，规定的七个字段也都存在。问题是模型返回了本次请求并未提供的已有目的编号。

`management-service/internal/interactionpurpose/resolver.go:162`会拒绝非空且不属于当前方案目的集合的编号，报“目的编号未来自当前方案”。已有目的为空时，`P12`不能被认定为合法已有编号。输入、输出和本场一致源码足以确定会命中这一校验；本次没有保存管理接口502的原始响应体，不能伪称原始响应体已取到。

因此，这是一处需要交接的解析契约问题，但它**没有直接终止本条问题的调度**。本条仍不播的下一处停点，是入队后未领取，而非模型完全没有回应或整条流程被502终止。

### 第一优先：把流式供料改成真正追加，打通准备与领取

Core已有`POST /internal/v1/rooms/{roomID}/audio/program/append`，实现在`core-service/internal/coreaudio/program_append.go`。线上Core构建对应的`effd7d5`提交中也已包含该文件；实施时仍核对实际运行版本与路由。

建议管理端流式供料调用这条追加能力：新声音下载、校验完成后，立即按当前节目与正式版本追加到轨道队列，使它出现在未来窗口；收到追加确认后继续准备后续段落。使用当前的刷新替换接口，会让下一段一直藏在待刷新区，等当前段结束才替换，无法满足自动互动提前准备的要求。

需要一起守住的边界：

1. 首段准备好即可开播，后台继续准备后续段落；准备能力允许时至少维持“当前段＋一段完整待播内容”。缓存时长可按约20～30秒作为软目标，并同时检查待播完整单元数，不能只看当前段剩余时长。
2. 追加必须校验租户、房间、节目编号、正式版本；同一单元重复提交幂等，不同内容不能复用同一编号。Core已有对应校验，管理端按其协议接入。
3. 暂停、停止或切换节目后，旧供料不再进入新节目。已有准备好的完整音频可以复用，但不能把未合成或未校验的声音当成待播单元。
4. 仍按完整句边界插播，保留预算、冷却、事件有效期与串行播放。先让合格的未来单元可见，再让现有自动欢迎准入与自动问答领取正常通过；不要用取消所有准备限制来掩盖供料问题。
5. 改为追加后，检查长期队列裁剪、重试、停止与刷新冲突；“已追加确认”与“已经实际播放”继续分别记账。

这一步是本场“人工可以、自动不行”的主要修复方向，重点文件是管理端`recording_stream.go`及Core客户端协议适配；不是只修改互动生成提示词或返回策略。

### 第二优先：修正问题解析编号的契约

已有目的为空时，应明确向模型传递空列表，规定不得自行填写已有目的编号。模型只判断目的语义；没有匹配项时返回空编号，由程序按现有本地目的编号机制分配。若模型仍返回陌生编号，按清晰的协议错误处理或在严格条件下识别为新目的，保留事实引用校验、置信度和作用域校验，不把陌生编号直接视为合法旧目的。

这个修复减少解析退回，但本场已经走通了降级入队，所以必须与第一步区分验收。

### 第三优先：把“没处理到哪里”留成可解释记录

领取返回等待未来窗口时，管理端目前直接结束本次轮询，排查者看不到这次具体为何不领取。建议按决策保存并去重记录等待原因和上下文：当前完整待播单元数、主线可用切点、准备回归单元、是否被其它互动占用，以及最后一次推进时间。
