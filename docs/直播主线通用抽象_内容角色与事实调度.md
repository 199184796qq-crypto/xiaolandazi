# 直播主线通用抽象：内容角色与事实调度

> 2026-10-06 讨论补充见第十至第十六节：记录当前重复根因、行业分层、底座与用户边界、小段生成协议、服装模拟评价、落地验收和商品直播间定位。前文的线性流程仅是示意，不得实现为强制循环。本文是设计与诊断记录；每节会单独注明已实现与待实现部分。

## 结论

主线话术的普遍性，不来自收集更多商品模板，而来自稳定的“内容角色”和“时间调度规则”。

```text
主线话术 = 时间状态 × 内容目的 × 事实角色 × 表达动作 × 主播风格 × 当前约束
```

主播风格只负责“像谁说话”，事实库只负责“能说什么”，主线调度器负责“此刻该说哪一类内容”。互动策略不进入主线调度，由 Core 单独负责打断、回答和回归。

## 一、事实和内容角色分开

同一个事实可以承担不同作用。

例如“39年老油坊”可以作为：

- 信任证明：说明来源稳定；
- 价值解释：说明为什么强调自产自销；
- 使用场景承接：适合重视家常味道的人；
- 回顾内容：重新把重点收回来。

因此：

```text
事实是什么 ≠ 现在为什么讲它
```

事实库只保存“能说什么”，主线调度器决定“现在用它完成什么任务”。

## 二、通用内容角色

第一版固定以下通用角色，角色不绑定任何商品：

| 内容角色 | 解决的问题 |
| --- | --- |
| `orient` | 让观众知道当前在讲什么 |
| `value` | 为什么值得继续听 |
| `difference` | 和普通选择有什么不同 |
| `evidence` | 用什么事实来证明 |
| `scenario` | 在什么情况下有用 |
| `decision` | 用户如何判断和选择 |
| `action` | 下一步怎么做 |
| `recap_bridge` | 回顾当前重点并转到下一段 |

这些角色可以覆盖菜籽油、衣服、食品、家电、服务，甚至聊天直播。变化的是事实内容，不是角色体系。

例如“快递”只是一个事实，不是默认开场角色。它通常属于：

```text
fact_role = fulfillment
usable_in = decision / action / after_order
```

只有当前主线角色需要发货、配送或下单说明时，才选择它。

## 三、通用表达动作

主播风格不直接决定讲什么，而是决定同一个内容角色怎么说。第一版表达动作包括：

- 直接说重点；
- 拆开解释；
- 举使用场景；
- 先提出判断再给依据；
- 换顺序重述；
- 短句确认；
- 回顾后自然转场。

例如同样是 `evidence`：朴素主播可以先说事实再解释；专业主播可以先给结论再说明依据；热情主播可以先强调感受再补充事实；慢节奏主播可以一段一段拆开讲。

模型最终接收的是结构化任务，而不是混杂的大段提示词：

```text
内容角色：evidence
事实依据：39年老油坊、自产自销
表达动作：先结论后解释
主播风格：四川口语、称呼自然、偶尔停顿
```

## 四、主线是状态机，不是固定稿

通用主线可以从以下骨架开始：

```text
cold_start
→ orient
→ value
→ difference
→ evidence
→ scenario
→ decision
→ action
→ recap_bridge
→ next_round
```

这不是死顺序，而是可根据时间和内容状态跳转的主线图：

- 刚开播：优先 `orient`、`value`；
- 正常推进：优先 `difference`、`evidence`、`scenario`；
- 讲久了：增加换角度展开、回顾和转场；
- 活动阶段：提高 `decision`、`action`；
- 信任不足时：提高 `evidence`；
- 没有价格或活动事实时：跳过 `action`；
- 长时间循环：降低直接重复，改变内容角色和表达动作。

## 五、通用运行数据

主线运行状态建议抽象为：

```json
{
  "mainline_state": {
    "phase": "continuous",
    "round": 3,
    "current_role": "evidence",
    "recent_roles": ["value", "scenario"],
    "recent_facts": ["shipping", "price"],
    "next_fact_cursor": 4
  },
  "unit_plan": {
    "role": "evidence",
    "fact_selector": {
      "allowed_roles": ["proof", "origin", "material"],
      "exclude_recent": 3
    },
    "expression_move": "claim_then_explain",
    "target_chars": 180
  }
}
```

事实本身需要有可用于调度的角色标签：

```json
{
  "key": "shipping",
  "value": "中通、极兔、申通",
  "fact_roles": ["fulfillment", "decision"],
  "not_for_opening": true
}
```

## 六、主线生成算法

不要使用“按事实库排序，取第一条事实”的方式。应该使用：

```text
当前时间状态
→ 选择内容角色
→ 筛选适合该角色的事实
→ 排除最近使用内容
→ 选择表达动作
→ 用主播风格生成
→ 更新主线游标和已讲记录
```

因此，数据库里排在第一位的事实不再自动成为每次开头。只有当内容角色匹配时，它才会被选中。

## 七、和互动策略的边界

本抽象只服务主线话术：

```text
主线时间轴 → 内容角色 → 事实轮换 → 主播风格表达
```

互动策略单独负责：

```text
观众问题 → 是否打断 → 如何回答 → 如何回归主线
```

互动不能重置主线的事实游标，也不能决定主线下一段默认从哪个事实开始。

## 八、已确认的总体方向（实现基准）

本节记录当前讨论已经确认的设计原则。后续实现、测试和界面设计都以本节为基准；前文如果有把主线理解成固定顺序、固定广告段落或只允许复述正式事实的早期示例，应按本节修正。

### 8.1 Core 的边界保持封闭

对 Core 来说始终只有一条主线声音。声音可以来自原始真人录音、AI 预生成音频、本场低频更新音频，或全时段 AI 持续生成音频，但这些差异都属于 Core 之外的内容与声音供给层。

Core 继续负责既有的播放、音轨切换、打断、恢复和安全点，不负责：

- 选择下一个内容话题；
- 调用大模型；
- 解析主播风格或事实依据；
- 决定主动互动、逼单或回环策略。

### 8.2 所有生成方式共用一个“主播大脑”

固定 500 字、2000 字、固定时长、长时间模拟、AI 预生成和全时段 AI 主线，都不能各自维护一套生成逻辑。它们都调用同一个持续主线运行时，只改变停止条件、声音准备方式和发布方式。

```text
主播大脑：决定现在讲什么、从什么角度展开、下一段如何承接
主线运行时：保存时间、记忆、预算、临时安排和声音缓冲
内容审计：区分硬事实、可授权扩展和违规表达
声音供给：TTS 或原始音频
Core：只播放最终主线声音
```

全时段 AI 模式的基本循环是：

```text
预生成少量小段
→ 读取当前主线状态和声音缓冲
→ 生成下一段任务与话术
→ 审计、必要时只修正当前小段
→ TTS
→ 放入主线声音供给
→ 继续下一段
```

不能把声音片段边界当成重新开场、整轮结束或整场结束。

### 8.3 LLM 是内容大脑，事实是锚点而不是全部知识

事实、商品、活动和链接回答“哪些具体内容有依据”；主播风格回答“如何表达”；LLM 负责在当前目的下选择角度、解释、场景、类比、回顾、转场和行动方式。

有限事实不意味着只能机械复述。生成时允许使用以下内部内容类型：

```text
anchor_fact       正式事实
explanation       对事实的解释
general_knowledge 通用知识
scenario          假设场景或使用建议
opinion           主播观点
commercial_claim  商品属性、价格、库存、评价等商业断言
```

其中：

- `anchor_fact` 和 `commercial_claim` 必须有正式来源；
- `explanation`、`general_knowledge`、`scenario` 可按用户授权的扩展程度使用；
- `opinion` 可以体现主播个性，但不能伪装成真实顾客评价、真实销量或主播亲历；
- 扩展知识不能反向新增商品属性、功效、资质、库存或价格承诺；
- 审核边缘优先换成合规表达，不因为一句话需要改写就让整段沉默。

扩展授权控制“说得多远、推得多开”，但不能覆盖用户明确锁定的禁区、平台规则和 L1/L2 绝对规则。

### 8.4 记忆采用渐变时间窗口

主播不需要保存整场逐字稿。主线运行时应保存不同清晰度的记忆：

- 热记忆：最近几十秒至几分钟的原文尾部、当前事实、未完成话题和最近表达方式；
- 温记忆：最近一段时间的话题、角度和摘要，只用于避免机械复读和自然回环；
- 冷记忆：更早内容只保留主题覆盖和大致次数，不再提供逐字依据；
- 固定记忆：价格、规格、禁说项、主播风格、用户授权和当前有效规则不能因时间衰减。

记忆模糊只影响承接和重复判断，不能覆盖最新正式事实。已准备、已排队和 Core 确认已播放必须分开记录；没有播放证据时不能声称观众已经听过。

### 8.5 主动互动与被动打断分开

被动互动是观众事件触发的打断：

```text
观众问题 → 互动策略判断是否打断 → 回答 → 回归主线
```

主动互动是主线主动发起的内容动作，例如“认同的公屏扣 666”“喜欢宽松的扣 1”“想看尺码的打出来”。它不是固定的新阶段，而是可以嵌入价值、场景、选择和转化环节的横向能力。

主动互动必须记录发起、收到反馈、暂未收到反馈和过期状态。没有真实反馈时不能生成“大家都扣了”“很多人都在下单”等结论。主动互动的结果只以可观测的聚合信号反馈给主线，具体问题回答仍由互动策略负责。

### 8.6 逼单是行动目的，不是固定口号

主线可以使用轻提醒、选择引导、价值确认、真实活动提醒、消除顾虑和明确行动等不同转化动作。转化强度由主播设定、内容成熟度、有效活动、真实反馈和最近催单冷却共同决定。

发货、售后、物流等事实不是默认开场环节，而是根据当前内容目的挂到证据、选择、行动或售后安抚中。没有有效价格、活动或其他行动依据时，仍可引导查看规格、选择尺码、预约或关注，但不能凭空制造稀缺和紧迫感。

### 8.7 通用骨架和直播类型配置

通用内容目的池包括：开场接住、主题认知、价值与看点、差异或新角度、证据与信任、场景与选择、行动与转化、回顾与转场。它们不是所有直播间必须完整执行的固定七步。

不同直播类型只配置启用的角色和权重：

- 电商直播重点使用证据、场景、选择、转化；
- 教育直播可把价值、证据、场景替换为解释、示例、练习和确认；
- 聊天或娱乐直播重点使用主题、故事、观点、主动互动和转场；
- 音乐、舞蹈等演出直播可以弱化商品选择和逼单，保留介绍、参与和关注引导。

因此系统实现的是“内容目的池 + 类型配置”，不是为每个行业写一套固定状态机。

### 8.8 直播大屏数据是反馈信号，不是内容事实

主线可以使用在线人数、进房、评论、订单、点击等观测信号调整节奏、解释深度、主动互动频率和转化力度；没有来源的数据必须标记为未知，不能让模型自行补数字。

真实观测、系统推断和模拟测试必须分开。模拟热度只能用于测试，不能被播报成真实在线人数或真实观众反馈。数据不足时使用平稳的默认节奏，不让少量噪声导致主播频繁跳转。

### 8.9 后续实现不可偏离的边界

后续实现应优先完成：

1. 持续主线运行时和渐变记忆；
2. LLM 内容大脑任务协议及扩展授权；
3. 主动互动动作与转化冷却；
4. 真实、推断、模拟信号的分层；
5. 固定长度测试、长时间模拟和全时段 AI 共用同一生成链路；
6. 在不改 Core 的前提下接入现有主线声音供给和安全刷新接口。

任何新功能都不能把主播风格、事实依据、互动策略和主线状态机重新混成一个提示词，也不能把 Core 变成内容决策器。

## 十、2026-10-06 当前问题与已核对根因

### 10.1 用户观察与诊断结论

长时间测试反复围绕“快递”和“油坊”展开，每次表达角度略有变化，但核心材料没有推进。问题不是模型天然喜欢物流，也不是主播口头禅不足，而是调度链路不断从头开始、给模型的可用材料过窄。

本轮已核对本地调用链：

1. `web-console/src/views/LiveStrategyView.vue` 的 `runReusableLongTest` 多次调用固定长度测试接口，每次只把前文末尾约 120 字放入主题，没有传递完整的连续游标与近期调度记录。
2. `management-service/internal/httpapi/live_agent_plan_style_preview.go` 每个请求重新调用 `BuildFixedPlans`，`VariantCount` 为 1；目标 500 字被换成两个虚拟时间单元。
3. `management-service/internal/speechexpander/planner.go` 的 `keysForStep` 使用当前请求内的单元索引和变体偏移取事实；每次索引重新从 0 开始，于是又取到事实列表前两项。
4. `fullShowFactKeys` 只从 `FormalFacts` 取调度键，未统一覆盖商品、有效福利和补充事实等全部授权材料。
5. 两个单元到不了后面的 `benefit_link` 阶段；末段被安排成 `recap_confirm`，链接选择又容易落到相同位置。这会进一步放大“材料重复、固定链接、短稿每次收口”的问题。
6. `scopeAnchorStyleSegmentContext` 只给当前单元分配到的事实及关联材料。模型不能选择没有送进该小段上下文的其他材料。
7. `generateAnchorStyleTest` 每次请求创建新的字数账本和 `mainlinebrain` 会话，影子记忆只在本次请求内部延续，跨请求仍断开。

因此，把“不要讲快递”反复写进提示词，不能替代连续状态和材料调度的修复；换一份事实顺序，还会出现新的首条材料垄断。

## 十一、从“事实轮播”改为“目的驱动”

### 11.1 真人样本为什么不是简单事实驱动

菜籽油样本有事实支撑，但组织话术的主轴是成交目的：价值种草、价格说服、风险降低、行动提醒反复交织；发货、油坊、试吃是服务这些目的的材料，不是固定依次播报的目录。

同一个事实可以反复讲，关键在于当前解决的是不同问题。例如发货信息可以在“下单顾虑”中提供保障，也可以在有真实发货顺序依据时支持行动提醒；不能因为事实排第一就每轮先讲物流。

```text
当前内容目的
→ 选择相关的事实组合
→ 选择解释、场景、判断或证明方式
→ 按扩展授权生成
→ 用主播风格表达
→ 更新连续状态，判断下一步
```

小段是生成与声音准备的边界，不是必须换话题的边界。同一目的可以跨几个小段展开，一个小段也可以引用多个相关事实；不能把“一个主材料”实现成“只准提一个事实”。

### 11.2 营销体系分别放在哪一层

| 体系 | 在系统中的用途 | 不应被实现成什么 |
| --- | --- | --- |
| 流程阶段、AIDA | 帮助判断当前内容目的、宏观推进与回环 | 每轮必须完整走完的固定顺序 |
| FABE | 卖点的组织方法：特征 → 优势 → 用户利益 → 证明 | 每个小段都必须写出四步 |
| SPIN | 需要需求教育或顾虑拆解时的可选方法 | 所有商品都先制造问题和焦虑 |
| 价格锚定、风险降低、信任、稀缺等机制 | 有对应事实和条件时，帮助选择表达动作 | 无条件制造优惠、销量、库存和倒数 |
| 4P/4C | 商业配置与经营策略的参考 | 逐句话术生成顺序 |

FABE 中，优势和利益不能仅凭模型推理就变成该商品的性能承诺；证明必须能关联已确认的事实或可验证材料。可以停留在场景与选择建议，不必为了填满四格发明功效。

试吃和退款主要用于降低购买风险；老厂年限属于来源与经营经历，不自动等于外部权威认证。样本里的库存、时间、销量、价格和承诺不因提取风格而进入正式事实。

### 11.3 烈度单独控制

用户明确提出分不同烈度：烈度大，行动引导可以更密集；烈度小，讲解和场景可以更舒缓。

应分开以下配置：

- 转化烈度：行动提醒密度、直给程度、价值确认和顾虑拆解的节奏。
- 扩展授权：允许把正式材料延伸到哪些解释、场景、类比和观点，以及延伸程度。
- 模型采样参数：文本生成的随机性，不作为前两项的替代。

高烈度不等于允许编造稀缺。没有真实库存或截止时间，也能更直接地帮助选款、确认价值、查看链接和下单，但不能生成“最后 6 桶”“最后 2 分钟”。烈度低也不等于不卖货，只是给选择更多铺垫。

## 十二、通用底座、直播类型、行业和用户的分层

### 12.1 五个纵向层，独立的横向输入

| 层 | 主要职责 | 举例 |
| --- | --- | --- |
| 通用运行底座 | 时间推进、状态保存、预算、近期记忆、重试与提交、声音供给接口 | 跨请求游标、局部回修、已生成与已播放分开 |
| 直播类型骨架 | 决定可用的内容目的及默认权重 | 电商、教育、聊天、演出 |
| 行业策略包 | 提供行业常见顾虑、讲解方法、适用条件和角色权重 | 服装的版型/尺码/搭配；食品的口味/使用/规格 |
| 商家与本场配置 | 提供真实经营材料、用户授权、经营目标 | 商品、价格、福利、物流、售后、证据、烈度 |
| 本场动态决策 | 结合当前话题、时间、近期覆盖和可信反馈决定下一小段 | 继续一个疑问、换角度、价值确认、转场 |

主播风格、事实依据、有效商品与福利、表达禁区、临时状态是独立的横向输入；被动互动策略与 Core 保持既有边界。行业策略包不是另一份商品事实库，也不负责强制设置某个主播的口头禅。

行业包应保存“顾虑主题、可用方法、需要什么材料、何时适用”，而不是保存一篇所有主播照读的稿子。系统不能凭“这是衣服”自动声称不缩水、不起球，也不能凭“这是食品”自动声称老人孕妇适用。

### 12.2 哪些可固定，哪些要配置，哪些必须有来源

| 类别 | 可以放什么 | 边界 |
| --- | --- | --- |
| 底座机制 | 状态协议、生命周期、预算计算、上下文边界、来源记录、Core 接口 | 固定工程机制，不固定每轮营销顺序 |
| 系统可配置默认值 | 类型/行业策略、角色权重、回环和冷却、近期窗口、讲解方法 | 可版本化、可调整，不散落为商品特判 |
| 用户或可信来源材料 | 商品属性、真实价格/优惠、履约与售后承诺、证明、真实库存与反馈 | 缺失就是未知，不能从样本或模型常识补成商业事实 |
| 主播与本场设置 | 风格样本、插件、今天状态、扩展授权、转化烈度、人工安排 | 用户决定表达与经营偏好，不改写已确认的硬事实 |
| 合规与平台规则 | L1/L2、表达禁区和规则版本 | 与扩展授权分开管理，不把平台规则永久写死，也不由授权直接关闭底线 |

明确不能固定的规则：物流永远开头、固定十阶段循环、每三段催拍、一个单元只能提一个事实、每个片段都形成完整广告闭环、所有行业都要倒数逼单。

“不准这样说”应尽可能保留沟通目的、换成允许的说法；但新说法不能只是换词继续暗示被禁止的同一功效。例如不准说“老人小孩吃了好”，可以转向日常烹饪、香味与口味选择，不改成“老人小孩负担更小”。

## 十三、统一的小段推进协议与验收要求

### 13.1 所有模式必须共用连续运行时

固定字数、固定时长、长时间测试和全时段 AI 只改变停止条件及播放方式。HTTP 请求结束、TTS 文件结束、当前字数批次结束，都不自动等于主播重新开场或整场结束。

下一小段任务至少能表达：

```text
连续会话/游标与当前内容目的
当前要解决的问题、未讲完的话头
主材料与相关支持材料、来源和有效性
可用表达方法、扩展授权、转化烈度
主播风格、个性插件、本场临时状态
近期话题/事实/角度/行动记录与前文尾部
本段字数预算、总剩余预算、是否真的准备结束
```

该协议是可实现的设计要求，不表示每个字段目前都有接口或已上线。决策层可以有合理默认值，不要求用户逐项填写内部字段。

### 13.2 生成、回修和提交

1. 根据连续状态选择当前目的，再选一组相关材料；不能先遍历事实再拼营销动作。
2. 生成一小段。后段必须承接前段的语义状态，不仅仅避开几个重复词。
3. 事实与表达检查失败时定位出错小段；保留已合格内容，只要求该段换说法或补正。
4. 计算已接受字数和剩余预算；接近目标时加强当前小段长度约束，过长局部缩短、过短按当前话头补足。
5. 只有被接受的单元才推进调度游标；失败重试不多计一次覆盖。正式播放另记播放确认，不能把排队文字当成观众已听到。
6. 返回新的连续状态，下一请求继续。用户主动新开一场时才重置；结束标识必须明确，不靠“这是请求末段”猜测。

字数容差沿用可配置的测试标准，不追求逐字等长。固定长度只是输出预算，不要求整段一定完成一次完整成交。

“30 分钟测试”也不能只等价于调用六次 500 字：应明确是加速模拟还是按播放时间运行，时长预算、文字量和 TTS/播放时间要有可解释的关系。此前界面的时长标签不能作为已满足真实时长的证据。

### 13.3 调度观测留在开发诊断层

为每个小段记录：为什么选这个目的、选了哪些材料、为何避开最近材料、是否延续话头、模型与耗时、回修原因、游标是否提交。

用户页面仍以易懂的文案、进度、停止与反馈为主；不能把内部 fact key、状态机标签和结构化诊断卡重新堆回已要求简化的页面。没有真实分析轨迹时，不把进度文案伪装成模型内部思考。

## 十四、服装 500 字服务器模拟及业务评价

### 14.1 本轮模拟条件与事实边界

本轮通过服务器当时配置的 `deepseek-v4-pro` 生成，不是助手直接代写；分三次推进，最终约 492 字。只是调用验证工具的模拟，未证明正式产品接口已完成跨请求调度修复。

使用的是假设测试材料，未写入正式事实库：1 号通勤长袖衬衫、70% 棉与 30% 聚酯纤维、宽松落肩与圆弧下摆、米白/浅蓝/深灰、S 至 XL、日常价 89 元，并假设详情页提供成分、尺码表和正侧面实拍。

未提供折扣、销量、库存、顾客评价、物流、售后及免烫/不起球/不缩水/透气等性能。模型两次分别延伸出“挺括感”和“面料这个厚度”，同一服务器模型只对对应小段局部回修，去掉无依据属性。这说明审计仍有必要，也说明不必整篇推倒重写。

### 14.2 只看业务，不看主播像不像

评价约为 6.5/10，是针对中等转化强度的主观文案评价，不是实际成交数据。

优点：开头从通勤选衣烦恼切入，有具体搭配场景，颜色、尺码和查看链接的选择路径较清楚；相比反复讲物流，已具备产品导购逻辑。

主要问题：

- 更像“通勤穿搭导购”，不是充分的中烈度成交推进。
- 第二小段继续枚举颜色与搭配，和第一段都在解决“好搭”，没有明显推进到另一个购买顾虑。
- 成分参数只是出现了，没有与已证实的用途价值或验证方式衔接；也不能为填补逻辑而推导面料性能。
- “89 元、性价比实在”缺少价值解释。可以联系实际使用选择和可查看的成分/图片，不需要编对比价。
- “对照着选一般不会差太多”把尺码建议说得过稳。须先明确尺码表是成衣尺寸还是适穿身体范围，再给对照建议。
- 证据入口没有被充分使用；已有假设实拍和尺码材料，应帮助用户知道看什么，而不只是泛泛夸好看。

建议的业务推进是“认知商品 → 解决一个顾虑 → 给出验证方式 → 帮助选择 → 行动”。这是本次诊断的参考路径，不是要写死成服装或全部行业的五段模板。低烈度、长场直播中的穿搭讲解片段可以不完成全部动作。

### 14.3 训练反馈要抽成可迁移的能力

可以学习：减少重复解决同一顾虑、把参数和用途/验证联系起来、尺码建议保留条件、后段自然承接、行动引导有依据。

不应学习：永远先讲搭配、永远三段、固定价格、固定颜色、固定衬衫场景，或某一篇油/衣服稿子的专用句子。业务推进评分与主播风格相似度分开，不把业务反馈误编译成口头禅。

## 十五、后续落地顺序与跨品类验收

### 15.1 推荐顺序

1. 先补跨请求连续协议：前端长测、后端计划、近期记忆和提交游标共用同一会话；修掉反复从索引 0 开始的问题。
2. 统一授权材料目录：事实、商品、有效福利和证据带来源、用途、链接关联、有效期；不再只调度 `FormalFacts`。
3. 接入目的驱动调度：内容目的与材料分开，支持一个目的跨段、多个相关事实同段；固定角色轮换只作回退默认值，不成为唯一决策。
4. 接入直播类型/行业可配置策略和独立烈度；保留模型按当前话头决定展开方法的空间。
5. 增加业务推进评价和可修改反馈；继续使用局部回修、近期渐变记忆和有条件回环。
6. 固定长度与长测先验证，再在不改 Core 的前提下把同一链路接到持续声音供给；发布需另行执行与验证。

### 15.2 必须覆盖的测试

| 测试 | 验收重点 |
| --- | --- |
| 把物流放事实第一位，连续多次请求 | 不能因为数据库顺序反复物流开头；要观察整体目的和主题推进，而非禁止必要物流 |
| 商品、福利存在，但补充事实很少 | 模型仍能在授权范围内围绕产品价值、场景、选择展开，不退化成只讲油坊/物流 |
| 菜籽油换衣服，再换其他品类 | 底座无需商品特判；行业策略改变顾虑和方法，不迁移原商品属性 |
| 一个话题跨两个小段 | 第二段能接话继续，不重新开场、不机械形成完整广告闭环 |
| 同一材料改变目的和烈度 | 低烈度讲解较舒缓、高烈度行动更明确；两者事实不变，都不制造库存或倒数 |
| 福利过期、库存/反馈未知 | 失效材料退出可用集合；未知不补为“很多人买”“马上没货” |
| 局部失败、重试、停止 | 不重复推进游标，不丢已接受内容；用户停止后不继续无控制地产出 |
| 固定 500/2000 字与连续长测 | 都使用同一推进链路，接近结束局部控字；批次边界不等于直播收尾 |
| 真实播放接入 | 已准备、已排队、已播放分别记账，Core 原有打断与回归行为不被破坏 |

尚待验证的假设：目的驱动能否在材料很少时显著改善持续业务推进；不同行业默认权重和烈度效果如何；渐变记忆窗口多大最自然；服务器配置模型在统一协议下的稳定性和成本。需要同一条件下对比样本，不能凭一篇模拟宣称已解决无限直播。

### 15.3 2026-10-06：逐段模型调度与渐进输出

- 主播测试（固定字数和长时间测试共用的接口）每个小段生成前，由配置的生成模型从允许目的和授权材料菜单中选择下一段。环节目录是菜单，默认顺序只是兜底，不再强迫模型按固定流程走。
- 调度只返回目的、一个主材料、最多一个相关辅助材料和中文理由；程序验证材料存在、授权、商品关联和目的适配。模型超时或选择无效则按已接受历史重新计算兜底，不丢弃正文。
- 下一次决策使用实际提交的小段和最近记忆。失败候选不推进游标。字数、时间、开场收尾权限和插件执行机会仍由原时间推进链路控制。
- 页面展示本次已生成小段的实际目的顺序，逐段注明模型安排或系统兜底；调度理由不进入主话术或 TTS。
- 点击单段测试立即打开输出框，POST 接口可协商 SSE。每个通过本段校验的小段真实返回后立即追加，完成后独立返回全篇检查和风格训练记录；后续失败保留已返回文字并告知未完成。当前是逐小段返回，不是模型 token 级输出，也不是模拟打字。
- 不改变 Core 播放、打断或回归，不把测试生成记为真实已播放。尚未接到正式无限音频生产链路，不能宣称整个自动直播已完成。

## 十六、商品的直播间定位与可变讲解方案

商品卡记录的是相对稳定的“直播间定位”，不是“本场定位”。允许的定位为主推、引流、福利、利润、搭配、普通；除“普通”外可以兼任。这个字段表达商品在该直播间长期承担的大作用，随商品卡版本保存，方案重新生成时不会被自动改写。

每次方案或下一小段生成的是另一层数据：商品讲解方向。它可以根据当前主题、最近已讲内容、商品正式属性、有效福利、转化烈度和直播间定位，重新安排：

- 哪个商品重点讲、正常讲或适时带到；
- 返场采用经常、短频、按活动时机、相关场景或动态安排；
- 当前优先使用哪些已确认角度；
- 哪个商品可以承接到哪个商品，以及当次承接理由。

因此必须保持：

```text
商品卡 room_roles（长期直播间定位）
→ 当次 product_plan（可变讲解方向）
→ 逐小段模型调度（根据实际历史重新判断）
```

“主推、引流、福利、利润、搭配、普通”都是后台经营标签，不是可朗读事实。福利定位不代表免费，利润定位不代表亏本或高利润，也不能凭标签生成优惠。价格、赠品、活动条件仍从有效福利读取；商品属性仍从商品卡和事实清单读取。

商品卡只要求用户维护简单定位；未设置时模型可以在当次方案中动态判断，但不能擅自回写长期定位。用户通过卡片点击或自然语言修改定位时生成商品新版本；删除商品时定位随商品一起停用，不留下单独引用。方案里的重点、频率和承接保持可变，不反向修改商品卡定位。

当前已接入：定位版本化存储、商品卡自动保存、自然语言增删定位、生成上下文、兜底调度权重、逐段模型可见的商品讲解方向和测试页人话展示。后续若增加“采用整份方案”，应另存方案级覆盖，不得复用或覆盖商品卡的长期定位字段。
