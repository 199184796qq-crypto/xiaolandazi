## 1. 要解决的问题：复读感的真正根因

**现象**：同一个「卖点×角度」，长直播里反复讲时，观众觉得主播在复读。

**根因（实测确认）**：不是"角度数量不够"，而是**同一个角度每次生成，模型都被事实包里最突出的信息点吸走**（通常是价格），导致信息结构高度同质。

### 三组实测对照（2026-10-15，qwen3.7-flash，temperature=0.7，enable_thinking=false）

固定同一个「卖点×角度」= `规格选择与价格算账 × 麻辣味与五香味两种口味的选择提示`：

| 方案 | 喂的事实 | 20 次结果 |
|---|---|---|
| ① 关键词筛事实 | 只筛"麻辣/五香/价格" 4 条 | 100% 滑向"95.6 vs 85.6 省10块"三件套 |
| ② 全量事实不筛 | 全部 41 条 active 事实 | 单条信息变丰富，但 20 条之间**依然高度同质**——模型自己挑"最吸睛的 7~8 条"反复用，其余 30 条很少被讲 |
| ③ **侧面筛事实** | 每个侧面只喂专属事实 | **7 个话题各 2~3 轮，信息结构彻底拉开** ✅ |

**关键结论**：
- 扩大事实 = 单条更肥，但条与条之间照样复读。
- 只有"**按侧面筛事实**"才能拉开信息结构。

## 2. 方案核心：侧面 = 事实筛选器（不是软约束，也不是第三维）

### 2.1 三个角色的定位

| 维度 | 是什么 | 数量 | 是否参与调度 |
|---|---|---|---|
| 卖点×角度 | 话术的**定位坐标**（讲什么大类、哪个具体点） | 47 个（静态挖出） | ✅ 调度 key（防重复/加权/复用都看它） |
| 侧面 | 话术的**切入维度**（从哪个角度讲、喂哪几条事实） | 7 个（通用维度池，产品无关） | ❌ 不参与调度，运行时轮换 |

### 2.2 正确关系：`卖点×角度 + 侧面`，不是 `×侧面`

```
卖点×角度（47 个静态坐标）
   └─ 每次生成时，按使用次数轮换侧面（7 个循环）
        └─ 侧面决定"这次喂哪几条事实"
             └─ 模型手里只有这个侧面的事实，自然只能讲这个侧面
```

**为什么不是三维笛卡尔**：`×侧面` 会变成 47×7=329 个预生成槽位，审核成本 ×7；而 `+侧面` 是运行时换筛子，**329 种讲法是"47 坐标 × 7 喂法"白捡的，零额外模型成本**。

### 2.3 侧面的数量上限：受事实维度约束，不是想扩就扩

- 侧面数量 = 事实能切出的"互不重叠维度"数。
- 41 条事实天然切出 7 个维度（见下），所以 7 个侧面正好。
- 盲目扩到 12/15 个会撞两类问题：**空侧面**（没事实支撑，生成单薄甚至胡编）、**事实被切碎**（每个侧面只剩 1~2 条，话术越讲越空）。
- 真正有增量的扩展方向：从事实包里**挖产品专属侧面**（如"送礼场景/定制服务/物流时效"），不是凭空加通用维度。

## 3. 完整链路

### 准备阶段（静态，开播前一次）

```
① 用户输入：商品信息 + 活动福利 + 事实依据（物流/售后/注意事项）
        ↓
② 程序+模型挖掘：卖点（8 大类）→ 每个卖点下的角度
        ↓
   卖点×角度 = 47 个静态坐标（"讲什么"）
        ↓
③ 给每条事实打【侧面】标签（可跨多侧面）
```

### 直播阶段（运行时，每次生成一段）

```
④ 调度选本段：47 个「卖点×角度」里选 1 个（防重复 + 加权）
        ↓
⑤ 侧面轮换：该角度讲到第 N 次 → 切到第 N % 7 个侧面
        ↓
⑥ 按侧面筛事实：只取"该侧面"标签的事实（不喂价格，模型只能讲这个侧面）
        ↓
⑦ 正文生成：卖点×角度 + 侧面事实 + 主播风格 + P0 → 话术
        ↓
⑧ 润色 → TTS → 播放
```

## 5. 数据模型变更

事实表（`live_agent_plan_facts`）每条事实需要增加**侧面归属**：

```json
{
  "id": 39,
  "fact_value": "线下门店价格为95.6元",
  "sides": ["利益算账", "对比参照"]   // ← 新增：一条事实可跨多侧面
}
```

- 一条事实可归属 0~N 个侧面（0 表示通用兜底事实）。
- 筛事实时：取 `sides 包含当前侧面` 的事实喂给正文模型。

## 6. 现有代码改造点

| 位置 | 现状 | 要改成 |
|---|---|---|
| `anchorcycle/angle_plan.go` `CurrentFissionSide()` | 已按 `Used[key].Count % 7` 轮换侧面 | 保留轮换，但侧面从"软约束字符串"升级为"**事实筛选条件**" |
| `httpapi` 正文生成的事实组装（`HookFacts`） | 按【商品】筛事实（1号链接喂1号链接全部事实） | 升级为按【商品 + 侧面】双维筛选 |
| 正文生成 prompt | 侧面只是一句"切入侧面"提示 | 改为：只把当前侧面的专属事实放进"可说"层，其余侧面的事实**不喂** |
| 事实入库/审核 | 无侧面字段 | 事实打侧面标签（见 §7 决策点①） |

**核心改动就一处**：事实筛选从「按商品」升级为「按商品 + 按侧面」。调度、复用、加权、P0、润色、TTS 全部不动。

## 7. 待 Codex 对齐的 3 个决策点

1. **事实打侧面标签的方式**：
   - A. 程序规则（关键词/白名单映射，快但粗）
   - B. 人工在界面上给每条事实勾选侧面（准但费人工）
   - C. 审核模型在挖卖点时顺便给事实分类（省人工但多一次模型调用）
   - 建议：**A + B 结合**——程序先按规则预分类，人工在界面上微调，存库后复用。

2. **空侧面兜底**：某「卖点×角度」的某个侧面没有对应事实时：
   - A. 跳过该侧面，直接轮下一个
   - B. 降级用该商品全量事实生成
   - 建议：**A**（跳空侧面，避免又滑回价格）。

3. **角度 vs 侧面优先级**：当角度（如"麻辣五香选择"）和侧面（如"品质来源"）指向不同内容时，以谁为准：
   - 建议：**侧面优先**——侧面决定"喂哪些事实"，角度只保留商品维度约束（哪个链接、哪个口味）。

- [ ] 同一个「卖点×角度」，连续生成 7 段（轮 7 个侧面），信息结构互不相同，不再 100% 滑向价格。

- [ ] 事实表新增 sides 字段，旧事实可正常加载（缺 sides 视为"通用兜底"）。
