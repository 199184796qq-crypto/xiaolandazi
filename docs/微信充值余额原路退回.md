# 微信充值余额原路退回

已于 2026-10-03 发布生产，版本 `20261003-wechat-refund-v1`。手机钱包、电脑“我的钱包”和财务退款核验页面已更新；此次发布未向微信提交真实退款。现有微信充值、奖励与返佣提现保留；不接入商家转账或新银行卡收款。

## 业务口径

- 手机和电脑“我的钱包”现金卡增加“余额退回”，显示可退本金和冻结金额。奖励和返佣仍走原提现审批。
- 仅已核验到账的微信充值本金可自动原路退回；所有现金消费按充值本金优先、充值到账顺序 FIFO 核算。赠送、线下入账、历史调账、商品退款等不能变成可退充值本金。旧流水不完整时保守扣减或拒绝自动退回，转人工核对。
- 用户输入金额，服务器重新核验原支付交易的商户、AppID、付款人哈希、订单金额、实际付款金额和支付时间，再在同一数据库事务中分配来源并冻结。一次最多拆分 20 笔充值；更多笔需分次操作。
- 原交易须未超过 365 天，同一原交易累计最多 50 个子退款单。一个原交易有退回未结束时不再受理它的下一笔；前后提交至少间隔一分钟。
- 含微信支付优惠、实际付款少于订单金额的充值暂不自动退回，需人工核对优惠与本金口径，避免把券当现金退回。
- 退给原付款人，由微信决定原支付账户/银行卡路径；他人代付退给代付人，不可指定新的收款人。

## 资金与幂等

新增 `fin_wechat_cash_refunds`（客户请求）和 `fin_wechat_cash_refund_items`（逐笔原交易子退款），启动时增量建表。

钱包 `balance_cents` 表示可用余额，`frozen_balance_cents` 表示冻结金额，不得再次用 `balance - frozen` 判断可消费金额。

1. 锁现金钱包行，以 READ COMMITTED 重读本金流水，校验请求幂等键和逐笔来源。
2. 可用余额减申请金额，冻结余额加申请金额，同时写 hold 流水和来源子单后提交。
3. 事务外使用微信官方 APIv3 SDK 调用退款，发送原微信 `transaction_id`，固定 `out_refund_no` 和原订单总金额。商户 API 私钥只留服务器。
4. 创建接口受理不代表最终到账；即使创建响应为 SUCCESS，本地也等后续查单/签名通知确认。
5. SUCCESS：冻结余额减少；记录经营支出，不再二次扣可用余额。
6. CLOSED：冻结减少，可用余额恢复；release 流水恢复到同一原充值来源和原付款日期。
7. PROCESSING、ABNORMAL、网络超时、无法核验：保持冻结，不人工标记成功，不凭错误响应解冻。

同一用户请求的幂等键绑定金额；同一子退款号重复提交只能退一笔。数据库租约阻止多个请求/进程同时派发，重试先查询原退款号，确认不存在后仍以同号同参数重新提交。每分钟 leader 扫描到期记录，逐步退避到 5、10、30 分钟；浏览器关闭不影响核验。

新发起的旧现金人工提现 API 会提示改用“余额退回”；历史人工提现记录和已进入审核的操作仍可处理，奖励、返佣流程不变。

## 接口

- `GET /api/v1/wallet/wechat-refunds`：当前用户的可退本金、冻结金额和最近 100 条记录。
- `POST /api/v1/wallet/wechat-refunds`：`amount_cents`（整数分）和 `idempotency_key`（16–96 位）。
- `POST /api/v1/wallet/wechat-refunds/{refundID}/query`：仅核验本租户记录，遵循租约和退避，不重复发起新单。
- `POST /api/v1/payments/wechat/refund-notify`：官方 SDK 验签并 APIv3 解密；不依赖登录 cookie 或后台审计。商户号、退款号、原交易、币种、金额及实际退回金额均校验。
- `GET /api/v1/finance/wechat-refunds`：财务结算审核权限可看全部最近 200 条；“收益结算”新增“充值本金退回”标签。
- `POST /api/v1/finance/wechat-refunds/{refundID}/query`：财务可核验，不提供手工“已退款/解冻”按钮。ABNORMAL 到微信商户平台按子退款号处理，然后等查单或通知。

退款通知地址从已配置的微信支付通知地址取相同 HTTPS 域名，路径为 `/api/v1/payments/wechat/refund-notify`。无需新增密钥；发布前确认反向代理能公开访问此 POST 路由、请求体不改写，微信商户账户有足够退款出资余额。

## 验证和发布注意

单元测试覆盖本金/赠送隔离、年龄与次数限制、签名伪造、通知解密、错误商户/金额、原交易参数以及旧现金接口保护。

隔离 MySQL 用随机前缀和 SQL 对象白名单，覆盖跨充值拆分、并发重复提交、超时保留冻结、重复回调、异常保持冻结、关闭解冻和退款/消费并发；不读取或改动真实业务行，不调用微信。

生产发布须同时发布新后端和两端钱包，启动增量建表；部署后先做未登录和伪造通知检查。首笔真实测试由用户明确确认金额和充值单后进行。存在任何待核验子退款时不可回滚到不支持退款对账的旧后端，否则冻结资金无人核验；如需回退界面，应保留此后端和对账 worker。
