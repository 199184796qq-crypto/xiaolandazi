## 三、剩余待移植项（按建议顺序）

### 移植点 1：事实应答三步 → 两段式（ROI 最高）

**现状**：提问走三步模型调用，单问 input 约 1.5 万 token（意图 2758 + 规划 4325 + 回答 8235）。

**对比**：新链路欢迎单次只要 ~2600 input（两句）。

**方向**：把「意图解析 + 业务规划」合并，或让回答直接吃事实包（像欢迎钩子那样），压成「选角度 → 直接生成」两段。这是减少 token 的第一目标（用户已明确「第一优化目标是减少 token」）。

**风险**：
- 意图解析（purpose resolution）在 core 侧发起，改了要联动 core，不是 management 单侧能完成。
- 业务规划的「角度去重」（selectInteractionPlanAngle）有防复读价值，不能简单砍掉。

### 移植点 2：主播腔调卡接进旧链路（解决「风格没味」）

**现状**：新链路 welcomeVoiceCard 有「风格 + 量化基准 + 禁用表达」卡，欢迎/下单都带；旧链路 answerSystemPrompt 只有裸的「直播口播合成器」prompt，没腔调卡。

**方向**：把 welcomeVoiceCard 接进 answerSystemPrompt（这也是 memory 里记过的「风格没味」根因——主线只吃评分骨架、没吃 StyleMD 腔调）。

**风险**：低。纯增量，不影响现有行为。

### 移植点 3：弹幕（reply_chat）第三档接入模型判断

**现状**：`classifyChat`（interaction_lightweight.go:83）当前是黑盒——有内容就归第一档（提问），TODO 标注「后续接入模型判断真提问 vs 夸赞闲聊」。

**方向**：接模型判断弹幕性质，夸赞闲聊归第二档（礼仪回应，走新链路），真提问归第一档（事实应答）。

**风险**：中。多一次模型调用，且要定义「夸赞闲聊」的边界。

## 四、关键约束（移植时不能破坏）

1. **话术基座四层**：任何一次模型交互都走「内容四层（必说/可说/不提/改写）+ 表达四层（腔调 + 避重）」，不允许脱离四层。
2. **称呼前置全局复用**：resolveInteractionAddressing 是统一入口，各策略只读结果，不各自算。
3. **P0 红线 + pUser 约束**：生成阶段必须内嵌，不能依赖 TTS 前审核（已去掉）。
4. **token 落表**：所有模型调用走 completeInteractionAnswer / completeWelcome，保证成本可统计。
5. **主播腔调 = 评分基准反推骨架**（RenderAnchorExpressionView），不是 StyleMD 母版；「风格没味」根因是 StyleMD 没进主线 prompt。
