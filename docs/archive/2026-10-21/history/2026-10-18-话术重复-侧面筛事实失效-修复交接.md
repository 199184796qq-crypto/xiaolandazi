原因是 `CategoryFromFactText()` 提取分类时被归属前缀干扰：


```go
// 事实文本现在带归属前缀（这是「绑事实到商品」新设计加的）：
//   "- [用户指定公共；appointment/到店消费预约要求] 到店消费无需预约"

//   带公共前缀 → 返回 "用户指定公共；appointment"  ❌（应该是 "appointment"）
//   带商品前缀 → 返回 "用户指定商品=\"2号链接\"；audience"  ❌（应该是 "audience"）
```

## 三、修复方案

**核心：让 `CategoryFromFactText` 先剥离归属前缀，再提取分类。**

### 方案 A（推荐，最小改动）：在 `CategoryFromFactText` 内剥前缀

`fission_side.go` 的 `CategoryFromFactText` 按以下顺序处理（伪代码，不是已实现补丁）：

```text
找到候选 '['
取得 '[' 后面的文本
如果以“用户指定公共；”开头：剥去此前缀
如果以“用户指定商品=”开头：
    JSON解码完整商品字符串
    核对字符串结束后紧随中文分号“；”
    剥去整个归属前缀
在剩余文本中查找标题结束符 ']'
从干净的 category/fact_key 标题中提取 '/' 前的分类
无分类标记时，沿用原函数继续寻找下一个标记的行为
```

`stripFactScopePrefix` 为建议的包内辅助函数名，具体命名可由实现者决定。处理两种前缀：
- 公共：`用户指定公共；` → 剥掉，剩下 `appointment/到店消费预约要求`
- 商品：`用户指定商品="2号链接"；` → 解码JSON字符串并核对后续中文分号，剥掉后剩下 `audience/适合人数`。引号内可能含 `；`、`/`、转义引号，不能简单 Split 或按第一个引号/分号定位。

### 关键注意点（避免重蹈 content_pool_sources 的坑）

1. **商品前缀的引号内可能含 `/` 和 `；`**，不能简单按 `；` 或 `/` Split。参考 `E:\直播伴播\management-service\internal\httpapi\content_pool_sources.go` 的 `parseContentFactHeader`：用标准库 `encoding/json.Decoder` 读字符串，再按 `InputOffset()` 定位并验证紧随其后的 `；`，之后才提取真正的分类。若支持链接名内含 `]`，还须先读完JSON字符串再找标题结束符，不能先在引号中截断。
2. **`anchorcycle` 包不能 import `httpapi` 包**（会循环依赖）。`explicitPlanFactScope` 在 `httpapi/live_agent_plan_fact_scope.go`，`CategoryFromFactText` 在 `anchorcycle/fission_side.go`。方案 A 需要在 `anchorcycle` 包内**重新实现一个轻量剥前缀函数**，或把剥前缀逻辑下沉到共享包。
3. **只剥程序生成的「用户指定公共；」和「用户指定商品="..."；」两种前缀**；普通 `[xxx/yyy]` 保持旧行为；`[商品卡]`、`[有效福利]` 不伪造分类。不从正文中的“用户指定”等词猜归属。
4. 修复只影响分类解析，**不改写原始 Data、Products、Shared、事实ID、来源ID或四层指导**，也不把其它商品事实纳入本任务。
5. 非法JSON、缺分号、空链接、未闭合标题等输入应不 panic、不越界、不把链接片段当成分类；错误格式的返回约定在测试中明确。不要用“最后一个分号后都是分类”的宽松猜测吞掉损坏数据。

### 可选：同时核对 `HookFacts()` 的商品归属过滤

`E:\直播伴播\management-service\internal\anchorcycle\angle_hook.go` 的 `HookFacts()` 先按任务商品范围筛事实，`HookFactsForSide()` 再按侧面裁剪。两层不可混同。本次实际请求中1号、2号各自商品范围存在区别，当前证据支持公共材料重复透传，不能据此宣称全量商品串入。回归仍需覆盖“公共可用、当前商品可用、其它商品不可用”。

### 另一个已确认入口：完整事实会再次进入正文提示词

`E:\直播伴播\management-service\internal\httpapi\text_generation.go` 主线请求除 `generationMaterialViews(state.HookFactsForSide())` 外，还执行：

```go
state.ContentStrategy.Render("主线", state.GenerationFacts())
// 放入 packet["内容方向与采用条件"]（当前分支未启用 AnglePlan / hookMode 时）
```

`GenerationFacts()` 来自 `HookFacts()` 全量任务事实；`E:\直播伴播\management-service\internal\contentstrategy\strategy.go` 的 `Render()` 将匹配内容方向的「完整关联事实」再次写入该字符串，**没有使用侧面筛后的集合**。本场真实请求确实包含此字段，并在这里带入用券事实。

所以最小解析修复能恢复 `可说` 的侧面筛选，但**不能据此承诺整份模型上下文已经被裁剪或重复已根治**。后续修改这个入口要另行登记 `text_generation.go` / 对应测试的交接；验收要检查整份消息，而非只数 `可说`。完整事实仍应供事实审核和必要条件校验使用，避免把“减少主动复述”变成“丢掉使用边界”。

### 重复的放大因素与本次边界

- 事实归一化把 `must_say` 存成 `【必说】`，其母版原意为“本条事实中必须讲准的客观内容”，不等于每段都读。本场用券 `【必说】` 在正文用户消息中出现两次（完整关联事实、改写指导各一次）。这是提示信号混杂，不能写成调度器显式下发“每段都讲券规则”。
