# 方案提示词四分区与双元提示词

用户需求：四个标签分别编辑主播人设、事实依据、直播话术要求、互动回答要求；保存时生成两份组合提示词。直播互动沿现有流程使用互动组合，重新生成只替换事实框。

## 已实现

- 四个标签各对应独立文本，切换保留当前草稿；支持键盘方向键、Home、End，桌面和手机布局字号至少16px。
- 主播互动元提示词 = 主播人设 + 事实依据 + 互动回答要求。
- 主播话术生成提示词 = 主播人设 + 事实依据 + 直播话术要求。
- 编译只补分区标题、换行，不额外写入业务规则、不调用模型。页面可展开查看两份合成预览。
- 单独保存提示词和顶部保存方案都走四分区保存入口。两份编译文本及四框原文在一条SQL中写入，按租户/方案隔离。
- “重新生成”读取当前方案正式商品卡、活动福利及有效一级事实，包括已保存的表达限制和参考表达；仅替换事实框。已有事实草稿先确认覆盖，成功后仍需保存。失败或组合超长时保留原稿；没有资料则明确显示事实框为空。
- 切换方案、租户/支持范围期间的迟到读取、保存回执和重新生成结果均校验所属范围，避免覆盖另一个方案。

## 存储与兼容

`live_agent_plan_prompts` 新增可空的 `sections_json` 和 `speech_prompt_md` 两列，启动时按列存在性增量迁移，不重写历史行。

`prompt_md` 保存编译后的互动组合，因此既有 `GetLiveAgentPlanPrompt` → `interactionplan.Freeze` → 单人/多人统一互动生成入口自然读取互动组合；原批量、调度、后置称呼、整段TTS与输出协议保持。

GET/PUT提示词接口返回 `sections`、`interaction_prompt_md`、`speech_prompt_md`，并保留 `prompt_md` 兼容字段。render接口新增 `facts_md`，旧 `prompt_md` 母版响应仍保留，避免缓存旧页面误用新字段。

历史提示词在读取时按已识别章节投影到四框，尚未保存时数据库原文不变。商品、福利、事实、用词消歧归事实框；原直播目标和话术规则归话术框；互动约束和输出格式归互动框；原人设及共用表达规则归人设框。未知内容保留在当前分区。完全无章节的旧文本完整放在互动框，并提示用户检查。保存时才采用新组合。正在运行的场次仍沿用已有冻结快照，新场读取保存后的组合。

本次按照用户明确指定的互动入口接线。主播话术生成提示词独立持久保存并由GET接口返回；本次没有把它额外注入旧录音主线逐句改写或其它模型调用。

## 模型输入与费用

新增模型调用0，新增TTS调用0。两份提示词由程序拼接；“重新生成”是读取与格式化方案资料，不调用模型。

互动请求使用一份人设、事实与互动要求，不含直播话术要求，不把两份提示词一起发送。只添加非空分区的标题和换行（最多约30个格式字符；不是精确token）。用户填写或重新生成后选择保存的正文决定实际请求长度。未向供应商发送付费测量请求，不提供虚构的精确token或费用变化。
