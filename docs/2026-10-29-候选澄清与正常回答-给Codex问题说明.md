# 候选澄清与正常回答问题说明（给 Codex）

更新：2026-10-29 13:52（北京时间）

## 一、当前目标

先把正常回答链路做稳：

```text
用户问题
→ 意图
→ 选事实
→ 回答
```

在这个基础上，只在“歧义会改变答案”时插入一次候选澄清：

```text
模型找出歧义词
→ 给 2～3 个有依据的候选
→ 生成一句候选澄清
→ 用户选择候选
→ 恢复 effective_question
→ 重新走意图/事实/回答
```

不是所有边界都复述原问题问“对吗”。

## 三、真实测试结果

### 1. 我在新建发货吗

返回：

```text
小王老乡，您是想问“我在新建发货吗”，对吗？
```

意图：

```json
{"ambiguous": null, "options": null}
```

模型没有输出候选，程序仍然走了复述式澄清。

### 2. 新建区

返回：

```text
小王老乡，新建区能送达，一般是下单后第二天上午发货，发京东空运；不过新建区的到货时效我这边还没核实……
```

“新建区”被当成新问题，没有恢复原问题。

### 3. 2人吃几号 → 半只

第一句：

```text
小王老乡，您是想问“2人吃几号”，对吗？
```

第二句“半只”又触发：

```text
小王老乡，您是想问“半只”，对吗？
```

没有把“半只”当成候选答案。

### 4. 2人吃几号被答成上海包邮

出现过：

```text
小王老乡，上海这单是包邮的……至于2人，我这会儿真不敢给你准话。
```

问的是2人，意图复用了“上海包邮”的语义 bucket。

## 四、根因

### 1. 候选澄清只是“要求”，不是“强制”

母版要求模型输出候选，但模型仍可返回：

```json
{"ambiguous": null, "options": null}
```

程序没有：

```text
疑似地名/对象 + scope 为空 + 无事实
→ 强制候选澄清
```

也没有：

```text
缺少候选 → 重试一次
→ 仍缺失 → 开放式询问
```

### 2. pending 写入点不对

当前 fallback 澄清写在：

```text
decisionexecutor/fallback_clarification.go
generateNoFactBoundary
```

但 Core 在到 Worker 之前就做了相关性/任务分类，“是”可能根本到不了 Worker。

正确位置：

```text
Management /internal/v1/interaction-purpose/resolve
意图判断之前
```

### 3. effective_question 没有贯通

意图接口内部可能恢复了原问题，但：

```text
PurposeResult / Signal / Candidate / decisionItem
```

仍然可能用原始“是”或“新建区”。

测试入口已经修了一部分，把 `intent.Input` 传给模拟回答；但直播链路仍未统一。

### 4. pending 只接受“是/短候选”，但候选匹配不完整

当前 `matchClarificationOption` 已支持从 `新建区/新建县等地名` 里拆词匹配，但：

```text
第一句根本没有 options
第二句自然无法匹配
```

### 5. 语义 bucket 复用没有按地区/人数隔离

“2人吃几号”复用“上海包邮”的 purpose，说明：

```text
judge prompt 的地区规则还不够
或 bucket 结论没有绑定地区/人数
```

## 五、正确实现顺序

### 第一步：意图必须有候选

在 `interactionpurpose.Result` 已有：

```go
Ambiguous bool
Clarify string
Options []string
```

需要：

```text
1. 模型返回 ambiguous=true 时，必须同时有 clarify + 2～3 options
2. 缺失则重试一次
3. 仍缺失则程序开放式询问
4. 不得把“是”作为 options
```

### 第二步：程序检测“该澄清但模型没说”

建议条件：

```text
1. 问题包含疑似地名/商品名/指代/省略
2. intent.scope 为空或对象不明确
3. 当前事实无法覆盖
4. 不同解释会导致不同回答
→ 程序强制生成候选澄清
```

不要按“在+地点”写死。

### 第三步：pending 写在意图接口

```text
resolveInteractionPurpose
→ 意图判断前查 pending
→ 意图返回 ambiguous 时写 pending
→ options 一并存
→ 下一句先匹配 options
→ 命中后 effective_question = 原问题 + 选中候选
```

不要只在 Worker 里写。

### 第四步：贯通 effective_question

需要从 Management 响应到 Core 再到 Worker 传递：

```text
raw_text
effective_question
clarification_context
user_id
event_id
```

至少保证：

```text
Core Signal.Content 用 effective_question
Candidate.Question 用 effective_question
decisionItem 用 effective_question
```

### 第五步：用户 ID

当前 key 依赖昵称，容易串人：

```text
小王 / 小王老乡 / 同昵称不同用户
```

必须：

```text
user_id 优先
昵称只展示
无 user_id 不建立可凭“是”恢复的 pending
```

### 第六步：最近上下文按用户

当前房间最近 chat 不区分用户。

需要：

```text
同一 user_id 的最近对话优先
其他观众单独标注
不能让 A 的上下文污染 B 的歧义判断
```

```text
C03 2人吃几号
→ 候选：半只450g / 整只900g
→ 用户“半只”
→ 恢复原问题并回答

C04 上海包邮吗
→ 不触发澄清，直接答包邮

C05 新疆包邮吗
→ 不触发澄清，答空运补费

C06 你叫什么
→ 身份回答，不触发澄清

C07 同昵称不同 user_id
→ 不能互相消费 pending

C08 用户只回“是”
→ 二选一场景不能确定选项
→ 不恢复，重新询问或要求明确选项

C09 问“2人吃几号”
→ 不得复用“上海包邮”的 bucket
```
