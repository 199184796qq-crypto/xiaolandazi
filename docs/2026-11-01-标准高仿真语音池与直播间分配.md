# 标准、高仿真语音池与直播间分配

2026-11-01，本地实现，尚未部署。覆盖上一份火山接入文档中临时采用保守RPM/RPS的策略：用户已明确火山为每账号10并发，不套用阿里限频。

## 方案与后台

- 用户在方案的“声音”页选择“标准”或“高仿真”，选择项不显示供应商。标准对应阿里TTS账户池，高仿真对应火山Doubao声音复刻2.0账户池。
- 方案快照的`voice_identity.tts_pool`保存`standard`或`high_fidelity`，与provider、model、voice_id、profile_id、binding_id一起保存及回显。录音主线继续使用自己的原声，互动使用方案选定声音。
- 切换池不把同一个音色ID交给另一供应商；必须选择对应池中的可用声音才能保存。高仿真当前只使用已登记的已有S_音色，不提供上传训练/设计入口。
- 后台“TTS账户池与调度”新增“直播间语音池分配”，按tenant和room设置允许标准、高仿真或两者。版本号用于防止管理员互相覆盖；空列表、未知池和跨账号房间拒绝。
- 方案仍独立于房间，声音随方案走。房间授权只是使用范围，不为同一方案建立房间专属音色。未配置房间授权时默认允许两池，实际合成还需要对应账号、已开通模型和匹配音色。

## 两类调度规则

| 项目 | 标准池：阿里 | 高仿真池：火山 |
| --- | --- | --- |
| 每账号限制 | 180次/分钟、3次/秒，可设低 | 默认最多10个同时合成，可按实际额度设为1—10 |
| 多个房间 | 共享该账号的滚动窗口额度 | 共享该账号的10个并发位，不按房间各分10个 |
| 请求完成/失败 | 不提前返还分钟或秒级额度 | 立即释放对应并发位 |
| 当前账号满额 | 找同池、同模型、相同声音映射的下个账号 | 找同池、同模型、相同声音映射的下个账号 |
| 所有兼容账号都满 | 排队 | 排队 |

火山请求不经过阿里RPM/RPS校验、滚动窗口扫描或每秒启动间隔。后台火山表单隐藏这些输入，API保存时也归零；兼容旧配置读取时按火山并发规则执行，历史错误大于10/空并发值按10封顶。并发占用在MySQL事务和共享锁下登记，多个工作进程不能各自再放10个。运行租约维持原2分钟保护，火山HTTP客户端90秒上限；完成或失败沿原FinishTTS结算。

只有同供应商、精确模型与已配置的同声音映射能接单。不会因标准池或高仿真池拥堵切到另一供应商。一个账号多个Key不增加账号额度。火山近60秒/近1秒仍显示调用次数统计，但不是限流阈值。

主线排队时沿既有等待钩子使用当前方案的可用缓存；互动音频未就绪时暂缓互动，不先打断主线。无可用缓存时仍须等待补料。没有增加模型上下文、LLM调用或自动TTS重试。

## 校验与迁移

开播/发布先校验方案档位与声音身份，再检查房间授权。旧快照未写tts_pool时保持原声音，按实际provider检查房间权限；历史Tencent声音不被标成标准或高仿真。合成入队及实际领取时再次检查，防止运行中授权变化或旧调用入口绕过。

修改授权会取消该房间已不允许的等待请求；已经发送的合成继续完成。操作不会开停直播，也不会替换主线缓存。新表`mgmt_tts_room_pool_policies`由现有TTS迁移入口创建；不重写历史方案、不添加方案专属数据库列。后续发布应沿现有发布锁、全场空闲与实际运行源码继承规则执行。

修正了无旧式binding_id的已有音色保存：使用原始已就绪档案的tenant/profile/provider/model/voice_id精确核对；停用、伪造或跨账号档案拒绝，不创建假绑定。
