## 2026-09-24 已确认：现金收款与银行缴存分离

用户在比较现金入账与必须先存银行两种方案后回复“好的”，确认采用：财务实际点收客户现金，登记到公司现金账户，经过规定的独立审核并正式入账成功，即可认定真实客户；不以现金已存入银行作为额外前置条件。本节明确本次批准的业务规则，不表示公司现金账户、交接和缴存模块已在本轮实现。

### 客户收款、公司资金保管、客户钱包分别记账

- 客户收款/认定：销售暂收并登记现金时为“现金已收申报，待财务点收/审核”；不能凭经办人申报直接认定真实客户。财务接收但未审核时仍为“待财务审核”；实际点收、公司现金账登记、审核入账成功后才显示“真实客户·财务已入账”。不能把公司内部尚未交接或缴存误显示为客户从未付款，不得重复催收同一笔钱。
- 公司现金保管：记录原收款单、当前保管人、交款人、财务接收人、交接时间、金额及收据。现金已正式入账但未存银行，可同时显示“财务已入账 / 现金待缴存”。不允许用自由文本“钱在财务手上”替代点收和现金账记录。
- 银行缴存：另建关联原现金账记录的内部转移单，记录来源现金账户、目标银行账户、经办/审核人、缴存金额、银行凭据与核对时间。缴存完成只减少公司现金账户余额、增加银行账户余额，不新建客户付款、不再次充值、不重复认定客户或统计业绩。交接和缴存必须可以追溯，差异留异常待办，不改写原客户付款金额。
- 客户钱包：公司现金/银行账户不是客户钱包。款项用途为充值时才增加客户钱包；直接购买设备、时长卡或会员时按订单履行，不同时重复加钱包余额。现金转入银行也不触发客户钱包或权益变动。

### 后续实现接点

财务维护受控的公司现金/银行收款账户，销售按权限选择账户；收款表单使用“付款人/付款单位”“收款账户”“交易流水号/收据编号”等清楚标签。线下销售是业务场景，不代表一定付现金：银行转账、现金和支付渠道方式要分别识别，不能把所有 offline 记录直接当作现金。

现金账户、点收、交接、缴存、差异和待办要复用现有财务能力并先核对现有模块，避免另起平行账。提交人/经办人与审核人的职责继续分离；财务点收不绕过入账审核。银行缴存期限、现金余额上限及分级审核阈值未由用户确定，不自行写死。

所有认定由服务端财务事实提供。完成首次现金审核入账后，销售端同步真实客户与售后回访口径；后续缴存不改变首次确认时间。表格/卡片、只读资金详情和分页沿用既有要求；入账仍不自动派运维，协助继续由销售或客户按需申请并另行授权。

### 验收要求与本轮边界

验收需覆盖：销售暂收未审不认定；财务已接收但未审不认定；现金正式审核入账后即使尚未存银行也认定；现金缴存不重复收款/钱包充值/计业绩；部分缴存、分笔收款合并缴存均可关联追溯且金额不超可用现金；交接或缴存失败不抹去已确认客户付款；权限、经办审核分离、重复提交和并发重试；离职交接不丢失现金责任人和凭据。

本轮仅确认并保存规则及检查已知接点，未创建真实现金账户、现金交接、缴存、收款审核或资金变动。当前 `CustomerReceiptForm.vue` 的收款账户仍为自由文本，不能把填写该文本解释为已完成受控公司现金账登记；`postCustomerReceiptTx` 中 `lockWalletAccountTx(..., "cash")` 指客户现金钱包，也不能冒充公司库存现金账户。完整现金流程应在实现并验证后另行记录交付状态。

## 核心认定

真实客户认定必须关联客户/订单、有效收款记录、审核人与审核时间、正式入账凭据。审核通过与入账成功缺一不可；流水必须是客户付费收款，不能把任意资金变动或资源流水视为成交。

## 待实施业务流程

意向顾客 -> 销售跟进/确认合作 -> 预开户或关联已有账号 -> 收款待审核 -> 财务核实并入账 -> 系统认定真实客户并同步销售/客户可见状态 -> 持续跟踪资金记录。客户需要协助时，另由销售代申请或客户自助申请进入统一运维工单；入账不自动派单。

销售开户只表示“已开户，待财务确认”，不是“成功成交”。已有账号不重建、不删资料，也不修改其登录状态。正式客户数和成交转化率以财务确认结果统计，开户数单列。

销售可以录入/提交收款资料、关联客户或订单、查看自己的审核进度；不能自行设置已入账、审核通过、真实客户或修改金额账本。智能体必须使用同一套服务端权限与业务接口。

## 一致性与历史处理

同一笔收款只审核/入账一次，来源凭据与入账记录关联；幂等键和交易唯一性防止重复提交、重复回调造成重复入账。审核通过但入账失败不能发布真实客户结果；入账凭据、首次客户认定和结果通知事件须在同一事务中提交，通知投递可在提交后可靠重试。入账结果通知不创建运维派单。

历史已开户账号不因 active 或曾被销售标记 won 自动补成真实客户。没有可核实财务证据的状态保持待核实，不伪造审核人、流水或入账时间。销售离职交接保留原开发人、原财务证据与历史订单归属。

退款/冲正需保留原入账历史及审核轨迹。是否在全部退款后排除“当前有效付费客户”、定金如何认定、企业客户由员工代付如何匹配，尚未由用户确定；不得擅自把这些政策写死。无论采用何种后续规则，资金消费完不应被等同于从未付费。

## 2026-09-24 补充：财务待办、销售同步与按需协助闭环

### 1. 同一业务状态，按角色展示

客户认定是客户级事实；收款审核是每张单据的状态；账号启用是登录状态；工单是服务状态，四者独立。已有真实客户的新充值正在审核，不得把客户重新降为意向顾客或未认定客户。

| 情形 | 销售端显示 | 财务端显示/待办 | 是否首次认定真实客户 |
| --- | --- | --- | --- |
| 已开户，无确认收款 | 已开户，待收款确认 | 待收款客户清单；不伪造已收款或应收凭据 | 否 |
| 已提交转账/线下凭据，或已核验平台支付结果但尚未审核入账 | 待财务审核；已提交时间及资料 | 待审核数量、关联客户与单据、金额、渠道、提交人、等待时长 | 否 |
| 资料不完整或被驳回 | 待补资料/审核未通过，显示可公开原因 | 保留记录；待销售/客户补充，不重复生成同一审核任务 | 否 |
| 核实通过但正式入账失败 | 入账异常，尚未完成 | 异常待办与重试入口，不能提示已入账 | 否 |
| 首笔有效收款审核且入账成功 | 真实客户（财务已入账）；时间及确认单号 | 已入账，可追溯审核人与凭据 | 是，一次 |
| 后续充值/付款待审 | 客户仍为真实客户；该笔交易显示待审核 | 新交易单独待办，不重复认定客户 | 不重复 |

没有收款资料和没有实际到账不能混成“财务未处理”。财务需能看未入账状态；待收款清单不等于待审核收款清单。无有效订单/约定金额时不凭空记应收账款。

### 2. 提醒是持久待办，不是一次性弹窗

财务工作台保留待核款、待审核、入账异常与超时未处理计数；红点/站内消息链接至有权限的对应单据。查看消息不代表审核，不因已读清除尚未完成的财务任务。超时阈值及升级提醒在系统设定配置，本次不自行约定时限。

新收款材料、支付核验完成、补件重提触发财务提醒；审核驳回/待补件、入账失败、入账成功触发申请方和当前有权销售的结果提醒。重复提交、重复回调、重复读取不重复建待办或重复入账。

账本和客户认定由服务端提供同一权威结果；销售、财务和客户页面重新进入、刷新或重连后都能取到最新状态。入账后才产生成功事件，离线通知可补投；失败提示不得靠前端伪造成功。提醒接收与明细访问均重新校验当前岗位、客户归属和租户权限，不能把后续资金消息继续发给离职/已交接销售。

### 3. 客户资金档案贯穿全程

每个账号使用稳定客户组织ID关联资金记录。待审核资料从首次提交就留痕，首次入账是客户认定时间点，不截断前期资料；之后充值、订单付款、钱包消费、退款、冲正等继续追加并可回溯。

销售对当前负责客户提供只读资金记录：业务类型、原单号、金额、收/支方向、渠道、审核/入账状态、发生/提交/入账时间，以及可公开审核说明。财务可按岗位查看完整经办、审核和凭据链；客户只看自己的记录与对外说明；普通运维不因此得到完整资金流水和银行账号。账号、支付凭据和个人联系方式按角色脱敏，不直接复用管理员全量返回对象。

列表、卡片、详情和汇总从同一真实记录取数，支持日期/交易类型/渠道/状态/单号过滤、稳定排序和数据库分页。资金汇总区分实际外部收款、钱包充值、钱包消费和退款，不把“充值后用钱包买卡”计算成两次外部收款。权益时长消耗另列，不冒充资金支出。交易金额与余额严格区分，线下直接购买/平台直接付款并不必然增加钱包余额。

历史流水不删除、不改原金额；更正通过可追溯冲正/补记，退款关联原收款与订单。已核实资金用完不代表从未付费；全额退款、定金是否影响当前有效付费客户口径沿用前文待确认事项，不由界面自行决定。

### 4. 销售与客户双入口，统一运维工单

销售入口：我的客户 -> 申请运维协助（限当前负责客户）。客户入口：我的/服务支持 -> 申请运维协助（只能是当前租户）；轻量手机端也提供该入口，不依赖直播采集、公屏或复杂策略页面。

请求内容包括问题描述、协助类别、希望联系时间、联系人及必要的直播间/设备引用；没有创建直播间的开户/安装咨询同样可提交，不能让申请依赖一个尚不存在的直播间。申请人/申请端/客户ID/创建时间由服务端生成或校验，不能由客户端指定他人身份。

工单主线：待受理 -> 已分派/已接单 -> 处理中 -> 待确认 -> 已完成；补充待客户反馈、取消、退回和重新打开的路径。具体可配置的自动关闭时限尚未确定，不自动关闭。销售与客户能查看与自己有关的进度、当前处理人和对外说明；内部排班、私密备注不向客户暴露。完成要有处理结果与确认记录，不能只把状态改成完成。

申请与授权分开：销售可以代申请，不能代替客户授予敏感代操作权限。客户自助申请也不默认勾选所有权限。涉及 L3 维护、主播训练或复刻声音，继续走现有客户/直播间/运维人员/能力授权校验。授权可拒绝或撤销；撤销后停止受限动作但保留工单记录。更换处理人时重新核验授权，不从原处理人自动继承。既有 L1/L2/L3 权限边界不因派单改变。

防重复仅做可解释提示：发现同客户同问题有未完成工单，可进入原工单补充；不要禁止客户为不同问题发起新单。客户转交销售后由现负责人跟进，工单原申请人、原处理人和历史财务归属不改写。

### 5. 与当前代码衔接及验收边界

现有 `staff_finance.go` 提供审核和入账事务，`account_finance.go` 提供基础资金档案读取；需增加客户认定及销售范围只读视图，不能把销售直接接到财务全量接口。现有 `live_support.go` 主要是客户授权与受权操作能力，`customer_handoffs.go` 是运维侧交接处理；它们不等于已有完整的双入口申请、派单和申请人进度闭环。检查中未确认统一持久通知模块，实施前应继续核对，不以命名搜索无结果断言项目完全不存在通知能力。

下一批验收至少覆盖：未收款与待审核区分；财务提醒去重；驳回补件；入账事务失败不认定；成功后销售可见；已认定客户后续充值仍可跟踪；钱包充值与消费不重复计收；客户/销售越权读取拒绝；销售代申请与客户自助申请进入同一工单；只申请不授权不能代操作；运维更换人员需重验授权；完成确认与重开；离职交接不泄露后续流水；字号、蓝光、双视图和真实分页。
