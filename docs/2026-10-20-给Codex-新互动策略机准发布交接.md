## 0. 一句话定位

用一套**全新的、最轻量的互动策略机**替换掉旧的三步模型链路（意图分析 → 规划 → 回答），
按互动类型分派到独立策略，每个策略内部「程序选材 + 模型说」分离，且**全部走话术基座（四层 + P0 + pUser）**。

当前用**代码常量开关** `useLightweightInteractionMachine = false` 隔开新旧链路，
**默认 false = 旧链路零影响**，发布后按需切 true 灰度。

## 1. 为什么重建（背景）

旧互动三步链是 token 大头，实测（session 314/359）：

| 步骤 | stage | input token | 说明 |
|---|---|---|---|
| 意图分析 | interaction_purpose_resolution | ~667 | 判「问题背后什么目的」 |
| 规划 | interaction_agent_plan | ~7866 | **最贵之一**，且重判意图（意图分析已算过一遍） |
| 回答 | interaction_agent_answer | ~8726-11092 | **最贵**，prompt 拼 10 层内容 |

核心问题：三步链对「关注/点赞/欢迎」这类**不需要查事实**的礼仪互动也全量走重链路，token 大量浪费。

---

## 2. 三档划分（9 类互动 → 三档）

互动类型由 **core 判定** `mission_kind` 下发，management 不判类型。

| 档位 | 枚举 | mission_kind | 处理 |
|---|---|---|---|
| 第一档【事实应答】 | `tierFactAnswer` | reply_question / complaint | 查事实 + 组织答案（**未实现，占位**） |
| 第二档【礼仪回应】 | `tierAcknowledge` | reply_follow / reply_like / welcome_named / welcome_batch / conversion_signal / warmup | 按类型分派独立策略（**已实现**） |
| 第三档【聊天兜底】 | `tierChat` | reply_chat | 先判弹幕性质（**黑盒粗判，未接模型**） |

`classifyInteraction` 纯程序判定，不调模型；空/未知 kind 保守归第一档。

---

## 3. 三个独立策略（第二档的核心）

用户明确：关注/点赞、欢迎、下单是**三种本质不同**的策略，不能混在一个「礼仪回应」里。

统一接口（`interaction_lightweight.go`）：

```go
type InteractionStrategy interface {
    Respond(ctx context.Context, session model.LiveRuntimeSession, item decisionItem) string
}
```

| 策略 | 触发 kind | 本质 | 当前实现 |
|---|---|---|---|
| `likeFollowStrategy` | reply_follow / reply_like | 称呼 + 一句感谢，不带信息 | 模板骨架（**未接模型**） |
| `welcomeStrategy` / `modelWelcomeStrategy` | welcome_named / welcome_batch / warmup | 称呼 + 欢迎 + 介绍活动/优惠 | **已接模型**（见 §4） |
| `orderStrategy` | conversion_signal | 感谢下单 + 承接发货 | 模板骨架（**未接模型**） |

分派入口 `dispatchLightInteraction(ctx, session, item)`：按 mission_kind 精确路由，带 nil 兜底。

## 4. 欢迎策略（唯一已接模型的策略）

`interaction_welcome.go`。两块：① 欢迎（称呼）② 介绍活动/优惠。

### 活动/福利选材（用户最终拍板）

```
welcomeBenefits
 ├─ 主路径：modelRecognizeBenefits
 │    把「全量事实」SafeFacts 喂模型，模型 ResponseJSON 返回 {"benefits":[{type,content}]}
 │    空 / 失败 ↓
 └─ 兜底：programFallbackBenefits
      程序在「活动福利 benefits 表 + 事实依据 facts 表」里筛（不含商品卡）
```

### 关键结论（多轮查证，别搞错）

- **「全量事实」= 方案安全事实快照 SafeFacts**（`interactionApprovedFacts` 返回），
  **不是** `live_agent_plan_facts` 表。SafeFacts 含 `[商品卡]...团购价/原价`、`[有效福利]`。
- **原价不在任何原始表**：`live_agent_plan_product_links` 表只有 `daily_price`（团购价），
  原价只在 SafeFacts 里（源头是商品图人工录入 → 安全事实快照 → 方案 product_focus）。
- **实测**（benefit-recognition-test 探针）：喂 facts 表 → 模型漏原价 + 脑补价格算术；
  喂 SafeFacts 全量 → 又全又准零编造（巴国布衣 3 条省 210/58/30 全对；杨鸭子省 10 + 包邮全对）。

### 欢迎策略模型调用

| 项 | 值 |
|---|---|
| 主路径识别 stage | `interaction_welcome_benefit_recognize`（ResponseJSON，MaxTokens 500，8s） |
| 欢迎正文 stage | `interaction_welcome`（ResponseText，MaxTokens 150，8s） |
| 话术基座 | 四层（必说/可说/改写/不提）+ P0 红线 + pUser |
| 无福利 / 模型失败 | 降级 `welcomeStrategy{}`（纯程序欢迎） |

### 兜底两源筛选规则

- ① 活动福利 `ListLiveAgentPlanBenefits`：`ActivityPrice`/`Gift`/`Activity`/`ProductName`，带 `StartsAt`/`EndsAt` 有效期过滤。
- ② 事实依据 `ListLiveAgentPlanFacts`：`Category ∈ {promotion, price, redemption, activity, discount, campaign, benefit}`。
- 命中 1-2 条即停。商品卡**不进**兜底。

## 6. 话术基座铁律（三个策略接模型时都必须遵守）

每次模型调用硬性带齐三块（用户 2026-10-19/20 明确）：

1. **四层结构**：必说（本次任务）/ 可说（事实包）/ 不提（未知项 + 红线词）/ 改写（改说）。
2. **P0 红线**：`policy.LoadGeneration().PromptText`。
3. **pUser**：`agentmemory.Prompt(store.ListActiveAgentMemories(ctx, tenantID, roomID))`。

且**轻量化**：不塞全量事实快照、不塞策略黑板。
