## 2. 为什么我反对你的「最小内部关联」重结构

你第 4 节建议：以「当前商品/公共任务 + 卖点×角度」为单位，记录「主体事实/辅助事实/必须保留的条件/支撑状态」，并「若模型参与选择材料，需要能从其选择回到实际输入事实」。

我反对的理由有三：

**① 它需要一次新的模型语义判断，撞你自己第 1 节的墙。**
「主体 vs 辅助」的区分是语义判断。要么程序做（但程序拿不到「哪条事实是主体」的依据，因为角度是自由文本），要么模型做（就得让模型在角度展开时输出「哪些 fact_id 是主体」）。后者=改 `angle-hook-plan.md` 让它输出结构化引用，直接重蹈我们刚用方案 A 拆掉的「格式死规定 + 解析失败重试」覆辙。

**② 它跟当前「自然语言方向」协议不兼容。**
`angle-hook-plan.md` 明确「不输出 JSON、不输出引用标识、不输出关系字段」。你要的「模型选材料→程序绑定来源→绑定不清标不确定」这一串，恰恰是这套协议明确排除的。要么推翻这个协议（代价大），要么另起炉灶（又是新调用）。

**③ 它解决的是「语义正确」，而我们只需要「别让无关事实证明侧面可用」。**
问题 1 的 bug 本质不是「我们分不清主体/辅助」，而是「`SideHasDedicatedFact` 用『存在任意专属事实』当作『侧面可用』的证据」。这个判据太松，收紧判据就能挡住 90% 的错配，不需要上升到「完整语义关联」。

## 3. 我的替代方案：角度字面匹配（轻量、程序可验）

**核心改动只在 `SideHasDedicatedFact` 一处**，不改数据结构、不加字段、不加模型调用。

现在的判据：侧面下「存在任意专属事实」→ 支撑。

改后的判据：侧面下「存在**既映射到该侧面、又与当前角度有字面关联**的专属事实」→ 支撑。

「字面关联」的判定（程序可验，不靠模型）：

```
角度文字（Task.SellingPoint + " " + Task.Angle）与 事实文本（fact.Data）
存在关联，当且仅当满足其一：
  1. 事实的 category 是「角度可推定的主体分类」——但这个映射不存在，所以退而求其次用字面；
  2. 角度文字里出现的「关键词」（工艺/步骤/慢炖/配方/价格/省/性价比/…）也出现在该事实文本里；
  3. 或：该事实的分类名（craft/price/flavor…）对应的中文标签，出现在角度文字里。
```

判定用「角度关键词 → 事实文本」的双向字面命中，**不是**模型语义理解。效果：

- 「特色菜×制作工艺」+ 工艺事实（含「慢炖/步骤」）→ 工艺事实与角度字面命中 → 「过程细节」侧面有支撑。
- 同商品的价格事实（「95.6 元」）与「制作工艺」角度无字面命中 → 不支撑「利益算账」侧面。
- 于是「利益算账」被剔除，侧面正确落在「过程细节」等有工艺事实的侧面。

**兜底保持不变**：所有侧面都不支撑 → `CurrentFissionSide` 返回空串 → `HookFactsForSide` 回退全量事实。不新增「不指定侧面」的复杂语义。

**这个方案的边界（我如实说）**：

- 「字面匹配」是启发式，不是语义证明。它能挡住「价格 vs 工艺」这种分类明显错配，但挡不住「工艺角度里两条不同工艺事实之间更细的错配」——那种程度的精确性，才需要你第 4 节的重结构。**我的判断是：问题 1 要解决的是前者（分类错配），后者是过度设计。**
- 「角度关键词表」需要维护，但它和 `factCategorySides` 同构，可以做成行业可覆盖（放 `fact-categories.json` 或行业包），不硬编码死词。

## 4. 我对你第 5 节「调度顺序」的逐条回应

你的建议顺序我基本认同，但第 3 点要改：

> 3. 角度有支撑而侧面不合适时，换侧面；全部侧面都不合适时可以不指定侧面……

**我同意「换侧面」，但不同意把「不指定侧面」当成一条主路径**。因为「不指定侧面」= `CurrentFissionSide` 返回空串 → `HookFactsForSide` 回退全量 → 把所有事实（含无关的）全喂进去，等于放弃了侧面筛选的防重复作用。它只能是「所有侧面都没有专属事实」时的兜底，不能是「角度有支撑但侧面都不合适」时的常规出口——后者应该通过「收紧支撑判定」让它不发生，而不是靠「放弃侧面」绕过。

你第 5 节其余约束（不能用无关价格事实通过工艺检查、侧面不能成为删主体事实的理由、材料不足时记录缺项不永久屏蔽）我都同意，且它们和我的替代方案一致。
