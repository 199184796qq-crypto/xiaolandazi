# 商品事实、福利与话术统一设计

状态：第一、二阶段核心链路已落地，继续完善语义学习与一致性巡检
更新时间：2026-10-05

## 1. 目标

商品卡、福利活动和补充事实不是三套互相复制的文案，而是三类事实来源：

- 商品卡承载商品、SKU、链接、规格、日常价、适用人群等商品事实；
- 福利活动承载活动价、赠品、满减、时间窗口和参与条件等交易事实；
- 补充事实承载检测、认证、资质、品牌依据、安全改写和禁止表达；
- 最终话术和实时互动只消费编译后的统一可生成事实清单。

主播风格、节奏和声音只决定“怎么说”，不得创造或覆盖事实。

## 2. 核心原则

1. 一条逻辑事实只保留一个权威来源，页面之间不复制。
2. 商品卡和福利卡是事实视图，不是另存一份展示副本。
3. 统一是统一读模型，不等于把所有领域数据塞进一张大表。
4. 进入生成器前必须校验租户、方案、商品链接、SKU、状态、有效期和版本。
5. 商品链接已失效时，绑定它的福利不得进入卡片、检索、生成或互动。
6. 删除必须清理从属关系、生成上下文、缓存和语义索引；审计记录与有效业务数据隔离。
7. 智能体自然语言操作必须转换成结构化动作，经校验和必要确认后调用与页面相同的领域服务。

## 3. 统一生成事实协议

最终生成上下文提供 `authorized_facts`：

```json
{
  "fact_manifest_version": "live-generation-facts/v1",
  "authorized_facts": [
    {
      "fact_id": "product_link:12:spec:v3",
      "source_kind": "product",
      "source_id": 12,
      "source_key": "1号链接",
      "scope_kind": "product_link",
      "link_key": "1号链接",
      "product_name": "四川菜籽油",
      "predicate": "spec",
      "label": "规格",
      "value": "5L",
      "status": "active",
      "version": 3,
      "can_generate": true
    }
  ]
}
```

来源类型：

- `product`：商品卡和链接事实；
- `benefit`：当前有效福利事实；
- `supplemental_fact`：补充证据、资质与合规事实。

原有 `product_links`、`benefits`、`formal_facts` 暂时保留，作为页面和审计兼容视图；生成模型以 `authorized_facts` 为统一事实清单。

## 4. 福利与商品卡关系

- `link_key` 为空的福利属于方案全场福利；
- `link_key` 非空的福利必须能匹配当前有效商品链接；
- 找不到有效商品链接的福利视为幽灵福利，不得进入生成上下文；
- 福利只在 `starts_at <= now <= ends_at` 且状态为 `active` 时生效；
- 活动价不能覆盖日常价的语义，生成时应区分“日常价”和“当前活动价”；
- 商品卡可以展示当前有效福利，但读取同一份福利记录，不复制数据。

## 4.1 商品卡的通用字段 + 个性属性

商品卡不是为某一个商家硬编码的一张固定表，而是两层模型：

- 通用层：链接编号、商品名称、规格、日常价、数量/组合、适用信息。这些字段在所有品类中都可稳定展示和检索；
- 个性层：挂在商品链接下的属性子项，使用 `attribute_code + display_name + value_text + unit` 表达当前品类独有事实，例如菜籽油的压榨工艺、服装的面料、家电的功率。每个子项有自己的状态和版本。

页面默认只展示通用层，卡片底部用箭头展开个性层。新增、修改、删除子项都通过同一套领域接口完成，保存后立即返回新的卡片模型；个性属性不会复制到“事实依据”页面，而是由事实编译器直接转换为 `source_kind=product` 的可生成事实。

反推解析时，模型只能把原文明确出现、且不属于通用字段的品类事实放进个性层；不确定的内容进入待确认候选，不得凭常识补齐。福利活动仍然作为独立事实来源，卡片只读取并展示当前有效福利。

## 5. 删除语义

- “下架/停用”是可恢复状态，但必须立即退出展示、检索与生成；
- “从方案删除链接”删除当前方案关系，并停用链接专属福利；
- “彻底删除商品”需要单独的影响范围预览和二次确认；
- 商品链接删除与链接福利停用必须处于同一数据库事务；
- 历史修订只用于审计，不得被业务查询或向量召回作为有效事实。

## 6. 智能体 CRUD

自然语言最终统一为：

```json
{
  "operation_id": "uuid",
  "action": "create|update|disable|delete|restore|read",
  "resource": "product_link|attribute|sku|benefit|fact|evidence",
  "target": {
    "tenant_id": 1,
    "plan_id": 2,
    "link_key": "1号链接",
    "resource_id": 3
  },
  "changes": {},
  "expected_version_no": 4
}
```

价格、活动时间、批量修改、覆盖已有值、删除和已发布方案修改必须展示差异并确认。

## 7. 语义学习

理解顺序：明确ID/链接编号 → 标准属性词典 → 商户及品类别名 → 向量语义记忆 → 大模型候选判断 → 用户澄清。

只有在用户确认且操作成功后才写入学习记忆。记忆必须按租户、商户和品类隔离，支持查看、纠正、停用和删除。向量召回只提供候选，不能绕过数据库有效性校验和危险操作确认。

## 8. 分阶段落地

### 第一阶段（当前）

- 最终话术上下文增加统一 `authorized_facts`；
- 过滤停用商品、过期福利和无主福利；
- 删除商品链接时同步停用链接专属福利；
- 商品卡展示当前有效福利；
- 生成检查页面展示统一可生成事实数量；
- 增加幽灵福利和失效事实测试。

### 第二阶段（当前已完成核心链路）

- 商品个性属性已落到 `live_agent_plan_product_attributes` 子表，并有独立修订表；
- 正式商品接口返回嵌套属性，商品卡支持箭头展开、添加、修改、删除；
- 反推分析输出 `attributes`，只接收品类特有且有原文证据的属性；
- 智能体支持 `product_attribute.add/update/disable`，沿用权限、确认卡、版本冲突和审计链；
- 删除商品链接会在同一事务停用属性和链接专属福利；属性事实进入统一生成清单。

### 第三阶段

- 语义学习记忆、属性别名和商户术语管理；
- 商品/福利/事实向量索引的删除事件与重试；
- 删除清理报告、孤儿扫描和一致性巡检；
- 互动生成与主线生成共享相同的事实编译器。

## 9. 验收条件

- 页面、预览稿、正式稿和实时互动读取同一事实来源；
- 删除商品链接后，相关福利不能继续出现或被生成；
- 过期福利不能进入最终话术；
- 不同链接之间不能串用价格、赠品和规格；
- 所有生成版本保存当时使用的事实清单和版本；
- 用户能够解释某句话使用了哪条商品、福利或补充事实。
