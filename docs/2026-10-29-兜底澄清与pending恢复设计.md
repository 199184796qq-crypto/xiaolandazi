# 兜底澄清与 pending 恢复设计

更新：2026-10-29 13:30（北京时间）

给 Codex 的参考文档。目标不是再加一个局部钩子，而是把“兜底澄清 → 用户确认 → 恢复原问题”做成全局能力。

## 一、目标

任何问题在回答链路走到以下结果时：

```text
没有命中事实
断言缺失
部分事实边界
事实裁决失败
```

只要：

```text
1. 是真实提问
2. 不是身份/投诉类
3. 同一用户同一问题还没澄清过
```

就：

```text
不直接播边界
→ 生成一次澄清追问
→ 写入 pending
→ 同一用户回答“是/对/嗯/要/可以”
→ 恢复原问题
→ 重新走意图/事实/回答
→ 仍无事实才中控兜底
```

关键：

```text
全局按“链路结果”触发，不按问题句式写死
最多澄清一次，不能循环
```

## 二、当前已实现

### 1. pending 存储

文件：

```text
management-service/internal/decisionexecutor/fallback_clarification.go
```

结构：

```go
type fallbackClarification struct {
    Original string
    Expires  time.Time
}

var fallbackClarifications sync.Map
```

key：

```text
tenant_id:room_id:user
```

user 取值顺序：

```text
item.Nicknames[0]
item.resolvedAddress
```

TTL：

```text
45 秒
```

### 2. 写入澄清

`generateNoFactBoundary` 顶部：

```go
if !item.ClarificationAsked &&
    !identityQuestionPattern.MatchString(question) &&
    !upsetQuestionPattern.MatchString(question) &&
    saveFallbackClarification(session, item, question) {
    return "您是想问“" + question + "”，对吗？"
}
```

`boundaryOrClarify` 覆盖 `factguard.Assertions` 的断言缺失分支。

回答末尾也有一段：

```text
如果文本只剩否定/边界，且没有正向结论
→ 写 pending，改成澄清句
```

### 3. 消费澄清

`generateSingleInteractionDirectAnswer` 开头：

```go
question := primaryQuestion(item)
if original := takeFallbackClarification(session, &item, question); original != "" {
    item.SampleQuestions = []string{original}
    question = original
}
```

`takeFallbackClarification` 只在用户回答以下短肯定时消费：

```text
是 / 对 / 嗯 / 是的 / 对的 / 要 / 可以
```

其他内容：

```text
删除 pending
```

### 4. 防循环

```go
item.ClarificationAsked = true
```

消费 pending 后设置，后续边界不再澄清。

## 三、当前真实测试结果

### 已生效

```text
我在新建发货吗
→ 小王老乡，您是想问“我在新建发货吗”，对吗？

2人吃几号
→ 小王老乡，您是想问“2人吃几号”，对吗？

上海包邮吗
→ 小王老乡，上海包邮，不用补空运费。

你叫什么
→ 身份回答，没有被澄清劫持
```

### 未生效

用户接着回答：

```text
是
```

实际返回：

```text
小王老乡，海南、黑龙江……2人这块我先怂一下……
```

没有恢复原问题“我在新建发货吗”。

## 四、根因判断

pending 的消费点太晚。

当前只在：

```text
generateSingleInteractionDirectAnswer
```

入口检查。

但“是”这条事件可能先走了：

```text
generateDecisionTextMutable
→ 意图
→ 事实
→ 其它 mission 分支
```

还没到 `generateSingleInteractionDirectAnswer`，就已经生成了别的回答。

所以 pending 没有被消费。

## 五、正确落点

把 pending 检查前移到：

```text
management-service/internal/decisionexecutor/worker.go
func (w *Worker) generateDecisionTextMutable(...)
```

入口，在以下动作之前：

```text
意图
事实选择
mission 分支
回答生成
```

伪代码：

```go
func (w *Worker) generateDecisionTextMutable(ctx, session, item) (string, error) {
    if item != nil {
        question := primaryQuestion(*item)
        if original := takeFallbackClarification(session, item, question); original != "" {
            item.SampleQuestions = []string{original}
            item.ClarificationAsked = true
            // 清掉旧的 purpose/angles/facts，按原问题重新走
            item.PurposeID = ""
            item.PurposeKnowledge = nil
            item.IntentAngles = nil
            item.ScopedFacts = ""
            item.AnswerScope = ""
            item.FullFacts = ""
        }
    }
    // 原有流程
}
```

注意：

```text
恢复后要重新走意图/事实
不能沿用“是”这条的旧 fact 选择
```

## 六、用户标识必须稳定

当前 key 依赖昵称/称呼，容易不一致：

```text
小王
小王老乡
```

建议：

```text
1. Core 事件带 user_id
2. decisionItem.UserIDs[0] 优先
3. 没有 user_id 才退回昵称
4. 同一房间同一 user_id 才是同一人
```

测试注入接口已经支持：

```json
POST /internal/v1/rooms/29/test-events
{"user_id":"sim-1","nickname":"小王","content":"我在新建发货吗"}
```

内部无直播测试接口也要把 `user_id` 传进 decision：

```json
POST /internal/v1/rooms/29/test-interaction
{"plan_id":4,"user_id":"sim-1","nickname":"小王","text":"..."}
```

## 七、并发与多实例

`sync.Map` 只适合单 Management 实例。

当前生产只有一个 Management，可以先用。

如果以后多实例：

```text
Redis: clarify:{tenant}:{room}:{user}
TTL 45s
value: {original, created_at}
```

不要用进程内 map 跨实例。

## 八、边界与异常

```text
用户回答“不是/算了/新的问题”
→ 删除 pending，按新问题处理

用户不回答
→ 45 秒过期

同一问题第二次仍无事实
→ 不再澄清，走中控兜底

身份/投诉
→ 不进入澄清

澄清句本身不承诺事实
→ 只说“您是想问……对吗？”
```


### 回归

```text
上海包邮吗 → 上海包邮，不澄清
你叫什么 → 身份回答，不澄清
砍不砍 → 切块，不澄清
2人吃几号 → 第一次澄清，第二次边界
```

## 十、验收标准

```text
1. 第一次无事实/边界：澄清一次
2. 同一用户“是”：恢复原问题
3. 不再把“是”当新问题
4. 同一问题最多澄清一次
5. 身份/投诉不澄清
6. 上海包邮等有事实问题不误澄清
7. 有直播/无直播测试接口结果一致
```
