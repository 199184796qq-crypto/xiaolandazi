## 0. 审查结论与关键修订

原方案覆盖方向正确，但以下问题必须先纠正，否则可能切断正常互动、重复播放、重复付费或在恢复后补扣停滞时长。

| 问题 | 修订要求 |
|---|---|
| 将停播后获取的 `running=false` 当作 10:19:35 的现场状态 | 区分日志事实与事后快照；同时处理 `running=true + waiting_for_content=true`。 |
| “互动开始10秒内返回”会打断正常长回答 | 以本条回答及获准衔接音频的预计结束时间为基准；结束后12秒内完成返回或明确降级。 |
| 回收步骤先把 `ManualPaused=false`，后面又要求尊重暂停 | 不清除人工意图；暂停、停止、代次变化均禁止自动出声。 |
| 只检查 `CurrentTaskID`，不足以抵御换场和迟到回调 | 比较 tenant/session/program/Core boot/control revision/task/return token，所有外部动作前重验。 |
| `Reset` 被视为普通 idle 操作 | 当前 `Reset` 会关闭订阅并删除房间状态；保留它的停止语义，缺料降级须使用不拆订阅的状态转换。 |
| Supervisor 重跑原循环会重新随机标签顺序、从第一轮第一句开始 | 先持久化本场供料检查点和追加回执，再允许重建 worker；不得直接重跑入口。 |
| 启动恢复读取“当前发布方案”可能改变本场内容、音色和语速 | 恢复本场冻结的版本、事实和声音身份；无法证明一致则降级并提示，不猜测。 |
| 水位将 `buffered_mainline_ms` 与 `future_window` 相加 | 前者已经包含后续音轨剩余时长；统一只用前者，后者用于定位切点。 |
| `phase=interrupt` 超15秒直接判静音 | 正常回答可以超过15秒；以同代次有效音频输出进度、任务期限和缺料状态综合判断。 |
| 检测到停滞时只跳过一次扣费或暂停调用结算 | 当前结算使用累计工作秒数，下次会追扣；必须持久化不计费区间/消费水位，并贯穿恢复和最终结算。 |
| 发布门禁放在最后一阶段，且只在发布端检查 | 门禁最先落地；服务端锁内检查、切换/重启前重验，并与开播准入共享互斥协议。 |
| 无条件承诺重启后5秒内 append | 分开验收接管、有效缓存追加和需要外部模型/TTS的恢复；外部不可用时有界降级。 |

## 2. 目标不变量、状态与期限

| 编号 | 必须满足的不变量 |
|---|---|
| I1 | 正常回答、已准入衔接音频和合法尾保护不被固定10秒/15秒时限截断。有效结束或失败后，12秒内退出该互动占用，进入主线、缺料idle、人工paused或stopped。 |
| I2 | 普通互动在准确主线剩余缓冲低于15秒时不启动；低水位准备和派发均受控，高优先紧急控制走单独的已授权路径。 |
| I3 | 缺料不能无限占用 `interrupt/returning`；确认音频送播停滞后15秒内阻断新增伴播时长扣费，恢复及停播不追扣已排除时段。 |
| I4 | 只接管仍运行、同执行域、未暂停、未结束、无resume pending且身份可验证的本场供料；旧worker和旧回调不能写入新场。 |
| I5 | 有活动直播或查询结果不确定时，普通发布和回滚不能切换会影响其后台的运行目录或重启Management/Core/网关；门禁先于任何业务发布。 |
| I6 | 已生成、已追加、已实际送播是三个不同进度；恢复不重复购买、追加或冒记完整播放。 |

### 2.1 音频状态与场次状态分开

```text
音频：mainline → interrupt → returning → mainline
                                  └→ idle_waiting_content
人工：paused / stopped（始终优先，不被回收器覆盖）
供料：healthy → recovering → healthy / degraded
计时：billable ↔ blocked_audio_stall / unverified
```

`idle_waiting_content` 是业务原因，底层可使用 `phase=idle + waiting_for_content=true` 表示；不要求把数据库场次直接改成stopped。缺料恢复可以继续同一场，不能自动新建场次或替客户重新开播。

### 2.2 统一期限

- `expectedAudioEnd`：同任务实际服务端音频启动时间 + 已确认回答时长 + 获准且有上限的衔接音频 + 当前头尾保护；时长单位和是否已包含保护只计算一次。
- 正常terminal后的 `returnDeadline = terminalAt + 12s`。
- terminal丢失的兜底：到 `expectedAudioEnd + 4s` 进入失败补偿，并在该次失败判定后12秒内退出互动占用。
- 所有期限有身份校验和绝对上限；获准衔接只在同任务内更新期限，不允许无界续租。
- 不再保留一个晚于硬截止的“提前30秒告警”。改为恢复开始、接近截止和执行结果日志，重复告警去重。

## 3. A：Core互动返回与安全降级

### 3.1 先统一现有返回路径

核对以下现有代码后实现，不另建一套互不相通的状态机：

- `core-service/internal/coreaudio/client.go`：`CompleteProgramInteraction`、`resumeAfterInteraction`、`prepareProgramResumeLocked`。
- `core-service/internal/coreaudio/mainline_recovery.go`：`RecoverProgramInteraction`及现有恢复围栏。
- `core-service/internal/coreaudio/interaction_return.go`：返回位置、token、衔接音频及finished状态。
- `core-service/internal/httpapi/audio_runtime.go`、`audio_interaction_recovery.go`：terminal、超时与speechRuntime/decision收尾。

普通terminal、丢失terminal补偿、返回超时复用同一个幂等收尾操作。操作名称可为 `AbortProgramInteraction` 或扩展现有恢复接口，最终以复用围栏和兼容现有适配器为准。

拟新增的返回结果至少区分：`resumed`、`idle_waiting_content`、`manual_paused`、`stopped`、`stale_or_already_finalized`。返回nil不能被当作“主线已经恢复”；只有新的真实主线PCM回执可确认恢复成功。

### 3.2 身份与人工意图优先

回收前记录并在每次外部动作前重验：tenant、runtime session、Core boot、program ID、控制代次、当前互动task ID、返回token及当前人工意图。

- 人工pause/stop、换program、换场、换Core boot、迟到terminal：退出旧观察，绝不启动声音，也不清新任务状态。
- **不写 `ManualPaused=false`；不盲目清空新 `CurrentTaskID`。**
- 已进入主线的同任务重复回收仅返回结果，不重复发布或增加sequence。
- 锁内确定动作与预期代次，锁外执行I/O；执行前后复核。控制revision不能只在文档中出现，接口和发布主线都要携带并验证。

### 3.3 按真实可播位置决定结果

| 条件 | 处理 |
|---|---|
| 同场、无人工暂停、存在未播放的有效主线 | 取消旧互动发送和镜像任务，关闭旧返回门，按稳定音轨位置恢复；不得重播已完成的最后一句。 |
| `running=true` 但 `waiting_for_content=true`、无后续音轨 | 取消旧互动，释放returning/decision占用，转缺料idle；保持同场和可追加能力，新音轨到达后按既有围栏恢复。 |
| 无program或program已停止 | 仅在能证明引擎仍属于该旧互动时收尾idle；不得重新设置Running、开启节目或影响后继任务。 |
| 人工暂停 | 保持paused和恢复位置，清理旧互动占用但不出声。 |
| 身份不符、读状态失败 | 不对未知/新任务做破坏性回收；同一观察有界退出，标记恢复不确定并告警，不无限占用后台观察线程。 |

顺序队列自然耗尽、`prepareProgramResumeLocked`耗尽分支和正常互动返回耗尽分支都要一致进入缺料状态，不能只改 `recoverExpiredRoomAudioInteraction` 中的 `!Running` 判断。

### 3.4 引擎idle与下游协议

当前 `roomaudio.Engine.Reset` 会关闭全部PCM订阅、删除房间状态并重置输出时间基准，不能直接用作临时缺料降级。

拟新增或扩展非破坏性idle转换：在确认为同旧任务时清互动游标、互动时间线、切点和返回占用，保留订阅、主线位置及本场输出时间基准。人工暂停状态不被覆盖。

控制通知应经现有audiohub/播放器控制通道发送，先核对网页和网关支持的action；如增加新action，须同步消费者及回归，不能假定Engine已有 `ControlEvent{Action:"idle"}` 广播能力。停止旧发送源后才准许新主线出声，验证无交叠。

### 3.5 speechRuntime和decision结果

- 回答PCM确认完整、terminal正常，但回主线缺料：可完成该回答并单独标记返回缺料，不能把未恢复的主线标成playing。
- terminal丢失、回答被强制取消或PCM不完整：保留失败/部分完成信息；不得伪造 `COMPLETED`、播放覆盖或成功使用计数。
- 所有收尾按同task/decision CAS更新；释放、失败或完成操作重复执行不重复计数。后续decision只在状态一致且水位允许后启动。

## 4. B：Management供料监督与同场接管

### 4.1 复用现有所有者机制

`startLiveAnchorProducer` 已有进程上下文、`cycleCancels`本地登记、共享owner租约和房间模型scope。Supervisor复用这些机制，不用另一个room-only map取代分布式所有权。

建议新增 `recording_supply_supervisor.go`，将Ensure、停止、周期扫描和接管编排集中管理；本地键至少包含tenant/room/session，旧worker结束时用token比较后删除，不能把新worker登记删掉。

已运行worker心跳不等于持续供料。保存最近成功追加、最近播放进度、当前等待原因；缓冲健康时按水位等待无需持续追加，不能因lastAppend过久反复启动worker。

### 4.2 持久检查点是启用恢复的前置条件

原 `runRecordingStreamProducer` 会初始化轮次、随机顺序、队列、block序号；**不能在新进程直接重跑它来宣称恢复成功。**

同场恢复记录拟包含：

- tenant/room/runtime session/execution realm；冻结的plan/version、事实/审核/声音身份（含模型、音色、语速）。
- Core boot、program ID及执行/控制代次；owner token/epoch与检查点revision。
- 当前轮次、该轮已选定标签顺序、标签稳定ID、源句稳定key、下一供料位置及必要的轮次统计。
- 每个待交付音轨的稳定unit ID、媒体ID、不可变内容摘要、完整追加payload或其版本化恢复依据。
- 分开的生成成功、Core已接收、PCM已覆盖/完整播放水位；待确认追加请求。
- 现有更新规划器的预算与尝试状态引用；不重置余额、轮次或成功请求计费幂等键。

选用已有可靠持久仓库或新增会话级表前，先核对重启持久性、CAS、租约及迁移/回滚兼容性。只有进程map或短TTL缓存不满足要求。客户长期声音缓存和本场恢复检查点分开管理。

### 4.3 追加与丢失应答协议

1. 生成完成后先持久保存媒体与稳定unit身份；可用缓存直接复用，不重复请求模型/TTS。
2. 在向Core追加前保存待确认意图，包含同场program/version、unit ID及**同一追加payload摘要**。
3. Core确认接收后CAS更新已接收水位，推进下一供料位置；尚未播放的已接收内容不能再作为新unit重复追加。
4. 应答丢失时查询接收回执，或按已有幂等协议用相同ID和payload重试；**不能重新签一个不同URL并仍声称payload相同**。当前Core按序列化track计算摘要，恢复设计必须兼容这一点；媒体URL更新若需新协议，要显式版本化并测试。
5. 保存成功但未追加、已追加但检查点未落盘、已播放但Management未收到回执，都应有可确定的对账结果。

`track_index`会随队列裁剪变化，不能作为持久恢复唯一依据。采用稳定track/unit ID、追加回执和播放覆盖；`complete=false`或未确认的内容不能算已完整播过。

### 4.4 接管顺序与禁止条件

启动后及周期扫描均需限并发，建议4个房间；先具备数据库/Core读取能力和该执行域leader权限，再处理候选场次。

接管前共同核验：数据库仍是该running session、Core仍属于同场program/boot、未人工暂停/停止、无resume pending、检查点与冻结版本相符、无存活owner。

- 获取/续约共享owner后再次验证；每次付费调用、检查点提交和append前验证所有权与控制代次。
- 使用本场冻结版本，不读取“当前最新发布版本”替换正在运行的快照。
- 只恢复未送播的后续供料，不重新调用startProgram，不重播开场，不重新洗牌当前轮顺序。
- Core重启、program缺失、检查点缺失/损坏或身份无法证明一致：进入degraded、明确提示并阻断受影响的时长扣费，不猜进度、不恢复历史场或自动新建场次。
- 老场没有新检查点时须使用明确的兼容策略；禁止以“补一个空检查点”重开首轮。已结束515仅作为回放夹具，绝不恢复其生产场次。

worker错误可按1/2/4/8/15秒上限退避并加抖动。恢复必须从已确认检查点继续；panic保留错误栈和归属信息，停止该worker并由监督器接管，不能吞掉panic后静默运行。租约丢失必须立即停止新的写入与付费请求。

### 4.5 恢复期限的可验收范围

- 数据库、Core、租约可用：管理服务ready后5秒内完成可恢复场次的接管/状态分类。
- 媒体已经有效缓存、Core有追加空间：接管后5秒内可追加后续音轨；缓冲已充足时可保持正常背压，不能为了指标强行追加。
- 需要新模型/TTS或外部不可用：沿用现有请求超时和预算控制；无音频进展达阈值时降级并阻断时长扣费，不保证冷生成5秒成功。

## 5. C：准确缓冲水位与互动准入

### 5.1 唯一水位口径

当前Core顺序节目快照的计算为：

```text
buffered_mainline_ms = max(0, 从当前轨到队尾的音轨时长合计 - 当前播放位置)
```

因此**不能再加future_window时长**。future_window为有界准备窗口，仅用于前瞻内容和安全切点。测试必须覆盖超过32条轨及90秒窗口，避免把截断窗口误当完整队列。

根据同场最新快照判定；`waiting_for_content=true`、无program、人工暂停、身份不符或快照过期/读取失败都不启动普通互动。老版本字段不可辨认时保守拒绝并标明原因，不能拿历史快照假装新水位。

### 5.2 阈值与滞回

下列值是可配置业务默认建议，写入现有配置时同步解析、版本兼容、中文字段说明及母版清单，不仅添加未读取的JSON。

| 水位/状态 | 普通互动策略 |
|---|---|
| 低于15秒 | 不开始普通P1/P2/P3互动。 |
| 15秒至不足20秒 | 允许符合其它条件的P1；暂停P2/P3准备与派发。 |
| 20秒至不足30秒 | 若此前因低水位暂停P2/P3，继续保持；尚未进入限制状态时沿用正常准入。 |
| 至少30秒 | 清除低水位限制，恢复正常调度。 |

P0紧急控制、人工停止/暂停不能被此普通互动门槛阻断；若业务另有P0语音动作，明确其权限、预算和无主线返回策略，不能隐式放行所有高优先任务。

### 5.3 两次校验与费用边界

Management在准备模型/TTS前做一次准入，Core在实际切点开始互动前再验一次同场水位与恢复入口，防止排队期间缓冲耗尽。

低水位是暂缓还是终止由事件TTL和现有队列规则决定，记录 `mainline_low_buffer`、阈值、快照年龄和decision身份；不能无限409重试。准备好但未采用的声音保留复用；已经实际成功的模型/TTS请求照实入账，不能因准入被拒改成零成本。

## 6. D：送播停滞检测与伴播时长止损

### 6.1 不能仅看phase或心跳

Management reconciler现有周期约5秒。读取Core的同场program、音频引擎输出进度和合法任务期限，必要时增加明确的Core boot/输出epoch和最后有效媒体帧时间。

- 正常30秒回答即使全程interrupt，只要媒体进度持续前进，就不是停滞。
- `output_pts_ms`属于引擎时间基准，Reset/Core重启可能归零；必须连同boot/program/输出epoch比较，换场时重建观察状态。
- `updated_at`、服务健康、订阅数、数据库online均不能单独证明正在送音频。
- 输出计数持续增长也可能只是人为填充静音；如发送端存在这种行为，需区分媒体帧与维持连接的静音填充。正常素材的停顿和首尾保护不按音量阈值误判故障。
- Core送PCM不等于盒子完整发声。物理连接故障依据真实WebSocket心跳/回执另行检测；本阶段不能宣称有实机音量或听感检测能力。

### 6.2 检测状态机

```text
healthy → suspect_stall → blocked_audio_stall → recovering → healthy
                  └→ unverified（读取失败或身份不确定）
```

运行场次中，没有有效媒体输出进度、没有合法人工暂停或有界启动宽限且没有可解释的有效任务进展，连续15秒视为确认停滞。建议每5秒采样，以最近一次确认有进展的时间为起点；遇调度延迟不得靠“次数”延长期限。若轮询间隔不足以保证15秒内止损，应增加Core事件或更短的独立检测周期，并以测试的最坏上界验收。

Core查询失败记unverified，不宣告设备离线或直播结束；将未验证区间持久暂挂，不先扣后无限追补。重新取得可信进度后只确认有证据的区间，永久不确定部分需单独对账，不能混进正常工作时长。

确认停滞后：释放当前互动占用/转缺料idle、通知供料Supervisor、写结构化故障和用户可读状态，阻断新增伴播时长扣费。默认不直接结束场次；真正room offline、配额耗尽、人工stop等既有规则保持。

### 6.3 累计计时必须闭环修改

当前 `settleLiveRuntimeMeterTx` 使用：

```text
requested = coreWorkingSeconds - session.TotalBilledSeconds
```

所以只在reconciler里跳过一次结算，或者只加内存 `silentSince`，**不能实现“不扣停滞时长”**；恢复或停播结算会把差值补回来。

实施时必须设计持久的Core累计消费水位、不计费区间和净可计费秒数，使正常结算、人工暂停/继续、手动停播、系统停播、Core重启对账和Management重启均走同一规则：

1. 一次观察到的Core累计增量只消费一次，绑定session/boot/meter epoch。
2. 确认停滞后不再新增扣费；已标记不计费的增量只推进消费水位，不增加已扣费秒数。
3. 恢复有可信媒体进度后，只计恢复后的可计费增量，不追扣blocked区间。
4. 已结束场次、历史账单和供应商请求账务保持；本次不自动退款或回算515历史费用。
5. 暂停原因区分人工与音频故障；后台恢复只能解除自己的故障阻断，不能取消人工暂停或因配额不足重新启播。
6. leader切换、多进程并发和重试均使用事务/CAS及幂等审计，重启不能清空阻断状态后补扣。

若不采用独立计费水位，而选择暂停Core工作计时，必须证明暂停的是同场计时而不会取消供料/回收成品，并且所有恢复与结算入口保留不计费区间；不能把现有“人工暂停整场”直接冒充暂停扣费。

伴播时长扣费、模型/TTS供应商请求成本和可选更新预算是三套账；已有成功请求仍真实记录，故障恢复复用已成功资产和原请求身份，避免二次购买。

## 7. E：发布与回滚门禁（首先实施）

### 7.1 服务端统一门禁

覆盖 `scripts/publish-production.ps1`、`scripts/server/deploy-release.sh`、对应rollback脚本，以及实际使用的局部替换/运维发布入口。只加到一个旧脚本里不能阻止另一个入口直接重启。

部署和开播必须协调：同一分布式/主机发布互斥协议，在服务端设置有期限的维护意图，新的开播在短临界区内暂缓。只拿部署锁而不让开播参与，无法消除“检查无直播后用户恰好开播”的竞争窗口。

锁内依次执行：

1. 读取actual current、进程完整指纹和保护配置，验证前驱与发布范围。
2. 检查所有租户、所有执行域的活动/启动中场次，以及Core working、paused、resume pending、有效节目和进行中的互动；不能只查room29或数据库running。
3. 任何查询失败、超时、身份矛盾或旧Core不支持必要字段均拒绝切换/重启，不当作“没有直播”。
4. 实际运行目录切换前及每个服务重启前重新核验，保持维护意图和锁直到关键动作及健康核验完成。
5. 失败回滚同样重验。若已经有新活动场次或后继发布，不得为回滚强行重启或回旧整包覆盖；停止自动回滚并报告可恢复状态。

纯静态前端发布可使用经过验证的无重启流程；必须保留实际后台完整文件、母版与旧资源，证明不会通过共享current改变运行中后台的资源来源。

### 7.2 紧急例外

本次不提供一个普通 `--force-live` 开关直接跳过门禁。若未来确有维护期间中断直播需求，另行设计人工明确授权、精确影响场次、维护审计、计费止损和可回退步骤；文件里的示例参数本身不构成中断生产直播的授权。

## 9. 验收矩阵

以下是待实施的测试要求，不是本轮已经通过的结果。使用假时钟、HTTP/数据库桩及独立临时存储完成故障注入，不调用真实付费模型/TTS，不开停客户直播。

### 9.1 Core与输出链路

- 运行中有后续主线：正常terminal返回主线，12秒内有真实主线PCM。
- **事故主用例：33条顺序音轨，互动切在第33条末尾，running仍true、waiting为true；terminal后12秒内引擎退出interrupt，speechRuntime/decision一致收尾。**
- 已停止/无program且引擎仍属旧task：只清旧占用，不新建节目；同时覆盖该位置已有新program/新互动的迟到回调。
- 人工pause/stop与回收同刻竞争、控制代次变化、重复terminal/重复回收：人工意图获胜，无重复主线及无双源PCM。
- 合法30秒/60秒回答及获准衔接：不在开始10秒或phase15秒时被中断。
- terminal丢失：预计音频结束加4秒后进入补偿，规定期限内安全退出，不制造成功播放回执。
- 缺料idle不关闭网页/网关订阅；新内容到来后接续同一场，控制协议在各消费者上兼容。

### 9.2 供料与重启

- 同场重复Ensure、两个Management节点、leader切换及旧worker迟到退出：任一时刻只允许一个有效写入者。
- 在生成前/成功后、意图落盘后、Core接收后应答丢失、检查点保存前崩溃：恢复恰好一次供料，不重复支付、不重复追加。
- 当前轮标签顺序与下一句稳定；队列裁剪、已接收未播放及部分播放均不从第一轮重跑。
- 开播后编辑发布新方案/改语速：恢复仍使用本场冻结身份；新配置留给下次开播。
- 停止/暂停/新场、Core重启、旧检查点损坏/缺失：不接管错误场次，不无限重试；进入明确降级。
- 有效缓存且可追加时达到5秒目标；外部服务超时达到有界降级与告警，不声称冷TTS必定5秒完成。

### 9.3 水位、计时与发布

- 精确14.999/15/19.999/20/29.999/30秒边界；滞回、无program、waiting、快照过期、P0控制例外。
- FutureWindow有多轨/截断时不重复累加；准备时水位足够、实际派发时不足会被Core拦住且不重复买声音。
- 30秒正常互动持续输出不阻断计费；输出停滞时15秒内阻断新增扣费，恢复及最终stop不补扣排除区间。
- Core PTS归零、Management重启、leader切换、查询失败、累计秒数回退：不跨场比较，不重复扣费，不伪报设备离线。
- 既有成功模型/TTS成本真实保留，计费阻断不改变历史金额；同场重复审计/恢复不重复记录。
- 任意租户running、paused/resume pending、启动竞争、Core/DB查询失败：发布和回滚拒绝。
- 无直播时按实际后台继承正常发布；多发布竞争和失败回滚不覆盖后继版本。
