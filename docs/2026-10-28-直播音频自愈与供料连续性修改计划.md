# 直播音频自愈与供料连续性修改计划（给 Codex）

> 基线：2026-10-28 事故 `session 515`（room 29）。
> 目标不是“永不故障”，而是：**任何故障都能在有限时间内回到主线；回不去就明确 idle，绝不卡在 interrupt，也绝不静默计费。**

## 0. 事故结论

时间线（北京时间）：

```text
10:14:50  session 515 开播
10:17:31  最后一次 recording stream block appended
10:18:13  最后一次追加
10:18:27  发布计费配置，Management 重启
10:18:29  新 Management 进程启动
10:18:29  之后没有任何 block 追加
10:19:20  互动开始，主线只剩最后一段（track 32/33）
10:19:35  主线播完，program.running=false，waiting_for_content=true
10:19:35  互动报 COMPLETED，resumeAfterInteraction 因节目已停直接返回
10:19:35  之后 audio-engine 永久停在 phase=interrupt
10:20:05  30 秒看门狗只打印 “still returning”，没有强制恢复
```

两个独立断点：

1. **供料断**：Management 重启后，录音流供料 worker 没有恢复，主线没有新 block。
2. **返回断**：节目已经 `running=false`，Core 的互动返回路径直接 return，没有把 `roomAudio` 从 `interrupt` 拉回 `idle` 或主线。

现有看门狗 `awaitInteractionMainlineResume` 只观察、不修复；`recoverExpiredRoomAudioInteraction` 又明确拒绝 `!program.Running`，所以两条恢复路径都失效。

---

## 1. 目标不变量

必须同时满足：

```text
I1 互动开始后，10 秒内必须回到主线，或进入明确的 idle。
I2 主线缓冲低于 15 秒时，不允许再开新互动。
I3 主线无内容时，不能停留在 interrupt，也不能继续静默计费。
I4 Management 重启后，running session 的供料必须自动恢复。
I5 有活动直播时，发布脚本禁止重启 Management/Core，除非显式 --force-live。
```

非目标：

- 不保证不出现任何音频故障；
- 不自动替客户重新开播；
- 不改 TTS 价格、不复用旧缓存策略；
- 不物理删除客户录音、方案、事实和历史账单。

---

## 2. 总体设计：四道保命链路

```text
A. Core 互动租约 + 强制回收
B. Management 供料 Supervisor + 重启恢复
C. 主线缓冲水位 + 互动准入
D. 静音检测 + 计费止损
E. 发布门禁
```

A/B 是止血，C/D/E 是防复发。

## 3. A：Core 互动租约与强制回收

### 3.1 新接口

在 `core-service/internal/coreaudio/client.go` 增加：

```go
var ErrInteractionNotActive = errors.New("互动任务已不处于可回收状态")

func (c *Client) AbortProgramInteraction(
    ctx context.Context,
    roomID int64,
    interactionTaskID string,
) (audioout.RoomProgramSnapshot, error)
```

行为：

1. 加锁，取 `program := c.programs[roomID]`。
2. 若 `program == nil` 或 `program.CurrentTaskID != interactionTaskID`，返回 `ErrInteractionNotActive`。
3. 清理互动状态：
   ```go
   program.InteractionReturn = nil
   program.Suspended = false
   program.ManualPaused = false
   program.CurrentTaskID = ""
   ```
4. 如果 `program.Running && len(program.Tracks) > 0`：
   - `resumeMS := prepareProgramResumeLocked(program, program.ResumeOffsetMS)`
   - `ensureProgramTrackLocked(program)`
   - `program.Sequence++`
   - `roomAudio.PrepareResume` / `StartResume`
   - `publishMainline(program, sequence, resumeMS, now-resumeMS, interactionTaskID)`
   - 日志：
     ```text
     core audio interaction forced mainline room=%d task=%s resume_ms=%d
     ```
5. 如果 `!program.Running` 或没有 track：
   - `roomAudio.Reset(roomID)`
   - `c.hub.Expire(interactionTaskID)`
   - 保持 `program.WaitingForContent = true`
   - 日志：
     ```text
     core audio interaction forced idle room=%d task=%s reason=program_stopped
     ```
6. 返回 `ProgramSnapshot`。

要求：

- 幂等：重复调用不重复发布主线；
- 不覆盖人工暂停/停止：若 `ManualPaused` 为 true，只做 idle，不自动播；
- 必须同时清 `speechRuntime` 的 returning 状态（见 3.3）。

### 3.2 看门狗改造

文件：`core-service/internal/httpapi/audio_runtime.go`

`awaitInteractionMainlineResume` 增加硬截止：

```text
hardDeadline = start + duration + guard + 12s
```

逻辑：

1. 每 25ms 检查 `speechRuntime.Interrupt` 与 `roomAudio`。
2. 若已回主线，保持现有 completed 逻辑。
3. 到 hardDeadline 仍不是主线：
   - 调 `AbortProgramInteraction(roomID, taskID)`；
   - 若返回 nil：标记 speechRuntime `COMPLETED`（forced）或 `FAILED`（idle）；
   - 若返回 `ErrInteractionNotActive`：只清理本地观察，不报错；
   - 日志：
     ```text
     interaction watchdog forced recovery room=%d task=%s result=%s
     ```
4. 30 秒 notice 保留，但只作为提前告警，不再作为唯一动作。

### 3.3 恢复入口修正

文件：`core-service/internal/httpapi/audio_interaction_recovery.go`

`recoverExpiredRoomAudioInteraction` 当前：

```go
if err == nil && (!program.Running || program.Task == nil || program.Task.ID != taskID) {
    return
}
```

改成：

```go
if err == nil && (program.Task == nil || program.Task.ID != taskID) {
    return
}
if err == nil && !program.Running {
    // 不再放弃；交给 AbortProgramInteraction 做 idle 收尾
}
```

然后优先调用 `AbortProgramInteraction`，而不是只调 `CompleteProgramInteraction`。

### 3.4 roomAudio 强制 idle

文件：`core-service/internal/roomaudio/engine.go`

若现有 `Reset(roomID)` 只清状态、不广播，补一个：

```go
func (e *Engine) ForceIdle(roomID int64)
```

行为：

- `phase = idle`
- `activeSource = none`
- 清 `currentSegmentID` / `interruptCursorMS`
- 保留 `mainlineCursorMS` 供下一段恢复
- 广播一次 `ControlEvent{Action:"idle"}`

如果 `Reset` 已满足，直接复用，不新增重复 API。

### 3.5 测试

- `AbortProgramInteraction`：
  - program 运行中 → 回主线，`phase=mainline`；
  - program 已停 → `phase=idle`，不残留 interrupt；
  - 重复调用 → 幂等；
  - task 不匹配 → `ErrInteractionNotActive`；
  - 人工暂停 → 不自动播。
- 集成：
  - 模拟“互动开始 → 主线播完 → 互动 COMPLETED”，断言 12 秒内 `phase != interrupt`；
  - 模拟 receiver terminal 丢失，4 秒 expire 后仍能回收。
- 更新 `audio_interaction_recovery_test.go`、`interaction_return_pipeline_test.go`。

## 4. B：Management 供料 Supervisor 与重启恢复

### 4.1 现状

- `recording_stream.go` / `recording_stream_tabs.go` / `recording_stream_units.go` 是**进程内 goroutine**。
- Management 重启，goroutine 消失；`live_runtime_sessions` 仍是 running，但没人再 append。
- `recordingReadyQueue` 只在内存里。

### 4.2 新组件

新增：

```text
management-service/internal/httpapi/recording_supply_supervisor.go
```

核心结构：

```go
type recordingSupplySupervisor struct {
    mu      sync.Mutex
    workers map[int64]*recordingSupplyWorker // room -> worker
    store   *appdb.Store
    core    *coreclient.Client
}

type recordingSupplyWorker struct {
    tenant, room, runtimeID int64
    versionID int64
    cancel    context.CancelFunc
    done      chan struct{}
    lastAppendAt time.Time
    lastError    error
}
```

方法：

```go
func (s *Server) EnsureRecordingSupply(ctx context.Context, tenant, room, runtimeID, versionID int64) error
func (s *Server) StopRecordingSupply(room int64)
func (s *Server) RecoverRunningRecordingSupplies(ctx context.Context) error
```

要求：

- `Ensure` 幂等：同 room + runtimeID 只允许一个 worker；
- worker 退出时从 map 删除；
- worker 内部循环包一层 `recover`，panic 不拖垮进程；
- 失败退避：1s/2s/4s/8s，最大 15s；
- 每次 append 更新 `lastAppendAt`，并写一条结构化日志。

### 4.3 启动恢复

`management-service/cmd/management/main.go` 启动后：

1. 等待 DB 可用；
2. 查询 `live_runtime_sessions`：
   ```sql
   status='running'
   ```
3. 对每个 session：
   - 取 room / runtimeID；
   - 取当前发布的 `live_agent_plan_versions`；
   - 调 `EnsureRecordingSupply`；
4. 记录：
   ```text
   recording supply recovered tenant=14 room=29 session=515 version=242
   ```

注意：只恢复 `running` 且未 `SessionResumePending` 的场次；暂停/停止不恢复。

### 4.4 改造现有启动函数

把 `recording_stream_tabs.go` / `recording_stream_units.go` 里的长循环抽成：

```go
func (s *Server) runRecordingStreamSupply(
    ctx context.Context,
    tenant, room, runtimeID int64,
    version model.LiveAgentPlanVersion,
) error
```

现有 HTTP handler 只负责调用 supervisor.Ensure，不再直接 `go` 一个裸循环。

### 4.5 测试

- Management 重启后，supervisor 从 DB 恢复 running session；
- 同 session 重复 Ensure 不产生双 worker；
- worker panic/返回 error 后按退避重启；
- stop session 后 worker 退出；
- 集成：模拟重启，断言 5 秒内出现新的 `recording stream block appended`。

## 5. C：缓冲水位与互动准入

### 5.1 读取水位

Core `ProgramSnapshot` 已提供：

```text
buffered_mainline_ms
future_window
waiting_for_content
running
```

Management 在派发互动前读取：

```text
bufferMS = buffered_mainline_ms + future_window 剩余时长
```

### 5.2 阈值

配置建议放在 `interaction-scheduling.json`：

```json
"mainline_buffer": {
  "reject_below_ms": 15000,
  "pause_warmup_below_ms": 20000,
  "resume_above_ms": 30000
}
```

规则：

- `bufferMS < 15s`：拒绝新互动，返回 `mainline_low_buffer`；
- `15s <= bufferMS < 20s`：P1 问题可答，P2 欢迎/暖场暂停；
- `bufferMS >= 30s`：恢复正常。

### 5.3 互动开始前检查

在 `dispatchRoomAudioInteraction` 或 claim 前：

```go
if bufferMS < rejectBelow {
    writeError(409, "主线缓冲不足，暂不插播")
    return
}
```

同时写一条 decision skip 记录，方便统计。

### 5.4 测试

- buffer 14.9s → 拒绝；
- buffer 16s → 只允许 P1；
- buffer 31s → 全恢复；
- 无 program / waiting_for_content → 拒绝。

## 6. D：静音检测与计费止损

### 6.1 数据源

Core 已有 `/v1/rooms/{id}/audio-engine`：

```text
phase
active_source
output_pts_ms
mainline_cursor_ms
updated_at
```

Management reconciler 每 5 秒轮询。

### 6.2 规则

```text
session status=running
且 phase=interrupt 持续 > 15s
或 output_pts_ms 连续 15s 不前进
→ 标记 silent_audio
→ 暂停计费
→ 记录审计
→ 可选：自动 stop session（默认只暂停计费并告警）
```

### 6.3 实现点

- `management-service/internal/liveruntime/reconciler.go`：
  - 增加 `lastOutputPTS map[stateKey]int64`、`silentSince map[stateKey]time.Time`；
  - 新增 `getCoreAudioEngine`；
  - 新增 `stopForSilentAudio`/`pauseMeteringForSilentAudio`。
- 日志：
  ```text
  billing manager silent audio tenant=14 room=29 session=515 silent_for=18s
  ```
- 测试：fake Core 返回固定 output_pts，15 秒后计费不再增长。

### 7.1 规则

`publish-production.ps1` / `deploy-release.sh` 重启前：

```text
查询 live_runtime_sessions status='running'
有 running → 默认拒绝
```

显式 `--force-live` 才允许，并记录审计。

### 7.2 检查点

- 发布前；
- 重启 Management/Core 前；
- 回滚前同样检查。

### 7.3 测试

- running session + 普通发布 → 拒绝；
- running session + `--force-live` → 允许并写审计；
- 无 running → 正常发布。

## 8. 状态机与截止时间

```text
IDLE
  → MAINLINE
  → INTERRUPT (互动开始)
  → RETURNING
  → MAINLINE (正常)
  → IDLE (主线无内容/人工停止)

INTERRUPT 最长允许：
  duration + 500ms guard + 12s
```

任何路径都不允许 `INTERRUPT` 无限停留。

## 9. 分阶段实施

### Phase 1（止血，优先）

- Core `AbortProgramInteraction`；
- 看门狗硬截止 12s；
- recovery 去掉 `!program.Running` 放弃逻辑；
- 测试 + 无直播发布 Core。

验收：模拟“主线播完 + 互动结束”，12 秒内必须 `phase != interrupt`。

### Phase 2（供料恢复）

- Supervisor + Management 启动恢复 running session；
- 现有 recording stream 改造为 supervisor 管理；
- 无直播发布 Management。

验收：Management 重启后 5 秒内恢复 append。

### Phase 3（准入与计费）

- buffer 水位检查；
- silent audio 计费止损；
- 配置与指标。

### Phase 4（发布门禁）

- 脚本检查 running session；
- 文档与回执。

## 10. 验收指标

| 指标 | 目标 |
|---|---:|
| 互动结束到回主线 | ≤ 12s |
| 互动卡在 interrupt | 0 次 |
| Management 重启后供料恢复 | ≤ 5s |
| 主线 buffer 低于 15s 仍开互动 | 0 次 |
| 静音计费 | 15s 内停止 |
| 有直播时误重启 | 0 次 |

## 11. 风险与约束

1. **强制回主线可能重叠**：必须校验 `CurrentTaskID`/`ControlRevision`，只回收当前任务；不要动人工暂停。
2. **重复供料**：Supervisor 必须按 room+runtimeID 单例，重复 Ensure 只返回现有 worker。
3. **恢复风暴**：Management 启动恢复要限并发（例如 4 个 room/批），失败退避。
4. **历史数据**：不改历史账单，不物理删客户录音/方案。
5. **发布**：Phase 1/2 必须无直播时发布；发布脚本门禁先于重启生效。
