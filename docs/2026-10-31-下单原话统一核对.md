# 下单原话统一核对

用户要求：发现下单、催单等意图后仍须核对观众原话；原话符合程序已下单规则的，统一按下单处理。

## 实现

- Core入口继续先做程序核对，通过后进入现有下单调度器：按不同用户聚合、标准单人/人数感谢模板、整段TTS、真实铃声前置；不进入语义模型批次，不计入语义互动人数。
- 完成短语补充明确付款表达：刚付完钱、刚付完款、刚结完账、付完钱了、付完款了、结完账了、已结账、已经结账、结账了。裸条件表达“付完钱就发货”“结完账再说”不作为新增证据。
- Management后置打铃核对与Core保持同一套完成短语、空白归一及保守排除条件。取消“模型类型为下单意向就直接确认”的捷径；催单、闲聊、提问等标签不能否决符合规则的原话。
- 后置只检查该任务关联的当前观众原话 `SampleQuestions`，不再回退到生成的Summary或Title，也不采信模型Meaning、回答正文或历史对话。原话不通过则不响铃，已有回复继续原处理。
- 已通过场次、人数、期限与标准正文验证的程序下单模板，用显式 `DecideConfirmed` 入口复用现有铃声防重和间隔；人数补报不需要重新携带个人原话，也不再伪造“下单意向”标签绕过核对。当前唯一业务调用位于已验证的行为模板分支。

这次没有改模型分类协议、提示词、回答内容或后置称呼。对已提前生成并入队的语义回复，核对通过后接下单铃声音频流程，保留既有正文；新弹幕在Core前置确认后直接使用原下单调度和模板。保留原有保守排除：未完成、疑问、退款、历史订单、代他人及投诉等，不因单个“不”字直接排除。

## 关键用例

| 观众原话 | 模型类型 | 程序结果 |
|---|---|---|
| 五香味刚付完钱了，麻烦安排发货。 | 催单 | 完成表达通过，按下单处理 |
| 五香味这单刚结完账，支持一下主播。 | 闲聊 | 完成表达通过，按下单处理 |
| 我拍了五香，多久发 | 提问 | 完成表达通过，按下单处理 |
| 我想买五香 / 我还没付款 | 下单意向 | 不确认、不因模型标签打铃 |
| 什么时候发货 | 催单 | 无完成证据，不确认 |
| 已拍? / 我拍了但有破损 | 任意 | 沿保守排除，不确认 |
| 无原话，只有Summary或Meaning称已付款 | 下单意向 | 不确认 |
| 通过验证的order_count_v1人数补报 | 闲聊 | 使用程序确认入口，保留铃声 |
