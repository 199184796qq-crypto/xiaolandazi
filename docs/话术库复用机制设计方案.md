# 话术库复用机制设计方案

> 替代现有 SpeechPool 复用机制。本文档供实现方（Codex）与业务方对齐，所有字段、参数、行为均为明确约定。

## 1. 背景与目标

现有复用机制（`SpeechPool`）存在两个问题：

1. 复用比例是固定的（新鲜期 60 分钟后，每 3 段复用 2 段 ≈ 67%），不能随时间/内容积累递进。
2. 话术池存在 `State` 里，**每次开播 `anchorcycle.New()` 重建 → 话术池清空**，跨场零复用；唯一的跨场声音缓存（OSS，5 小时 TTL）因"话术文本指纹"对不上而基本失效。

**目标**：建立一套"永久话术库 + 新陈代谢"的复用机制，让长直播和跨场直播能稳定省成本，同时通过"复用率随库填充度自适应 + 调度打乱 + 30% 持续换血 + 开场每次全新"保证观众听不出复读。

## 2. 核心机制（一句话）

**文字和声音不设消亡时间，永久入库；它们的消亡只发生在"新内容挤进来、顶掉最旧那条"的瞬间。** 复用率不按时间、而按"该卖点×角度 slot 已存几条"自适应。

## 3. 数据模型

### 3.1 存储位置与 Key

- 介质：Redis（跨场持久化，**不设 TTL**，与现有 `State` 同店但 key 独立）
- Key：`livecompanion:tenant:{tenantID}:plan:{planID}:speech_lib`
- 结构：一个 JSON 文档，顶层是 `slot -> []条目` 的映射

### 3.2 结构定义

```json
{
  "送礼×算账": [
    {
      "text": "哥哥姐姐们，家里送亲友的看过来……",
      "voice_url": "oss://xiaolan/voice/t14/p4/xxx.wav",
      "side": "利益算账",
      "created_at": 1750000000000,
      "last_used_at": 1750000123000,
      "use_count": 5
    }
  ],
  "发货×时效": [ "..." ]
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `text` | string | 已采纳、可播出的正文（复用即直接播这段文字）|
| `voice_url` | string | 该文字对应的 TTS 音频 OSS 地址，**与 text 一对一绑定** |
| `side` | string | 生成时使用的切入侧面（记录用，便于观察多样性）|
| `created_at` | int64(ms) | 入库时间（FIFO 淘汰依据）|
| `last_used_at` | int64(ms) | 最近被复用时间（LRU 复用选择依据）|
| `use_count` | int | 累计复用次数（观察指标）|

### 3.3 Slot 划分

- **slot key = `卖点×角度`**（与现有 `Task.Key` 一致，plan 4 共 47 个）
- 切入侧面（fission side）**不是独立 slot**，只作为条目字段记录（保持现状的 `%7` 轮换，不参与调度）

## 4. 复用决策规则（填充度自适应）

### 4.1 场景分流

| 场景 | 是否复用 | 说明 |
|---|---|---|
| 开场 opening | ❌ 永不复用 | 每次实时生成（已实现"开场不得缓存"）|
| 实时互动 | ❌ 永不复用 | 实时生成（已关闭互动缓存复用）|
| body 段 | ✅ 按填充度复用 | 见 4.2 |

### 4.2 body 段复用率 = f(slot 填充度)

判断当前要生成的「卖点×角度」slot 已存几条，据此决定本次复用概率：

| slot 当前条数 | 本次复用率 | 逻辑 |
|---|---|---|
| 0 条 | 0%（必生成）| 没得复用 |
| 1 条 | 30% | 只有 1 条，复用即复读同一条，克制 |
| 2 条 | 60% | 2 条轮换，复读感低 |
| 3 条（满）| **70%（稳态）**| 3 条轮换 + 30% 换血 |

**实现建议**：用稳定 hash（如 `sha256(runID + taskKey + seq)` 取模）决定"本次复用 or 生成"，保证同一段在重试/重放时决策稳定，避免抖。

### 4.3 复用时选哪一条

- 从该 slot 中选 **`last_used_at` 最久**（LRU）的一条，避免连续复读同一条
- 命中后更新该条 `last_used_at`、`use_count + 1`
- 直接复用 `text` + `voice_url`，**不调文本模型、不调 TTS**

## 5. 淘汰机制（FIFO）

- 每个 slot 容量上限 = **3 条**
- 新生成并采纳一条后：
  1. 追加进该 slot
  2. 若 slot 条数 > 3，淘汰 `created_at` 最早的一条（FIFO）
  3. 淘汰时：从库删除该条 + **删除 OSS 上的 `voice_url` 声音文件**

> 这就是"30% 更新 = 30% 清除"的闭环：每场 30% 段落新生成，顶掉库里最旧的 30%，库总量稳定在 47 slot × 3 条 = 141 条，持续换血。

## 6. 声音处理

- 文字与声音一对一，复用文字就复用声音（省 TTS）
- 声音文件存 OSS，`voice_url` 随条目一起存库
- 淘汰条目时**同步删除 OSS 声音**，避免孤儿文件
- 废弃现有的"OSS 声音缓存 5 小时 TTL"独立机制，声音生命周期改为**跟随话术条目**

## 7. 复用率参数（可配置，含默认值）

| 参数 | 默认值 | 说明 |
|---|---|---|
| slot 容量上限 | 3 | 每个卖点×角度最多存几条 |
| 复用率(1 条时) | 30% | |
| 复用率(2 条时) | 60% | |
| 复用率(3 条满) | 70% | 稳态复用率 |

建议做成后台可配置（`anchor_generation_config` 或独立 setting key）。

## 10. 边界情况

1. **库空（第一场冷启动）**：前 ~47 段全生成填库，同一 slot 第二次出现才开始 30% 复用。这是物理必然，非 bug。
2. **slot 从未被讲过**：0 条 → 必生成。
3. **voice_url 失效/OSS 文件被删**：复用前校验声音存在，失效则降级为"重新生成该条"。
4. **并发（同场多段）**：话术库读写需加锁或 CAS，避免同 slot 并发写覆盖。
5. **跨 plan / 跨场**：key 含 tenant:plan，不同 plan 库隔离；同 plan 跨场共享（实现"第二场 70% 用上场"）。

## 11. 验收标准

1. 开场每次开播都是新生成的话术，不出现复用。
2. 同一卖点×角度 slot：第一次必生成，积累到 2~3 条后复用率逐步到 70%。
3. 复用命中时，日志无 `mainline_text` / `mainline_tts` 调用（零成本）。
4. slot 超过 3 条时自动淘汰最旧，且 OSS 声音同步删除。
5. 跨场（第二场开播）能读到上场的话术库并复用。
6. 实时互动、开场不产生库条目、不触发复用。
