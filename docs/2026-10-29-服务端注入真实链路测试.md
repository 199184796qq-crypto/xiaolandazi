# 服务端注入真实全链路测试

更新：2026-10-29 12:30（北京时间）

本文记录“模拟观众弹幕 → 服务端真实意图 → 事实选择 → 回答文本（TTS 之前）”的测试方法。以后不要再用本地模型 probe 冒充服务端链路。

## 一、两条测试链路

### 1. 注入真实观众弹幕（有直播时）

```http
POST /internal/v1/rooms/{roomID}/test-events?tenant_id=14
X-Core-Token: <CORE_INTERNAL_TOKEN>
Content-Type: application/json
```

请求：

```json
{
  "user_id": "sim-1",
  "nickname": "小王",
  "content": "上海包邮吗"
}
```

行为：

```text
写入 live_room_event_archive / room event store
→ 发布到 Core hub
→ 和采集器进来的观众弹幕走同一条事件链路
```

事件 payload 会带：

```json
{"test_simulation": true}
```

注意：

```text
有直播：事件进入真实意图/回答/TTS 链路
无直播：事件只入库，不会触发回答
```

### 2. 无直播跑 TTS 之前的完整链路

```http
POST /internal/v1/rooms/{roomID}/test-interaction?tenant_id=14
X-Core-Token: <CORE_INTERNAL_TOKEN>
Content-Type: application/json
```

请求：

```json
{
  "plan_id": 4,
  "user_id": "sim-xiaowang",
  "nickname": "小王",
  "text": "上海包邮吗"
}
```

行为：

```text
真实意图接口
→ purpose / task_angles
→ 方案事实 / 领域卡 / 语义库
→ 回答生成
→ 返回 reply
```

不创建房间事件、不播音、不写真实公屏。

返回：

```json
{
  "question": "上海包邮吗",
  "intent": {
    "purpose_id": "benefit",
    "purpose": "确认上海是否包邮",
    "task_angles": []
  },
  "reply": "小王，上海包邮，不用补运费。",
  "execution_mode": "intent",
  "plan_name": "绸都杨鸭子直播间 智能体方案01"
}
```

## 二、Token

服务器上读取，不要写到公开文档或聊天：

```bash
set -a
. /etc/xiaolan/management.env
# 或 . /etc/xiaolan/core.env
set +a
echo "$CORE_INTERNAL_TOKEN"
```

请求头：

```http
X-Core-Token: <token>
```

## 三、标准测试步骤

### 第一步：确认服务状态

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/healthz
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8081/healthz
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8083/healthz
```

### 第二步：无直播完整链路

```bash
curl -sS -X POST \
  "http://127.0.0.1:8080/internal/v1/rooms/29/test-interaction?tenant_id=14" \
  -H "X-Core-Token: $CORE_INTERNAL_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"plan_id":4,"user_id":"sim-xiaowang","nickname":"小王","text":"上海包邮吗"}'
```

### 第三步：检查意图

返回里必须看：

```text
intent.purpose_id
intent.purpose
intent.task_angles
```

不能只看 reply。

如果 purpose 写成了另一个地区，例如问成都却返回“上海”，说明语义归并缓存复用了错误结论。

### 第四步：检查事实

从 `intent.task_angles[].关联事实` 看实际选中的 F 编号。

例如：

```text
包邮范围：F091 / F027 / F026
地区运费：F091 / F045 / F046
```

必须能对应到事实库，不能是模型编的编号。

### 第五步：看最终回答

回答是 TTS 之前的文本，不经过音频。

如果回答出现：

```text
先说包邮
又说这个地区没确认
```

说明不是链路断了，而是缺少可推导的地区结论或事实覆盖。

## 四、有直播时注入弹幕

```bash
curl -sS -X POST \
  "http://127.0.0.1:8081/internal/v1/rooms/29/test-events?tenant_id=14" \
  -H "X-Core-Token: $CORE_INTERNAL_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"sim-1","nickname":"小王","content":"上海包邮吗"}'
```

预期：

```http
HTTP 201
```

返回：

```json
{
  "event_type": "chat",
  "user_id": "sim-1",
  "nickname": "小王",
  "content": "上海包邮吗",
  "payload": {"test_simulation": true}
}
```

然后查：

```text
live_room_event_archive
live_model_exchanges
live_generated_speech_history
```

确认：

```text
事件真的入库
purpose resolution 真的发生
没有 purpose resolution fallback
最终回答落库
```

## 五、必查日志

```bash
sudo journalctl -u xiaolan-core.service --since "-10 min" --no-pager \
  | grep -E 'purpose resolution fallback|room=<room>'

sudo journalctl -u xiaolan-management.service --since "-10 min" --no-pager \
  | grep -E 'interaction-purpose|decision tts text'
```

出现：

```text
purpose resolution fallback
```

说明意图接口失败，后面的回答不能算真实意图结果。

## 六、数据库核对

```sql
-- 最近弹幕
SELECT id, content, occurred_at
FROM live_room_event_archive
WHERE room_id = 29 AND event_type = 'chat'
ORDER BY occurred_at DESC, id DESC LIMIT 10;

-- 意图模型调用
SELECT id, stage, latency_ms, input_tokens, output_tokens, created_at
FROM live_model_exchanges
WHERE room_id = 29 AND stage = 'interaction_purpose_resolution'
ORDER BY id DESC LIMIT 5;

-- 最终回答
SELECT id, question_text, generated_text, created_at
FROM live_generated_speech_history
WHERE room_id = 29
ORDER BY id DESC LIMIT 10;
```

## 七、已验证过的真实结果

### 无直播，小王，两个人吃几号

```text
purpose_id = spec
purpose = 按人数确定合适分量
回答：小王老乡，这个范围人吃的话选半只装就行，450g那款……两个我心里也没数。
```

结论：

```text
昵称链路通
意图链路通
最终回答仍缺“半只适合1～2人”事实
```

### 无直播，三个地区

```text
成都包邮吗 → purpose 成都/川渝；回答先包邮后说四川没确认
新疆包邮吗 → purpose 新疆；回答不包邮、空运补费
北京包邮吗 → purpose 北京；回答先包邮后说北京没确认
```

结论：

```text
地区意图污染已修
非偏远地区的“包邮补集”还没有程序化
```

## 八、禁止事项

```text
1. 不准用本地 interaction-purpose-probe 的结果冒充服务端链路
2. 不准把全量事实 + 手写回答范围的结果说成服务端通过
3. 不准只看健康检查 200 就宣布意图链路正常
4. 不准在文档里写 token 明文
5. 不准用 test-events 无直播注入后说“已经回答”，它只入库
```

## 九、通过标准

一条测试只有同时满足才叫通过：

```text
1. 请求走真实服务端接口
2. HTTP 200
3. purpose_id 与问题地区/对象一致
4. task_angles 里的 F 编号能在事实库找到
5. Core 日志没有 purpose resolution fallback
6. 回答不自相矛盾
7. 回答落库文本与接口返回一致（有直播时）
```

缺任何一条，只能叫“部分验证”，不能叫通过。
