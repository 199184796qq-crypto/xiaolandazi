# 播放服务返回位置越界：修复要求（给 Codex）

日期：2026-10-23
事故：场次 476，11:29:55 停止，`stop_reason=formal_mainline_failed`

## 一、证据

```
Core   11:29:55.173  panic serving 127.0.0.1:49892: runtime error: slice bounds out of range [60:8]
Core   11:29:55.453  agent runtime transition room=29 state=stopped reason=system_error working_seconds=1389
Mgmt   11:29:55      formal mainline session=476 code=core_request_failed stage=播放服务 failed: Post "...": EOF
```

结论与你一致：互动结束后恢复到旧位置，追加音频时数组越界，panic 断连，Management 收到 EOF 后停场。

## 二、修复分三步，按顺序落地

### 第 1 步（止血）：panic 不许断直播

- 处理音频交付/追加的 handler 加 `recover`，panic 转 5xx 结构化错误，不中断连接之外的状态。
- 位置切片前做防御性收敛：

```go
if start > end {
    log.Printf("resume position clamped want=%d len=%d", start, len)
    start = end
}
```

要求：**任何位置错误只能影响这次回位，不能停场**。

### 第 2 步（正确性）：位置降级链

互动结束取返回位置时，按顺序判定：

1. 位置在当前队列内且对齐安全切点 → 精确返回；
2. 越界 → 收敛到「互动切入点的后一个句界」；
3. 该句已播完 → 从下一句开头继续；
4. 队列为空 → 通知补料（播桥接或等待），不得静默；
5. 全不成立 → 回到队列第一句开头。

原则：**宁可丢半句，不重播整段，不静默**。

### 第 3 步（治本）：用 generation 判失效

插播时同时记住：

```text
1) 切入点：track_id + 段内偏移
2) 切入时队列的 generation / 序号
```

回位前先比 generation：

- 一致 → 用 (1) 精确返回；
- 不一致 → 直接走第 2 步降级链。

不要靠事后检查数组边界判断位置是否有效，那只能兜底，判不准。

## 三、顺带要改的错误提示

现在 Core panic 导致 Management 只看到 `EOF`，前端只能显示「音频交付失败，请检查播放服务」，无从下手。

要求：

1. Core 返回结构化错误，例如

```json
{"error":"resume position out of range","code":"resume_position_invalid","stage":"audio_delivery"}
```

2. Management 原样透传 `code` 和 `stage`（我这侧改）；
3. 前端按 `code` 显示具体中文原因，而不是统一的“请检查播放服务”。

## 四、验收标准

| 场景 | 期望 |
|---|---|
| 互动插播后队列被裁剪 | 不 panic，从下一句开头继续，丢半句可接受 |
| 互动插播后队列清空 | 不静默，触发补料/桥接 |
| 连续多次互动 | 每次都能回位，无重复播报 |
| 人为构造越界位置 | 被收敛并打日志，不 panic |
| 场次结束时 | 无 `system_error` 导致的停播 |

## 五、我这边配合的事

- Management 侧：透传 Core 的 `code`/`stage`，不再统一成 EOF 文案。
- 起播缓冲改动（`4f6bb0e`，攒 60 秒再开播）暂不发布，等 Core 稳定后一起上，避免两个变量混在一起。
- 部署与验证：Core 新版本发布后我负责开播验证上述验收项，并对比 30 分钟内的 `composite.pcm` 请求时长与停播记录。
