# 2026-10-28 方案领域卡落地

## 目标

保存直播方案时自动生成一张不可见的领域卡，把“用户可能怎么问”映射到具体事实 ID，供互动回答做召回。领域卡不显示在后台，不替代审核事实包。

## 生成时机

- 保存方案版本时，在生成正式事实包之后同步生成；
- 与版本一起写入 `generation_context_json.domain_card`；
- 卡带 `source_sha256`、`built_at`，事实变化后新版本重建；
- 模型失败或 JSON 不合法时不阻塞保存，版本不带卡，互动走旧事实路径。

## 生成流程

1. 从本次 `derived_safety` 的审核事实逐条拆出 `fact_id + text`；
2. 模型输出自由命名的维度，每个维度包含：
   - `name`
   - `phrases`（观众自然问法）
   - `conditions`（本地/外地、川渝/非川渝、偏远等）
   - `fact_ids`
3. 程序校验：
   - 只保留真实存在的 fact ID；
   - 每条事实至少归入一个维度，漏掉的自动进“其他”；
   - 每个维度至少一条事实、一个问法；
   - 条件/例外不单独丢。
4. 校验通过后写入版本。

## 回答时怎么用

`interaction_single` 在生成回答前：

```text
问题 + 领域卡
→ 匹配维度（问法/维度名）
→ 取该维度全部事实（含条件规则）
→ 直接作为回答事实
```

领域卡没有匹配时，才回退到原来的 `factselect`。

因此：

- “上海抽真空吗”会拿到“本地不抽真空，外地真空包装”；
- “上海什么时候到”会拿到“川渝隔天送达/第二天发货”，由模型判断上海不属于川渝；
- 不会把全量事实塞给模型。

## 代码

- `management-service/internal/domaincard/domaincard.go`
  - 卡的 schema、解析、校验、问法匹配；
- `management-service/internal/httpapi/domain_card.go`
  - 保存时模型建卡、校验、失败兜底；
- `management-service/internal/httpapi/live_agent_plan_versions.go`
  - 保存版本时写入 `domain_card`；
- `management-service/internal/decisionexecutor/`
  - 读取版本卡，回答前按卡召回事实。

## 测试

- `internal/domaincard`：
  - 卡解析/校验/漏事实进“其他”；
  - 上海抽真空、上海什么时候到、西藏包邮的维度匹配；
  - 无匹配返回空。
- `internal/decisionexecutor`：
  - 有卡时条件事实被选中，且不泄漏无关时效事实；
  - 无卡时保持旧路径。

## 限制

- 卡依赖模型输出，首次保存会多一次模型调用；
- 卡是召回层，不负责判断条件是否适用，条件仍由回答模型判断；
- 旧版本没有卡，继续走旧检索；
- 本次未改前端，卡不在后台显示。
