## 10. 一处设计说明

方案级目录多了一层 `plans`：


## 12. 发布过程中实际遇到的问题（避坑清单）

昨晚从构建到发布，逐条踩过。**下面是原样记录，codex 别再重走一遍。**

### 12.1 仓库 HEAD 编译不过

`git worktree` 检出 108e7e63 后直接 `go build` 失败：

```
internal/interactionplan/generator.go:261: undefined: interactionpolicy.ReadOptional
internal/decisionexecutor/worker.go:135: undefined: timeReportDraft
internal/decisionexecutor/worker.go:1481: undefined: retryableTimeReport
internal/decisionexecutor/worker.go:1508: undefined: isTimeReport
internal/decisionexecutor/worker.go:1509: undefined: timeReportContextKey
```

这些是**已提交的调用点引用了未提交的新增文件**，是别人在途工作的遗留，不是本功能引起。结论：

**不要从 git HEAD 构建。** 必须从"线上实际运行源码快照 + 本功能改动"构建。

### 12.2 线上源码已经前移，别用旧快照

第一次我用的是 `mandarin-silence`（4a72b15）的源码快照，编译通过，但那是**过时**的：01:28 线上已发布 `1a56589`（互动开关）。用旧快照发上去等于把互动开关的 Management 改动回退。

**正确基线：`E:/直播伴播-local/interaction-controls-release-20261102/fixed-runtime-source.tar.gz`。**

### 12.3 vcs 戳怎么来

发布器用正则从二进制里抠：

```
vcs.revision=([0-9a-f]{40})
vcs.modified=(true|false)
```

快照没有 `.git`，直接编译两个戳都没有。做法：

1. 快照里 `git init`，把线上源码提交成基线（得 `89b684c2…`）
2. 把本功能 4 个文件放回去但不提交
3. `go build -buildvcs=true`

这样 `revision` = 基线提交号、`modified` = true，与既往 `vcs_modified=true` 的发布语义一致。

**注意**：`git init` 时要先把本功能文件挪走再提交，否则基线里就含了改动，`modified` 会是 false。

### 12.4 基线采集脚本要和发布器同源

第一次用 `mandarin-silence` 的 `remote_capture.py`，采到 **28 张**保护表；而线上已有 29 张（互动开关新增两张）。发布器比较时直接 `customer/configuration baseline changed`。

**capture 与 deployer 必须来自同一个 release 模板**，表集合和哈希方式都要一致。

### 12.5 保护表在发布瞬间还会被再比一次

发布器不是只比文件，它**在激活前重新采一次**并断言与基线完全一致：

```python
database_before = protected_database()
if base.get('protected_database'):
    assert database_before == base['protected_database'], 'customer/configuration baseline changed; recapture'
```

所以基线要**在发布前几分钟内重采**，并且先确认无活跃直播。我昨晚采完 30 秒后就失败过一次，重采后才过。

### 12.6 metadata 缺键直接 KeyError

不是断言失败，是 `KeyError`，报错里看不出是哪个功能要求：

```
KeyError: 'frontend_backup_verified'
KeyError: 'core'
```

发布器里有这么一段，会遍历 `management` 和 `core` 两个服务：

```python
for service in ('management',):
    assert metadata['predecessor_exact_match'][service] and metadata['predecessor_sha256'][service] == ...
```

实际运行时那份模板遍历的是 `('management','core')`，所以 `core` 也必须给。**纯 Management 发布也要把 core 的指纹写进 metadata**，否则 KeyError。

### 12.7 改发布器必须同步更新 package.json

`run_deploy.py` 第一行就校验：

```python
assert sha(OUT/'deploy_tts_pools.py').read_bytes() == package['deployer_sha256']
```

昨晚每改一次发布器都忘了更新，白跑三次。

### 12.8 同名 release_id 会撞暂存目录

发布器里：

```python
if target.exists():
    prepared = ...
    assert inventory(target) == prepared, 'existing staging release differs; refuse overwrite'
```

昨晚失败留下的 `/opt/xiaolan/releases/20261102-plan-warmup-89b684c/` 如果内容与本次包不一致，会直接拒绝。**要么换 release_id，要么先删这个目录。**

### 12.9 Windows 写文件带 BOM

用 PowerShell `Set-Content -Encoding UTF8` 写 `.sh`/提交信息，会在开头加 BOM：

- shell 脚本第一行变成 `﻿ENVF=...`，直接 `No such file or directory`
- `git commit -F` 出来的标题变成 `﻿方案级首段预热缓存`

改用 `[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))`。

### 12.10 失败模式是安全的

所有失败都发生在**激活之前**，服务器状态未变：`current` 仍指向 `20261102-interaction-controls-1a56589`，三个 PID 未动。只有惰性目录残留。可以放心重试。
