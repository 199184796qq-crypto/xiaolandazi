## 一、背景与目标

**目标：降低「意图识别」的 token 消耗。**

现状根因（已实测）：意图识别每来一个观众问题都要调一次完整「解意图」模型，单次 input ~2754 token，且直播间同类问题（如反复问"套餐"）会重复解，白白烧 token。

**方案：不再用 embedding 相似度阈值作「语义归并」主判据（实测不可靠，"8个人吃饭" vs "4人餐" 相似度仅 0.57），改用「判断模型」做语义归并；但 embedding 层仍保留为「精确族 + 高分差」双重兜底的保守层（见下文「关于保留 embedding 层的说明」）：**

1. 每个观众问题先跟**本房间的历史语义桶**让一个便宜的判断模型（qwen3.7-flash，`enable_thinking=false`）判断是否同类。
2. 同类 → 直接复用历史桶里存的结论（`Source="bucket"`），跳过完整解意图（单次 ~310 input，便宜约 8 倍）。
3. 不同类 → 走完整解意图，解完后把「问题 + 结论」存成新桶。
4. 桶按 `room_id` 隔离，存 MySQL `semantic_documents` 表（复用现有表，`content_type='purpose_bucket'`）。

### 关于「保留 embedding 层」的说明（回应 Codex 的疑问）

Codex 指出「代码仍保留 embedding 回退，与文档『放弃 embedding』矛盾」。核实后确认：**代码是对的，是交接文档措辞不准确**，此处澄清。

`Resolve` 实际是四层漏斗，从省到贵：

1. **精确缓存**（`Source="exact"`）：零成本，同问题原文 + 同事实包直接复用。
2. **判断模型层**（`Source="bucket"`）：语义桶新增，跨措辞归并，~310 token。
3. **embedding 语义缓存**（`Source="semantic"`）：**保留**，但被 `preciseFamily`（关键词族强约束）+ `bestScore>=.94 && 领先第二名>=.08`（高分差）双重兜底，只有「几乎精确复读」才命中。**注意：这层并非零成本**——`Search` 会调 `s.embedder.Embed` 生成新问题向量并记输入 token，准确说法是「命中后省去完整解意图调用」，而非「零 token、零模型调用」（已按 Codex 指正修正）。
4. **完整解意图**（`Source="model"`）：~2754 token。

embedding 层**不该删**：它命中后省去完整解意图调用，删了会让「精确复读类」问题每次都落到完整解意图，反而更费。`Resolve` 的实际顺序是「精确缓存 → 判断模型 → embedding → 完整解意图」，走到 embedding 时判断模型已调用过一次，故 embedding 层的价值在于**省掉最后的完整解意图**，而非省掉判断模型。**两层的保护机制不同**：判断模型层命中靠「返回索引合法 + FactsSHA 一致」，embedding 层命中靠「`preciseFamily` 关键词族一致 + 高分差」；`preciseFamily` 检查只在 embedding 分支，判断模型分支没有这项保护（也不需要有）。「放弃 embedding」的准确含义是「放弃用 embedding 相似度阈值做**跨措辞语义归并**（那不可靠），改由判断模型承担归并」，而非删除 embedding 这层精确兜底。

### 关键设计点（务必读）

1. **判断模型输入极简**：只喂「新问题原文 + 历史桶的问题列表」，**不喂事实包**。这是省 token 的核心。
2. **保守原则（宁可 miss 不可误判）**：母版铁律要求"非常确定才 same=true"。误判 = 复用错回答 = 直播事故；漏判只是多花一次解意图。
3. **FactsSHA 不匹配不冒险复用**：`judgeReuse` 里 `if cached.FactsSHA != factsSHA { return false }`——事实包变了旧结论可能引用失效事实，直接放弃复用。
4. **存桶门槛**：`storeBucket` 只在 `Confidence >= .85` 且 `Source == "model"` 时才存，低置信度结论不进桶。
5. **桶存两条行**：`source_version=1` 存问题原文（判断模型热路径读它），`source_version=2` 存结论 JSON（命中后取）。`source_id = "bucket:" + SHA(Normalize(question))`。
6. **降级安全**：判断母版缺失 → `Judge` 不注入 → 完全走旧逻辑，零风险。

### 落库 bug（Codex 第 4 点，已修复）与真实 MySQL 验证

Codex 指出 `UpsertPurposeBucket` 把 `embedding_blob` 设为 `NULL`，但生产表 `semantic_documents.embedding_blob` 是 `mediumblob NOT NULL`，INSERT 会直接失败 → 桶永远写不进去；且 `storeBucket` 用 `_ =` 吞掉了错误，静默失效。**两点均确认属实，已修复（`e0a981f`）**：

1. `embedding_blob`：`NULL` → `x''`（空 blob 占位）。语义桶本来就不走向量检索，空 blob 是正确的占位。
2. `storeBucket`：`_ = r.Repo.UpsertPurposeBucket(...)` → `if err := ...; err != nil { log.Printf(...) }`，写失败有日志。

**真实 MySQL 验证**（生产库事务内回滚，未留痕）：`SELECT LENGTH(x''), (x'' IS NULL)` 返回 `0, 0`（空但非 NULL）；`INSERT ... embedding_blob=x''` 的 `ROW_COUNT()=1` 成功，证明 NOT NULL 约束接受空 blob，`NULL` 才是真凶。

### 附：interaction-purpose-judge.md 全文

```markdown
# 意图语义归并 v1

## 任务
判断「新观众问题」是否和「历史已分析问题」属于同一类（问的是同一件事，可以复用同一个回答结论）。只做判断，不生成口播，不解析意图。

## 输出（严格 2 字段 JSON）
只输出一个 JSON 对象本身，不要用 ``` 包裹，不要输出任何 JSON 之外的文字或解释。

- same：是否命中同类历史问题（布尔）
- match_index：命中的历史问题序号（从 0 开始），same=false 时省略

示例：
{"same":true,"match_index":2}
{"same":false}

## 铁律
1. 只有"非常确定是同一类"才输出 same=true。拿不准、有歧义、相似但可能是两回事，一律 same=false。
2. 宁可漏判（多调一次完整解意图）也不可误判（复用错回答）。误判的代价远高于漏判。
3. 判断时先想"问的是哪一类事"，再比类别。类别不同直接 false。

## 类别判据
同一类里换措辞、换数字、换人数、换语气都算同类；跨类别（哪怕句子有重叠词）不算同类。

常见类别（按需扩展，不写死）：
- 选套餐/几个人吃：在问"选哪个套餐""几个人吃哪个""N 人餐"
- 价格/多少钱：在问"多少钱""价格""贵不贵"
- 门店位置/能不能用：在问"哪里有店""XX 店能用吗""地址"
- 券/优惠：在问"券""优惠""折扣""再发点券"
- 打包外带：在问"能打包带走吗""外带"
- 服务/设施：在问"唱生日歌吗""有包间吗""停车"
- 打招呼/闲聊：在问"在吗""刚来""主播"

## 红线
- 只根据问题本身判断类别，不引入商品事实、不补充假设。
- 数字、人数不同不算跨类，但若数字/人数本身就是问题核心且历史结论绑定具体数字（如"4人餐"推荐），且新问题数字明显不同（如"8个人"），应判 false，避免复用错人数。
```
