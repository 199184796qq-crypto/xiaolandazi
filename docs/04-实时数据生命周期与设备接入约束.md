# 实时数据生命周期与设备接入约束

更新时间：2026-09-21

## 1. 当前阶段事实

当前项目还没有真实硬件设备接入。

因此：

- device_online 字段已经保留，用于后续设备运行状态；
- 目前不启用“设备每 10 秒心跳一次、30 秒未续租自动判离线”这类强制心跳机制；
- 暂时不能把“设备未发送心跳”直接判定为设备离线，否则本地开发阶段的测试直播间会被自动停止；
- 设备心跳、设备身份认证、设备断线检测，等真实设备通信协议接入后再实现。

## 2. 当前已经生效的实时公屏存储规则

实时公屏数据只存 Redis，不再长期写入 MySQL。

Redis Key：

~~~text
livecompanion:room:{room_id}:events
livecompanion:room:{room_id}:event_seq
~~~

默认每个直播间最多保留最近 500 条实时事件。

Redis TTL 当前保留 24 小时，仅作为异常情况下的兜底过期时间，不代表业务数据要保存 24 小时。

正常生命周期结束时应主动删除，不依赖 TTL。

## 3. 清理规则

发生以下情况时，该直播间 Collector 停止，同时清空对应 Redis 实时数据：

- 用户关闭监控；
- device_online 被明确设置为 false；
- Collector 判断直播结束 / 直播离线；
- 房间被删除；
- Core Service 正常关闭；
- Core Service 重启时，会先清理旧的实时事件，再按房间运行状态重新决定是否启动采集。

## 4. MySQL 数据边界

MySQL 只保存长期配置和业务实体，例如：

~~~text
core_rooms
~~~

实时公屏历史表 core_room_events 已废弃并删除。

MySQL 不承担直播期间高频弹幕、进房、点赞、关注、礼物等实时公屏数据的长期存储。

## 5. 新直播间默认状态

新建直播间默认：

~~~text
monitor_enabled = false
device_online = false
~~~

也就是说，新建房间不会因为“创建成功”就自动开始永久监控。

后续正式产品中，应由真实业务条件控制：

~~~text
monitor_enabled = true
AND
device_online = true
AND
直播间实际处于直播状态
~~~

满足条件后才进入正式运行态。

## 6. 设备接入后的待实现闭环

真实设备接入后，再实现以下能力：

1. 设备身份认证；
2. 设备与客户 / 直播间绑定；
3. 设备定时心跳；
4. Redis 心跳 TTL；
5. 心跳超时自动判定设备离线；
6. 设备离线后自动停止 Collector；
7. 自动清空该直播间 Redis 实时公屏；
8. 设备恢复在线后，根据 monitor_enabled 和直播状态决定是否恢复采集。

预期流程：

~~~text
设备在线
  ↓
持续心跳
  ↓
device_online = true
  ↓
已开启监控 + 正在直播
  ↓
启动 Collector
  ↓
实时公屏写 Redis
~~~

设备断电 / 断网：

~~~text
心跳超时
  ↓
device_online = false
  ↓
停止 Collector
  ↓
清理 Redis 实时公屏
~~~

## 7. 当前开发阶段特别说明

在真实设备完成之前：

- 不启用自动心跳超时；
- 不让本地开发依赖真实硬件；
- 可以通过内部运行状态接口模拟 device_online；
- monitor_enabled 和 device_online 只用于验证生命周期逻辑；
- 等设备协议确定后再接入真正的心跳和自动恢复机制。

以上约束作为当前版本的正式开发规则，后续涉及设备、Collector、Redis 生命周期的实现应以此为准。
