## 一、先给实测数字

滚动 60 分钟账本（`live_cost_ledger`，每 10 分钟由 cron 写入）：

| 项 | 实测 |
|---|---|
| 模型 | 0.08 元/小时 |
| TTS | **1.54 元/小时** |
| 合计 | **1.62 元/小时** |
| 新合成音频 | **40 分钟/小时** |

按 4 字/秒校准（用录音缓存里「文本长度 ÷ 音频时长」反推，实测正好 4.00）：

```
1.3 元 → 8125 字 → 约 34 分钟新音频/小时
1.0 元 → 5600 字 → 约 23 分钟新音频/小时
```

**结论：当前每小时合成 40 分钟新音频，1.62 元，超出 1.3 目标 25%。**

## 二、40 分钟新音频的根因（已修）

代码把「复用率」按单元数算，但每轮实际重建台词：

1. `recordingCacheLookup` 会过滤掉 `hits >= 6` 的版本，一句只剩该版本时被当成"没缓存"，整句重新润色 + 重新合成。
2. `pruneRecordingCacheEntries` 直接删除到期条目，音频随之不可用。

已修（`e7b3af1`，已上线）：

- 查询不再按 hits 过滤，所有有效版本都可读到；
- 淘汰只停止参与"新生轮换"，音频保留可回退；
- 每句最多 4 个版本的容量上限保持不变。

## 三、三阶段封顶（待实现）

按版本池填充度（可用版本数 / 4）分阶段：

| 阶段 | 填充度 | 策略 |
|---|---|---|
| A 冷启动 | < 33% | 不封顶，仅记录（1.3 以上可接受） |
| B 中间 | 33%–80% | 封顶 1.3 元/小时 |
| C 池满 | ≥ 80% | 封顶 1.0 元/小时 |

超限时的行为（**不中断直播**）：

```text
有任意可用版本 → 强制复用（忽略掷骰与命中计数）
一个版本都没有 → 播原文（跳过润色调用，仍付一次 TTS）
```

明确不做的事：不因预算不足而留空、不跳过 P0/事实校验、不停止供料。

## 四、需要你确认的三点

1. **阶段判定的口径**：按"可用版本数 / 4"的平均值，还是按"已有 ≥1 版的句子占比"？前者对长尾更敏感。
2. **封顶的时间轴**：沿用你方案里的"滚动 60 分钟有效直播时间"，还是按自然小时？账本目前用滚动 60 分钟。
3. **TTS 计费口径**：账本现在按「音频时长 × 4 字/秒」反推字符数（因为 `media_assets.metadata_json` 没有可靠的计费字符）。你方案要求按实际发送文本计费字符，这需要 TTS 调用点直接记账——是否同意我在 TTS 网关层加一个字符数字段，而不是继续用时长反推？
