## 一、P0：「别犹豫了」漏过红线，程序侧完全没有拦截点

### 现象

主线第 3 段（exchange id 30153，播出资产 id 93453）输出并已播出：

> 「大家**别犹豫了**，直接拍链接，到时候舒舒服服到店吃……赶紧看看1号和2号链接」

其中「别犹豫了」「赶紧」（「赶紧抢/赶紧冲」）都在红线词意图内，但整段 Passed 通过、未被重写。

### 根因（三层全断）

**第 1 层：生产 P0 母版的程序词表里根本没有这个词。**

`/opt/xiaolan/current/configs/prompts/anchor-style/compliance/L1/p0-hard-block.md`（12,913 字节，mtime 10-18 22:18）里 `l1.p0.unsupported_urgency` 只有 14 个词，到「秒杀」就截断：

```
最后一天, 最后一波, 马上涨价, 马上恢复原价, 随时结束, 仅此一次, 仅此一天,
再不抢就没了, 不会再便宜了, 错过就没机会了, 万人抢购, 万人疯抢, 抢疯了, 秒杀
```

git 仓库版（13,868 字节）有 **23 个词**，多出 9 个：

```
名额有限, 仅剩, 最后几个, 手慢无, 锁单, 赶紧抢, 快点下单, 别犹豫了, 再不买没了
```

这 9 个词由提交 `d3eaf29`（2026-10-20 07:28「互动话术半省规划 + 历史累积改动追平」）加入 git，**从未部署到生产**。生产文件停在 10-18 22:18 的老版本。

**第 2 层：这条规则的 `review_mode` 是 `semantic`，而语义复核已经下线。**

`contentguard.Scan` 会照常把 semantic 类 term 命中写进 `Report.Hits`，`CheckP0Candidate` 也照常判 `Passed=false`——但前提是**词表里得有这个词**。词表没有，扫描直接零命中，等于没检查。

**第 3 层：只剩 prompt 软约束，而「不提」和「改说」的粒度不一致，模型没听。**

生产 `p0-generation.json`（3,249 字节）里「不提」列表确实写了「别犹豫了」（grep 命中 1 处），但它的「改说」是**类别级**的，只举个例子：

- 不提（33 个词）：`最后一天 … 手慢无 … 别犹豫了 … 再不下手`
- 改说（1 句）：`…禁止由此衍生任何催单话术（手慢就没了、不等人、抓紧、赶紧冲等一律禁止）`

**33 个词共享 1 条改说，而这条改说只点名了 4 个词，覆盖率 12%。** 讽刺的是这条改说里已经写了「任何催单话术一律禁止」，模型还是说了「别犹豫了」——**实测证明类别级改说罩不住词级禁令**。

### 结论

「别犹豫了」目前在**整条链路上零拦截**：程序词表缺词 → 扫描零命中 → semantic 判断环节又已被删除 → 词级改说也不存在 → 模型想怎么说就怎么说。


### 建议改法（需 Codex 走增量链）

1. 在生产现场 `p0-hard-block.md` 就地补回缺失的 9 个词（把 urgency 的 `terms` 数组补到 23 词），同步更新该规则 `note` 字段，重建该文件 MANIFEST 哈希。
2. **不要**用 git 版整文件覆盖生产（生产有 169 个现场母版，git 只有 136，覆盖会回滚 33 个现场文件）。
3. 补完后建议加一条**回归断言**：编译后的 policy 里 `l1.p0.unsupported_urgency.terms` 长度必须 == 23，少一个就报错，防止再次静默截断。
4. 顺带评估：`review_mode: semantic` 的规则在语义复核下线后，命中即硬拦（无语境判断）。这会带来退回率上升，需要确认这个取舍是否可接受，或者给 semantic 类补一个轻量程序判断（例如只在「无活动依据」时才拦）。

## 一（补）：生成侧与审核侧词表系统性不一致，31 个词只写在 prompt 里

### 设计现状

按代码注释（`internal/httpapi/text_content_views.go:37`），本来是「一条红线 ↔ 一条改说，一一对应」：

> 读取「生成侧」P0 精简 JSON（红线 + 裸词表 + 专属改说，一一对应），把红线词表合并进四层「不提」、把「改说」合并进四层「改写」。**审核侧继续用 p0-hard-block.md 的词表**。

也就是说，**同一套红线维护在两份母版里**：`p0-generation.json`（喂模型）和 `p0-hard-block.md`（程序扫描）。两份各自演化，已经脱节。

### 实测差异（生产现场逐条比对）

审核侧 9 条规则 / 生成侧 8 条规则：

| 红线类别 | 生成侧「不提」 | 审核侧可扫 | 审核侧扫不到的裸词 |
|---|---:|---:|---|
| 绝对词与极限词 | 34 | 69 | 0 |
| 医疗与保健功效 | 24 | 27 | 0 |
| 虚假与夸大功效 | 17 | 18 | 3（食品级、孕妇可用、婴儿可用）|
| **无依据限时逼单** | **33** | **14** | **20**（不等人、仅剩、今天才有、再不下手、再不买没了、**别犹豫了**、别等、名额有限、就这个价、快点下单、手慢就没了、手慢无、抓紧、抓紧上车、最后几个、真不是天天有、赶紧冲、赶紧抢、锁单、错过这波）|
| 站外引流与私下交易 | 10 | 10 | 0 |
| 贬低同行 | 4 | 2 | 2（不如我们、比XX品牌好）|
| 免检承诺 | 2 | 2 | 0 |
| 背书数据 | 6 | 2 | 6（回购率、好评率、榜单第一、经营年限、销量第一、门店数量）|

**合计 31 个词：生成侧明确要求模型「不说」，审核侧却扫不到，等于无验证。**

反向也有缺口：审核侧 `l1.p0.food_selected_permanent_ban`（`review_mode: hard`，5 词）里有 `非转基因更安全`、`可食用`，**生成侧从来没告诉模型这两个词不能说**——模型说了就硬拦，但事前没有任何提示。

### 为什么这不是小事

1. 模型收到的禁令比程序能验证的多 31 个词，**幻觉空间就在这 31 个词里**。本场的「别犹豫了」正好落在里面。
2. 反向缺口会造成「模型不知道为什么被退回」——`非转基因更安全` 这类词说了就被硬拦重写，但 prompt 里没有预警，白白消耗重写轮次。

### 建议改法：建立单一事实源 + 词级改说

**A. 一套词表，两处渲染（治根本）**

把红线词表收敛成一份 `p0-terms.json`，作为唯一事实源；`p0-generation.json` 与 `p0-hard-block.md` 的 `terms` 都从它生成（或启动时校验一致）。禁止两份手工维护。

**B. 词级挂「改说组」，强制一一对应**

不要一词一句（token 会爆），而是**词级挂组 ID、组级写一句改说**，要求「每个词必须能映射到某个改说组」，映射不到就启动报错。

以催单类为例，33 个词收敛成 4 组即可 100% 覆盖：

| 改说组 | 覆盖词 | 改说 |
|---|---|---|
| 催决策 | 别犹豫了、抓紧、抓紧上车、赶紧冲、赶紧抢、快点下单、别等、再不下手、错过这波、手慢无、手慢就没了 | 想选哪个自己看，我陪你把分量和价格说清楚，不用催 |
| 假稀缺 | 仅剩、最后几个、名额有限、锁单 | 有库存依据就照实说数量，没有依据就不提库存 |
| 假限时 | 最后一天、仅此一天、仅此一次、今天才有、真不是天天有、就这个价、随时结束、错过就没机会了 | 事实包写了截止时间就如实转述，没写就说「活动以页面为准」 |
| 涨价威胁 | 马上涨价、马上恢复原价、不会再便宜了、再不买没了、再不抢就没了 | 只讲当前价格和已确认的优惠，不预测未来价格 |

**C. 加启动期一致性断言（防再次静默脱节）**

服务启动或加载 P0 策略时校验：

- 生成侧每个词都能在审核侧找到（否则 fail fast，不允许「只提醒不校验」）
- 审核侧每个词都能在生成侧找到（否则模型无预警被拦）
- 每个词都有改说组 ID，且该组有非空改说
- 词表总条数 == 预期值（本类应为 33），防止再被静默截断

任何一条不满足，就拒绝启动或拒绝开播，而不是像现在这样静默放行。

## 二、P0：`accepted_macro_feedback` 是成本黑洞，且连续 7 次纠正完全无效

### 数据

同一场 17 分钟内：

| stage | 次数 | input | output | 占主线 input |
|---|---|---|---|---|
| mainline_text | 13 | 35,499（已更新） | 2,544 | 52% |
| **accepted_macro_feedback** | 8 | **30,550** | **596** | **45%** |
| mainline_text_rewrite | 1 | 1,842 | 231 | 3% |
| opening_selection | 1 | 299 | 15 | 0.4% |

单次 ~4,364 input 换取 ~85 token 的纠正指令，投入产出比约 50:1。

### 更严重的是它无效

连续 8 次输出的都是同一类纠正：

> 「自指缺失，多使用『我们家』；补充语气词『啊』」

实测主线 11 段正文统计：

| 指标 | 出现次数 |
|---|---|
| `我们家` | **0 次（全部 11 段）** |
| `啊` | 0~1 次/段 |
| 实际自指用法 | 全部用「咱们家」 |
| 实际语气词 | 哈 / 哟 / 嘛 / 呀 / 哦 |

即：**纠正指令发了 8 遍，一次都没落地**。因为它是纯文字提示塞进下一段 prompt，模型不照做；而下游没有任何验证环节检查「这次纠正有没有生效」。

### 副作用：纠正指令在制造复读

`30272` 的纠正写着「下一段开头避开『哥哥姐姐们』，改用『纠结几人的看2号链接哈』或『想要的往下看』」，而实测正文里 `94225`（04:40）开头正是「纠结几人的看2号链接哈！」、`30256`（04:42）开头正是「想要的往下看」。**模型把纠正指令里的示例句照抄成开头**，纠正本身成了新的模板来源。

### 建议改法

按优先级三选一（越靠前越省）：

1. **直接砍掉这个 stage**（推荐先做）。主线已有 `state.Used/RecentSameTask` 措辞轮换 + `mainline_text_rewrite` 润色两道去重机制，这个回灌是第三道且无效。
2. 若要保留，把「纯文字纠正」改成**程序可验证的硬指标**：把密度基准（自指 / 语气词 / 称呼）交给程序统计（`anchorstylescore` 已有能力），不达标就带着明确缺口重写该段，而不是让模型自己写一段纠正话。
3. 至少要修「纠正指令里带示例句」这个坑：禁止在 instruction 里出现可直接照抄的完整句子，改成抽象约束（如「开头不得使用上一段的前 6 个字」）。

## 三、P0：主线事实复述率过高，几乎每段重念全套

### 数据（11 段主线正文）

| 事实 | 出现段数 |
|---|---|
| 免费停车 | **11 / 11** |
| 地址「滨江中路」 | **11 / 11** |
| 冰淇淋（10种） | 10 / 11 |
| 高峰期等位 | 10 / 11 |
| 领券再减 30 | 8 / 11 |
| 锅底油碟 | 7 / 11 |
| 仅堂食 | 4 / 11 |

### 判断

每段基本是同一个骨架：`开场关切 → 套餐明细（X道荤素菜+10道凉菜+10种冰淇淋+锅底油碟）→ 地址 → 免费停车 → 不预约/高峰期等位 → 领券减30 → 看链接`。事实本身没错，但连续 11 段重复同样的信息，观众听到的是同一个人在念同一张说明书。

### 建议改法

- 在 system 的「近期已采用内容」里，除文本摘要外**额外带上「本轮已用过的事实条目 ID 列表」**，并明确「已用过的事实本段不得再完整复述，只能引用其中一项或跳过」。
- 地址 / 停车 / 预约这类「一次性信息」，建议程序层做**节流**：同一场直播每个事实最多完整出现 N 次（比如地址 2 次、停车 1 次），超出后从 `可说` 事实包里剔除，只在开场段和收尾段放行。
- 卖点轮盘的「角度」需要真正拉开差异，现在 11 段里至少 4 段角度是重合的（都是「算账划算」或「人少推荐6人餐」）。

## 五、P1：互动侧筛事实错配（答非所问）

### 现象

用户问「今天可以用吗？」，模型拿到的事实包是：

```
F001 - [用户指定公共；appointment/到店消费预约要求] 到店消费无需预约，高峰期可能需要排队
```

播出的答案是「对呀，到店消费无需预约，高峰期可能需要排队嘛。」

**问的是「今天能不能用（券）」，答的是「要不要预约」**——事实筛选把「appointment 类别」错配给了「活动时效」问题。

### 建议改法

在 `generationMaterialViews` / 侧面筛事实那一层，给「时效类问题」（今天/明天/现在/截止/还能用吗）加一条硬优先：必须优先取 `activity_time` / `validity` 类事实；取不到就按「不提」处理，输出「这点需要帮您确认」，**不允许拿其他类别的事实顶上**。

## 六、P1：`single_greet` 先播空话，`single_answer` 30 秒后才播答案

### 现象

- `30170`（single_greet，04:35:00 播）：「无奈的、笑笑你说，对呀，我这就帮您确认哈。」
- `30214`（single_answer，约 04:35:30 才播）：「对呀，到店消费无需预约，高峰期可能需要排队嘛。」

用户听到的是「我这就帮您确认」+ 半分钟沉默 + 迟到答案。同一模式在本场出现 3 次（「券呢」也是先「我这就给你弄好嘛」再答）。

### 建议改法

`single_greet` 只负责称呼和承接，**禁止出现「我这就去确认」「马上给你查」这类承诺句**（除非 answer 已经在手），否则会形成空承诺。或者在 greet 与 answer 之间加时长门限：answer 未就绪时不播 greet。

## 七、P2：主线缓存命中率 0%

### 数据

同一场、同一 pool 账号（`当前口播模型账号`）、同一 profile：

| stage | 次数 | input | cached | 命中率 |
|---|---|---|---|---|
| interaction_welcome_hook | 7 | 7,469 | 5,376 | **72%** |
| mainline_text | 13 | 35,499 | **0** | **0%** |
| accepted_macro_feedback | 8 | 30,550 | **0** | **0%** |
| mainline_text_rewrite | 1 | 1,842 | **0** | 0% |
| interaction_welcome_greeting / single_greet / single_answer | 20 | 33,290 | 0 | 0% |

只有 `welcome_hook` 吃到缓存（每次固定 768 token），其余全零。

### 已定位线索

`mainline_text` 的 `request_json` 里 `Messages[0]` 是 **Role=user**（内容是 5,587 字符的「不提 / 不提红线词」JSON 块），**没有 system 消息**。而 `provider_qwen.go` 的 `cache_control: ephemeral` 是挂在 system 上的。没有 system → 没有缓存断点 → 前缀缓存不成立。

这与之前 session 314 的分析（system 前缀在两种形态间跳变）是同一个根因的另一种表现：**主线这条链路的 system 前缀不稳定，甚至不存在**。

### 建议改法

把 `renderCycleTextMessages` 的输出固定为「1 条 system（稳定前缀：母版 + 表达标尺 + 有效P0 + 不提） + 1 条 user（本段任务/事实/避重）」，拒绝把 P0 boundary 前置成 user。预期主线 input 成本可降 40% 以上。

## 八、P2：主播风格母版残留「菜籽油」语境

主线 system 的「主播腔调」段（来自 scorecard 反推）里仍有：
