## 2. 第一批修改：给模型真实的四层材料

建议为“话术优先的已提供正文润色”建立明确的任务组装入口。共用 `rewriteCycleText` 还有其它调用方，不能直接为修录音润色而全局改坏事实改写或实时主线。

P0继续作为独立规则提供；四层材料必须由程序真正组装到这次请求里，不要仅在母版里口头声称存在。四层应围绕当前源语义单元，不塞入其它商品示例，不把模型当作内部索引管理器。

以下是组装形状示例，使用34198真实原文；它不是替换全部系统母版的成品：

```text
【必说】
当前原文：没有弹幕的时候，AI 会自动循环讲解产品卖点、福利活动，持续引导看小黄车，避免长时间冷场掉流量。
保留的信息：无弹幕时自动循环讲解产品卖点和福利活动；持续引导看小黄车；原文描述的减少冷场目的。
硬事实：只允许使用当前原文及本次明确提供的事实，不从规则示例补充事实。

【可说】
允许改变语序、连接词和口语表达，让这句话更适合自然口播。
只使用本次提供且允许的风格；未提供称呼时不用自行加入商品或人物设定。

【不说】
不新增商品名、价格、链接号、产地、配料、保质期、物流或成交承诺。
不把“避免/减少”的表达升级成必然结果；不虚构正在发生的互动。
不输出示范模板、占位符、解释或索要材料的话。

【怎么改写】
只润色上面的当前原文，保留信息和确定性程度。
输出可以是一个或数个完整句，只返回最终口播正文。
不输出标题、编号、JSON、分析过程；不能改写时按约定返回明确的不可改写结果。
```

实施注意：

- 母版移除真实品牌、价格、链接等具体案例；确需示意时使用明确非事实的结构说明，不能混进可说资料。
- “固定硬信息”由程序从可信输入提供或绑定。商品与价格、单位、适用条件的关系也属于硬信息，不只是几个独立词。
- 信息完整的当前原文，不应因没有商品名/价格而被当作材料不足；这可能本来就是 AI 服务介绍、承接或公共话术。
- 先用本次归档原句验证实际最终 messages，确保真实发送内容与设计一致；不能只检查某份 Markdown 已经写了四层。
- 保留当前真实 P0 生效策略、允许项和显式豁免，不擅自增加与当前方案无关的限制，也不能为了润色率关闭准入。
- 此处先保持单单元单次请求。五句 marker 批量不是必要修复；后续即使用批量，源ID、匹配与顺序仍由程序维护。

## 3. 第二批修改：润色结果必须有状态，审核通过必须核对报告

### 3.1 不再用“返回原字符串”代表所有结果

现在 `polishRecordingTextLimit` 遇到无模型、调用失败、空结果、旧版超长或审核异常等情况返回原文；`polishRecordingBatch` 又先把输出填成原文，检测到未改写或数字不匹配时只是 continue。调用方看到非空字符串就继续合成。

这会把“有效改写”“允许原样使用”“被拒绝后降级”“请求失败”压成同一种返回值。结果既不利于准入，也使缓存和三成更新统计失真。

建议结果合同至少区分：

| 结果 | 后续行为 |
| --- | --- |
| 有效改写 | 绑定当前事实和规则验收结果，进入语义编译与TTS |
| 合格但无需改写 | 可依业务规则复用原稿；不能算新润色版本/更新成功 |
| 任务偏离、事实变化或审核不通过 | 不合成该候选；保留拒绝原因，按预算重试或使用已验证旧成品 |
| 请求失败、超时、空结果 | 记录可恢复失败，优先沿用有效库存；不能冒充润色成功 |
| 停播/换场取消 | 正常取消，遵守场次所有权；不记成文案故障或继续提交旧回执 |

程序持有稳定 source/group/unit ID；结果保留源正文、候选正文、状态、原因、事实/规则版本与最终批准正文指纹。格式规范化、补句号、TTS和缓存不能在后面悄悄把拒绝结果改成成功。

确需原文降级时，走明确的原稿可用检查与适用的审核策略；可缓存经批准的降级音频以节省TTS，但标记清楚。不要为了“看起来润色了”强迫模型无意义换词，也不要在失败时悄悄把原文当成新稿。

### 3.2 当前 P0 检查把“无执行错误”误当“通过”

`recording_stream.go` 当前使用 `CheckP0Candidate(&candidate) == nil`。但 `anchorcycle/p0.go` 中正常完成扫描即使 `P0Report.Passed=false`，也仍可能返回nil；返回error与报告是否通过是两个维度。`CheckApprovedText` 才会核对报告及批准正文。

固定函数离线复现已经得到：**报告不通过、函数无error，润色调用方仍接受候选。** 这证明接口使用有误，不代表本次已查到某条违规稿真实播出。

建议检查执行结果、报告Passed及最终正文指纹；文字在补标点或重组后若发生变化，需要按批准合同处理，不能拿旧凭据套新文字。缓存加载也应核对其适用的事实和规则版本。保留现行显式免审/豁免模式的真实语义，不能一概增加付费审核。

### 3.3 现有数字比较不等于事实保持

`recording_polish_batch.go` 的 `numbersKey/sameNumbers` 只提取有序ASCII数字组。真实函数离线会放行以下变化：

- `12.5元` → `12、5元`。
- `15%的优惠` → `15元的优惠`。
- `两斤` → `三斤`。

同样的数字还可能被换绑到另一商品。建议校验“对象—数值—小数—单位—条件”的事实关系，识别中文数量、范围、否定、时态及确定性程度；命中冻结事实时核对其绑定关系。不能用一个数字正则宣称已经证明任意自然语言同义，也不能认为过了P0就一定没改事实。

## 4. 第三批修改：先决定复用还是更新，再调用模型

### 当前顺序与离线复现

现行入口是 `runRecordingStreamProducer`，不是无调用方的 `runRecordingStreamProducerTabsLegacy`。

`recording_stream_units.go` 先预润色整个当前标签，再逐句查缓存。批量开关当前为false，外层“五句一组”实际仍逐句调用模型；一组有一个需要更新，也会把整组送去润色。

缓存命中后直接continue，既丢弃刚得到的新润色，也不回填 `Versions/Refreshed`；即使本轮被选为刷新，也被旧缓存抢先截走。持久条目又只保留一源一句，无法实现现有版本池。

真实生产函数搭配本地模型/TTS/Core桩的回放结果：

| 场景 | 实际结果 | 暴露的问题 |
| --- | --- | --- |
| 五条暖缓存跑六轮 | 30次润色、0次TTS | 音频命中仍反复调用模型 |
| 五条冷数据跑六轮 | 30次润色、5次TTS、5条持久记录 | 新润色被旧缓存挡住，未形成四版本池 |
| 一源句三次成功改成两句 | 6条TTS音轨、0条持久缓存 | `len(units)==1` 排除了成功多片成品 |

这些计数是**离线桩行为复现**，不是生产真实计费或真实播放统计。

建议目标顺序：

```text
读取并校验有效库存，恢复版本历史
  → 按本模式既有策略选择本轮复用/新生成
  → 复用：选择有效成品，直接进入有序就绪窗口
  → 新生成或缺货：仅为需要的单元组装四层请求
      → 验收结果/事实/P0 → 语义编译 → TTS及归档
      → 发布完整就绪组 → 保存对应多片成品及版本
```

具体要求：

- 被策略选中的“更新”必须真正进入新稿路径；生成失败沿用有效旧版，但保留更新未完成状态，不能算30%更新成功。
- 缓存命中必须恢复历史；生成尝试、有效版本、播放/复用次数分开记。
- 不改变现有业务规定的首开新生成、话术优先前四轮版本积累以及后续复用/刷新策略。实时主线的滚动七三和话术优先的版本池不是同一个分母，不要混为一谈。
- 将持久条目改成“一源语义组对应多个已验证音频片”的成品包，不因改写自然拆成两句而拒绝入库。
- 不能用最终TTS文本与原文 raw字符串不同来推断已润色。目前原文仅补句号也能触发 `Polished=true`；必须沿用上游真实结果状态。
- 全文hash用于整份快照校验即可；复用依赖尽量落实到稳定源单元/事实关系，换标签顺序不应使无改动正文全部冷启动。
- 音频键使用实际解析后的音色、模型、语速、情感开关、指令及合成规则版本。当前调用VoiceKey未传情感开关；这是错误复用风险，尚未证明是本次低缓存量的直接原因。
- 文字及准入键携带实际事实、规则/提示词/编译版本；事实变化重验对应文字与声音，单改语速只换声音。保留音轨ID并重新签URL的现有做法，不持久化临时签名URL。
- 历史v1被v2门槛拒绝属于迁移问题，不能说v2每轮都被清空，也不能批量把未知旧稿改成“已润色”。

## 5. 第四批修改：语义完整、可互动切入与PCM时间轴分开

应保留已经做对的部分：现行代码会对润色结果重新分句、每片独立TTS，再按实际PCM生成该片时间轴。这比旧版“整段TTS却丢失内部句界”前进了一步，不能继续套用446旧实现的全部结论。

但目前切句仍把单个 `。！？；!?;` 和换行当边界，再给任意尾巴补句号。末字符检查和固定A96/B85分数不是语义证明。

固定函数回放发现：

| 输入 | 当前编译结果 | 应改为 |
| --- | --- | --- |
| `本套餐337元，`换行`仅限工作日使用。` | `本套餐337元，。`和`仅限工作日使用。`，两端合同均能放行 | 换行不直接断句；价格和限制保持同一约束组，组未闭合不能插互动 |
| `他说“只限堂食。”` | 闭引号变成单独的`”。`片 | 闭引号/括号附着前一句 |
| `欢迎！！！` | 一句欢迎及两个纯标点片 | 连续标点归并，无纯标点TTS |
| `如果您提前预约` | 补句号后被标安全 | 续接主句或标不完整，不以补点制造安全边界 |
| 210字无句末原文 | 211字单次TTS | 用语义组与真实耗时预算控制，不能把取消字数上限等同长句供料无风险 |

这些回放使用固定1000ms的本地TTS桩，只证明文本/元数据门槛可被通过；没有证明真实音频、实机出声或真实切入效果。

实施分层建议：

1. 源单元先合并换行碎片、成对引号、条件依赖；去掉纯标点。
2. 润色后再验证语义和事实关系。独立完整的句可独立TTS；价格与适用条件可有多个片，但保持约束组，播放到组末才允许插入互动。
3. 只有确认完整的尾句才规范标点。补句号只是格式处理，不能改变语义结论或润色状态。
4. 每个TTS片使用真实PCM帧数建立起止；没有词级时间戳时，不按字数比例编造片内切点。
5. Core继续做结构和范围校验；切点同时记录来源、语义组是否闭合、真实片尾。不要用固定A96说明模型置信度。

## 6. 连续供料：小窗口提交，失败保留覆盖

当前首三单元启动逻辑仍在整标签预润色之后。真实日志21:05:44.131开始本轮producer，21:06:14.981才出现首块启动日志，相差约30.85秒；这只证明该服务流程耗时，**不是实机首出声的精确时间**。

建议采用有序小窗口：先补够少量完整就绪组就提交，后续生成与播放并行；按已确认可播秒数及实际生成耗时补水位，限制并发并维持顺序。不要为准备第一个块先请求整个标签的所有模型调用，也不要等下一标签全部完成才append。

失败恢复建议：

- 一组第二片TTS失败时保留第一片的成功产物及失败游标，有限重试失败片；约束组未完整就绪时不能只播价格而漏限制。
- 当前 `compileRecordingSpoken` 可返回partial+error，调用方却跳整个源句；需要显式处理部分成功，避免静默漏正文和重复合成。
- 拼块、归档、签名或append暂错按阶段及预算重试。当前部分路径仍直接退出producer，不能只修一句“补句号”便认为整场不会再被供料失败结束。
- 已验证旧成品可用于连续供料；真正无可用内容且超过恢复预算时，才按实际阶段报告原因。不能无限重试掩盖永久错误，也不能伪造有音频或放行危险切点。
