# 方案提示词原文保存与回显修复

用户要求：四个分页各自保存原始文本，再生成两份元提示词；切换方案回来只回显各页原文。

状态：本地修复验证及前后端发布完成，源码已提交推送，正式回执见下文。没有写入生产客户方案，没有模型或 TTS 调用。

## 原因与修复

旧实现发送前、HTTP 接收后和数据库入库前会清洗四页文本，去掉首尾空白、提示行并统一换行；没有四分区数据的旧方案还会根据标题拆分完整提示词。这使编辑原文与派生内容混在一起。

现在 `sections_json` 只存四个原始字符串，保留空页、空白、提示行以及页内相同标题。两份组合使用副本编译，沿用既有清洗规则，不反写原文；四页原文和两份派生组合在同一条 SQL 中保存。GET 只返回原始四字段供编辑器回显，不按标题重新分配。

组合关系保持：

- 主播互动元提示词 = 主播人设 + 事实依据 + 互动回答要求。
- 主播话术生成提示词 = 主播人设 + 事实依据 + 直播话术要求。

顶部“保存方案”先读取/冻结当前四页快照，再保存正式版本及提示词资产；保存期间锁定编辑。未打开提示词页也先读原文，避免未加载空稿覆盖。全部清空可显式保存。正式版本与提示词仍是两个既有接口，不能宣称跨接口事务：若版本成功而原文失败，顶部明确提示部分成功，保留草稿并支持单独重试；重新打开提示词页不会因保存错误加载旧文覆盖草稿。迟到响应和方案范围隔离继续保留。

旧方案没有四页原文时，完整旧提示词单独只读展示，运行读取仍使用旧内容；仅保存正式版本不会用四页空稿擦除旧文。用户填写四页并保存后才切换为新组合。此前已经被旧版本清洗而未另行保留的内容无法凭派生文案自动还原，本次不猜测拆分、不批量迁移客户数据。

本修复没有增加模型规则、上下文或调用。编译清洗仍在派生副本中执行；主线调用接入范围、互动调度、后置称呼和 TTS 保持。
