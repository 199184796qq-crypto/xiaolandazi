# 保存方案去阻塞 — 排查结论与待办改动

> 状态：排查完成，待 Codex 实施收尾。日期 2026-10-18。

## 一、问题现象

用户点「保存方案」仍报错：**「事实引用了快照之外的资料」**。

## 二、报错源头（唯一出处）

```
management-service/internal/contentpools/pools.go:307
→ return errors.New("事实引用了快照之外的资料")
```

它位于 `ValidateSet(set Set) error` 内，触发条件是：某个内容池 `Pool.Facts` 里的某条事实 `Fact.Sources` 含一个不在 `set.Sources.Rows` 的 `sources` 白名单里的资料 ID。

## 三、关键判断：保存入口已经绕开了 ValidateSet

保存方案的 HTTP 入口是 `liveAgentPlanVersionCreate`（`internal/httpapi/live_agent_plan_versions.go`），它只走两条路径，**都不调 `ValidateSet`**：

1. **实时模式**（`isRealtimeScheme` 为真）：走 `prepareDerivedSafety`（`live_derived_safety.go:549`）。该函数内部只调 `loadDerivedInput`、`syncDerivedReviews`、`applyDerivedReplacements`、`removeUnsafeFactLines`，**不碰 `ValidateSet`**。
2. **静态/非实时模式**：走 `latestSavedContentPoolSet`（`content_pool_api.go:292`），注释明确「跳过来源快照 SHA 比对与 ValidateSet 全量核对」。只有 `set.ID == 0`（方案还没任何内容池）时才回落。

所以 **`ValidateSet` 的报错不是保存入口触发的**。

## 四、`ValidateSet` 的实际调用方（仍会触发报错的链路）

| 位置 | 链路 | 是否卡保存 |
|---|---|---|
| `content_pool_api.go:283` `readyContentPoolSet` | 内容池「读取/核对」 | 否（已从保存链路摘除） |
| `db/live_content_pools.go:286` `CommitContentPoolSet` | 内容池「更新」落库 | 否（更新链路） |
| `content_pool_generation.go:453` | 内容池「生成 job」 | 否（生成链路） |
| `content_pool_runtime.go:16/160` | 运行时读取 | 否 |
| `content_corrections.go:363` / `edit.go:116` / `db/content_corrections.go:83` | 纠正/编辑落库 | 否 |

**结论：后端「保存方案」入口已彻底去阻塞。** 报错若在点保存时出现，来源一定在**保存前的前端/其它接口**，而非保存接口本身。

## 五、需要 Codex 确认并处理的事

### 1. 先定位「报错到底是哪个请求返回的」

打开浏览器 Network 面板，点保存，看 409 报错的**接口 URL 和请求体**，确认是：
- `POST .../live-agent-plan-versions`（保存）→ 理论上不可能报这个错；
- 还是 `POST .../content-pools/update` / `.../content-pools/generate`（更新/生成）→ 报错正常，属于内容池更新链路，与保存去阻塞无关。

### 2. 若确认为保存接口仍报错（预期不会，但需排除）

需要排查 `prepareDerivedSafety` 里 `prepareSavedAnchorTaskState`（`validateRealtimeScheme` 内部，`anchor_generation_scheme.go:130`）是否会间接触发 `ValidateSet`。查法：

```
grep -rn "prepareSavedAnchorTaskState" management-service/internal/httpapi/
```

确认该函数及其下游是否调用了 `readyContentPoolSet` / `ValidateSet` / `LatestContentPoolSet` 之外仍带校验的读取。

### 3. 若报错来自「更新受影响内容」（最可能）

那是内容池更新链路的正常完整性校验，与「保存方案去阻塞」是两件事。当前产品口径：
- 保存方案 = 不强制更新、不卡完整性；
- 更新内容 = 仍做 `ValidateSet` 完整性核对。

若用户期望「更新」也不卡这个错，需要另行决策是否放宽 `ValidateSet`，**不建议**直接放开（它是内容池数据完整性的兜底）。

## 六、已完成的改动（勿重复做）

- 后端：`prepareDerivedSafety` 改写失败不再卡保存，改整条剔除风险事实（`removeUnsafeFactLines`）并回执 `removed_risks`。
- 后端：保存入口改用 `latestSavedContentPoolSet`，跳过 `ValidateSet`。
- 前端：`LiveStrategyView.vue` 删除内容池状态（`needs_update`/`failed`）对保存的阻塞，删除 `waitForContentPoolReady`，`savePlanOneClick` 不再 `contentPools.update()` 前置。
- 前端：保存成功展示被剔除风险事实列表（`removedRisks`），支持点击定位。
