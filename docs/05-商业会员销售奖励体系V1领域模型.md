# 小蓝搭子商业系统 V1：会员、销售、奖励与结算领域模型

更新时间：2026-09-21

## 1. 目标

本文件定义小蓝搭子商业系统的长期底层约束。目标不是只满足当前的“会员 + 时长卡”，而是保证后续增加内部销售、外部代理、客户推荐、返佣、退款、结算、财务统计时，不需要推翻历史数据模型。

当前产品边界：

| 系统 | 使用者 | 主要职责 |
| --- | --- | --- |
| 小蓝搭子客户端 | 终端客户 | 直播、账户、会员权益、钱包、时长、充值/消费/退款记录 |
| 运营管理后台 | 运维/运营 | 客户、设备、直播间、AI 伴播、运行状态 |
| 商业管理后台 | 财务/商业运营 | 会员、时长卡、钱包、订单、退款、奖励、佣金、代理结算、经营统计 |
| 销售工作台 | 内部销售 | 只读自己的客户、流水、业绩、提成 |
| 代理工作台 | 外部代理 | 自己代理范围内的客户、业务与结算 |

初期仍允许共享一个 Management Service 和 MySQL，按模块和权限隔离，不为了形式拆微服务。

## 2. 十条架构红线

后续所有商业功能必须满足：

1. 关系有历史。
2. 规则有版本。
3. 订单有快照。
4. 钱有不可变流水。
5. 时长有独立批次和有效期。
6. 奖励必须有来源。
7. 佣金有 Pending / Confirmed / Settled / Reversed 状态。
8. 退款和纠错使用反向流水，不修改历史流水。
9. 权限不仅有角色，还必须有数据范围。
10. 后台配置修改只影响未来，不回写已经成交的历史。

统一单位：

| 数据 | 存储单位 |
| --- | --- |
| 人民币金额 | 分，整数 |
| 使用时长 | 秒，整数 |
| 折扣/返佣/提成比例 | 万分比，10000 = 100%，8500 = 85% |
| 时间 | UTC DATETIME(3) |

## 3. 客户关系模型

客户主体仍然是 mgmt_tenants。商业资产属于 Tenant，不属于某个登录 User。

### 3.1 五条关系线必须分离

同一个客户可以同时拥有：

- 首次来源：自主注册 / 内部销售 / 外部代理。
- 当前内部销售负责人。
- 当前外部代理归属。
- 一级客户推荐人。
- 当前会员、钱包和时长资产。

禁止设计一个万能 parent_id。

### 3.2 首次来源

crm_customer_profiles.source_type：

- direct：自主注册。
- internal_sales：内部销售首次开发。
- external_agent：外部代理首次开发。

首次来源作为历史事实保留。后续换销售、换代理不能覆盖首次来源。

### 3.3 内部销售关系

crm_customer_sales_assignments 保存有效期：

- tenant_id
- sales_staff_id
- effective_from
- effective_to
- assigned_by_user_id
- reason

客户从张三转给李四时，结束张三关系，再新增李四关系，不能 UPDATE 掉历史。

### 3.4 外部代理关系

crm_agent_orgs 表示代理机构，crm_agent_members 表示代理机构成员。

crm_customer_agent_relations 独立保存客户与代理机构的有效期关系。

代理是外部组织，不等于内部销售人员。

### 3.5 客户推荐关系

crm_referral_relations 只允许一级：

A 推荐 B，B 消费只奖励 A。
B 推荐 C，C 消费只奖励 B，不奖励 A。

一个被推荐客户只有一个推荐人。关系调整只能由授权管理人员执行，并进入永久审计。

## 4. 权限模型

现有 mgmt_users.role 暂时保留兼容，商业 V1 已预留标准 RBAC：

- iam_roles
- iam_permissions
- iam_user_roles
- iam_role_permissions

预计角色：

- super_admin
- ops_admin
- business_admin
- finance_admin
- sales
- agent_admin
- customer

权限必须再叠加数据范围。

例如 sales.customer.read 不是“可以读所有客户”，而是只能读当前销售归属范围内的客户。

销售工作台默认只读，禁止：

- 修改客户资料和密码。
- 发会员。
- 赠送时长。
- 人工充值。
- 退款。
- 修改余额。
- 调整返佣。
- 修改销售/代理/推荐关系。
- 修改商品价格和商业规则。

财务或商业管理员才允许执行资金与权益调整。

## 5. 商品目录与会员

### 5.1 稳定 ID + 版本

会员和时长卡都拆成“稳定商品”和“版本”：

会员：

- catalog_membership_plans
- catalog_membership_plan_versions

时长卡：

- catalog_time_card_products
- catalog_time_card_versions

例如“标准会员”是稳定 Plan；价格从 199 元改成 239 元时，不覆盖旧版本，而是创建 V2。

旧客户当前周期仍使用成交时版本，新购买或新周期使用新版本。

### 5.2 会员版本字段

会员版本至少包含：

- 价格。
- 结算周期。
- 每周期基础时长。
- 默认时长卡折扣。
- 是否允许自动续费。
- entitlements_json：未来直播间数、设备数、AI 能力等权益。

会员不是一个固定价格标签，而是“商品 + 权益”。

### 5.3 时长卡版本字段

时长卡版本至少包含：

- 售价。
- duration_seconds。
- validity_days。
- 是否参与客户推荐返佣。
- 是否参与内部销售提成。
- 是否参与代理结算。

时长卡必须有有效期。购买后按成交版本生成真实到期时间，后续后台修改产品有效期不得改变已经购买的旧卡。

### 5.4 会员 × 时长卡折扣

catalog_membership_card_discounts 保存会员版本和时长卡版本之间的特定折扣。

价格优先级：

1. 当前会员版本 + 当前时长卡版本的专属折扣。
2. 当前会员版本默认时长卡折扣。
3. 100% 原价。

折扣采用 basis points，不使用浮点数。

## 6. 订单与快照

biz_orders 是商业成交的中心证据。

订单创建时必须保存当时的关系快照：

- membership_id_snapshot
- membership_plan_version_id_snapshot
- sales_assignment_id_snapshot
- sales_staff_id_snapshot
- agent_relation_id_snapshot
- agent_org_id_snapshot
- referral_relation_id_snapshot
- referrer_tenant_id_snapshot

订单商品行 biz_order_items 保存：

- 商品稳定 ID。
- 商品版本 ID。
- 商品名称快照。
- 时长快照。
- 有效期快照。
- 原价快照。
- 实付价快照。
- 折扣快照。

客户以后换销售、换代理，历史订单仍归属于成交时关系。

历史成交价格也不跟随后台新价格变化。

## 7. 钱包与财务

### 7.1 钱包账户

fin_wallet_accounts 支持一个 Tenant 下多个钱包账户类型。

初期：

- cash：真实充值形成的可消费余额。
- reward：活动或推荐形成的奖励余额。

未来如需要真实提现，可再增加 commission，不把“可提现佣金”和充值现金混在一个余额里。

### 7.2 钱包流水

fin_wallet_ledger 是金额变化的最终事实流水。

必须保存：

- 变动前余额。
- 变动金额。
- 变动后余额。
- 业务类型和业务 ID。
- 关联订单。
- 操作人员。
- 原因。
- idempotency_key。
- reversal_of_entry_id。

已发生流水不修改、不删除。

退款和纠错创建新的反向流水。

### 7.3 充值

fin_recharge_orders 单独保存充值订单。

充值只代表“钱进入钱包”，不触发销售提成、代理结算和客户推荐返佣。

提成/返佣只在真实商品订单支付后产生。

### 7.4 消费

用户端需要分别展示：

- 资金流水。
- 充值记录。
- 消费记录。
- 时长卡订单。
- 会员订单。
- 退款记录。

商业后台除明细外还需要按时间区间聚合：

- 账户余额总额。
- 累计/本月/今日充值。
- 累计/本月/今日消费。
- 累计/本月/今日退款。
- 净消费。
- 会员销售额。
- 时长卡销售额。
- 已售时长。
- 剩余有效时长。
- 已消耗时长。
- 已过期时长。
- 推荐奖励成本。
- 内部销售提成成本。
- 外部代理结算成本。

充值额和销售额必须分开统计。

### 7.5 退款

fin_refund_orders 记录：

- 原业务类型和原业务 ID。
- 退款金额。
- 退款方式。
- 退款原因。
- 处理人员。
- 状态。
- 处理时间。

退款不能删除原消费订单。

退款需要联动：

- 钱包反向流水。
- 未消耗时长回收。
- 推荐返佣冲正。
- 销售提成冲正。
- 代理结算冲正。

## 8. 时长资产

### 8.1 Bucket 模型

quota_buckets 表示每一批真实时长。

来源示例：

- membership_cycle
- time_card_purchase
- referral_reward
- manual_reward
- service_compensation

每个 Bucket 独立保存：

- 原始秒数。
- 剩余秒数。
- 生效时间。
- 到期时间。
- 来源。
- 状态。

禁止只给客户一个 total_hours 字段。

### 8.2 扣减顺序

采用 FEFO：最早过期的时长先用。

排序基础：

- expires_at ASC
- priority ASC

因此会员月度额度、推荐奖励卡、购买时长卡可以自然共存。

### 8.3 时长流水

quota_ledger 保存每一次：

- 发放。
- 消耗。
- 到期。
- 回收。
- 退款恢复。
- 人工冲正。

历史不修改，只新增反向记录。

### 8.4 使用事件

quota_usage_events 预留真实计费事件。

未来只有满足计费条件时才产生 billable_seconds，例如：

- 设备在线。
- 直播监控开启。
- AI 伴播开启。
- 直播间确实处于工作状态。

真实扣时第二阶段接入设备心跳后实施。

## 9. 推荐、销售提成和代理结算

三者可以共享“规则引擎”，但账必须分开。

### 9.1 Program + Version + Rule

- inc_programs：稳定规则方案。
- inc_program_versions：版本和生效期。
- inc_rules：具体事件、条件和动作。

Program Type：

- referral_reward
- referral_commission
- internal_sales_commission
- agent_settlement

Rule 采用受控 JSON 配置，只允许系统定义好的条件和动作，不允许后台执行任意 SQL/JS。

可用条件未来包括：

- 商品类型。
- 商品 ID。
- 会员等级。
- 客户来源。
- 客户注册天数。
- 实付金额。
- 首单/非首单。
- 累计消费。
- 当前销售。
- 当前代理。

可用动作：

- 固定时长奖励。
- 固定金额奖励。
- 按比例返佣。
- 按比例销售提成。
- 按比例代理结算。

### 9.2 一级推荐

推荐奖励可同时支持：

- 注册成功送时长。
- 首次消费送时长。
- 首购会员送时长。
- 有限时间内按真实消费返佣。

返佣期限落地到具体 referral relation 的 commission_start_at / commission_end_at。

后台以后把 180 天改成 90 天，不自动缩短已经绑定关系的老客户期限。

### 9.3 内部销售提成

销售提成只与销售归属客户的真实商品消费相关。

销售提成不进入客户钱包，进入 inc_earnings 的 sales_staff beneficiary。

以后可以支持：

- 首购与续费不同提成。
- 会员和时长卡不同提成。
- 客户前 3 个月 / 4-12 个月不同提成。
- 阶梯销售额提成。

订单生成时保存销售关系和适用规则快照。

### 9.4 外部代理结算

外部代理独立于内部销售。

一个客户可以来源于外部代理，同时由公司内部销售负责维护。

代理收益进入 agent_org beneficiary，不进入销售提成账。

### 9.5 Earning 状态

inc_earnings 统一保存奖励/佣金/代理收益：

- pending：等待退款观察期。
- confirmed：可结算。
- settled：已经结算。
- reversed：被退款或纠错冲正。

订单支付后先 Pending，等待配置的 pending_days 后再 Confirmed。

退款产生新的负向 earning/reversal，不删除原 earning。

## 10. 结算

inc_settlement_batches / inc_settlement_items 用于未来按周期结算内部销售和外部代理。

状态建议：

- pending
- approved
- paid
- cancelled

已经 settled 的提成若后续订单退款，生成负向调整进入下一结算周期，不回改历史批次。

## 11. 永久商业审计

Redis 继续保存管理员热审计流，但资金与权益类关键动作必须同时进入 MySQL 永久审计 biz_audit_events。

必须永久审计：

- 人工充值。
- 退款审批。
- 钱包调账。
- 会员调整。
- 时长奖励。
- 时长回收。
- 推荐关系调整。
- 销售归属调整。
- 代理归属调整。
- 商业规则发布。
- 提成/返佣人工调整。
- 结算审批。

密码内容、密码 Hash 永远不能进入任何审计日志。

## 12. 数据删除规则

在客户尚未产生任何商业流水前，可以保留当前开发期的物理删除能力。

一旦客户出现以下任意记录：

- 充值。
- 消费。
- 退款。
- 钱包流水。
- 时长资产。
- 提成/返佣。
- 结算。

该 Tenant 不允许物理删除，只允许停用/归档，保证财务和审计链完整。

后续正式启用商业模块时，需要同步升级现有“删除客户”接口为这一规则。

## 13. 幂等和并发

所有会改变钱、时长、订单、奖励的接口必须支持 idempotency_key。

例如同一个支付回调重复三次，只允许：

- 一次钱包入账。
- 一次订单支付。
- 一次时长发放。
- 一次佣金计算。

钱包扣款和时长发放必须在可控事务中执行；需要读取余额后写入时使用数据库锁，防止并发重复消费。

## 15. 第一阶段实施顺序

阶段 A：底座（当前）

- 建商业表结构。
- 增加头像字段。
- 预留 RBAC。
- 不生成假的会员和假的余额。

阶段 B：客户前台

- 账户管理页面。
- 财务管理页面。
- 修改密码移入账户管理。
- 充值按钮先展示未开放状态。
- 所有金额/订单为空时展示真实空状态。

阶段 C：商业管理后台

- 会员 CRUD + 版本发布。
- 时长卡 CRUD + 版本发布。
- 会员 × 时长卡折扣。
- 客户商业档案。
- 真实财务统计空态。

阶段 D：钱包和购买

- 人工充值。
- 钱包流水。
- 用余额购买会员。
- 用余额购买时长卡。
- 原子扣款 + 发权益。

阶段 E：退款和奖励

- 退款。
- 时长回收。
- 推荐奖励。
- 一级返佣。
- 返佣冲正。

阶段 F：销售与代理

- 销售归属。
- 销售工作台。
- 销售提成。
- 外部代理组织。
- 代理工作台。
- 代理结算。

阶段 G：真实扣时

设备心跳稳定后接入 usage events 和 FEFO 扣时。
