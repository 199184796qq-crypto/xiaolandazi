# 追加回执体积问题（给 Codex）

## 一、现象

现场次 475（08:54–10:44，连播约 110 分钟）期间，Management 日志出现 190 次：

```
recording stream append accepted with partial snapshot tenant=14 room=29
decode_error=unexpected end of JSON input
```

每次都是同一句，不是偶发。

## 二、根因

Management 侧调用 `POST /internal/v1/rooms/{id}/audio/program/append` 后，按固定 32KB 读取回执：

```go
raw, _ := io.ReadAll(io.LimitReader(resp.Body, 32<<10))
json.Unmarshal(raw, &snapshot)   // 超长即截断 → unexpected end of JSON input
```

而 Core 的 append 回执返回的是完整 `audioout.RoomProgramSnapshot`（`core-service/internal/httpapi/audio_program_append.go` 直接 `writeJSON(w, 200, result)`），其中包含三个**随时间增长**的数组：

| 字段 | 内容 | 增长方式 |
|---|---|---|
| `playback_receipts` | 每条主线的覆盖回执 | 与播出段数线性增长 |
| `mainline_playback_receipts` | 每段的播放回执（含 StartedAt） | 与播出段数线性增长 |
| `future_window` | 未来排队轨道（每项还带 timeline / safe_points） | 与缓冲队列长度相关 |

播得越久，JSON 越大，超过 32KB 就必然截断。

## 三、截断造成的实际影响

1. `snapshot.Generation` 解不出来，恒为 0；
2. `ProgramID` / `VersionID` 的一致性校验被跳过（`if snapshot.ProgramID != "" && ...` 走不到）；
3. 追加虽然返回 200、音频也确实进了 Core，但 Management 拿不到本应拿到的写后读一致信息。

目前没有观察到播出中断，属于"静默降级"。

## 四、这个接口为什么会这样设计

`RoomProgramSnapshot` 同时承担了几件事：

- 一致性：`generation` / `program_id` / `version_id` / `last_applied_job_id`
- 供料决策：`buffered_mainline_ms` / `waiting_for_content` / `future_window`
- 展示与互动：`timeline` / `safe_points` / `track_text`
- 回执对账：`playback_receipts` / `mainline_playback_receipts`

"命令返回新状态"本身没问题，问题在于**把展示与全量对账数据放在了每 3 句一次的热路径上**。Management 实际只用到其中少数标量。

## 五、我已做的临时处置

1. **Management 侧**（已上线 `20261023-receipt-1b15fcd`）：改为流式解码，上限 8MB，不再截断；非 200 仍只读 32KB 的错误体。
2. **Core 侧**（已提交 `2eb2205`，**未部署**）：append 回执做裁剪
   - `mainline_playback_receipts`：只保留最近 1 小时（有 StartedAt），最多 500 条
   - `playback_receipts`：无时间戳，只保留最近 200 条
   - `future_window`：最多 100 条
   - 所有标量字段不动

这两条只是把体积按住，没有改变"热路径返回聚合视图"这个设计本身。

## 六、需要你决策的点

1. **是否给 append 单独定义一个精简回执**（只回 `generation` / `track_id` / `track_index` / `buffered_mainline_ms` / `accepted`），把完整快照留在 `GET /audio/program`？
2. 如果保留完整回执，**裁剪口径**用时间窗口（1 小时）还是条数上限，还是调用方通过参数声明（如 `?receipt=compact|full`）？
3. `future_window` 里每项都带 `timeline` 和 `safe_points`，对追加方是否必要？
4. 是否需要在回执里显式给出 `truncated: true`，让调用方知道这不是全量？
