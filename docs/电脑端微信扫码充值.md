# 电脑端微信扫码充值

电脑端“我的钱包”使用微信 Native 支付：输入金额，点“充值”，在电脑弹窗直接显示微信付款二维码。手机用微信扫一扫确认金额并付款，不需要在手机重新登录网站。手机端原有 JSAPI 充值保持不变。

## 流程与资金保护

1. 登录客户电脑端，打开 `/finance`。“充值”金额按整数分校验，最多两位小数；充值单由服务端绑定租户、金额和 `wechat_native` 支付方式。
2. 服务端使用现有商户号、AppID、商户签名私钥和微信支付验签公钥，调用官方 APIv3 Native 下单；通知地址沿用现有支付通知。商户平台已开通 Native，不修改密钥，也不依赖旧版 Native 回调链接配置。
3. 微信验签后的 `code_url` 固定保存在该支付尝试里；服务端本地生成 256×256 PNG 二维码，不发送给第三方二维码服务。二维码不包含网站登录凭据。有效期 15 分钟。
4. 电脑弹窗每 5 秒查单。支付成功以服务器验签的通知/查单为准；校验商户号、AppID、订单、币种、金额及 `NATIVE` 类型后，余额、充值流水、收款和经营入账在同一事务提交。
5. Native 的付款人由微信成功结果确定，不能由浏览器指定。付款人摘要在交易锁内首次绑定，供余额原路退回校验，退款回到原扫码付款人的微信账户，不支持用户另填收款账户。
6. 重复点击、创建响应丢失、刷新页面沿用当前会话保存的幂等键和充值单；不会因未知结果自动创建另一笔充值。重复回调/查询只入账一次。
7. 二维码过期后不再展示。重新获取前先查询旧支付：成功则入账；未付款须确认微信关单后才允许新支付尝试；支付确认中或查询异常时不换号。后端原有每分钟对账兜底继续工作。

## 接口与迁移

- `POST /api/v1/wallet/recharges`：`amount_cents`、`idempotency_key`、`payment_method: "wechat_native"`。手机省略支付方式仍为 `wechat_jsapi`。
- `POST /api/v1/wallet/recharges/{rechargeID}/wechat-native-prepay`：返回金额对应的充值单、`payment_no`、`qr_code_data_url`、`expires_at`。
- `GET /api/v1/wallet/recharges/{rechargeID}`：恢复本租户充值单。
- `POST /api/v1/wallet/recharges/{rechargeID}/wechat-query`：查单并按已验证结果结算。
- `POST /api/v1/payments/wechat/notify`：现有验签与解密回调。客户端“支付成功”不能代替它。
- 仅增加 `fin_payment_transactions.provider_code_url VARCHAR(512) NOT NULL DEFAULT ''`，不清理或改写历史资金数据。

所有客户操作需要登录且校验同源。跨租户读取/预支付被拒绝。错误响应不打印私钥、密钥或原始含敏感信息的微信报文。

## 验证

- 管理服务 `go test ./...`、`go vet ./...` 与 Linux 构建通过。
- 官方 SDK Native 下单测试校验金额、商户、通知与类型；有签名响应通过，伪造响应拒绝。二维码 PNG 尺寸、非法二维码 URL 和非法金额测试通过。
- 隔离 MySQL 三轮测试通过：随机前缀表、SQL 对象白名单，不访问真实业务行；8 个并发成功结算只产生一次余额、流水、收款和经营入账。错误金额/商户/AppID/币种/付款人/交易类型拒绝；Native 原路退款来源校验通过。测试表已自动清理。
- 电脑前端类型检查与生产构建通过；浏览器侧金额、响应丢失幂等重试、刷新恢复、二维码过期/非法图片与退款回归测试通过。
- 未替用户创建真实支付或退款。实际微信扫码、扣款和到账闭环需用户自行确认金额后验证，可先充 0.01 元。

## 发布方式

`scripts/server/deploy-wechat-native.sh` 只更新管理服务、`web-desktop` 和兼容电脑端 `web`。从现有退款版本完整复制保留手机页面、直播核心、设备、采集和销售端，只重启管理服务。配置文件摘要以及核心/设备进程 ID 必须不变。

先验证新后端健康、增量列、原有退款表、未登录/跨站保护及伪造支付/退款通知，再发布电脑端入口；保留旧哈希静态资源。发生发布检查失败时保留具备支付和退款对账能力的后端，避免未完成资金处理无人核验。
