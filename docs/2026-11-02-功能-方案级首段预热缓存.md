# 功能：方案级首段预热缓存

2026-11-02。**已实施并上线，运行源码fefa0c6；下方保留原设计，准确修订及发布回执见《2026-11-02-方案级首段预热核验与发布.md》。**

实际方案目录使用<root>/<tenant>/plans/<plan>/recording-cache/<namespace>/plan-paragraphs/<key>/，不用room0布局。火山原生检查点与阿里不同；缺失可走现场合成，存在不确定付费结果时保留并报错，不静默重买。预热完成前仍可能等待，费用不固定，原设计的零等待/固定费用/损坏即重新合成说法以本段及核验文档为准。

## 1. 需求

> 保存方案时候系统自动拉取第一个 TTS 到方案级的缓存区，后面用户在哪个直播间使用这个方案开播，就复制到这个直播缓存中，作为开始使用。

三句话拆成三个动作：

1. **保存方案时**：系统自动合成该方案的**首段**，存到**方案级缓存区**
2. **开播时**：把方案级缓存**复制**到该直播间的缓存
3. **结果**：开播立刻有声音，不用等 10 秒以上

## 2. 现在的行为

| 环节 | 现在 |
| --- | --- |
| 保存方案 | 只存文本，不合成 |
| 开播 | 首段现场合成，400 字约 10 秒；2000 字约 52 秒 |
| 换房间开播同一方案 | 各房间各自合成一遍，互不复用 |

第 596 场实测：开播 22:45:42，第一条真实合成 22:47:34——**前两分钟全靠上一场的缓存**，没有缓存时只能干等。

## 3. 缓存布局

现有：`<mediaRoot>/<tenant>/<room>/<plan>/<namespace>/paragraphs/<段落key>/`

新增方案级：`<mediaRoot>/<tenant>/0/<plan>/<namespace>/plan-paragraphs/<段落key>/`

用 `roomID = 0` 表示方案级，复用现有 `recordingcache.Scope`（`ScopeFor` 允许 roomID ≥ 0）。

段落 key 沿用 `scriptFirstParagraphKey(v, text)`——它包含供应商、模型、音色、语速、文本、指令和普通话令牌。**文本或声音任一变化，key 就变，不会拿旧缓存冒充。**

## 4. 保存时的动作

### 4.1 挂在哪

**挂在「保存方案」按钮**（用户指定）。

对应接口：`POST /api/v1/live-agent-plans/{planID}/versions` → `live_agent_plan_versions.go:320 liveAgentPlanVersionCreate`。

选这里的依据不只是用户要求——代码注释本身写着：

> Saving is the activation point for the next live.

保存就是下一场的生效点，在这里预热语义最对。

挂点放在版本落库成功之后、响应之前（预热本身异步，不拖慢响应）。

### 4.2 做什么

```go
func (s *Server) warmPlanFirstParagraph(tenant, plan int64, v model.LiveAgentPlanVersion) {
    go func() {                       // 异步，不阻塞保存响应
        ctx, cancel := context.WithTimeout(context.Background(), 3*time.Minute)
        defer cancel()
        if !usesScriptFirstParagraphs(v) { return }
        dir := planCacheScope(tenant, plan).CacheDir(namespaceFor(v), "plan-paragraphs")
        units, err := scriptFirstUnits(v, dir)
        if err != nil || len(units) == 0 { return }
        first := units[0]             // 只合成首段
        if _, err := s.ensureScriptFirstParagraph(ctx, tenant, 0, 0, v, first, true); err != nil {
            log.Printf("plan warmup failed tenant=%d plan=%d: %v", tenant, plan, err)
        }
    }()
}
```

要点：

- **只做首段**，不是整篇。首段按设计 200–400 字，约 0.01 元
- **异步**，保存接口不等它
- **失败只记日志**，不影响保存
- 已有缓存时 `ensureScriptFirstParagraph` 直接命中，不重复购买

### 4.3 成本

| 情况 | 花费 |
| --- | --- |
| 首次保存某个新文本 | 首段 200–400 字 ≈ 0.01 元 |
| 反复保存、文本没改 | **0**（key 命中，直接复用） |
| 只改了后面段落 | **0**（首段 key 未变） |
| 改了声音/语速 | 重新合成一次首段 |

关键在 key：`scriptFirstParagraphKey` 包含供应商、模型、音色、语速、文本、指令。**只要首段文本没变，点多少次保存都是 0 成本**，所以挂在保存按钮上不会烧钱。

## 5. 开播时的动作

在 `volcengine_script_stream.go:183` 算好 `units` 之后、进入供料循环之前：

```go
s.hydrateFirstParagraphFromPlan(ctx, tenant, room, v, units[0])
```

实现：

```go
func (s *Server) hydrateFirstParagraphFromPlan(ctx, tenant, room int64, v, unit) {
    roomDir := unit.Dir
    if _, err := os.Stat(filepath.Join(roomDir, "paragraph-job.json")); err == nil {
        return                        // 本房间已经有，不覆盖
    }
    planDir := filepath.Join(planCacheScope(tenant, v.PlanID).CacheDir(ns, "plan-paragraphs"), unit.Key)
    if _, err := os.Stat(planDir); err != nil {
        return                        // 方案级没有，走正常现场合成
    }
    copyTreeAtomic(planDir, roomDir)  // 先拷到临时目录再 rename
    log.Printf("plan warmup hydrated tenant=%d room=%d plan=%d key=%s", tenant, room, v.PlanID, unit.Key)
}
```

要点：

- **只复制首段**，后续段落仍按正常预取
- **不覆盖**房间已有的付费缓存
- **原子**：先拷到 `roomDir.tmp` 再 rename，避免半份文件被当成有效缓存
- 复制的是整个 unit 目录：`paragraph.wav` + `paragraph-job.json`（付费检查点）+ `cache.json`
- 带着检查点一起复制，房间不会重新购买

## 6. 必须处理的边界

| 情况 | 处理 |
| --- | --- |
| 方案文本改了 | key 变，方案级缓存自然失效，重新合成 |
| 方案换了声音 | key 含音色，同上 |
| 房间已有付费音频 | 不覆盖，直接用房间的 |
| 方案级缓存损坏 | 复制前校验 WAV 头与 SHA；坏了就当没有，走现场合成 |
| 多房间同时开播抢同一份 | 只读复制，无冲突；每个房间各一份副本 |
| 磁盘占用 | 每多一个房间多一份首段（400 字约 2.9 MB），按房间数线性增长 |
| 方案发布后立刻开播 | 预热可能还没完成，退化为现场合成 |

## 7. 存储成本

| 项 | 单份 | 10 房间 | 100 房间 |
| --- | --- | --- | --- |
| 首段 400 字 WAV | 约 2.9 MB | 29 MB | 290 MB |

可接受。若在意，可改成开播时直接从方案级目录播、不复制，但那要改 Core 的 URL 来源，本轮不做。

## 8. 验收

| # | 场景 | 判据 |
| --- | --- | --- |
| 1 | 保存并发布新方案 | 方案级目录出现首段 `paragraph.wav` |
| 2 | 发布后立刻开播 | 若预热已完成，首条音轨直接入队，无新 TTS 请求 |
| 3 | 换房间开播同一方案 | 第二个房间不出新 TTS 请求 |
| 4 | 修改文本后发布 | 重新合成一次，旧缓存不被复用 |
| 5 | 房间已有缓存 | 不覆盖，不重复购买 |
| 6 | 预热失败 | 保存成功，开播退回现场合成，只记日志 |
| 7 | 预热费用 | 每版本最多一次首段合成 |

## 9. 不做什么

- 不做整篇预热（成本高、大部分段落用不上）
- 不做开播时直接从方案级播（要改 Core 取音频路径）
- 不做跨租户共享（避免越权）
- 不做定时刷新（文本变了 key 自然变）

## 10. 与其它改造的关系
