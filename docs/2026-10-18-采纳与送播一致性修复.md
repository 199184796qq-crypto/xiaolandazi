## 结论与真实证据

session 310 中，17 段被采纳、15 段有 Core 开始记录；中间讲解为采纳 13 段、开始 11 段。两段已完成 TTS，却在话术库归档校验时被当成过期范围丢弃：

| 采纳候选 ID | 内容 | 采纳时间（北京时间） | 丢弃时间 |
| --- | --- | --- | --- |
| `a3f53a95089558ed8fc4005b6c20edb7` | 公共用券规则 | 16:02:56 | 16:03:22 |
| `f87a6297254e7c9d2177fd70341cae68` | 1 号套餐配置 | 16:16:42 | 16:16:56 |

根因已精确复现，不是仅根据日志推测“下一段改变了当前任务”：

1. `text_generation.go` 的局部重写阶段使用 `mainline_text_repair`。`agentgateway.PrepareTextRequest` 不为这个阶段设置正文生成规则指纹，返回的 `TextPromptSHA` 为空。
2. 每次请求结束后，`state.TextPromptSHA` 都会被本次请求值覆盖。下一段普通生成又把它填回。
3. `speech_library.go/libraryTextSHA` 同时计算了真正的 `TextPromptContract`，却还把随请求变化的 `state.TextPromptSHA` 放进同一哈希。
4. 已采纳段落交给声音协程时，正文生产者可能已经开始下一段。即使该段冻结的任务、事实和母版不变，仅临时字段从空切成正常值，也会触发 `library scope stale`。
5. 旧程序跳过声音后，采纳时消耗的商品、卖点、角度及公共配额仍保留，后续调度误以为这段已获得供给机会。

使用生产当时 `d01e2d9` 的 139 个提示词文件、同一个已采纳任务和两份真实状态快照回放，仅切换该字段就复现两组完整 want/got：

- 公共段：`fd2c752e…8e2a1` → `2cb75e2d…15a44`。
- 商品段：`c65f1754…78d62` → `b66dc547…d8d1f7`。

旧校验没有拿“当前下一段任务”替换已采纳段落任务；误变来自共享状态中的临时规则字段。

## 修复行为

### 稳定声音范围校验

`libraryTextSHA` 改为使用已经解析的实际正文规则 `TextPromptContract`。局部重写与普通请求交替不再误使声音过期。租户、房间、方案、场次、事实、任务、实际母版、模型及表达约束等原有范围校验保留。

没有放行所有 stale 错误，没有把不匹配音频强制送播，没有清理话术库。真实事实或规则变化仍会拒绝旧音频。

### 确定未送出的段落返还配额

- 采纳时冻结 `Segment.Quota`，记录消费的内容类别、商品、卖点及角度键。回调依据这一段的归属返还，不依据当时已经轮换到的商品。
- 明确声音生成/归档失败，或调用 Core 前的轨道校验失败，记录 `delivery_status.status=failed`。正式直播的普通中间讲解段只返还一次对应有效调度计数。
- `Accepted` 原稿、重试轨迹、采纳总数及阶段进度保留，便于核对“采纳了但没有送出”；开场、收口、可选讲解、承诺续讲不冒充普通轮盘配额返还。
- 有 Core 确认下发记录的段落不返还。下发确认不等于实际 PCM 播放完成，实际播放仍看 Core 回执。
- 不把声音失败写成角度审核失败，不因此屏蔽整个角度。

下一次安全的正文边界，根据返还后的有效计数重排尚未消费的配额窗口。进行中的重写、审核重试、承诺续讲与可选讲解不被打断；原有避重和阶段历史不倒退。补偿的是后续讲解机会，不是强制重播那份失效原稿。

商品间 1.2 上限、商品内卖点 1.3 上限、公共 20% / 商品 80% 目标保留。公共配额使用同一材料可用期间的累计缺额；公共材料缺失或已被排除的期间不累计公共欠额，恢复后不会为历史缺料集中补讲。正常无送播失败的完整窗口仍为 1 个公共 / 4 个商品。

### 并发、重启及结果不明

- 声音协程以待登记队列提交结果；读取同场最新状态，并使用运行租约和 CAS 保存，避免旧声音快照覆盖新采纳稿件。
- 遇到租约忙或 CAS 冲突保留待办，后续循环重试；重复回执和已保存状态重载后均不二次返还。
- 迟到回执发现 `RunID` 已变，停止处理，不能改到下一场。
- Core 调用后的超时、响应丢失或无法确认，记录 `status=unconfirmed`，不自动返还或重发，因为 Core 可能已经入队。这类状态仍需用实际 Core 回执核对，本次未实现自动对账重发。
- 失败状态重载后不会重新合成和重复下发同一候选。停止时仅作一次有时限的登记尝试，不承诺进程强杀情况下内存待办持久化。
