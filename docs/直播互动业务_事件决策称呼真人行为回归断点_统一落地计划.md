# 直播互动业务：事件决策、称呼、真人行为、回归与断点统一落地计划

> 项目：小蓝直播搭子  
> 文档定位：产品方案 + 业务规则 + 技术落地计划  
> 更新时间：2026-09-29  
> 状态：作为后续互动链路升级的统一执行基线  
> 关联文档：`docs/策略黑板_互动打断回归TTS升级方案.md`

## 1. 这次要解决的核心问题

当前直播伴播已经具备事件采集、互动时间窗、打断、回归、称呼、TTS、主线恢复等基础能力，但如果各模块继续独立发展，会出现几个问题：

- 互动事件只是“来了就处理”，没有统一判断价值；
- 直播间冷、热状态对互动行为影响不够系统；
- 打断、开头、称呼、互动内容、回归话术容易被拆成多段处理；
- 称呼容易退化成固定词库；
- 真人行为容易退化成“轻咳 / 重复 / 口头禅”的固定枚举；
- 主线恢复容易长期形成固定规律，听起来像录制音频被插播；
- 回归只按时间点恢复，不够重视语义分段和“已被互动内容覆盖”的部分；
- 前台如果直接暴露大量概率、阈值、冷却，会让普通用户无法使用；
- 后台内部参数虽然复杂，但缺少统一可观测和验证入口。

本次统一升级目标：

> **前台用户决定“互动更偏向什么效果”；后台系统决定“什么时候值得打断、怎么表达、从哪里回去”；最终由一次大模型生成完整话术，TTS 播放后按语义断点恢复主线。**

## 2. 最终业务主链

正式业务链定义如下：

```text
直播事件产生
    ↓
事件价值判断
    ↓
直播热度修正
    ↓
事件聚合 / 竞争 / 互动预算
    ↓
选出本轮真正值得处理的事件
    ↓
确定主线安全打断点
    ↓
确定互动结束后的回归目标
    ↓
确定开头方式
    ↓
确定称呼对象与称呼方式
    ↓
确定交互内容目标
    ↓
选择本轮真人行为约束
    ↓
确定回归话术目标
    ↓
策略黑板冻结
    ↓
一次性生成完整可播话术
    ↓
文本审核 / 事实校验
    ↓
TTS
    ↓
主线在安全点暂停
    ↓
播放互动声音
    ↓
按语义断点恢复主线
    ↓
重复检查 / 实际回归记录
```

核心原则：

> **所有策略只做决策和约束，不分别生成几段文字再拼接。最终只有一个生成器一次性生成整段主播要说的话。**

## 3. 三大阶段划分

### 3.1 第一阶段：决定“这件事值不值得打断”

这一层只处理“事情”。

输入包括：

- 弹幕；
- 明确问题；
- 新进房；
- 关注；
- 点赞；
- 下单；
- 价格、库存、物流、售后等购买信号；
- 重复问题；
- 低热度长时间无互动；
- 后续新增业务事件。

输出：

```text
InteractionDecision
- 本轮是否需要处理
- 主要事件是什么
- 合并了哪些事件
- 事件价值
- 为什么现在值得打断
- 最晚必须处理时间
- 当前互动预算是否允许
```

这一层不生成主播话术。

### 3.2 第二阶段：设计“这一整次插播怎么说”

正式顺序：

```text
打断点
→ 回归目标
→ 开头方式
→ 称呼
→ 交互内容
→ 真人行为
→ 回归话术
→ 一次生成完整文本
```

注意：

> **回归目标必须在最终文本生成之前确定。**

只有先知道互动结束后要回到主线哪里，大模型才能自然生成最后一句回归话术。

### 3.3 第三阶段：声音和断点执行

```text
完整文本
→ 审核
→ TTS
→ 等待安全切点
→ 暂停主线
→ 播互动声音
→ 播放完成
→ 执行语义断点恢复
→ 去重检查
→ 完成 Mission
```

## 4. 互动事件决策模型

### 4.1 不再把所有事件看成相同价值

每类事件应有“基础事件价值”，然后动态修正。

建议统一模型：

```text
最终事件价值
= 系统基础价值
× 行业修正
× 用户偏好
× 当前热度修正
× 紧迫性
× 重复次数
× 等待时间
× 主线可打断程度
× 最近同类行为抑制
```

这里的“概率”不是直接决定一句话，而是决定事件进入互动任务时的相对优先级。

### 4.2 事件价值分层

建议后台默认分为：

#### 高价值

- 明确购买问题；
- 商品核心疑虑；
- 价格 / 规格 / 库存；
- 物流 / 售后；
- 已重复出现的问题；
- 下单 / 强意向信号；
- 当前行业配置的高价值问法。

#### 中价值

- 关注；
- 普通问答；
- 普通聊天；
- 礼物；
- 某些需要维护关系的互动。

#### 低价值

- 高频点赞；
- 高频进房；
- 无明显业务价值的重复打招呼；
- 高热直播间中的普通欢迎。

### 4.3 “问题债务”

问题不能只靠固定概率。

当问题：

- 多人重复问；
- 等待时间持续增长；
- 用户再次追问；
- 属于成交关键问题；

则自动增加优先级。

建议内部维护：

```text
QuestionDebt
- topic
- first_seen_at
- repeat_count
- unique_users
- waiting_seconds
- business_value
- current_priority
```

原则：

> **越多人问、等得越久、越接近成交的问题，越不能长期不回答。**

## 5. 直播热度与互动预算

### 5.1 不建议只按在线人数

直播热度不能简单写成：

```text
10人以下 = 冷
50人以上 = 热
```

而应综合：

- 在线人数；
- 30 秒进房数；
- 30 秒弹幕数；
- 点赞速度；
- 关注速度；
- 问题数量；
- 重复问题数量；
- 成交信号；
- 当前主线阶段。

统一为：

```text
COLD
WARM
HOT
OVERHEATED
```

### 5.2 不同热度下的自动行为

| 行为 | 冷场 / 人少 | 正常 | 热闹 | 爆量 |
|---|---|---|---|---|
| 回答问题 | 多 | 多 | 高价值优先 | 高价值 / 高频问题优先 |
| 欢迎新人 | 多，可点名 | 正常 | 聚合为主 | 只做聚合 |
| 点赞感谢 | 可以及时 | 聚合 | 降低 | 大批量聚合 |
| 关注感谢 | 可以单独 | 小批聚合 | 聚合 | 延后统一回应 |
| 普通聊天 | 积极 | 正常 | 降低 | 基本不打断 |
| 成交问题 | 高 | 高 | 很高 | 最高 |

### 5.3 引入“互动预算”

互动预算表示当前一段时间内主播可以花多少“注意力”在插播互动上。

#### 冷场

互动预算高：

- 欢迎可以多；
- 回答问题可以多；
- 聊天可以积极；
- 关注、点赞可适当回应。

#### 高热

互动预算降低：

- 主线不能被频繁切碎；
- 高价值问题优先；
- 普通欢迎延后聚合；
- 点赞、关注进入聚合池。

建议内部对象：

```text
InteractionBudget
- level
- max_missions_per_window
- remaining_slots
- current_heat
- reserved_for_high_value
```

## 6. 前台用户应该怎么配置互动

互动偏好必须给前台用户，因为这是主播最容易理解、最有价值的控制。

但是前台用户不能看到内部概率和算法。

### 6.1 前台页面：互动偏好

建议页面：

```text
互动偏好

整体互动
安静一点 ｜ 自然互动 ｜ 热情一点

回答问题
少一些 ─────●──── 多一些

欢迎新人
少一些 ─────●──── 多一些

点赞关注
少一些 ─────●──── 多一些

聊天互动
少一些 ─────●──── 多一些

成交互动
稳一点 ─────●──── 积极

✓ 小蓝会根据直播间实时人气自动调整
```

### 6.2 前台保存的不是百分比

用户层保存：

```text
overall_interaction = NATURAL / QUIET / ACTIVE
question_preference = LESS / NATURAL / MORE
welcome_preference = LESS / NATURAL / MORE
engagement_preference = LESS / NATURAL / MORE
chat_preference = LESS / NATURAL / MORE
conversion_preference = STEADY / NATURAL / ACTIVE
```

后台再把这些映射为内部权重。

### 6.3 自然语言也是正式配置入口

用户可以直接告诉智能体：

> 人少的时候多欢迎，多回答问题。

> 人多的时候不要一直点名，主要回答问题。

> 点赞不用太频繁感谢。

智能体把自然语言转换为用户层偏好。

## 7. 前后台配置边界

### 7.1 前台终端用户

允许：

- 整体互动程度；
- 回答问题偏好；
- 欢迎偏好；
- 点赞关注偏好；
- 普通聊天偏好；
- 成交互动偏好；
- 称呼偏好；
- 主播长期习惯；
- 今天 / 当前场状态；
- 通过智能体自然语言纠正。

不允许直接看到：

- 原始概率；
- 冷却秒数；
- 热度倍率；
- 事件基础分；
- 回归算法代码名；
- 去重阈值；
- 跨段算法；
- 真人行为内部状态机。

### 7.2 营销运维后台

允许：

- 行业默认互动倾向；
- 用户层授权后的具体偏好；
- 行业高价值问题；
- 常用称呼；
- 行业主播风格；
- 用户特殊行为修正。

### 7.3 运维领导 / 超级系统管理员

允许：

- 规则层；
- 事件基础价值；
- 热度修正规则；
- 互动预算；
- 时间窗；
- 冷却；
- 回归多样性；
- 语义覆盖阈值；
- 真人行为底层机制；
- 系统默认权重。

## 8. 打断与开头方式必须分开

### 8.1 InterruptPlan：什么时候停主线

负责：

- 当前播放位置；
- 当前语义句；
- 安全切点；
- 是否允许立即切；
- 是否必须等完整句；
- 切前上下文。

### 8.2 OpeningPlan：互动第一句话怎么进入

开头方式可以包括：

- 直接回答；
- 轻微复述问题；
- 先回应观众；
- 自然过渡；
- 短暂停顿后回答；
- 无显式开头直接进入内容。

注意：

> 开头方式只是“意图”，不是固定模板。

## 9. 称呼策略升级

### 9.1 称呼不能只是词库

称呼应拆成：

1. **称呼谁**
2. **怎么称呼**

### 9.2 称呼对象方式

正式定义：

```text
NONE
不使用称呼

SINGLE
点 1 个人

SAMPLE
聚合事件里抽 1～2 个昵称

GROUP
纯群体称呼

MIXED
点 1～2 个昵称 + 其他人整体称呼
```

### 9.3 聚合称呼示例

假设有 12 个新关注：

```text
称呼方式 = MIXED
可播昵称 = 小陈、阿芳
其余人数 = 10
```

最终可能生成：

> 小陈、阿芳，还有刚刚点关注的朋友们，欢迎你们。

也可能生成：

> 看到小周他们几个刚关注了，欢迎你们。

或者：

> 刚刚又来了不少新朋友，欢迎大家。

### 9.4 昵称可播筛选

昵称需要过滤：

- 太长；
- 符号过多；
- 疑似广告；
- 不适合公开直播；
- 很难自然朗读；
- 最近刚点过；
- 敏感 / 冒犯风险。

默认建议：

```text
max_named_count = 2
```

### 9.5 前台用户看到什么

只显示：

```text
称呼习惯
少点名 ｜ 自然 ｜ 多点名

常用称呼
朋友 / 老哥 / 宝子 / 大家 / ...

不喜欢的称呼
...
```

“MIXED、SAMPLE、冷却、昵称过滤”全部留在后台。

## 10. 真人行为系统：不做固定枚举

真人行为无法穷举，所以不能继续靠：

```text
轻咳
重复
倒装
停顿
口头禅
...
```

不断增加硬编码。

正式升级为：

```text
Trait + State + Reaction
```

### 10.1 Trait：长期习惯

例如：

- 经常说“你看哈”；
- 喜欢短句；
- 偶尔重复关键词；
- 句尾喜欢确认；
- 语速偏慢；
- 转场喜欢先总结一句。

### 10.2 State：阶段性状态

例如：

- 感冒；
- 嗓子不舒服；
- 疲劳；
- 兴奋；
- 刚喝水；
- 当前场声音偏轻；
- 其他用户自然语言描述的临时状态。

状态必须有有效期：

```text
current_session
30m
2h
today
custom_until
```

### 10.3 Reaction：当前情境反应

例如：

- 复杂问题 → 允许轻微复述；
- 需要思考 → 允许短暂停顿；
- 刚发生错误 → 允许自然自我纠正；
- 刚刚已经咳过 → 抑制再次咳嗽；
- 连续讲太久 → 提高自然停顿概率。

### 10.4 通用数据结构

```text
HumanBehaviorRule

source:
- trait
- state
- reaction
- user

conditions:
- event_type
- question_complexity
- heat
- emotion
- host_state
- recent_usage
- mainline_context

intensity:
0 ~ 1

base_weight
cooldown
max_per_5m
max_per_session
expires_at

instruction

channel:
- TEXT
- TTS_STYLE
- NONVERBAL_AUDIO
- MIXED
```

### 10.5 不要求每轮必须有真人行为

每轮最多：

- 0～1 个主要文本行为；
- 必要时额外 1 个纯声音行为。

不能为了“像真人”每次都加嗯、哎、咳、重复、口头禅。

## 11. 主播行为前台配置

前台不显示 `HumanBehaviorRule`。

建议只有两块：

### 11.1 主播习惯

用户直接写：

> 我平时说话比较慢，喜欢短句，偶尔说“你看哈”。

智能体解析成长期 Trait。

### 11.2 今天的状态

默认：

```text
状态正常
```

用户可以输入：

> 今天有点感冒，嗓子不舒服。

智能体给出：

```text
当前场启用：
- 语速稍慢
- 长句减少
- 声音略轻
- 偶尔允许清嗓 / 轻咳

下播后自动失效
```

## 12. 回归策略：既要语义正确，也要整场有变化

### 12.1 回归不能长期只用一种

目标：

> 降低“主线音频像录制”的规律感。

因此所有启用且当前语义条件允许的回归策略，都应该在整场直播中有使用机会。

现有策略：

- DIRECT
- BRIDGE
- FUSION_SKIP
- CROSS_RESUME
- RE_ANCHOR
- SWITCH_PLAN

### 12.2 不能强制凑次数

例如：

- RE_ANCHOR 只有长中断才合理；
- FUSION_SKIP 必须互动内容覆盖后续主线；
- CROSS_RESUME 必须存在合适跨段入口。

所以不能规定每场直播每种策略必须至少使用一次。

正确规则：

> **先筛选“本轮有资格使用的策略”，再在这些候选中做场次多样性调权。**

### 12.3 Coverage Debt：覆盖债务

建议每个回归策略记录：

```text
base_weight
eligible_count
selected_count
last_selected_at
consecutive_miss
coverage_debt
effective_weight
```

如果某策略本场多次具备条件但一直没有被选中，则 `coverage_debt` 增加。

### 12.4 最近重复惩罚

如果连续：

```text
BRIDGE
BRIDGE
```

下一轮 BRIDGE 权重自动降低。

如果 CROSS_RESUME 连续多次可用但没选中，下一次再可用时提高权重。

### 12.5 最终回归权重

```text
effective_weight
= base_weight
× semantic_fit
× coverage_debt_boost
× recent_repeat_penalty
× session_diversity_boost
```

但任何多样性策略都不能覆盖语义安全和主线正确性。

## 13. 回归策略与回归位置是两个维度

### 13.1 第一维：怎么回来

```text
DIRECT
BRIDGE
FUSION_SKIP
CROSS_RESUME
RE_ANCHOR
SWITCH_PLAN
```

### 13.2 第二维：从哪里回来

```text
原点
下一段
跳过 1 段
跳过 N 段
下一话题
新的锚点
新的主线
```

这两个维度必须分开。

## 14. 断点处理必须以语义分段为主

不能只保存：

```text
resume_at_ms = 123456
```

还要保存语义段。

例如主线：

```text
S1：咱们这个是菜籽油。
S2：原料用的是本地菜籽。
S3：采用传统物理压榨。
S4：整个过程不需要复杂加工。
S5：大家买回家炒菜特别香。
S6：保存的时候注意避光。
```

假设 S2 后打断，互动回答已经覆盖 S3、S4，则：

```text
cut_after_segment = S2
original_resume_segment = S3
covered_segments = [S3, S4]
planned_resume_segment = S5
actual_resume_segment = S5
skip_count = 2
resume_reason = semantic_coverage
```

后台应能直接解释：

> 原本回 S3，因为互动已经覆盖 S3、S4，所以实际从 S5 接回。

## 15. 回归话术与断点恢复必须分开

### 回归话术

主播嘴里说出来的桥接语言。

### 断点处理

Core 实际把主线音频从哪个语义段 / 时间点继续播放。

两者必须关联，但不能混为一个字段。

## 16. SpeechMission 策略黑板升级

建议统一结构：

```text
SpeechMission

EventContext
InteractionPlan

ResumePointPlan
OpeningPlan
AddressingPlan
InteractionContentPlan
HumanBehaviorPlan
ResumeSpeechPlan
GenerationRules
TTSDirective

```

### 16.1 每个 Plan 的职责

- `InteractionPlan`：为什么本轮要说、处理哪些事件、是否聚合；
- `InterruptPlan`：在哪里停、安全切点、切前上下文；
- `ResumePointPlan`：原始回归点、计划回归点、跳过哪些语义段；
- `OpeningPlan`：第一句话怎么进入互动；
- `AddressingPlan`：NONE / SINGLE / SAMPLE / GROUP / MIXED；
- `InteractionContentPlan`：本轮必须讲清什么；
- `HumanBehaviorPlan`：本轮是否启用 Trait / State / Reaction；
- `ResumeSpeechPlan`：最后一句把话带向哪里。

### 16.2 冻结原则

```text
策略黑板冻结
→ 再调用最终文本模型
```

正在执行的 Mission 不被后续热更新改写，新 Mission 使用最新配置。

## 24. 技术落地阶段

### 阶段 A：互动决策引擎

目标：

- 新增 EventValue；
- 接入 Heat；
- 接入 UserPreference；
- 新增 QuestionDebt；
- 新增 InteractionBudget；
- 多个到期事件进入统一竞争。

验收：

> 冷场时欢迎和问答明显更积极；高热时普通欢迎自动降频，高价值问题仍优先。

### 阶段 B：前台互动偏好

目标：

- 前台新增“互动偏好”；
- 不显示百分比；
- 少一些 / 自然 / 多一些；
- 自动保存；
- 热生效；
- 智能体可修改同一份用户层配置。

验收：

> 用户只调“多回答问题”，后台实时能看到问题类 Event Priority 和 Mission 命中发生变化。

### 阶段 C：称呼对象模型

目标：

- AddressingPlan 引入 NONE / SINGLE / SAMPLE / GROUP / MIXED；
- 昵称过滤；
- 聚合名单抽样；
- 默认最多 2 个昵称；
- 最近点名抑制。

验收：

> 聚合欢迎可以自然出现“点一两个名字 + 其他人一起欢迎”，而不是固定群称。

### 阶段 D：真人行为统一模型

目标：

- Trait；
- State；
- Reaction；
- 通用 Rule；
- 有效期；
- 冷却；
- TTS / TEXT 渠道；
- 用户自然语言生成配置。

验收：

> “今天感冒”只影响当前场；“口头禅”可以长期高频；“思考时重复问题”只在合适情境出现。

### 阶段 E：回归多样性

目标：

- eligible_count；
- coverage_debt；
- recent repeat penalty；
- effective_weight；
- 场次统计。

验收：

> 有资格使用过的回归策略不会整场一直为 0；同时不会为了凑次数强行使用不合理策略。

### 阶段 F：语义断点

目标：

- 主线 Segment ID；
- cut_after_segment；
- original_resume_segment；
- covered_segments；
- planned_resume_segment；
- actual_resume_segment；
- skip_count。

验收：

> 能明确解释“为什么跳过 2 段从 S5 恢复”，而不是只有一个毫秒时间点。

### 阶段 G：黑板与监控统一

目标：

- 前台只看简单结果；
- 内部后台看完整决策；
- 可按 mission_id 追踪；
- 可看到 EventValue → Heat → Decision → Text → TTS → Resume。

## 27. 重点测试场景

1. 冷直播间 3 人，连续有人进房 → 欢迎更积极；
2. 冷直播间有人问问题 → 问题优先级明显提高；
3. 高热直播间 30 秒进房 50 人 → 不逐个欢迎；
4. 高热直播间点赞 500 + 2 个商品问题 → 先处理商品问题；
5. 同一个问题多人重复 → QuestionDebt 上升；
6. 用户前台把“回答问题”调高 → 问题 Mission 明显增多；
7. 用户把“欢迎新人”调低 → 欢迎仍可保底，但明显减少；
8. 单人问题 → 允许 SINGLE；
9. 12 个关注 → SAMPLE / MIXED；
10. 昵称难念 → 自动退化 GROUP；
11. 最近刚点过名字 → 降低重复点名；
12. 本轮 NONE → 最终文本不强塞称呼；
13. 长期口头禅 → 可以较高频出现但不机械；
14. 感冒 State → 当前场提高轻咳 / 清嗓 / 短句倾向；
15. 下播后 State 自动失效；
16. 复杂问题 → 允许轻微复述；
17. 简单问题 → 不强行重复问题；
18. 最近已咳过 → 冷却抑制；
19. DIRECT 多次连续出现 → 下次权重自动下降；
20. CROSS_RESUME 多次可用未选 → Coverage Debt 提高；
21. RE_ANCHOR 全场没有资格 → 不为凑次数强行使用；
22. 回答覆盖 S3、S4 → 从 S5 恢复；
23. 跨主题恢复 → 回归话术提前生成；
24. 最终话术最后一句与恢复主线重复 → 去重触发。

## 28. 验收标准

### 28.1 产品验收

- 前台用户不需要理解概率；
- 前台可以明确控制“多回答 / 多欢迎 / 少点赞感谢”等偏好；
- 称呼能自然点 1～2 个昵称并兼顾群体；
- 用户可以用自然语言描述主播习惯和当前状态；
- 高级策略只在内部后台出现。

### 28.2 业务验收

- 每次插播都有明确事件价值；
- 冷 / 热直播间行为明显不同；
- 主线不会被普通低价值事件持续切碎；
- 问题不会因为随机概率长期得不到回答；
- 回归方式整场有变化；
- 断点恢复以语义为主；
- 最终文本始终是一整段。

### 28.3 听感验收

目标：

> 主播像一个真实的人在看直播间、决定要不要回应、自然插一句，再根据刚才讲了什么继续往下讲。

不能出现：

> 固定欢迎 → 固定称呼 → 固定回答 → 固定桥接 → 固定原点恢复。

---

## 29. 最终产品原则

### 原则一

> **前台用户配置“偏好和效果”，不配置“算法参数”。**

### 原则二

> **互动系统决定“值不值得回应”，称呼系统决定“回应谁”，真人行为系统决定“这一轮像什么状态的人说”，回归系统决定“说完从哪里继续”。**

### 原则三

> **所有计划在生成前统一写入 SpeechMission；最终只调用一次大模型生成完整主播正文。**

### 原则四

> **回归多样性是为了降低录制感，但绝不为了凑策略使用次数破坏语义正确性。**

### 原则五

> **人类行为不是固定枚举，称呼也不是固定词库；两者都必须支持由上下文和用户自然语言持续扩展。**

---

## 30. 一句话定义

> **有事发生，先判断这件事值不值得现在说；再决定从哪里停、怎么开口、叫谁、说什么、带什么真人状态、最后回到哪里；所有决定冻结后一次生成完整话术，TTS 播完，再按语义断点继续主线。**
