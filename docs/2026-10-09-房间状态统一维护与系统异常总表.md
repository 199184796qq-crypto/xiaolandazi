## 二、按实际代码形成的统一维护规则

### 唯一维护方

`core-service/internal/room/LifecycleManager` 是房间业务状态的决策入口。`Store` 负责持久化与统一查询。业务状态与采集工作状态分开：

- 业务状态：pending / connecting / live / offline / stopped，沿用已有接口值。
- 采集工作状态：connecting / connected / reconnecting / disconnected / stopped。
- 返回的可选字段：collector_state、collector_disconnected_at、collector_deadline。既有消费者不需要更换状态协议。

采集器只报告 connecting、live、disconnected、ended；不再直接调用“写房间状态”的方法。异步合并写入器只能写指标，不能通过晚到的 MarkLive 把房间重新拉成 live。

### 状态转移

1. 首次有效直播证据：状态管理器确认 live。
2. 断线：记录首次断线时间，保留原有业务状态；重连动作只更新采集状态，不把 live 降为 connecting。
3. 持续失联满 60 秒：独立计时器确认 offline，不依赖浏览器重试什么时候返回。
4. 重试或本进程内更换工作器：沿用原始截止时间，不新增第二个 60 秒。
5. 60 秒内取得有效直播证据：取消当前断线计时；之后再次断线，才开始新的 60 秒。
6. 平台明确结束：立即 offline，不等待宽限。
7. 用户停采：立即 stopped、禁用报告令牌，晚到证据不能恢复状态。
8. 进程关闭、房间删除、采集租约丢失：废止该工作器与计时器；不凭进程退出虚构平台下播。

连接“成功”的判断必须是采集器取得有效直播证据，不是仅打开浏览器页面或连上一个不能证明开播的传输连接。

### 与现有模块怎么衔接

- 状态管理器的结束通知继续进入原有 session_end 链：免费统计、付费 Agent 结束、声音清理均沿用已落地逻辑。
- 捕获事件入队与终止转移共用顺序闸门，防止旧 session_start / 事件在结束通知之后晚到。
- 顺序闸门与数据查询锁分开。真实事件观察器会反查房间，不能在持有数据锁时等待事件队列清空。
- 下播后又收到直播证据，可以恢复免费采集；保留结束修订号，让原有 session_reopen / 用户确认机制决定是否重新开启付费运行，不自动恢复旧场次。
- 非采集所有者的 Core 节点从新读取的数据库结果展示权威状态，不缓存第一次查询的状态不变。
- 开发环境事件注入也通过管理器，但复用现有令牌，不抢真实采集器的工作器身份。
- Management 不写采集状态；生成器退出前核对计费场次和 Core Agent 的明确停止原因。
- Core 停止操作改为原子保留原因；生成失败清理可带 boot_id 与 run_generation 条件，防止查询后发生新一轮运行时误停新 Agent。

### 不混淆的三类状态

房间是否正在直播、付费 Agent 是否工作、设备是否在线是三个不同对象。设备在线不代表平台开播；停止付费 AI 不应停止免费采集；采集暂时重连也不应让付费互动被误判为未开播。

## 五、上线与实播验收

1. 核对生产当前版本与本地包，保留既有前端、网关、完整母版目录和事实分类文件，不用旧发布包覆盖其他修复。
2. 两次检查没有 running / paused / 未结束场次，且没有活跃音频、设备占用；不替用户关闭现存连接。
3. 使用发布锁、确切文件白名单、哈希校验、健康检查、原版本回滚；本次无数据库结构变更。
4. 上线后验证同一房间 10 秒 / 59 秒断线：业务仍 live、允许互动领取、采集显示重连。
5. 验证满 60 秒失联：一次权威结束通知、Agent 结束、按真实累计工作秒数结算；不出现声音生成失败。
6. 验证明确平台结束与用户停采：立即停止；旧事件、旧异步指标、旧定时器不能恢复 live。
7. 验证断线后回连：免费链恢复，原场次不自动重新播放或计费。
8. 保留回滚条件：异常结束增加、正常互动被拒、查询阻塞、采集所有权冲突时停止推广并取证。
