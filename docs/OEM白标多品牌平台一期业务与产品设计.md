# OEM 白标多品牌平台一期业务与产品设计

更新时间：2026-10-03  
文档状态：一期需求基线，可进入技术拆分与开发

## 1. 项目目标

在不复制代码、不为每个代理商单独维护一套业务系统的前提下，将现有“小蓝搭子”升级为一套支持多品牌运营的 OEM 平台。

每个 OEM 运营商可以拥有自己的：

- 品牌名称、Logo、浏览器图标和主色。
- 客户前台、运营后台及移动端入口。
- 独立域名和登录页。
- 客户、员工、设备库存、直播间和账务数据范围。
- 设备显示名称、虚拟豆名称、销售价格和功能开关。

平台继续使用一套代码、一套发布流程和同一组核心服务。系统按 `oem_id` 隔离品牌和业务数据，按 `tenant_id` 隔离 OEM 下面的终端客户。

一期采用“共享平台标准 OEM”，后续可为大客户提供“独立部署 OEM”。两种模式使用同一套业务规则和数据模型。

## 2. 一期明确结论

### 2.1 不复制项目

禁止为每个 OEM 复制一套前端、后端或数据库代码。原因如下：

- 修复一个漏洞或升级一个功能时，不需要同时修改多套分支。
- 品牌差异通过配置实现，不通过改代码实现。
- 平台可以统一控制版本、功能、用量和结算。
- OEM 增加或停用时，不影响其他 OEM。

### 2.2 两级隔离模型

系统正式采用以下层级：

```text
平台方
  └─ OEM 运营商
       ├─ OEM 员工
       ├─ 终端客户 A（tenant_id）
       │    ├─ 用户
       │    ├─ 设备
       │    └─ 直播间
       └─ 终端客户 B（tenant_id）
            ├─ 用户
            ├─ 设备
            └─ 直播间
```

- `oem_id`：表示品牌和经营主体，是第一层业务隔离。
- `tenant_id`：表示终端客户，是第二层业务隔离。
- 一个终端客户只属于一个 OEM。
- 一个设备在任一时刻只属于一个 OEM；认领后再属于该 OEM 下的一个终端客户。
- 同一个登录账号一期只属于一个 OEM，不支持跨 OEM 共用身份。

### 2.3 默认品牌兼容

现有“小蓝搭子”作为系统内置的默认 OEM，历史客户、设备、房间、订单和账务全部归入默认 OEM。

迁移原则：

- 不改变历史 `tenant_id`。
- 不重新生成设备 SN、MAC、绑定码或直播间编号。
- 不影响现有设备联网、认领、房间绑定和 Agent 运行。
- 新增字段先允许兼容迁移，回填完成后再收紧为必填。

## 3. 概念与角色

### 3.1 平台方

平台方是系统最高管理主体，负责：

- 创建、审核、启用、暂停和注销 OEM。
- 配置 OEM 套餐、功能权限、资源额度与批发结算规则。
- 查看全平台运行状态、服务用量、异常和审计。
- 处理跨 OEM 的设备调拨、重大售后和数据合规事件。
- 管理系统版本、基础模型、语音能力、公共基础设施和安全策略。

### 3.2 OEM 运营商

OEM 运营商是对外经营一个独立品牌的主体，负责：

- 设置品牌资料和域名。
- 管理本 OEM 的员工、客户、设备、商品和售后。
- 设置面向客户的零售价格、虚拟豆名称及服务说明。
- 查看本 OEM 的收入、成本、用量和结算单。
- 不能查看其他 OEM 的客户、设备、流水或配置。

### 3.3 销售代理

现有系统中的销售代理继续表示销售渠道与分佣关系，不等同于 OEM 运营商。

- 销售代理可以帮助某个 OEM 获客、销售、跟进和结算佣金。
- OEM 运营商拥有品牌和经营后台。
- 同一机构可以同时是 OEM 运营商和销售代理，但必须分别授权、分别记账。
- 禁止继续使用一个含义不清的 `agent` 字段同时表示销售代理和 OEM。

### 3.4 终端客户

终端客户使用 OEM 品牌的网页或手机端，管理自己的：

- 账号与员工。
- 设备和绑定码。
- 直播间与 Agent。
- 会员、时长、虚拟豆和订单。
- 售后与服务记录。

终端客户不会看到平台方或“小蓝搭子”的内部名称，除非当前 OEM 本身就是默认小蓝品牌。

## 4. 产品版本

### 4.1 标准 OEM

一期默认交付标准 OEM：

- 共享服务器和数据库。
- 共享同一套前后端代码。
- 通过域名、登录会话和 `oem_id` 完成数据隔离。
- 支持品牌、颜色、名称、域名、价格和功能配置。
- 平台统一升级和运维。

适合中小代理商快速上线。

### 4.2 独立部署 OEM

独立部署作为后续高阶产品：

- 独立服务器、数据库、对象存储和域名。
- 可选择独立模型账号、短信、支付、语音服务与备案主体。
- 仍使用平台主干版本，不能形成无法升级的私人代码分支。
- 独立部署费、升级费、运维费和资源费单独结算。

一期只预留数据模型和配置能力，不在一期内自动开通独立集群。

## 5. 域名与品牌识别

### 5.1 域名规则

每个 OEM 至少有两个入口：

| 入口 | 示例 | 使用者 |
| --- | --- | --- |
| 客户前台 | `app.brand-a.com` | 终端客户 |
| OEM 后台 | `admin.brand-a.com` | OEM 管理员与员工 |

平台可提供默认二级域名：

```text
品牌代号.app.平台域名
品牌代号.admin.平台域名
```

OEM 也可以绑定自己的域名。自定义域名必须完成：

1. 域名所有权验证。
2. DNS 解析检查。
3. HTTPS 证书签发。
4. 域名与 OEM 唯一绑定。
5. 启用前的访问测试。

### 5.2 OEM 解析顺序

每个请求按以下顺序确定 OEM：

1. 根据请求 Host 查询已启用的 OEM 域名。
2. 登录后校验 Session 中的 `oem_id` 与域名 OEM 一致。
3. 内部设备请求根据设备库存归属确定 `oem_id`，不接受设备自报。
4. 平台内部任务通过受信任任务上下文携带 `oem_id`。

若域名与账号不一致，必须拒绝访问，不允许自动切换到另一个 OEM。

### 5.3 禁止信任客户端传入 OEM

浏览器、手机端或设备请求中即使存在 `oem_id`，后端也不能直接信任。后端必须根据域名、登录会话、设备归属或内部凭证推导真实 OEM，并在每次数据库访问时同时限制 `oem_id` 与 `tenant_id`。

## 6. 品牌配置中心

### 6.1 基础品牌配置

OEM 后台提供“品牌设置”页面，包含：

| 配置项 | 必填 | 说明 |
| --- | --- | --- |
| 品牌名称 | 是 | 例如“星火搭子” |
| 品牌简称 | 是 | 导航栏、窄屏和设备屏幕使用 |
| Logo 浅色版 | 是 | 浅色页面使用，建议 SVG/PNG |
| Logo 深色版 | 否 | 深色背景使用 |
| 浏览器图标 | 是 | ICO/PNG，自动生成常用尺寸 |
| 品牌主色 | 是 | 按钮、选中态和强调色 |
| 辅助色 | 否 | 标签、渐变和图表使用 |
| 登录页背景 | 否 | 未配置时使用平台通用背景 |
| 客服名称 | 是 | 例如“星火客服” |
| 客服电话 | 否 | 客户端帮助页展示 |
| 客服二维码 | 否 | 客户端帮助页展示 |
| 公司名称 | 是 | 协议、账单和页脚使用 |
| 官网地址 | 否 | 页脚和关于页面使用 |
| ICP 备案号 | 条件必填 | 使用自有域名且依法需要时展示 |
| 隐私政策 | 是 | 必须为已发布版本 |
| 用户协议 | 是 | 必须为已发布版本 |

所有图片上传必须限制格式、大小和尺寸，并保存历史版本。修改后支持预览，点击“发布”才对客户生效。

### 6.2 业务名称配置

OEM 可以修改面向客户的显示名称，但不能修改系统内部稳定编码。

| 系统概念 | 默认显示 | OEM 可配置示例 |
| --- | --- | --- |
| 产品名 | 小蓝搭子 | 星火搭子 |
| 设备默认名 | 小蓝搭子 | 星火盒子 |
| 唤醒名称文案 | 小蓝，小蓝 | 星火，星火 |
| 虚拟豆 | 小蓝豆 | 星火豆 |
| AI 助手 | 小蓝 | 星火助手 |
| 客服 | 小蓝客服 | 星火客服 |

一期注意：

- 网页文案和服务端返回文案可以按 OEM 配置。
- 设备唤醒词是否可真正更换取决于固件和离线唤醒模型，不能仅改网页配置。
- 未具备动态唤醒词能力前，后台必须标记“仅展示名称”或隐藏该项，不能制造已经生效的假象。

### 6.3 主题规则

前端统一使用设计变量，不允许页面硬编码品牌色：

```text
--brand-primary
--brand-primary-hover
--brand-primary-soft
--brand-accent
--brand-logo-url
--brand-login-background-url
```

系统必须检查主色与文字的对比度。若 OEM 选择的颜色导致按钮文字不可读，发布时提示并阻止生效。

## 7. 功能与套餐控制

平台方可以为每个 OEM 配置功能包。OEM 只能在平台已授权范围内向客户开放。

一期功能开关至少包括：

- 设备库存与两码两绑。
- 直播间与 Agent。
- 语音指令。
- 设备拍照与图片业务。
- 语音转写与分析。
- 会员与时长卡。
- 虚拟豆业务。
- 销售工作台。
- 售后工单。
- 自定义域名。
- 自定义品牌。

权限判断采用“双重授权”：

```text
平台授权给 OEM
        ∩
OEM 授权给终端客户套餐
        =
客户最终可用功能
```

前端隐藏只是交互处理，后端仍必须逐项鉴权。

## 8. 页面与导航设计

### 8.1 平台管理后台

新增一级菜单“OEM 管理”，包含：

1. OEM 列表。
2. 新建 OEM。
3. 品牌与域名审核。
4. 功能套餐与额度。
5. OEM 客户与设备概况。
6. 批发账单与结算。
7. 运行状态与异常。
8. 操作审计。

#### OEM 列表

列表列项：

- OEM 名称。
- 品牌名称。
- 状态。
- 客户数。
- 在线设备数 / 设备总数。
- 本月 Agent 用量。
- 本月应结算金额。
- 域名状态。
- 创建时间。
- 操作。

支持按名称、品牌代号、域名和状态搜索；默认每页 20 条并支持翻页。

状态统一为：

- 待配置。
- 待审核。
- 正常运营。
- 已暂停。
- 已终止。

暂停 OEM 后：

- 禁止新登录和新业务启动。
- 正在运行的 Agent 按平台停用策略安全停止并结束计费。
- 保留历史数据和审计。
- 设备显示清晰的服务暂停提示，不能自动切到其他 OEM。

### 8.2 OEM 运营后台

OEM 管理员登录后看到自己的品牌，不显示平台内部品牌。建议导航：

- 工作台。
- 客户管理。
- 设备与仓储。
- 直播间与 Agent。
- 商品与计费。
- 销售与售后。
- 员工与权限。
- 品牌设置。
- 账单与结算。
- 操作审计。

#### OEM 工作台

首页只展示当前 OEM：

- 客户总数及本月新增。
- 设备总数、在线、连续待机、工作中、离线。
- 正在运行的 Agent 数。
- 本月客户消费额。
- 本月平台成本和待结算额。
- 异常设备、余额预警和待办。

禁止出现跨 OEM 排名、其他 OEM 名称或平台密钥等信息。

#### 品牌设置页面布局

页面采用三栏或上下分区，不做超长大表单：

```text
左侧：基础资料 / 视觉主题 / 业务名称 / 域名 / 协议
中间：当前配置表单
右侧：桌面端、手机端和登录页实时预览
```

底部固定操作：

- 保存草稿。
- 预览。
- 提交审核。
- 发布（有权限且审核通过时）。

关键提示文案：

- 草稿：`修改尚未对客户生效。`
- 审核中：`品牌配置正在审核，当前线上版本不受影响。`
- 已发布：`当前配置已发布，新的访问将使用此品牌。`
- 域名异常：`域名解析或证书异常，暂不能对外启用。`

### 8.3 终端客户前台

终端客户前台延用现有业务页面，但所有品牌元素来自公共品牌配置接口：

- 页面标题和 Logo。
- 登录页和欢迎语。
- 导航名称。
- 设备默认名称。
- 虚拟豆名称。
- 客服资料。
- 用户协议和隐私政策。
- 主题色与浏览器图标。

页面中不得硬编码“小蓝搭子”“小蓝豆”“小蓝客服”等字样。

## 9. 登录、注册与账号归属

### 9.1 登录

用户必须从所属 OEM 域名登录。

- 相同手机号是否允许在多个 OEM 注册，由平台统一策略决定。
- 一期建议允许同手机号在多个 OEM 分别注册，但账号记录必须分别属于不同 `oem_id`。
- 登录查询唯一键应升级为 `(oem_id, username)`、`(oem_id, phone)` 或相同安全语义。
- 登录成功后的 Session 固化 `oem_id`、`tenant_id`、`user_id` 与角色。

### 9.2 注册与邀请

- OEM 可配置是否开放自主注册。
- 邀请码必须归属于一个 OEM。
- 从某 OEM 域名进入的注册，只能创建在该 OEM 下。
- 销售邀请、客户推荐和 OEM 归属分别记录，不能互相覆盖。
- 禁止使用其他 OEM 的邀请码完成注册。

### 9.3 员工权限

一期角色建议：

| 角色 | 数据范围 |
| --- | --- |
| 平台超级管理员 | 全平台 |
| 平台运营/财务/运维 | 按平台岗位授权 |
| OEM 超级管理员 | 当前 OEM 全部数据 |
| OEM 运营 | 当前 OEM 客户和业务，不含敏感财务配置 |
| OEM 财务 | 当前 OEM 账务、订单和结算 |
| OEM 仓储售后 | 当前 OEM 设备库存、出入库与售后 |
| OEM 销售 | 当前 OEM 且归属自己的客户范围 |
| 客户管理员 | 当前 tenant 全部数据 |
| 客户员工 | 当前 tenant 且按岗位授权 |

## 10. 设备、库存与固件

### 10.1 设备归属

设备业务增加 OEM 边界：

```text
设备硬件 -> OEM 库存 -> OEM 客户 -> 客户直播间
```

- MAC 和 SN 入库时必须归属于一个 OEM。
- 未分配 OEM 的设备只能处于平台仓，不得生成客户绑定码。
- 绑定码只能被同一 OEM 域名下的客户账号使用。
- 客户不能通过绑定码认领其他 OEM 的设备。
- 设备跨 OEM 调拨必须由平台执行，且只能在未认领或完成售后释放后进行。
- 所有跨 OEM 调拨必须保留原 OEM、目标 OEM、操作人、原因和时间。

### 10.2 固件策略

一期继续使用统一固件，降低生产和升级成本：

1. 设备以 MAC/SN 向服务器证明身份。
2. 服务器根据库存记录确定 `oem_id`。
3. Provision 返回该 OEM 的设备显示配置。
4. 设备屏幕显示品牌简称、设备名称、绑定码和状态。

设备不得通过请求参数自行选择品牌。品牌配置缓存必须包含版本号，联网后自动刷新。

后续如客户需要开机图、专属唤醒词或屏幕动画，可以生成 OEM 资源包，但仍优先避免编译独立业务固件。

### 10.3 绑定码规则

- 绑定码仍为 6 位数字并允许以 0 开头。
- 服务端查询必须同时匹配绑定码、有效期、设备状态和 `oem_id`。
- 对外错误统一为“绑定码无效或已过期”，不能借错误信息探测其他 OEM 的设备。
- 绑定成功后立即失效并写审计。

## 11. 计费与结算

OEM 模式存在两套独立账：

```text
平台方 -> OEM：资源批发账
OEM -> 终端客户：客户零售账
```

### 11.1 平台对 OEM

平台账单记录：

- Agent 运行时长。
- 模型、语音、图片和存储用量。
- 设备服务费。
- 套餐月费、域名或独立部署服务费。
- 调整、退款和冲正。

平台价格修改只影响未来用量，历史账单保留成交快照。

### 11.2 OEM 对客户

OEM 可以在平台允许范围内配置：

- 会员价格。
- 时长卡价格。
- 虚拟豆售价和业务扣豆规则。
- 设备销售价格。
- 优惠和销售佣金。

OEM 零售价与平台批发价必须分开存储，不能用一个 price 字段覆盖。

### 11.3 账务红线

- 资金、时长和虚拟豆使用不可变流水。
- 退款和纠错使用反向流水，不修改历史。
- 每笔客户消费记录 `oem_id`、`tenant_id` 和当时价格快照。
- 平台对 OEM 的账单不能被 OEM 员工修改。
- OEM 对客户的账单不能影响平台成本账。
- Agent 的主动停止、直播结束、设备持续离线 60 秒仍是最高优先级停止与停计费信号，OEM 不可覆盖。

### 13.2 登录态上下文

登录 Bootstrap 增加：

- 当前 OEM 的公开品牌配置。
- 当前用户的 OEM 角色。
- 平台授权且当前账号可用的功能列表。
- 当前 `tenant_id` 与客户权限。

设备 Provision 增加公开、安全、可缓存的品牌字段：

- 品牌简称。
- 设备显示名模板。
- 屏幕文案版本。
- 品牌资源包版本。

设备接口仍以硬件身份确定 OEM，禁止把 Host 或请求体中的品牌当作归属依据。

## 14. 安全与数据隔离红线

1. 每个业务查询必须带经过服务端推导的 `oem_id` 范围。
2. `tenant_id` 只能在当前 `oem_id` 下解析。
3. 禁止 OEM 管理员通过修改 URL、查询参数或请求体访问其他 OEM。
4. 对象存储路径、缓存 Key、异步任务和消息主题都必须包含 OEM 边界。
5. 导出文件、日志检索、通知收件人和统计聚合同样受 OEM 范围限制。
6. 平台人员跨 OEM 查看敏感数据必须有岗位权限并写审计。
7. OEM 停用后不得删除历史账务和审计。
8. 域名、Session 和 OEM 不一致时必须拒绝，不能静默纠正。
9. 所有品牌配置发布、域名启用、设备调拨和价格变更必须记录操作人、前后值与时间。
10. 自动化测试必须包含两个 OEM 使用相同用户名、SKU、房间号时互不可见的用例。

## 15. 一期业务流程

### 15.1 平台开通 OEM

1. 平台管理员点击“新建 OEM”。
2. 填写经营主体、品牌代号、负责人和服务套餐。
3. 系统创建 OEM、默认管理员和默认品牌草稿。
4. OEM 管理员收到激活入口并设置密码。
5. OEM 完善 Logo、颜色、客服、协议和域名。
6. 平台审核域名与品牌资料。
7. 发布品牌并启用 OEM。
8. OEM 开始创建客户、入库设备和配置商品。

### 15.2 OEM 入库与销售设备

1. 平台仓将设备分配给 OEM，或 OEM 在授权范围内录入设备。
2. MAC/SN 被写入 OEM 库存且默认允许激活。
3. 设备联网后按硬件归属读取 OEM 品牌配置。
4. 屏幕显示该 OEM 的品牌简称和 6 位绑定码。
5. 用户只能在该 OEM 的客户前台输入绑定码。
6. 认领成功后设备归属该 OEM 下的当前客户。
7. 用户再将设备绑定到自己的直播间，完成现有“两码两绑”。

### 15.3 OEM 停止服务

1. 平台将 OEM 标记为“已暂停”。
2. 禁止新登录、新订单、新设备认领和新 Agent 启动。
3. 正在运行的 Agent 安全停止并结束计费。
4. 设备收到服务暂停状态，不清除 Wi-Fi 和客户配置。
5. 数据、订单、流水和审计保留。
6. 恢复服务后重新鉴权并恢复可用，不补扣暂停期间费用。

## 16. 一期实施顺序

### 阶段 A：OEM 底座与兼容迁移

- 新增 OEM 核心表。
- 创建默认“小蓝搭子” OEM。
- 给 `mgmt_tenants`、用户、设备、房间、Agent 会话和关键账务表增加 `oem_id`。
- 回填全部历史数据并建立索引。
- Session 与请求上下文增加 OEM。
- 增加跨 OEM 隔离测试。

完成标准：现有小蓝业务功能无回归，所有历史数据可正常使用。

### 阶段 B：品牌配置与统一前端

- 实现 Host 解析和公共品牌接口。
- Web Console、客户移动端、销售端统一接入品牌配置。
- 消除前端与服务端面向客户的硬编码品牌文案。
- 完成 Logo、主题色、favicon、客服、协议和业务名称配置。
- 提供桌面端和手机端预览。

完成标准：使用两个不同域名访问时，同一套前端能呈现两个完整品牌。

### 阶段 C：OEM 运营后台

- OEM 员工和权限。
- 客户、设备、房间和运营数据范围。
- 功能套餐与客户功能授权。
- 品牌发布与操作审计。
- OEM 级统计与导出。

完成标准：OEM 管理员能独立运营本品牌且无法看到其他 OEM。

### 阶段 D：双层计费与结算

- 平台批发价与 OEM 零售价分离。
- 平台对 OEM 用量账单。
- OEM 对客户订单、虚拟豆与时长业务。
- 账单确认、退款、冲正和结算。

完成标准：同一笔业务同时产生可核对的客户零售记录和平台批发成本记录，两者互不覆盖。

### 阶段 E：设备品牌化

- Provision 返回 OEM 品牌与资源版本。
- 设备屏幕去除硬编码品牌文案。
- OEM 资源包缓存与回退。
- 验证绑定码只能在所属 OEM 使用。

完成标准：同一版固件的两台设备按库存归属显示不同品牌，且不能跨品牌认领。

## 17. 一期不做

- 不为每个 OEM 复制 Git 仓库或维护永久分支。
- 不允许 OEM 自行上传后端可执行代码。
- 不开放 OEM 修改平台安全策略、Agent 强制停止规则或设备鉴权规则。
- 不自动开通独立服务器和数据库。
- 不承诺所有固件能力都可动态换肤，专属唤醒词另行评估。
- 不允许跨 OEM 共享客户钱包、虚拟豆、时长或设备所有权。
- 不做多级 OEM 套娃；一期只支持平台 -> OEM -> 客户。

## 18. 验收标准

一期必须同时通过以下验收：

1. 平台可创建两个 OEM，并分别设置品牌、Logo、颜色和域名。
2. 两个域名加载同一套前端代码，但呈现各自品牌。
3. OEM A 管理员无法查询、导出或修改 OEM B 的任何数据。
4. 两个 OEM 可使用相同用户名、客户名称、SKU 和直播间外部编号，不发生串数据。
5. 历史小蓝客户、设备和房间全部归入默认 OEM，原业务正常。
6. 设备根据库存归属获得品牌配置，不能自行选择品牌。
7. OEM A 的 6 位设备绑定码不能在 OEM B 的前台认领。
8. 客户端不再硬编码“小蓝搭子”“小蓝豆”等默认名称。
9. OEM 停用后不能新开 Agent，运行中的 Agent 被安全停止并结束计费。
10. 平台批发账和 OEM 零售账独立、可追溯、可冲正。
11. 品牌发布、域名变更、设备跨 OEM 调拨和价格变更都有完整审计。
12. 自动化测试、接口测试和人工双域名联调全部通过。

## 19. 最终业务口径

对外销售时统一描述为：

> OEM 合作方使用自己的品牌、Logo、域名和客户后台开展业务；平台提供统一的设备接入、直播间 Agent、语音、图片、计费和运维能力。各 OEM 的客户、设备和账务相互隔离，系统统一升级，不需要重复开发和维护多套代码。

一期产品名称建议：

> 标准 OEM 品牌版

高阶产品名称建议：

> 专属部署 OEM 版

二者的差异是部署、资源和服务级别，不是两套无法合并的业务代码。
