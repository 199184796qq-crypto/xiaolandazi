# 给 DeepSeek：互动真人感与事实外接话设计交接

日期：2026-10-22。交接人：Codex。接收方：读取本项目文档的 DeepSeek 开发助手。

**用户当前重点：事实之外怎么接话，才能像在跟这个人说话。** 事实准确是基础，还需要识别对方在夸奖、抱怨、犹豫、闲聊还是补充上一句话，并选择合适的回应方式。不能把所有弹幕都处理成“找商品事实，再介绍商品”。

本文解释已经做过的测试，以及下一步建议怎么落地。本轮只写交接文档，没有修改业务、部署、追加模型或 TTS 调用。下面的接话设计和人工示例尚未接入生产，也没有经过真人感盲评或听音验收。

## 2. 我前面是怎么测试的

### 2.1 取真实材料，不给模型编一个理想直播间

通过只读数据库事务查询上述三个场次，分别取得 107、25、75 条 chat，共 207 条，同时读取历史模型消息及真实已发布事实。服务器归档只证明系统收到过这些内容，不证明每条都是已核实的真人买家发言。

另在固定历史时间窗核对了用户标识覆盖：4573 条 chat 中 4553 条带非空用户标识，2157 个不同标识。它说明有短期续接的基础，**不代表系统已经具备可靠的长期用户画像**。

测试时匿名化用户标识，不传真实昵称、订单身份、凭据或音频地址。每条只取同房间、同记录标识、发生在当前弹幕之前 10 分钟内最多 3 条发言，不偷看后文，不补造主播旧回答。10 分钟和 3 条是实验参数，还没有验证为最佳生产值。缺少标识时不能按同昵称拼人。

### 2.2 初测：先理解，再生成

26 组由 14 条真实归档弹幕、10 条人工构造边界、2 条去掉同人前文的消融组成。预期答案保存在程序样本里，没有传给模型。

每组先让模型分析这句话的意思，再用意图、当前事实与四层内容生成口播，共 52 次调用。模型只做内容任务；离线样本编号、原事件、事实版本和请求关系由程序维护。

真实拆句对照包括：

- “49 和 68 的有什么”之后再发“区别”：有同人前文时能接成价格规格比较，无前文时只能澄清比较对象；生成仍可能擅自对应到当前两款商品。
- “一号链接再优惠点”之后发“再打 10 元下来”：能识别讨价，但意图里丢掉了“一号”的对象。只判对大类还不够。
- “可以送上门吗”之后 2.627 秒发“东莞”：有前文才能知道地点是在补充配送问题。
- 真实历史模型曾把“两大两小”在目的中写成“两大一小”；本次能保留 2＋2。这是历史模型内容错误证据，不等于已证实历史播出了错误答案。

### 2.3 复测：先列可支持结论与未知点，再生成

选 12 组，沿用已有意图，再增加一次证据分析：哪些结论有支持、对应原文是什么、哪些点未知、到底需不需要追问用户。程序核对引用确实存在于当前事实中，再组装进“必说／可说／不提／改写”，之后生成口播，共新增 24 次调用。

这一轮程序直接排除其他观众的信息，不指望一句“不要串人”就完成隔离。事实版本也分开测试：资产 65 没有减 30 元，资产 90 有，不能把编辑中的新资料偷偷拼到旧版。

两轮均使用 qwen3.7-flash，关闭思考，temperature 0.25，完整保留当时有效的 8 条生成 P0 和 9 条结构化规则。共 76 次调用全部完成，无重试、无截断；初测 26 份意图均能解析。输入 262276 tokens，输出 6129 tokens。没有 TTS、互动入队、工具执行或生产写入。

结果由 Codex 逐条对照原话、前文、事实和实际能力审阅，没有再调用模型给自己打分。复测 3 组满足本样本核心要求、8 组需改、1 组不合格，**不能当总体正确率，更不是“真人感通过率”**。

### 2.4 这轮最重要的发现

1. 上下文有效，但数字、否定、对象仍会丢失；不能只验意图大类。
2. 引文都能找到，也可能把 6 人套餐与未归属的 3—4 人描述混用。引文存在不等于结论受支持。
3. 未知时仍会补“我帮您查／马上协调”，实际没有工具执行。
4. “当天现杀吗”即使明确标成未知，复测仍补出了“绝对没有隔夜货”“保证……最新鲜”等承诺。四层与 P0 已传入，不等于生成已经遵守。
5. 回答有时直接说“事实包”，或没有回应“链接一直跳”的不满，暴露了材料处理思路，没接住人在表达什么。

第 4 点是离线原型生成失败，没有测试生产最终句段处理和 TTS，因此不能写成“线上已播出违禁句”。

## 3. 新设计：把“怎么接这句话”与“知道什么”分开

现在需要两条独立判断，最后汇合成一次自然回应：

| 维度 | 要解决的问题 | 示例 |
| --- | --- | --- |
| 沟通任务 | 对方希望这句话被怎样回应？ | 感谢认可、回应质疑、承认不满、解释、澄清、接着聊、暂不回应 |
| 事实状态 | 回答涉及的具体主张有多少依据？ | 不依赖商品事实、已知、部分已知、未知、有矛盾 |

实际操作能力由程序另行提供，例如是否真的能查单、退款、通知门店，是否已经收到执行回执，不能让模型猜。

“这家真好吃”可以感谢；“主播还不睡”可以闲聊；“太贵了”需要回应价格感受。它们不一定需要新增商品事实。“相关但不知道答案”也不能被当成“不相关”直接丢弃。

因此，**不能拿 question=false、没有事实命中或没有现成目的编号，作为所有社交互动的淘汰条件**。无关刷屏、广告、重复口号仍按现有策略处理，不是所有字句都必须插播。

## 4. 怎样才有人味：先选一个真正有用的接话动作

### 4.1 先理解完整意思，不急着贴一个意图标签

至少保留本句原话、明确对象、数字条件、否定、同人前文和最新更正。允许一个主要沟通任务附带另一个诉求：

- “券只能一号用吗？链接一直跳”：既有券范围问题，也有操作不满。不能只介绍两个套餐。
- “南充第一中餐”：可能是认可。
- “你们是南充第一中餐吗”：是在问排名依据。
- “南充第一，等两个小时还没上菜”：是投诉或反讽，不能当夸奖感谢。
- “不是四个人，是六个”：要更新本次条件，不再沿用旧人数。

情绪判断只用于选择回应语气，不生成心理诊断，不把“贵”解释成对方穷或已经超预算。无法确定时保持中性，必要时澄清。

### 4.2 一个主要动作，最多一个必要追问

感谢、解释、回应不满、确认更正、澄清和延续话题，按当前需要选择。没有必要把每条都拼成“欢迎称呼＋评价问题＋介绍商品＋问一句＋点关注”。一句合适的感谢就能结束；问题已经答清楚也可以结束。

追问之前先判断：**用户补充这个信息后，是否真能让答案更有用？**

- 不知道用餐人数，问人数有用。
- 不知道能接受多辣，问口味有用，但不能因此凭空承诺能改辣度。
- 商家资料缺少领券金额，反复问用户选哪个链接通常补不了资料缺口。
- 投诉不一定适合当众索取订单或手机号；有真实售后路径时引导去该路径，不在公屏追问隐私。

### 4.3 允许普通接话，不把社交语言也关进事实库

| 表达类型 | 可以怎样说 | 边界 |
| --- | --- | --- |
| 感谢、普通关心、共情 | “谢谢你喜欢”“等这么久，确实影响吃饭” | 不需要商家事实逐字收录；不因此承认未知事故责任或补偿政策 |
| 接住用户自述 | 用户说吃过多次，可以回应“吃过好几回了呀” | 只是接住其自述，不升级成系统已核实订单、已确认老客 |
| 询问偏好、需求 | “你更在意口味，还是分量？” | 必须与当前选择有关，不每条机械二选一 |
| 主观感受、自然口语 | 按当前风格自然表达 | 不套成明确功效、认证、绝对排名或效果保证 |
| 客观主张、交易条件 | 按当前有效事实与条件说 | 用户夸“第一”不产生官方排名事实 |
| 实际动作与后续承诺 | 有能力且有相应执行状态时表达 | 没有执行就不说“已经催了”“正在查”“稍后回你” |
| 主播个人经历、观众身份 | 仅使用已确认且适用于当前角色的内容 | 不编“我刚吃过”“我刚下班”，不凭昵称叫表妹、老粉或推性别 |

普通建议也不应一刀切禁掉。“可以咨询门店”与“我已经替你联系门店”是两件事。具体入口、电话、营业状态和可办事项，要以真实配置为准；没有已核实入口，就别编指路。

### 4.4 称呼和节奏要服务这次对话

复用现有称呼计划，整段只决策一次；续聊可以省略称呼，不要求每条开头都喊“朋友／家人”。同人几秒内拆句先合并或更新未播任务，再决定是否回应，避免把两个半句分别播两遍。

“哈、呀、哎哟”只来自当前允许的主播风格与频率，不靠随机塞语气词制造真人感。不要硬塞错别字、假口吃或凭空的生活经历。重点是接对话、说重点、有自然停顿。

## 5. 把这些要求真正落到四层里

四层仍为“必说／可说／不提／改写”，所有实际模型任务继续带完整有效 P0。不要另加一段与四层互相冲突的厚重规则。

| 层 | 互动时装什么 |
| --- | --- |
| 必说 | 本次必须完成的沟通任务：答清问题、接住认可、回应不满、确认更正，或说明具体哪件事未确认。不是每次必须复读一句开场 |
| 可说 | 直接相关的有效事实，以及普通感谢、共情、基于用户自述的接话、真正有帮助的追问。无商品事实时也可以有社交内容 |
| 不提 | 本轮未知事项的肯定或否定推断、串人的信息、无依据身份和经历、未发生的动作、有效 P0 与当前表达禁区 |
| 改写 | 先回应当前这句话，口语短句；按称呼计划处理，不重复称呼；没有必要不追加追问、欢迎和购买引导 |

### 一个完整例子：用户问“鸭子是当天现杀的吗？”

假设本次只确认“每天制作”，没有确认宰杀时间，且没有查询工具：

- **必说**：直接回应宰杀时间尚未确认，不能把“每天制作”当成“当天宰杀”。
- **可说**：如有必要，可补充当前明确的制作事实；允许自然地说不确定，也允许只把未知说清楚后结束。
- **不提**：不推断当天杀或不是当天杀；不补“没有隔夜货”“保证新鲜”；不假称已查询、将代查或回访。
- **改写**：直接说具体未知，不说“事实包、字段、模型、数据库”。不强行把话题转回拍链接。

人工示例：“是不是当天现杀，这个我还没确认，不能随口答你。”

如果用户继续追问，再沿同一话题接着回应；只要没有新增信息，就不能为了换说法补出一个答案。多次同问是否播出，仍由聚合与频控决定。

## 6. 给 DeepSeek 看接话差异的人工示例

**以下是人工编写的设计示例，未调用模型验证，不是固定背诵模板，也不代表新增了任何商家事实。** 实际称呼、方言、长短按当前主播风格调整；不是要求逐条照抄。

| 弹幕 | 更合适的回应方向与示例 | 不要滑向哪里 |
| --- | --- | --- |
| 这是南充第一中餐 | 接住认可：“哎哟，这个评价高了，谢谢你这么认可！” | 不确认官方排名，不凭此认定来过店 |
| 你们真是南充第一吗 | 回答排名是否有依据：“这个排名我还没确认，不能这么给你保证。” | 不把未提供依据说成已经证实没有排名 |
| 南充第一，等两个小时没上菜 | 先回应等待：“等了两个小时还没上菜，这确实影响吃饭。你现在还在店里等吗？” | 不感谢“第一”，不说已经催菜；必要时再用真实服务路径 |
| 太贵了 | 接价格感受，可按语境追问：“你觉得这个价高了。你更在意总价，还是想看看里面都有些什么？” | 不先认定超预算，不训“这么多还嫌贵”，不自动降价 |
| 我妈吃不了辣 | 记住当事人偏好：“那辣度得留意。她是完全不吃辣，还是能接受一点点？” | 不凭此保证套餐能换口味，不猜健康情况 |
| 吃过好几次了，确实好吃 | “都吃过好几回了呀，谢谢你喜欢！”需要续聊时再问其喜欢哪道 | 不虚构订单，不每次加拍链接／关注 |
| 主播还不睡啊 | 当前确实在播时：“还在播呢。你是刚忙完，还是随便逛逛？”也可以只轻松接一句 | 不编自己困了、刚下班或已经吃饭 |
| 怎么一直说一样的 | 接受反馈：“听着重复了，是吧。你现在最想了解哪一点？” | 不假称系统已经调整；用户点出问题后还播同一套介绍 |
| 不是四个，是六个人 | “六个人，明白了。”随后只按六人及当前事实继续 | 不重复旧四人条件，不再问一次人数 |
| 有券吗？前文刚说过券 | 接着上一轮给已确认信息；只有已播回执能证明主播已经说过 | 不把生成未播的话当成观众已听见，不假称“刚不是讲过了” |
| 发个 1／重复活动口号 | 按实际活动与聚合规则决定是否简短回应或不单独播 | 不硬解释成购买、中奖、下单成功或商品咨询 |

这些示例的共同点是：回应对方这句话，保留分寸，允许自然结束。不是每一次都要解释边界，也不是每次都要往销售方向转。

## 7. 建议接入方式：小改链路，不另起一套播控

### 7.1 先由程序组装短期上下文

在当前事件前组装同人近期发言；如果要用主播历史，只能引用有实际送播状态依据的记录，生成稿与采纳稿不能当成对方已经听到。用户更正覆盖本次旧条件，切话题后旧人数、地点不自动沿用。

身份、事件顺序、场次和事实版本由程序绑定。模型可接收有角色与先后说明的必要文本，不负责回填 tenant/session/user/event/fact/product 的内部编号。不同观众默认隔离，跨场长期画像不作为本期前提。

同目录新出现的[用户事件 TTL 与保留策略](/E:/直播伴播/docs/2026-10-22-用户事件数据TTL与保留策略.md)记录了历史清理及 48 小时保留口径；这是另一任务的说明，本轮没有核验其生产执行。后续实现需对齐实际保留策略：原文过期就按缺上下文处理，不为接话恢复无限期归档。固定回归继续使用本次已脱敏实验材料，不依赖历史数据库永远存在。

### 7.2 生成前有一个简短的“本次怎么回应”内容结果

模型内容任务可返回：完整诉求、回应目的、已知答案内容、具体未知点、必要追问、口气建议。字段只描述语义内容，不带内部 ID 或事实关系表。

例如“太贵了”的结果应表达“回应价格顾虑；未获授权改价；可根据语境问总价还是内容”，而不是直接给一个“议价类”编号就结束。“鸭子现杀吗”的结果应保留“宰杀时间未知”，不能只返回“新鲜度问题”。

程序验证内容后组装四层，再生成一段完整短回应。**不建议照搬实验固定三次调用**；可以比较意图与回应计划合并的方案，也可让无需事实的社交回应走较轻的任务。两句两个气口可以在一段文本中完成，不必强制拆成两次模型请求。

若仍需兼容旧 purpose_id／fact_ids 协议，应在改造时一起调整母版、传输、解析、保存和消费方，由程序维护关联，不能在新模型任务中继续让模型复制内部编号。

### 7.3 缓存复用的是合适的内容，不是别人的处境

“太贵了”可以复用一般接话方式；“区别、再减点、还有吗”依赖对象与前文，不能仅凭原话命中上个人的结论。当前商品、事实条件、规则和上下文改变，相关判断与成品资格必须重新核对。

程序建立包含当前业务边界的缓存指纹。可复用通用意图或表达结构；人数、地址、称呼、订单状态、个人偏好及处理进度不能跨人搬运。已经播放过的重复回应还要受现有频控约束，不能为了复用反复播“谢谢认可”。

### 7.4 失败回退也要按任务区分

纯社交生成失败可暂不回应或使用合适的短回应；事实问题没答成，不能只播“问得好”就标记完成。投诉没有工具时仍可自然接话，但不能使用“马上处理”的兜底。

格式异常、语义不确定、事实未知、无工具、受频控和内容违规分开记录。后台显示真实中文原因，观众口播不出现内部字段或代码。原始返回仅在受控诊断中保留，遵守现有脱敏与保留期限。

新生成继续经过现有有效 P0 与最终文字处理；要验证真实调用链，不凭“传了 P0”就判为通过。接口成功、文字可用、TTS 成功、入队、Core 开始和完成播放仍分别记录。

## 9. 怎么验收“像人说话”，不能只看接口通过

先固定已有失败样本做回归，再补充没有用于调提示词的新样本。保留当前链路作为对照，在相同原话、上下文、有效事实、P0、模型设置下比较，不把新方案预期答案喂进去。

真人感评价与事实／P0 硬边界分别记录：

| 真人感维度 | 具体看什么 |
| --- | --- |
| 接对话 | 是在回应这一条，还是换个标题介绍商品；反讽有没有误当夸奖 |
| 续得上 | 拆句、更正、前后对象是否保留；有没有重复问刚回答过的事 |
| 态度合适 | 认可可感谢，投诉先回应不满；不机械“别着急”，不责怪用户 |
| 追问有用 | 问了以后是否能继续解决；允许不追问，未知商家资料不甩给观众 |
| 有分寸 | 不每段强行欢迎、点关注、推链接；能自然结束，无关刷屏可不播 |
| 表达自然 | 称呼、语气词、长短符合当前风格，不靠假经历和随机口头禅 |

建议让用户或运营在不知道哪套方案生成的情况下选择更合适的一条，并标明具体原因；不要只给模型一个“真人感 90 分”的自评分。现有 76 次测试没有完成这项盲评。

硬边界覆盖：数字／否定／商品对象、事实版本、未知点、串人、虚构动作、P0、格式失败回退。跨类目至少继续覆盖堂食、熟食电商和软件服务，不能在代码写“鸭子／南充／一号”特例。另覆盖同名不同人、缺身份、切方案、被屏蔽事件、事实更新、过期前文和同一问题重复发送。

先离线回放与只记录拟答的影子验证，再决定实播。新增模型、TTS 或生产改动是后续实施范围，本次未执行。听音时另外核对停顿、重音、语速和插入时机；文字自然不能证明声音自然。

## 10. 建议 DeepSeek 按这个顺序接手

1. **先查链路是否把可聊内容挡掉。** 分开社交、已知问答、相关未知和无关内容；处理空事实统一回退、只生成接住句却标完成、无工具的“马上处理”兜底。不能只加一句“说得自然”。
2. **补短期同人上下文及缓存边界。** 保留对象、数字、否定和更正；同人标识及事实归属由程序维护，不做长期画像前置条件。
3. **把回应目的写进四层，统一生成完整短回应。** 社交可不依赖商品事实；必要时答、谢、承认不满或追问，允许结束。沿用现有称呼计划和播控。
4. **做固定回归与独立真人感对照。** 失败样本先稳住，再看新弹幕、跨类目与耗时；不能用模型调用成功或 JSON 合法验收。
5. **列出具体文件改动和证据，再实施发布。** 本文没有修改授权范围内的业务代码，也不代表已测试通过可直接上线；先在协作登记领取文件，保护其它助手正在编辑的内容。
