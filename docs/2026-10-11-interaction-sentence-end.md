# 直播互动必须等待完整句末

用户报告网页和外接设备均发生主线未读完就切入互动，并明确要求修复、必须在一句话末切换。

## 已确认原因

第240场有三次无切点立即插播：北京时间22:10:33.276、22:16:32.492、22:26:20.067，对应决策104、113、126。
旧抢答选点排除整稿段尾；找不到点时仅将恢复位置设为整稿时长，没有指定实际切换位置。
Core因此立即停止主线，余音被跳过。恢复位置不能作为切换授权。
旧真实HTTP/PCM回放：最后一句3400ms，只输出20ms就接受了互动。

## 修改范围

- 普通互动和抢答都必须携带经当前音频时间轴核对的完整句末，包含最后一句的段尾。
- 没有点时返回既有409重排契约，管理服务保留已生成、已审核的声音，仅重新安排切点。没有新增模型调用。
- Core拒绝缺失切点、任意毫秒位置、已过期位置和不属于当前稿的切点。
- 物理PCM游标必须到达句末；等待超时不能授权提前切换。
- 选点与音频输出共享保留锁，在句末挡住下一句，避免等待线程调度延迟时下一句已经发声。
- 句末不与20ms输出帧边界重合时，保留本句全部采样、帧内剩余位置补静音；取消插播会恢复未播放的尾部采样。
- 已上线的6b58回归观察修复继续保留；没有改变互动频率、启动观察窗、模型、提示词、P0、事实、方案或业务策略。

## 验证

Core `go test ./...` 全套通过。
真实HTTP和本机PCM回放中，3400ms最后一句全部170/170帧输出后才切入；620ms短尾为31/31帧，920ms服务类目且hard_cut策略为46/46帧。
无句末返回409且主线不停止；缺失及任意中间切点拒绝；PCM停滞超时仍不切入。
600/615/999ms句末物理保留测试中，调度延迟80ms时下一句采样未泄漏；取消后全部尾部采样恢复。
食品、杯具和预约服务的音频回放均复用通用程序，没有品类特例或模型调用。
回放只到本机httptest，不向真实直播生成、注入或播放测试声音。
本机缺C编译器，未运行Go race检测；全套现有并发回放与本次实际HTTP/PCM测试通过。
