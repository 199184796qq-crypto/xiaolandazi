# 本地生活（团购）业务域方案 · 交给 codex 实现

> 状态：设计已定，待 codex 落地。范围：**先做「业务模式」入口**（电商 / 本地生活 二选一），团购的三张表（卖点维度/侧面映射/事实分类）作为第二期。
> 前置事实：现有系统已跑通「卖点×角度+侧面 → 四层结构话术 → 保存方案 → 直播间」全链路，且已有「品类自动判定 + 可手改」机制（`biz_domain` 的设计要完全对齐这套）。

---

## 一、目标

方案配置里加一个**业务模式**入口，用户二选一：

- **电商**（现有，默认）
- **本地生活**（团购/到店，新）

业务模式决定后续「卖点挖掘维度、侧面映射、事实分类、P0 补充清单」走哪一套。

---

## 二、入口位置（本次唯一 UI 改动）

在方案配置的**「商品资料 / 活动福利」之前**（即「事实与内容」分区的入口处，或配置流程最前面）加一个「业务模式」选择器：

```
业务模式   (●) 电商     ( ) 本地生活
```

- 默认「电商」。
- 单选，互斥。
- 位置：配置流程最前、早于「商品资料」「事实依据」这些 tab，让用户先定域、再填料。

参考现有实现：`web-console/src/components/PlanConfigurationNavigation.vue` 的 sections/tabs 结构，以及方案头部的 meta 区。入口的具体摆放（导航顶部新增一个 section，还是 facts 分区最前插入一个 tab）由 codex 按现有 UI 风格决定，但**必须早于商品/事实录入**。

---

## 三、后端字段

`management-service/internal/model/live_agent_plan.go` 的 `LiveAgentPlan` 加：

```go
BizDomain string `json:"biz_domain"`  // "ecommerce"（默认）| "local_service"
```

- 创建方案 `CreateLiveAgentPlanInput` 加 `BizDomain`，空值/非法值回退 `ecommerce`。
- 持久化到 `live_agent_plans`（或复用现有方案级 asset 存储，跟品类持久化 `live_agent_plan_product_category` 同一套套路，codex 自行选最贴近的方式，**不要新起不必要的大表**）。
- 提供 GET/PUT 接口：`/api/v1/live-agent-plans/{planID}/biz-domain`（PUT 校验取值，非法回 400），**完全对齐已有的 `product-category` 接口**。

---

## 四、切换业务模式触发什么（对齐品类机制）

1. **切换 biz_domain → 重挖卖点×角度**：复用现有「ExtractionPromptMD 变更检测」触发重挖（跟品类变更触发重挖是同一套）。
2. 切换时前端弹确认：「切换业务模式将按新域重新挖掘卖点×角度，已保存的卖点分级会重置。」
3. 默认电商，存量方案、老用户零感知。

---

## 五、业务模式决定哪几套表（第二期，本次先占位）

以下三张表 + P0 清单，按 `biz_domain` 分域选择。**本次入口只做开关 + 字段 + 持久化 + 接口，不实现团购表内容**；团购表内容作为第二期单独做，但入口要先预留 `biz_domain` 能流到卖点挖掘/侧面筛/事实分类的调用点。

### 5.1 卖点维度表

- 电商：`configs/prompts/anchor-style/category-selling-dimensions.md`（现有，11 品类 + 通用）
- 团购：新增 `category-selling-dimensions-local.md`（团购通用维度 + 团购类目专属维度）

团购通用维度（初稿，第二期细化）：
价格算账（团购价/人均/省多少）、套餐内容、地理位置、门店环境、服务体验、预约/使用、核销方式、口碑/评价、品质来源、场景适配、限时稀缺。

### 5.2 侧面映射表

- 电商：`fission_side.go` 现有 7 侧面（使用场景/过程细节/利益算账/对比参照/人群痛点/品质来源/使用方式）
- 团购：9 侧面（见下），新增「地理位置」「限时稀缺」，并重命名若干侧面

| 电商侧面 | 团购侧面 |
|---|---|
| 使用场景 | 到店场景（约会/聚餐/亲子/团建）|
| 过程细节 | 到店体验流程 |
| 利益算账 | 利益算账（保留）|
| 对比参照 | 对比参照（保留）|
| 人群痛点 | 团购痛点（排队久/贵/服务差/停车难/约不上）|
| 品质来源 | 口碑与来源 |
| 使用方式 | 预约核销方式 |
| — | ➕ 地理位置 |
| — | ➕ 限时稀缺 |

### 5.3 事实分类 category

团购新增 key（电商现有 flavor/craft/price/fulfillment… 保留，团购另加）：
`location`(位置) / `environment`(环境) / `service`(服务) / `appointment`(预约) / `validity`(有效期) / `redemption`(核销) / `per_capita`(人均) / `package`(套餐内容) / `reputation`(口碑)。

### 5.4 团购 P0 补充清单（第二期，P0 机制不变，只加团购专属违规词）

| 团购专属 P0 | 说明 |
|---|---|
| 无隐形消费 / 到店不加价 | 未确认不提 |
| 节假日通用 / 周末通用 | 未确认不提 |
| 过期可退 / 随时退 | 退款政策未确认不提 |
| 不限量 / 随时有位 | 限时稀缺反面，未确认不提 |

## 七、明确不做（防止 codex 跑偏）

1. 本次**不实现**团购三张表的内容，只做「业务模式入口 + biz_domain 字段 + 持久化 + GET/PUT 接口 + 切换触发重挖 + 前端二选一 UI」。
2. 不新增不必要的大表；优先对齐 `product-category` 的持久化方式。
3. 不改变现有电商链路行为——默认 `ecommerce`，存量方案无感。
4. 「业务域 ≠ 品类」：业务域决定用哪套表，品类决定挖哪些维度，两层独立，不要合并。

---

## 八、验收标准

1. 新建方案能选「电商 / 本地生活」，默认电商。
2. `biz_domain` 落库、可 GET/PUT、非法值回退/报错。
3. 切换业务模式触发重挖提示 + 重挖卖点。
4. 电商链路回归无破坏（存量方案、生成、保存、开播全部正常）。
5. `biz_domain` 能流到「卖点挖掘注入维度表」的调用点（为第二期团购表铺路，本次先用占位分支）。
