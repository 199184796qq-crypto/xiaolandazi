# 互动大 Token 调用排查：昵称规划，不是聚类（2026-10-28）

## 更正

早先记录把「每次约 9,700 token 的调用」归到了问题聚类。12:20 复核后更正：

- **问题聚类**（`question_cluster`）每 5 分钟才跑一次，系统提示词只有 122 字，token 不高；
- 真正的大头是**昵称称呼规划**（`interaction_addressing_plan`）：每个昵称单独一次调用，每次都重发整份称呼规则 + P0 硬禁清单（约 1.2 万字符 ≈ 9–10k token），输出上限 160 token。

证据：

1. 本场输出 token 分布：191 次恰好 160（`MaxTokens: 160`），聚类是 700 上限，不会卡在 160；
2. 昵称调用走 `nickname_plan.go:356 w.completePaidModel(...)`，直接调用、不进 `live_model_exchanges` 归档，所以按 stage 查不到；
3. `planNicknameAddresses` 的 system prompt = `p0-hard-block.md`(9,367 字符) + `interaction-nickname-addressing.md`(1,691) + `interaction-nickname-plan.md`(1,271)；
4. 注释写明「One nickname per call: failures never shift another person's alias」——为了失败隔离，一人一次。

## 影响

- 本场 12 分钟约 117 次、30 分钟约 191 次，每次 ~9.5k 输入 token，折合 15–18 万 token/分钟；
- 单次输出只占 160 token，成本几乎全在重复发送的规则文本；
- 计费此前还把这些调用记成 `qwen3.8-flash`（已修，见下文），所以看起来像聚类在烧。

## 聚类本身

- 触发：`Worker.Run` 每 5 分钟一次 `runCycle`，另有 `cmd/questioncluster-once` 手动跑；
- prompt：`question.cluster.system`（122 字）+ `buildModelInput` 的 JSON（全部 topics + 全部 samples + 最近 5 条问题）；
- 潜在问题：`buildModelInput` 遍历**全部** topics（不只 eligible），`SampleQuestions` 不截断；会话后期 topic 多时单次也会涨到几千 token，但频率低，不是主要成本。

## 修复建议（按收益排序）

1. **批量昵称**：一次调用处理 8–16 个昵称，prompt 只发一遍，token 直接降 8–16 倍；
2. **精简 mother**：昵称规划用不到整份 P0 硬禁清单，抽一份「称呼相关」的精简规则（目标 ≤1.5k token），或直接复用 `interaction-nickname-*` 两个文件、去掉 P0 全文；
3. **程序兜底**：常见昵称按规则生成（去符号、取前两字 + 朋友），模型只处理疑难名字；
4. **聚类侧**：`buildModelInput` 只送 eligible topics、samples 截断到 3 条，避免后期膨胀。

## 复现

```sql
-- 按输出 token 区分调用类型：160 = 昵称规划，700 上限 = 聚类
SELECT CAST(JSON_EXTRACT(request_json,'$.output_tokens') AS UNSIGNED) out_tok, COUNT(*) n
FROM live_cost_requests
WHERE room_id=29 AND kind='model' AND requested_at>='2026-10-28 03:35:00'
GROUP BY out_tok ORDER BY n DESC;
```
