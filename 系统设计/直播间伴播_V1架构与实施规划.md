# 直播间伴播 V1 架构与实施规划

> 重构日期：2026-09-22  
> 目标：先稳定跑通 1-20 个真实直播间，再逐步扩容。V1 的核心不是“让大模型一直在线说话”，而是建立一套低 Token、低延迟、可打断、可恢复、可追踪的直播 AI 伴播系统。  
> 核心闭环：**直播事件 → 事件引擎 → 监控 Agent 决策 → 场控 Agent/模板生成话术 → TTS/提词屏 → 终端执行 → 状态回流 → 自然恢复主线。**

---

# 1. 产品定位与核心原则

本项目不是单纯的 TTS 播放器，也不以“数字人形象”为核心，而是一套直播间 AI 销售伴播系统。

V1 必须同时解决五个问题：

1. 多直播间独立运行，不能串房、串话、串状态。
2. 绝大部分直播事件不能直接消耗大模型 Token。
3. AI 不能一直抢话，必须像真人场控一样知道什么时候说、什么时候闭嘴。
4. 任何互动都可以打断当前主线，但打断后必须自然恢复，不能半句话接半句话。
5. 所有决策、话术、TTS、播放、打断、恢复和成本都必须可追踪。

系统长期坚持以下原则：

- **一个监控 Agent 模板 + 一个场控 Agent 模板，可服务 N 个直播间。**
- 每个直播间拥有自己的 Room Runtime / Room State / 队列 / 短期上下文。
- **跨直播间并发，单直播间有序。**
- 系统状态是唯一事实源，Agent Session 不能作为唯一记忆。
- **所有事件都进入“监控体系”，但不是所有事件都调用大模型。**
- 规则、缓存、模板能解决的事情，优先 0 Token 解决。
- 监控 Agent 负责“要不要做、做什么”；场控 Agent 负责“具体怎么说”。
- Agent 不直接控制盒子，所有执行必须经过 Speech/Execution Engine。
- 主线、互动、逼单、欢迎等都统一抽象成 Action 和 Speech Task。
- 价格、规格、库存、优惠、发货、售后等关键事实必须由业务数据提供，禁止模型自由编造。
- 打断优先使用“句子/短语义段边界”，只有紧急场景才允许硬切。
- 主线可恢复；低价值欢迎、点赞、普通寒暄等过期后直接丢弃，不追着补播。

- 原来的“盒子播放”前面增加 **Execution Engine / Audio Focus**，专门处理抢占、等待和恢复。
- Agent 是系统能力之一，不是整个系统本身。

# 3. 两个 Agent 的职责边界

## 3.1 监控 Agent：只回答“现在要不要做什么”

监控 Agent 负责：

- 判断某个事件是否值得处理。
- 判断当前直播间最应该做什么。
- 判断是否需要欢迎、互动、讲品、逼单、提醒主播、保持安静。
- 在多个事件竞争时，选择优先动作。
- 根据销售阶段、在线人数、加购、成交、最近发言等状态做决策。
- 输出结构化 Action。

监控 Agent **不负责**：

- 写长篇话术。
- 直接调用 TTS。
- 直接控制设备。
- 保存直播间唯一状态。
- 自己维护整场直播的完整聊天历史。

监控 Agent 的输出必须短、结构化，不输出长解释。

示例：

~~~json
{
  "action": "WELCOME_USER",
  "priority": 4,
  "target_user_id": "u_1024",
  "channel": "VOICE",
  "generation_mode": "TEMPLATE_FIRST",
  "interrupt_policy": "NO_INTERRUPT",
  "ttl_ms": 5000,
  "reason_code": "RETURNING_USER_HIGH_VALUE"
}
~~~

不需要处理时：

~~~json
{
  "action": "NO_ACTION",
  "reason_code": "LOW_VALUE_EVENT"
}
~~~

## 3.2 场控 Agent：只回答“如果要做，具体怎么说”

场控 Agent 接收明确 Action 后，负责：

- 生成自然、口语化、适合当前商家风格的话术。
- 对用户问题进行简短回答。
- 对异议做自然销售表达。
- 生成欢迎、讲品、逼单、成交庆祝、冷场承接等文本。
- 根据 TTS 和提词屏渠道控制长度与表达方式。

场控 Agent **不负责**：

- 决定要不要说。
- 决定什么时候插话。
- 决定是否抢占另一条语音。
- 直接调用设备。
- 自由修改价格、库存、售后、发货等事实。

示例输入：

~~~json
{
  "action": "SALES_PUSH",
  "level": 1,
  "product_id": "p_001",
  "facts": {
    "price": "69",
    "shipping": "按下单顺序发货"
  },
  "style": "四川口语、自然、简短",
  "max_chars": 55
}
~~~

输出只要最终话术，不要输出分析过程。

# 4. 一个 Agent 模板，多直播间 Runtime

后台只维护：

~~~text
Monitor Agent Template
Control Agent Template
~~~

运行时：

~~~text
Room 001
├─ Monitor Runtime / Session
└─ Control Runtime / Session

Room 002
├─ Monitor Runtime / Session
└─ Control Runtime / Session

Room 003
├─ Monitor Runtime / Session
└─ Control Runtime / Session
~~~

原则：

- Agent 模板共享。
- Room State 不共享。
- Room Queue 不共享。
- 用户短期上下文不共享。
- 播放队列不共享。
- Token/TTS 计量不共享。

并发模型：

~~~text
直播间 A ─┐
直播间 B ─┼─→ 可以同时请求 Agent
直播间 C ─┘

但单个直播间内部：
Event → Decision → SpeechTask → Playback
必须有序仲裁
~~~

**跨房间并发，单房间有序。**

V1 可以先使用单服务 + Redis 完成；真正达到大规模后再拆分 Room Worker / 分布式队列。

Agent Session 不是直播间唯一记忆。直播间核心状态必须由我们自己保存。

建议 Room State 至少包含：

~~~json
{

  "runtime_status": "LIVE",
  "room_context_version": 108,
  "product_context_version": 16,

  "current_product_id": "p_001",

  "main_block_id": "A4",
  "main_sentence_index": 2,

  "online_count": 86,
  "recent_enter_count": 18,
  "recent_comment_count": 9,
  "recent_add_cart_count": 12,

  "anchor_speaking": false,
  "tts_state": "PLAYING",
  "current_speech_task_id": "sp_10086",

  "last_ai_spoken_at": 0,
  "last_sales_push_at": 0,
  "last_welcome_at": 0,
  "last_price_mention_at": 0,
  "last_after_sale_mention_at": 0,

  "recent_semantic_tags": [
    "PRODUCT_VALUE",
    "USE_SCENE",
    "PRICE"
  ],
  "recent_text_hashes": [],

  "pending_events": [],
  "pending_actions": [],
  "resume_point": null,

  "token_budget": {
    "hour_limit": 0,
    "used": 0
  },

~~~

Room State 必须回答：

1. 当前直播间在什么阶段。
2. 当前商品是什么。

6. 当前 TTS 是否正在播放。
7. 当前播放任务能不能被打断。
8. 被打断后应该从哪里恢复。
9. 当前事件是否已经过期。
10. 当前房间这一小时用了多少 Agent Token 和 TTS。

# 6. Event Engine：Token 优化的第一道门

这里是控制 Token 成本最重要的一层。

**所有原始事件都进入 Event Engine，但绝大多数原始事件不应该直接调用 Agent。**

## 6.1 标准 RoomEvent

建议统一事件类型：

~~~text
USER_ENTER
COMMENT
LIKE
FOLLOW
ADD_CART
ORDER_CREATED
ORDER_PAID
ONLINE_COUNT_CHANGED
PRODUCT_CHANGED
ANCHOR_SPEAKING_CHANGED
TTS_FINISHED
TTS_INTERRUPTED
TIMER_SALES_PUSH_DUE
TIMER_COLD_ROOM
DEVICE_OFFLINE
DEVICE_ONLINE
MANUAL_COMMAND
~~~

直播平台适配器只负责转成 RoomEvent，后续逻辑不关心平台来源。

## 6.2 去重

例如：

- 同一用户短时间重复进入：合并。
- 同一用户连续发送相同内容：合并。
- 多人连续问“多少钱”：归并为 PRICE_QUERY 热点。
- 点赞不按每次点击上报到 Agent。

## 6.3 聚合

进房：

~~~text
5 秒内进入 18 人
其中新用户 15
回访用户 3
高价值用户 1
~~~

不需要调用 18 次 Agent，而是形成一个聚合事件，或只对高价值用户生成单独事件。

点赞：

~~~text
5-10 秒窗口累计
达到阈值才生成 LIKE_MILESTONE
~~~

在线人数：

只有跨越关键阈值或趋势明显变化时才形成决策事件。

## 6.4 冷却

每种 Action 都有 cooldown：

~~~text
WELCOME_GROUP
SALES_PUSH
FOLLOW_REMINDER
LIKE_REMINDER
COUPON_REMINDER
COLD_ROOM_CHAT
~~~

冷却期内再次出现同类事件，直接抑制或合并。

## 6.5 TTL

事件和语音任务必须有有效期。

建议思想：

- 欢迎：非常短，过期就不要补。
- 点赞感谢：短。
- 普通互动：短。
- 明确用户问题：相对长一些。
- 主线内容：由阶段和商品上下文决定，不靠固定短 TTL。
- 商品切换后，旧商品所有待播内容直接失效。

具体秒数做成后台配置，不写死在代码里。

# 7. “所有事件监控”不等于“所有事件调用大模型”

从产品逻辑看，可以认为所有事件都由“监控 Agent 系统”接管。

但内部必须分两条路径。

## 7.1 0 Token 快路径

以下事情优先由规则直接决策：

- 点赞未达阈值 → NO_ACTION。
- 普通低价值进房 → NO_ACTION。
- 欢迎冷却期内 → NO_ACTION。
- 已有相同 FAQ 正在回答 → 合并。
- 直播刚刚逼单过 → 不再次逼单。
- 主播正在讲话 → 低优先级语音先等待。
- 当前商品已切换 → 旧任务丢弃。
- FAQ 精确命中并且策略明确 → 直接产生 ANSWER action。
- 当前主线正常、无有效事件 → 继续主线。
- 设备离线 → 禁止生成需要播放的任务。

这些路径全部可以 0 Token。

## 7.2 需要 Monitor Agent 的情况

只有出现以下情况才调用监控模型：

- 评论意图不明确。
- 同时出现多个高价值事件，需要判断先后。
- 当前数据是否应该进入逼单阶段无法由简单规则决定。
- 用户明显有购买意图但表达复杂。
- 当前房间气氛、销售阶段和最近话术需要综合判断。
- 异常事件需要结合上下文判断。

Monitor Agent 的输入不要带整场聊天记录，只发送 **Compact Room Snapshot**。

例如：

~~~json
{
  "event": {
    "type": "COMMENT",
    "text": "这个我给家里老人吃合适不"
  },
  "room": {
    "stage": "VALUE_BUILDING",
    "online": 86,
    "last_ai_speech_sec": 18,
    "last_push_sec": 210
  },
  "product": {
    "id": "p_001",
    "category": "食品"
  },
  "recent": {
    "last_semantic_tags": ["TASTE", "PRICE"],
    "active_user_turns": 1
  }
}
~~~

不要发送：

- 整场弹幕。
- 整场 Agent 对话。
- 整个商品知识库。
- 所有订单。
- 所有用户资料。

# 8. Token 最小化架构

Token 优化不是后期做，而是 V1 结构的一部分。

## 8.1 四道 Token Gate

~~~text
Gate 1：原始事件过滤
       ↓
大量事件 0 Token

Gate 2：规则决策
       ↓
可确定 Action 的事件 0 Token

Gate 3：模板/FAQ/缓存生成话术
       ↓
可直接生成文本的 Action 0 Token

Gate 4：只把真正复杂问题交给 Agent
~~~

目标不是“模型更便宜”，而是先减少模型被调用的次数。

## 8.2 Agent 输入只给最小上下文

Monitor Agent 只需要：

- 当前事件。
- 当前销售阶段。
- 当前商品 ID/必要标签。
- 少量近期统计。
- 最近几个语义标签。
- 当前是否正在讲话。
- 必要用户短期上下文。

Control Agent 只需要：

- Action。
- 当前商品相关事实。
- 当前用户问题。
- 商家风格。
- 最近少量已讲话术摘要/哈希。
- 最大字数。

## 8.3 不使用无限增长的 Session 历史

原则：

> Session 是临时推理上下文，不是永久记忆库。

建议：

- Room State 放 Redis。
- 商品事实放业务数据库。
- 用户短期对话单独保存，TTL 到期自动清理。
- Agent Session 可在商品切换、上下文过长、一定时间后轮换。
- 新 Session 只重新注入 Compact Room Snapshot，不重新塞入历史全文。

## 8.4 用户短期上下文只保留必要轮次

例如：

~~~text
用户：这个辣不辣？
AI：微辣口感……
用户：老人能吃吗？
~~~

第二句需要知道上一句对应同一个用户和当前商品。

但没有必要把 20 分钟前其他用户的评论也一起发给模型。

建议使用：

~~~text
room_id + user_id
→ short_context
→ TTL 1-3 分钟
→ 只保留最近少量有效轮次
~~~

实际轮次和 TTL 做配置。

## 8.5 商品知识按需取

用户问价格：

只给：

~~~text
price
promotion
shipping
~~~

用户问保质期：

只给：

~~~text
shelf_life
storage
production
~~~

禁止每次把整份商品资料塞进 Prompt。

## 8.6 输出强约束

Monitor Agent：

- JSON Schema。
- 不输出长分析。
- 不输出思维过程。
- reason_code 使用固定枚举。
- output token 上限很小。

Control Agent：

- 只输出最终口语话术。
- 按 Action 设置 max_chars。
- 不输出解释。

## 8.7 三级模型路由

不要所有请求都用同一种大模型。

~~~text
monitor_fast
→ 快、便宜，用于意图/动作判断

control_standard
→ 常规口语生成

control_strong
→ 复杂异议、复杂销售问题才升级
~~~

模型名称做配置，不把业务逻辑绑死在单一供应商或单一模型上。

## 8.8 决策缓存与话术缓存

可以增加：

~~~text
decision_cache_key =
product_id + sales_stage + normalized_event + key_state_bucket

text_cache_key =
product_id + action + persona + normalized_slots

tts_cache_key =
normalized_text + voice_id + speed + emotion
~~~

同样的高频事件不重复调用模型。

## 8.9 每房间 Token Budget

每个房间实时统计：

~~~text
monitor_input_tokens
monitor_output_tokens
control_input_tokens
control_output_tokens
cache_hit_count
rule_fast_path_count
agent_call_count
tts_chars
~~~

当单房间小时预算逼近上限时：

1. 降低低优先级 Agent 调用。
2. 提高模板/缓存优先级。
3. 降低欢迎、普通互动生成频率。
4. 复杂问题仍保留正常能力。
5. 预算策略只影响低价值动作，不影响关键用户问题和风险事件。

## 8.10 V1 Token 目标

阶段目标：

- 大部分原始事件走 0 Token 快路径。
- 进房、点赞、在线人数波动等高频事件原则上不逐条调用大模型。
- 高频 FAQ 优先模板/缓存。
- 只有真正需要判断或自然表达时才调用 Agent。
- 后台必须能看到“每直播间每小时 Token”和“每类事件平均 Token”。

不要只看模型单价，必须看：

> 每直播间每小时总 AI 成本。

# 9. 主线与互动双通道

## 9.1 主线通道

主线不建议自由生成长文，而是使用销售语义块。

V1 建议：

~~~text
A1 开场承接
A2 用户痛点
A3 使用场景
A4 产品价值
A5 差异对比
A6 价格塑造
A7 售后保障
A8 福利提醒
A9 温和逼单
A10 新一轮变体
~~~

每个块：

- 多个文本变体。
- 高频版本提前生成音频。
- 拆成多个完整短句/短语义段。
- 记录 semantic_tag。
- 有进入条件和退出条件。
- 不无限重复同一个块。

主线推进主要由系统状态机负责，不需要每一句都问 Agent“下一句说什么”。

## 9.2 互动通道

建议 Intent：

~~~text
PRICE_QUERY
PRICE_OBJECTION
QUALITY_QUERY
EFFECT_QUERY
AFTER_SALE
SPEC_QUERY
HOW_TO_USE
BUY_INTENT
NEGATIVE
GENERAL_CHAT
SHIPPING_QUERY
STOCK_QUERY
PROMOTION_QUERY
~~~

处理顺序：

~~~text
Comment
→ 本地/轻量 Intent 识别
→ FAQ/模板是否能直接回答
→ 必要时 Monitor Agent
→ Action
→ 场控文本
→ Speech Task
~~~

互动插入主线，但不污染主线状态。

# 10. 销售状态机与“什么时候逼单”

不要让 Monitor Agent 每隔几秒“看一下要不要逼单”，这样浪费 Token。

系统先计算指标：

~~~text
当前阶段
进入阶段时长
在线人数
商品点击
加购
订单
最近成交时间
最近逼单时间
最近互动数量
主播/AI 最近讲话
~~~

只有达到条件时，系统才生成：

~~~text
TIMER_SALES_PUSH_DUE
~~~

然后 Monitor Agent 再判断：

~~~text
现在是否真的适合逼单？
逼单等级是多少？
是语音还是提词屏提醒主播？
~~~

建议逼单分级：

~~~text
LEVEL 1：轻提醒
LEVEL 2：明确促单
LEVEL 3：阶段收口
~~~

Monitor Agent 决定 Action，不直接写话术。

# 11. 更自然的关键：不是“说得像人”，而是“行为像人”

自然度需要从系统层解决，而不是只靠 Prompt。

## 11.1 不欢迎每个人

普通进房默认不逐个欢迎。

优先欢迎：

- 回访用户。
- 高价值用户。
- 有历史互动用户。
- 重要客户。
- 明确触发规则的用户。

大量普通进房使用聚合欢迎，或者完全不说。

## 11.2 AI 必须有“沉默能力”

维护：

~~~text
last_ai_spoken_at
continuous_talk_seconds
silence_window
speech_density
~~~

避免：

- 一直说。
- 每条弹幕都抢答。
- 刚说完逼单，马上又逼单。
- 主播讲话时 AI 继续插嘴。

## 11.3 话术长度要按场景限制

例如：

- 欢迎：一句。
- 价格回答：一句到两句。
- 普通 FAQ：短。
- 异议处理：可以稍长。
- 逼单：短促。
- 冷场：一到两句。
- 主线：短句连续推进。

TTS 场景里，短句比长段落更容易自然打断和恢复。

## 11.4 最近话术去重

保存：

~~~text
recent_semantic_tags
recent_text_hashes
recent_opening_patterns
~~~

生成新话术前检查：

- 是否刚说过同一语义。
- 是否连续多次用相同开头。
- 是否连续多次称呼“家人们/叔叔阿姨”等同一称谓。
- 是否重复价格/售后。

能用规则判定就不要再调用模型。

## 11.5 商家 Persona

每个直播间/商家可以配置：

~~~text
语言风格
方言倾向
称呼习惯
语速
一句话最大长度
禁用词
敏感词
是否主动欢迎
是否允许强逼单
是否允许自动语音
是否只显示提词
~~~

场控 Agent 只在这个边界内自然表达。

## 11.6 人类主播优先

如果能从 PC/盒子获取 VAD 或主播讲话状态，则维护：

~~~text
anchor_speaking = true/false
~~~

当主播正在讲话：

- P4/P5 低优先级语音等待或丢弃。
- 用户问题可以先显示提词屏。
- 高优先级语音等主播自然停顿再播。
- 真正紧急的系统事件才允许强提醒。

即使第一版没有完整音频 VAD，也要把字段和接口先预留。

## 11.7 语音与提词屏不是二选一

Action 可以指定：

~~~text
VOICE
PROMPTER
BOTH
SILENT
~~~

例如：

- 普通用户问题 → VOICE。
- 主播正在讲品但需要提醒逼单 → PROMPTER。
- 重要风险 → BOTH。
- 数据异常但无需现场表达 → SILENT + 后台提示。

这样会比所有事情都 TTS 自然很多。

# 12. 事件优先级不能只靠一个数字

基础优先级仍保留：

~~~text
P0 风险/人工停止/强购买或关键成交事件
P1 明确商品问题
P2 用户异议
P3 销售动作/普通互动
P4 新用户欢迎
P5 点赞关注
P6 无事件，继续主线
~~~

但“优先级高”不等于“任何时候都硬切”。

需要 Preemption Policy：

~~~text
HARD_INTERRUPT
SOFT_INTERRUPT
QUEUE
COALESCE
DROP_IF_BUSY
PROMPTER_ONLY_WHEN_BUSY
~~~

例如：

| 新事件 | 当前主线 | 当前欢迎 | 当前逼单 | 当前用户问答 |
|---|---|---|---|---|
| 风险/人工停止 | HARD | HARD | HARD | HARD |
| 明确用户问题 | SOFT | SOFT | SOFT | QUEUE |
| 用户异议 | SOFT | SOFT | SOFT | QUEUE |
| 成交/强购买 | SOFT | SOFT | SOFT/合并 | 通常 QUEUE |
| 逼单 | 可替换主线 | DROP/QUEUE | COALESCE | QUEUE |
| 欢迎 | QUEUE/DROP | COALESCE | DROP | DROP |
| 点赞关注 | DROP_IF_BUSY | DROP | DROP | DROP |

最终矩阵做成配置表，不能把所有逻辑写死在 Agent Prompt。

# 13. 打断：优先“软打断”，减少生硬切音

## 13.1 为什么不能只做 stop_now

如果每次有弹幕都直接停止当前音频：

~~~text
“我们这个鸭子最大的特点就是——”
[突然停止]
“张姐问多少钱……”
~~~

听起来非常机械。

所以建议两类打断。

### 软打断 SOFT_INTERRUPT

流程：

~~~text
高优先级事件到达
      ↓
标记 interrupt_pending
      ↓
当前短句/短语义段播完
      ↓
暂停后续主线
      ↓
播放互动
~~~

要求主线音频必须拆成短句或短语义段。

### 硬打断 HARD_INTERRUPT

只用于：

- 人工停止。
- 风险话术。
- 严重错误内容。
- 设备异常。
- 明确需要立刻停止的控制命令。

直接 stop_now。

## 13.2 TTS 切成短 Segment

一个 Speech Task 不要生成 20-30 秒不可分割的大音频。

建议：

~~~text
SpeechTask
├─ Segment 1
├─ Segment 2
├─ Segment 3
└─ Segment 4
~~~

每个 Segment 是完整短句或短语义单位。

这样：

- 更容易软打断。
- 更容易取消后续未播段。
- 更容易自然恢复。
- 减少已经生成但完全没机会播放的长音频。

# 14. Audio Focus：所有“谁先说”都在这里解决

每个直播间只有一个 Audio Focus Manager。

状态示例：

~~~text
IDLE
PLAYING_MAIN
PLAYING_INTERACTION
PLAYING_SALES_PUSH
INTERRUPT_PENDING
INTERRUPTED
RECOVERING
PAUSED_BY_HUMAN
~~~

任何 Agent 都不能绕过它直接播放。

SpeechTask 必须带：

~~~json
{
  "task_id": "sp_10086",
  "room_id": "room_001",
  "action": "ANSWER_COMMENT",
  "priority": 1,
  "channel": "VOICE",
  "interrupt_policy": "SOFT_INTERRUPT",
  "resume_policy": "RESUME_MAIN",
  "interruptible": true,
  "expires_at": 0,
  "room_context_version": 108,
  "product_context_version": 16,
  "segments": []
}
~~~

执行前再次检查：

1. 任务有没有过期。
2. 商品有没有切换。
3. Room Context Version 是否仍有效。
4. 当前是否有人类主播讲话。
5. 当前是否已有更高优先级任务。
6. 设备是否在线。
7. 当前文本是否已经播过。

这一步可以拦住大量“迟到话术”。

# 15. 恢复机制：不是续音频，而是恢复语义

## 15.1 主线 Resume Point

主线被打断时记录：

~~~json
{
  "block_id": "A4",
  "sentence_index": 2,
  "segment_index": 1,
  "sales_stage": "VALUE_BUILDING",
  "product_id": "p_001",
  "product_context_version": 16,
  "room_context_version": 108,
  "interrupted_at": 0
}
~~~

## 15.2 恢复前重新判断

互动结束后不能无脑恢复。

执行：

~~~text
互动完成
  ↓
检查商品是否变化
  ↓
检查销售阶段是否变化
  ↓
检查是否又出现高优先级事件
  ↓
检查打断持续时间
  ↓
选择恢复策略
~~~

## 15.3 三种恢复策略

### A. 短打断：直接继续下一完整句

例如只回答了一个很短的问题。

~~~text
主线 A4 第2句
→ 被打断
→ 回答用户
→ 从 A4 第3句继续
~~~

绝不从“半句话”继续。

### B. 中等打断：加一句桥接语再继续

例如互动持续了一会儿。

~~~text
“好，刚才这个问题给大家说清楚了，我们接着看这个产品本身……”
~~~

桥接语优先使用模板，不需要每次再调用大模型。

### C. 长打断或上下文已变化：放弃原断点，重新规划主线

例如：

- 已经切商品。
- 已进入逼单阶段。
- 连续多个互动。
- 打断时间较长。
- 原内容已经不合时宜。

此时直接选择新的销售语义块，不强行回 A4。

具体短/中/长时间阈值做成配置。

# 16. 哪些任务可以恢复，哪些不能恢复

建议：

| Speech 类型 | 被打断后处理 |
|---|---|
| MAIN 主线 | 可恢复 |
| PRODUCT_INTRO | 视上下文恢复或重规划 |
| ANSWER_COMMENT | 一般作为原子任务；被更高事件打断后视 TTL 重答/放弃 |
| SALES_PUSH | 不做长时间恢复，过期后重新判断是否还需要逼单 |
| WELCOME | 不恢复，过期直接丢 |
| LIKE/FOLLOW THANKS | 不恢复 |
| COLD_ROOM_CHAT | 不恢复 |
| ORDER_CELEBRATE | 短 TTL，过期不补 |
| RISK_WARNING | 高优先级立即执行 |
| HUMAN_COMMAND | 最高控制权 |

原则：

> **真正值得恢复的是销售主线，不是所有被打断的话。**

这样系统才不会出现“几分钟后突然补一句欢迎张哥”的机械行为。

# 17. 多次连续打断

不要形成无限恢复栈。

建议：

~~~text
主线
  ↓
互动 A
  ↓
又来互动 B
~~~

处理：

- 主线 Resume Point 只保留一份。
- 互动 A 默认不再建立第二层永久恢复栈。
- B 优先级更高时，A 可结束、重答或排队。
- 高价值问答可保留短期 Pending Interaction。
- 低价值互动直接丢弃。

Resume Stack V1 最大深度建议非常小，避免状态爆炸。

# 18. 场控话术生成的成本优先级

产生 Action 后，不要立刻调用 Control Agent。

依次走：

~~~text
1. 已有音频缓存？
   ↓ 否
2. 已有文本缓存？
   ↓ 否
3. 固定模板 + 变量能生成？
   ↓ 否
4. FAQ 标准回答能生成？
   ↓ 否
5. Control Agent
~~~

例如：

~~~text
WELCOME_GROUP
ORDER_CELEBRATE
FOLLOW_REMINDER
LIKE_REMINDER
基础价格回答
基础发货回答
常规售后回答
~~~

大量场景可以不调用 Control Agent。

只有：

- 用户问题明显个性化。
- 用户异议复杂。
- 需要结合当前上下文自然承接。
- 需要生成不同风格变体。

才真正走模型生成。

# 19. TTS 与音频成本架构

## 19.1 离线音频优先

提前生成：

- 主线销售语义块。
- 高频 FAQ。
- 高频售后。
- 常用欢迎。
- 常用逼单。
- 常用成交庆祝。
- 常用桥接语。

每个语义块准备多个变体，避免机械重复。

## 19.2 实时 TTS 只用于动态部分

例如：

- 用户昵称。
- 个性化问题。
- 动态价格/库存/订单变量。
- 非标准 FAQ。
- 个性化异议处理。

## 19.3 TTS 前必须做最后有效性检查

流程：

~~~text
文本准备完成
   ↓
SpeechTask 仍有效？
   ↓
商品仍一致？
   ↓
事件没有过期？
   ↓
才调用 TTS
~~~

避免已经过期的任务还产生 TTS 成本。

## 19.4 TTS 缓存

建议：

~~~text
normalized_text
+ voice_id
+ speed
+ emotion
+ tts_engine_version
~~~

命中后直接复用音频。

## 19.5 成本指标

至少统计：

~~~text
单直播间每小时新增实时 TTS 字符
单直播间每小时 TTS 调用次数
TTS 缓存命中率
未播放就过期的 TTS 数量
因打断浪费的实时 TTS 字符
~~~

目标仍然是尽量让大部分主线和高频内容走离线/缓存，把实时 TTS 留给真正动态内容。

# 20. 更自然的播放节奏

Execution Engine 增加 Rhythm Controller。

可配置：

~~~text
min_gap_between_ai_speech
max_continuous_ai_speech
preferred_sentence_length
post_interaction_pause
post_order_pause
welcome_cooldown
sales_push_cooldown
~~~

原则：

- AI 说完不要立刻又接下一句。
- 用户问题回答完留一个自然停顿。
- 多个事件不要像机器播报一样连续串成通知列表。
- 同类问题聚合回答。
- 逼单之间保持间隔。
- 主播讲话优先。
- 重要问题可以先提词屏、后语音。

这些节奏参数全部配置化。

# 22. 单房间 Actor / Mailbox 模型

为了避免同一房间状态竞争，建议逻辑上每个房间只有一个事件处理入口。

~~~text
RoomEvent
   ↓
Room Mailbox
   ↓
Room Worker
   ↓
更新 Room State
   ↓
产生 Action
   ↓
产生 SpeechTask
~~~

跨房间：

~~~text
Room A Worker ─┐
Room B Worker ─┼→ 并发
Room C Worker ─┘
~~~

单房间：

~~~text
Event 1
Event 2
Event 3
   ↓
同一个 Room Mailbox 有序消费
~~~

这样可以避免：

- 同一个房间同时触发两次逼单。
- 两个 Agent 同时修改 Room State。
- TTS 抢话。
- Session 上下文乱序。

# 23. Agent Session 策略

每个房间可以拥有：

~~~text
monitor_session_id
control_session_id
~~~

但设计上不依赖 Session 保存完整直播状态。

需要支持：

~~~text
session_epoch
session_started_at
session_token_estimate
session_last_active_at
~~~

以下情况可以轮换新 Session：

- 商品切换。
- 上下文过长。
- 直播阶段发生大变化。
- Session 长时间不活跃。
- Agent 服务重连。
- 配置版本更新。

新 Session 从 Room State 注入最小 Compact Snapshot 即可恢复。

# 34. 最终设计结论

这套 V1 的核心不是“两个 Agent 一直在工作”，而是：

~~~text
系统一直在监听
↓
规则先过滤
↓
真正需要判断时 Monitor Agent 才工作
↓
真正需要自然生成时 Control Agent 才工作
↓
真正需要说话时才 TTS
↓
真正适合播的时候 Execution Engine 才下发终端
~~~

因此最终结构可以概括为：

> **事件驱动、规则优先、Agent 按需、状态外置、跨房并发、单房有序、短句播放、软打断优先、语义恢复、过期即丢、全链路计量。**

这也是后续降低 Token、降低 TTS 成本、提高自然度和稳定性的核心基础。

# 36. 2026-09-22 模型直调与成本基线

## 36.1 实测结论

百炼 Agent 应用形态在关闭思考后，Monitor 单次测试仍约 13 秒，不能进入直播实时主链路；同一 Qwen3.8-Flash 在模型体验中关闭思考后，Monitor 与 Control 均可近实时返回，且测试输出正确。

因此正式实现调整为：保留 Monitor / Control 两个逻辑角色，但不依赖百炼 Agent 应用外壳。主链路采用“本地规则引擎 + Qwen3.8-Flash 直接 API”。

```text
第三方公屏
→ Event Adapter
→ 本地规则/FAQ/模板快速路径
→ 必要时 Monitor Model API
→ Action
→ Compliance Pre-Check
→ Template/FAQ 优先
→ 必要时 Control Model API
→ Compliance Post-Check
→ TTS
```

Monitor 与 Control 默认关闭思考；工具、MCP、联网均不进入主链路。Monitor 正式 API 使用固定 JSON Schema；Control 只接收本次必要 facts、persona 与合规约束。

## 36.2 两角色职责

- Monitor：只做动作、优先级、通道、生成模式、事实字段需求的快速决策；不生成直播话术。
- Control：只把允许使用的 facts 组织成自然短话术；不决定是否发言，不补充 facts 之外的事实。
- Compliance Engine：系统组件，不新增第三个 Agent；负责国家、平台、行业、客户规则的前置约束与播出前复检。

## 36.3 Qwen3.8-Flash 当前价格基线

华北2（北京）公开原价：输入 0.8 元/百万 tokens，输出 2.7 元/百万 tokens，缓存命中输入 0.1 元/百万 tokens。官方说明该价格不含限时优惠，实际以百炼控制台为准。

成本公式：

```text
单次成本 = 输入Token × 0.8 / 1,000,000
         + 输出Token × 2.7 / 1,000,000
```

示例预算（仅作为容量规划假设，正式上线以真实埋点计量）：

- Monitor：若单次输入约 400 tokens、输出约 80 tokens，约 0.000536 元/次；1 万次约 5.36 元。
- Control：若单次输入约 500 tokens、输出约 50 tokens，约 0.000535 元/次；1 万次约 5.35 元。
- 若 1 万个复杂事件每次都同时调用 Monitor + Control，按上述假设约 10.71 元；实际系统因规则、FAQ、模板会拦截大量请求，真实成本应更低。

成本优化原则：规则优先、FAQ/模板优先、仅按需取 fact_keys、关闭思考、短输出、静态提示词尽量利用上下文缓存，并按直播间/客户记录真实 input_tokens、output_tokens、cache_hit_tokens 与模型费用。

# 37. 实时监控与回复 Redis 留痕

正式 Monitor Runtime 必须把“收到什么、怎么判断、最后说了什么”写入 Redis，测试网页只负责查看，不参与监控链路。

## 37.1 保留策略

- 现有公屏原始事件继续使用 `livecompanion:room:{roomID}:events`，当前代码 TTL 为 24 小时。
- 新增 AI 处理轨迹 `livecompanion:room:{roomID}:ai_trace`。
- `ai_trace` 默认保留 7 天，TTL 必须做成配置项，例如 `AI_TRACE_TTL_HOURS=168`。
- 每个房间同时设置最大保留条数，防止高流量房间无限增长；建议初始值 10000 条，可配置。
- Redis 只保存短期热数据和调试追踪；后续需要长期财务/账单/审计的数据再汇总落数据库，不能只依赖 Redis。

## 37.2 AI Trace 记录内容

每个真实公屏事件进入 Monitor Runtime 后生成 `trace_id`，至少记录：

- tenant_id / room_id / event_id / trace_id
- 原始事件类型、用户显示名是否可见、原始公屏文本
- Monitor 路径：RULE / MONITOR_MODEL
- Monitor 决策：action、priority、interrupt_policy、channel、generation_mode、fact_keys、reason_code
- Control 路径：TEMPLATE / FAQ / CACHE / CONTROL_MODEL / NONE
- 最终回复文字
- Compliance Pre/Post 结果及命中的 policy version
- Monitor / Control / total latency
- input_tokens / output_tokens / cache_tokens
- 单次模型费用估算
- created_at / completed_at / status / error

同一 `trace_id` 允许按阶段追加记录，便于重放完整链路。

## 37.3 Redis 数据结构

优先使用 Redis Stream：

```text
livecompanion:room:{roomID}:ai_trace
```

阶段示例：

```text
XADD ... stage=monitor_decision trace_id=... event_id=... action=ANSWER_COMMENT ...
XADD ... stage=control_reply   trace_id=... reply_text=... total_ms=... cost_cny=...
```

每次追加后执行长度裁剪并刷新 TTL。测试页面和运维页面只读取该 Stream；即使页面关闭，后台 Monitor Runtime 仍持续监控并留痕。

## 37.4 测试验收

真实直播间测试时必须同时验证：

1. 公屏真实事件进入系统；
2. Monitor 决策被写入 Redis；
3. 最终回复文字被写入 Redis；
4. 网页刷新或关闭后重新打开，最近记录仍可查询；
5. 同一个 event_id / trace_id 能串起原始事件、Monitor 决策和最终回复；
6. Token、耗时、费用能够按房间和小时汇总，为 1.5 元/直播间·小时硬上限提供数据基础。

# 38. 直播节奏优先调度与高频问题治理

## 38.1 核心原则

除人工强制、合规风险、设备/系统安全类硬中断外，**直播间自己的主线节奏是最高调度优先级**。

用户提问不是“来了就回答”，Monitor 产生的 `ANSWER_COMMENT` 只能表示“这是一个值得处理的候选问题”，不能直接等价为立即播报。所有候选回复必须再经过确定性的 `Rhythm Controller`（直播节奏控制器）决定何时处理、用什么方式处理、是否丢弃。

因此正式链路调整为：

```text
真实公屏事件
→ Event Adapter
→ 去重 / 聚合 / 问题聚类
→ 本地规则或 Monitor Model
→ Candidate Action
→ Rhythm Controller（最高调度权）
   ├─ VOICE_AT_SAFE_BOUNDARY
   ├─ DEFER_TO_QNA_WINDOW
   ├─ PUBLIC_CHAT_RESERVED
   ├─ PROMPTER
   └─ DROP / EXPIRE
→ 真正需要生成内容时才进入 Compliance / Template / Control
→ TTS 或预留文字回复接口
```

这意味着：**先决定“现在该不该说”，再花 Token 生成“怎么说”**。被延后、聚合、丢弃的问题不调用 Control，避免成本和节奏同时失控。

## 38.2 Room Rhythm State

每个直播间维护独立的 `RoomRhythmState`，至少包括：

- `phase`：当前直播阶段，例如 WARMUP / PRODUCT_INTRO / DEMO / CONVERSION / QNA / TRANSITION / COLD_ROOM
- `segment_id`：当前主线段落
- `segment_interruptible`：当前段是否允许插入回答
- `anchor_speaking`：主播是否正在讲话
- `ai_speaking`：AI 是否正在讲话
- `mainline_pending`：是否有必须继续的主线
- `question_rate`：短时间内问题进入速度
- `pending_question_count`
- `voice_answer_budget`：当前节奏窗口允许插入多少条语音回答
- `next_qna_window_at`
- `product_context_version` / `room_context_version`

主线 Segment 本身增加：

- `interruptible`
- `question_policy`：BLOCK / HIGH_VALUE_ONLY / ALLOW / QNA_WINDOW
- `min_hold_ms`
- `max_hold_ms`

即使某个问题业务优先级很高，也只能在允许的安全边界插入，默认仍使用“完整句/完整 Segment 后软切换”，不得在半句话中间抢话。

## 38.3 两种面向用户的回答方式

面向直播间用户保留两类正式回复通道：

1. `VOICE_DIRECT`：由伴播直接语音回答。
2. `PUBLIC_CHAT_REPLY`：由助手账号在公屏/群内直接文字回答。

当前阶段只实现 `VOICE_DIRECT`。第二种只预留接口，不接真实平台动作：

```text
PublicChatReplyAdapter
send(room_id, source_event_id, user_id?, text, trace_id) -> result
```

在接口未接通时，如果 Rhythm Controller 选择 `PUBLIC_CHAT_REPLY`，只能记录为 `PUBLIC_CHAT_RESERVED`，不得伪装成已经发送成功。

`PROMPTER` 仍可作为内部辅助通道提示主播/运营，但它不算面向用户的正式回答方式。

## 38.4 高频直播间的问题池

高频房间不按“一个问题 → 一次回答”处理，而是先进入 `Question Pool`：

- event_id 去重；
- 相同/近似问题语义聚类；
- 同一用户短时间重复提问合并；
- 同一 intent 设置冷却时间；
- 记录同类问题出现次数和最近时间；
- 只保留代表性问题文本；
- 超过 TTL 的旧问题自动失效；
- 商品/业务上下文切换后，旧 context_version 的问题直接失效。

当很多用户连续问同一个问题时，系统只需要在合适节奏点回答一次。只有在真实聚类计数达到阈值后，话术才允许使用“大家都在问 / 不少朋友在问”之类描述，不能凭模型猜测热度。

## 38.5 Rhythm Controller 决策规则

Rhythm Controller 是确定性系统组件，不是第三个 Agent。

默认规则：

- 主播正在讲话：不抢话；候选问题进入等待、提示主播或未来文字回复通道。
- PRODUCT_INTRO / DEMO：以主线讲解为主，只在自然停顿处理高价值且与当前内容高度相关的问题。
- CONVERSION：保护转化主线，不让普通问答打断完整逼单/转化段；问题进入队列。
- QNA：放宽语音回答预算，按聚类后的价值和新鲜度处理问题池。
- TRANSITION：优先完成转场，再切问题。
- COLD_ROOM：允许更多主动互动和问题回答，但仍受语音预算控制。
- 相同问题已刚回答：直接抑制重复回答。
- 问题已经过时、商品已切换、上下文改变：DROP/EXPIRE。
- 人工强制、合规风险、设备/系统安全：允许 HARD_INTERRUPT，优先于节奏。

业务 `priority` 与“是否可以打断主线”分离。Monitor 的 priority 不再拥有最终抢占权，最终执行权属于 Rhythm Controller。

## 38.6 高频保护与降载

按直播间实时问题速率动态进入不同模式：

```text
NORMAL
→ BUSY
→ HIGH_LOAD
→ OVERLOAD
```

进入高负载后逐级执行：

- 减少语音问题回答额度；
- 扩大相同 intent 聚类窗口；
- 优先处理重复次数高的共性问题；
- 只保留购买障碍、关键事实、当前商品强相关问题；
- 低价值问题转入未来 PUBLIC_CHAT_REPLY；
- 当前无法处理且很快失效的问题直接 DROP；
- 不因为问题数量增加而线性增加 Monitor / Control 模型调用。

问题洪峰只能增加“候选池深度”，不能直接增加“嘴巴说话频率”。

## 38.8 第一阶段真实直播验收

真实房间测试不以“所有问题都回答”为成功标准，而以“节奏没有被问题打乱”为第一标准：

1. 连续多人进房时不逐个语音欢迎；
2. 高频弹幕/提问时主线仍能完整讲完；
3. 同类问题能聚合，一次回答覆盖一批问题；
4. 主播讲话期间 AI 不抢话；
5. 转化段不会被普通问答频繁切断；
6. 到 QNA 或自然停顿时能挑选仍然有效的问题回答；
7. 过期问题、重复问题、旧商品问题正确丢弃；
8. 每条候选问题都能在 Redis 查到“为什么说 / 为什么没说 / 为什么延后”；
9. PUBLIC_CHAT_REPLY 只保留接口和状态，不在未接平台能力时伪造发送；
10. 最终统计同时包含“收到问题数、聚类数、实际语音回答数、延后数、丢弃数、模型调用数、成本”。
