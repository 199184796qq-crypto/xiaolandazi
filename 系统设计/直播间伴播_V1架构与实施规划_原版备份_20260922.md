# 直播间伴播 V1 架构与实施规划

> 目标：先做出能稳定跑通 1-20 个直播间的产品闭环，再扩容。V1 不追求大而全，核心验证“监听 → 判断 → 生成 → TTS → 盒子播音 → 恢复主线”。

## 1. 产品定位

本项目不是单纯的 TTS 播放器，也不以“数字人形象”为核心，而是一套直播间 AI 销售伴播系统。

核心能力：
- 监听直播间事件：弹幕、进房、点赞、成交、在线人数变化。
- 维护每个直播间独立状态 Room State。
- 按销售策略决定“现在要不要说、说什么、优先处理谁”。
- 主线塑品与实时互动并存。
- 实时语音可打断主线，互动结束后自然恢复。
- 盒子只负责连接、播放、控制和状态上报，业务逻辑全部留在服务端。
- 采用离线音频 + 实时 TTS 混合模式，控制成本。

# 2. V1 总体架构

```text
直播平台
  │
  ├─ 弹幕
  ├─ 进房
  ├─ 点赞
  ├─ 成交
  └─ 在线人数
  │
  ▼
┌──────────────────────────────┐
│  第一层：监听层 Event Layer   │
│  平台适配 / 清洗 / 去重 / 合并 │
└──────────────┬───────────────┘
               │ 标准事件
               ▼
┌──────────────────────────────┐
│  第二层：大脑层 Brain Layer   │
│  Room State                  │
│  事件优先级                  │
│  Intent 识别                 │
│  销售状态机                  │
│  Agent 决策                  │
└──────────────┬───────────────┘
               │ speech task
               ▼
┌──────────────────────────────┐
│ 第三层：语言层 Speech Layer   │
│ 话术库 / FAQ / LLM / TTS      │
│ 离线音频缓存 / 动态拼接        │
└──────────────┬───────────────┘
               │ 音频 + 控制指令
               ▼
┌──────────────────────────────┐
│ 第四层：执行层 Device Layer   │
│ WebSocket 长连接              │
│ 播放 / 暂停 / 抢占 / 清队列    │
│ 播放进度 / 播放完成状态上报    │
└──────────────────────────────┘
```

核心原则：Room State 是系统大脑，TTS 只是输出能力。

# 3. Room State：系统最核心的数据结构

每个直播间必须独立维护实时上下文，例如：

```json
{
  "room_id": "room_001",
  "status": "MAIN_PLAYING",
  "online_count": 23,
  "recent_order_count": 2,
  "main_stage": "VALUE_BUILDING",
  "current_block_id": "A3",
  "current_sentence_index": 2,
  "last_topics": ["痛点", "材质", "使用场景"],
  "last_price_mention_at": 0,
  "last_after_sale_mention_at": 0,
  "pending_events": [],
  "current_interaction_user": null,
  "device_status": "ONLINE"
}
```

Room State 要解决：
1. 现在主线讲到哪里。
2. 最近讲过哪些内容，避免重复。
3. 当前有没有互动事件。
4. 哪个事件优先级最高。
5. 当前用户问的是什么。
6. 上一次价格、售后、福利是什么时候讲的。
7. 盒子当前是否在线、正在播放什么。
8. AI 下一步应该继续主线、回答问题、逼单还是保持安静。

# 4. 主线与互动双通道

## 4.1 主线通道

主线不建议无限自由生成，而是基于“销售语义块”推进。

建议 V1 语义块：

```text
A1 开场承接
A2 用户痛点
A3 使用场景
A4 产品价值
A5 差异对比
A6 价格塑造
A7 售后保障
A8 福利提醒
A9 温和逼单
A10 新一轮变体
```

每个块准备多个句式变体和离线音频。

## 4.2 互动通道

弹幕进来后先做 Intent 分类，例如：

```text
PRICE_QUERY
PRICE_OBJECTION
QUALITY_QUERY
EFFECT_QUERY
AFTER_SALE
SPEC_QUERY
HOW_TO_USE
BUY_INTENT
NEGATIVE
GENERAL_CHAT
```

每类 Intent 对应固定销售策略，再让 LLM 做自然口语化。

原则：
- 模型负责判断、改写和补充；
- 价格、规格、售后等事实由后端数据强制提供；
- 不允许 LLM 自由编造关键参数。

---

# 5. 事件优先级

建议：

```text
P0 成交事件 / 强购买意向
P1 明确商品问题
P2 用户异议
P3 普通互动
P4 新用户进房
P5 点赞/关注
P6 无事件，继续主线
```

规则：
- 高优先级可抢占低优先级。
- 同级事件进入短队列。
- 大量进房事件必须合并，禁止逐个欢迎。
- 同一问题短时间重复出现时合并处理。
- 对同一用户短时间连续提问，要保留互动上下文。

# 6. 打断与恢复策略

不建议按“音频毫秒断点”硬恢复。

V1 采用“语义断点 + 句子断点”。

流程：

```text
主线 A3 第2句播放中
        ↓
收到 P1 弹幕
        ↓
终端停止当前主线
        ↓
记录：
block=A3
sentence=2
        ↓
播放互动回答
        ↓
互动结束
        ↓
判断：
继续 A3 下一完整句
或直接进入 A4
```

好处：
- 不会出现半句话接半句话。
- 恢复自然。
- 状态更容易调试。
- 对不同 TTS 引擎更兼容。

# 7. TTS 与音频成本架构

## 7.1 离线音频

优先离线生成：
- 主线塑品内容。
- 高频 FAQ。
- 高频售后回复。
- 常用欢迎词。
- 常用逼单句。

每个话术块建议先做 5-8 个变体。

## 7.2 实时 TTS

只用于：
- 用户昵称。
- 用户具体问题。
- 动态价格/库存/订单等变量。
- 非标准 FAQ。
- 个性化异议处理。

## 7.3 缓存

缓存 Key 可采用：

```text
product_id + intent + normalized_text + voice_id + speed
```

相同回复重复出现时直接复用音频。

最终成本指标不要看“直播 1 小时多少钱”，而看：

```text
单直播间每小时新增实时 TTS 字符数
```

目标是把实时 TTS 占总播音时长压到 5%-20%。

# 8. 服务端 V1 技术架构

第一阶段不要一开始拆大量微服务。

推荐：

```text
┌────────────────────────────┐
│        API / 中控服务       │
│  FastAPI 或 Go             │
│                            │
│  ├─ Room Manager           │
│  ├─ Event Dispatcher       │
│  ├─ Sales Agent            │
│  ├─ Speech Manager         │
│  ├─ Device Gateway         │
│  └─ Admin API              │
└───────────┬────────────────┘
            │
   ┌────────┼─────────┐
   ▼        ▼         ▼
 Redis     MySQL     OSS
```

V1 暂时不强制：
- RocketMQ
- Kubernetes
- 多套微服务
- 独立 Agent Gateway
- 独立音频分发集群

等真实并发上来再拆。

# 9. 盒子通信协议

建议 WebSocket。

## 服务端 → 盒子

```json
{"type":"play","task_id":"xxx","url":"...","priority":1}
{"type":"stop","task_id":"xxx"}
{"type":"clear_queue"}
{"type":"set_volume","value":80}
{"type":"ping"}
```

## 盒子 → 服务端

```json
{"type":"online","device_id":"xxx"}
{"type":"play_started","task_id":"xxx"}
{"type":"progress","task_id":"xxx","position_ms":3200}
{"type":"play_finished","task_id":"xxx"}
{"type":"play_error","task_id":"xxx","error":"..."}
{"type":"pong"}
```

必须有 task_id，所有状态都能追踪。

# 12. 开发推进顺序

## 阶段 0：冻结 V1 规则

先确定：
- 第一版接哪个直播平台。
- 第一版使用哪个 LLM。
- 第一版使用哪个 TTS。
- 盒子的系统环境和播放器实现方式。
- 商品数据格式。
- 主线语义块。
- Intent 分类。
- 事件优先级。

产出：
- V1 功能边界。
- 数据字典。
- 事件协议。
- 盒子协议。

## 阶段 1：做单直播间最小闭环

只实现：

```text
模拟弹幕
→ Room State
→ Intent
→ LLM 回复
→ TTS
→ PC 模拟盒子播放
```

验收：
- 一条弹幕能触发回复。
- 主线能被打断。
- 回复后能恢复主线。
- 全链路有 task_id 和日志。

## 阶段 2：接真实直播间

加入：
- 真弹幕采集。
- 真在线状态。
- 真实盒子。
- 弱网重连。
- 设备心跳。

验收：
- 连续直播 4 小时不乱状态。
- 断网重连后状态恢复。
- 弹幕不串房间。
- 音频不串流。

## 阶段 3：销售策略

加入：
- Intent 分类完善。
- 商品知识库。
- 异议处理。
- 销售状态机。
- 高频 FAQ 音频缓存。
- 主线多变体。

验收：
- 关键参数零幻觉。
- 话术短时间不机械重复。
- 高频问题优先命中缓存。

## 阶段 4：5-20 房间并发

加入：
- Room State 隔离。
- 限流。
- TTS 并发队列。
- 超时与降级。
- 成本统计。
- 监控。

验收：
- 20 房间并发不串房。
- 单房间故障不影响其他房间。
- 能看到每房间 LLM/TTS 成本。

## 阶段 5：商业化

再做：
- 账号/商户体系。
- 套餐与算力卡。
- 设备授权。
- 代理商。
- 到期停用。
- 计费账单。
- OTA。
- 多租户权限。

# 13. 第一阶段明确不做

V1 暂不优先：
- 1000 房间架构。
- Kubernetes。
- RocketMQ。
- 本地 5090 私有化推理。
- 复杂 BI。
- 多平台同时接入。
- 数字人画面。
- 超复杂 RAG。
- 多 Agent 自主协作。

原则：先跑通产品闭环，再做规模架构。

# 14. 关键验收指标

V1 建议重点盯：

```text
弹幕收到 → 开始出声延迟
目标：尽量 < 2 秒

直播间串话
目标：0

关键商品参数幻觉
目标：0

盒子断线重连
必须自动恢复

主线恢复
不得出现明显半句话拼接

高频 FAQ 缓存命中率
持续提高

实时 TTS 占比
目标 5%-20%

连续运行稳定性
先完成 4h，再 12h，再 24h
```

# 16. 接下来最先做的三件事

第一件：把 Room State 定死。
先形成完整字段、状态枚举、状态转换图。

第二件：把“事件 → 决策 → 语音任务”协议定死。
这样直播平台、AI、TTS、盒子之间不会互相耦合。

第三件：做 PC 模拟盒子。
在真实硬件接入前，先用 Windows 客户端模拟播放、停止、打断、恢复、状态上报，把服务器闭环跑通。

当以上三件完成后，再开始接真实直播平台和真实盒子。

# 17. 推荐的 V1 第一条开发链路

```text
假弹幕输入
   ↓
Event Normalizer
   ↓
Room State
   ↓
Priority Queue
   ↓
Intent Classifier
   ↓
Sales Policy
   ↓
LLM
   ↓
TTS
   ↓
Speech Task
   ↓
WebSocket
   ↓
PC 模拟盒子
   ↓
play_finished
   ↓
Room State 恢复主线
```

只要这条链路稳定，后面的工作本质上都是替换输入源、提升策略、加商业化能力。
