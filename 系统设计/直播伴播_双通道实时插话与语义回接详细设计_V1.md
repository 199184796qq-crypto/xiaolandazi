# 直播伴播：双通道实时插话与语义回接详细设计 V1

> 状态：详细设计阶段，仅方案落盘，不写代码
> 日期：2026-09-23
> 基础：沿用当前测试台、Qwen3.8-Flash、Qwen-Audio 3.0 TTS Plus、Redis、直播事件流。

## 1. 核心目标

把系统从“实时生成一句、播放一句”改成：

完整主线文案 → 一次生成连续母带 → 文案/音频一一对应 → 建立时间轴和安全切点 → 主线持续播放。

Monitor 判断必须互动时，主线不立即停；后台并行生成回答、回接话术和互动语音。互动音频 READY 后，在最近的自然安全点切入。互动结束后根据覆盖内容和剩余主线做语义回接。

核心原则：不是恢复到原来的秒数，而是恢复到正确的语义位置。

## 2. 双通道结构

Mainline Channel：负责预生成主线连续播放、当前位置、当前主题、未来安全切点。

Interaction Prepare Channel：负责接收 Interrupt Ticket、读取当前及后续主线、生成回答和回接、TTS、标记覆盖主题、计算恢复位置。

两条通道并行：主线继续播，互动在后台准备。只有互动语音准备完成后，才进入 WAIT_SAFE_POINT，等待自然句尾切入。

状态顺序：

QUESTION / WELCOME / EVENT → PREPARING → READY → WAIT_SAFE_POINT → INTERRUPT → RESUME。

## 3. 大音频怎么生成和切

主线建议 60～120 秒为一条 Track，一次调用 TTS 生成连续母带。不要先把文字切成很多 5～10 秒的小段分别 TTS，否则每段容易重新起调。

每条 Track 同时保存三份内容：

1. 完整原始文案。
2. 连续母带音频 master.wav。
3. Text-Audio Timeline，记录每个句子、主题、开始时间、结束时间和安全切点。

母带生成后再切，切片不是重新 TTS，而是从同一条母带裁出来，因此音色、情绪、呼吸和节奏保持一致。

## 4. 三级切分

Level 1：Track / Chapter。
建议 60～120 秒，作为一次 TTS 的母带单位。

Level 2：Semantic Unit。
按商品身份、产地、养殖、活动量、饲喂、肉质、现杀、规格、物流、做法等主题切分。这个层级主要用于决定“回答以后回到哪一块”。

Level 3：Safe Point。
真正允许切声音的位置，一般位于完整句尾、短语义结束、自然停顿、主题转换处。

## 5. Text-Audio Alignment

因为主线原文是已知的，所以每条母带生成后需要做文字和音频强制对齐。

最终每个语义单元至少得到：unit_id、topic、fact_ids、text、start_ms、end_ms、resume_safety、safe_points。

如果 TTS 接口未来可直接返回可靠时间戳就直接采用；否则用本地 Text-Audio Alignment 模块根据已知原文和音频做强制对齐。

## 6. Safe Point 评分

每个候选点做 0～100 分评分。

加分因素：完整句结束、语义完整、自然停顿、Topic 边界、下一句可以独立开始。

扣分因素：句子中间、因果关系未完、指代依赖严重、价格或数字说到一半、CTA 说到一半。

初始建议：80 分以上 A 级；65～79 B 级；50～64 只在高优先级事件使用；50 以下普通互动禁止切。

## 7. Interrupt Ticket

Monitor 不直接下“马上停”的命令，而是发 Ticket。

Ticket 至少包含：ticket_id、event_type、priority、question、created_at、max_wait_ms、ttl_ms、must_answer、heat_level。

Monitor 的含义是：“这个事件值得回应，请在允许时间窗口内找自然位置插进去。”

## 8. 收到 Ticket 后先做主线快照

系统记录：当前 plan、当前 unit、当前 topic、播放毫秒数、已经讲过的 topics/facts，以及未来 2～4 个 Semantic Unit。

同时从 Timeline 取未来若干 Safe Point，例如：

SP1：2.8 秒后，score 88。
SP2：5.9 秒后，score 94。
SP3：9.6 秒后，score 96。

## 9. 预测互动准备时间

系统持续统计真实的 LLM 延迟、TTS 延迟、FAQ 命中延迟和网络延迟，维护最近窗口平均值。

例如预测：LLM 1.8 秒 + TTS 2.8 秒 + 0.5 秒安全余量 = 5.1 秒。

Scheduler 不选 2 秒后的切点，而选预计 READY 之后的第一个高质量 Safe Point。

如果准备比预测晚，切点自动顺延；超过 Ticket TTL 后，普通互动丢弃或降级。

## 10. Interaction Builder 必须看到后续主线

生成互动回答时，不只给模型用户问题，还要给：当前正在讲什么、当前已讲什么、候选切点、切点之后的 2～4 个主线 Unit。

这样模型在写回答时就已经知道回答完要往哪里接。

Interaction Plan 应一次返回：

- reply_core：真正回答或欢迎内容。
- resume_tail：为了接回主线而写的最后一句。
- covered_topics：回答已经讲过哪些主题。
- covered_fact_ids：回答覆盖哪些事实。
- skip_units：建议跳过哪些主线单元。
- resume_unit：建议恢复到哪一段。
- resume_mode：回接模式。

程序再对这些结果做校验，模型不能直接控制播放器。

## 11. 回答和桥接建议一次 TTS

互动最终播放文本建议为 reply_core + resume_tail，一次生成 interaction.wav。

这样回答和回接尾巴使用同一次 TTS，语气连续。interaction.wav 播完后直接进入选定的主线 Unit。

## 12. 重复内容处理

主线每个 Unit 都带 fact_ids 和 topic。互动回答也返回 covered_fact_ids 和 covered_topics。

重复判断优先级：

1. fact_id overlap。
2. topic overlap。
3. semantic similarity。
4. 模型建议。

最终是否跳过由程序决定，不让模型自由跳。

第一版只做到 Unit 级跳过，不做一句话内部的 sub-unit 级裁剪。

## 13. 六种回接模式

R1 DIRECT：回答很短，没有覆盖后续内容，直接接原 next_unit。

R2 BRIDGE：回答稍长，原 next_unit 直接进入较突兀，用回答末尾的 resume_tail 自然带回。

R3 FUSION_SKIP：回答正好覆盖后面的主线。例如用户问“吃什么”，回答已覆盖 feeding，就跳过 feeding，直接进入 meat。

R4 CROSS_RESUME：回答覆盖多个后续主题，跳到第一个未覆盖且可以独立进入的 Unit。

R5 RE_ANCHOR：中断约 10～25 秒，原上下文变弱，先重新建立商品语义锚点，再进入新的主题。

R6 SWITCH_PLAN：中断约 20～30 秒以上或连续多个互动，放弃旧 Plan 剩余部分，保留 spoken_topics，从 Speech Bank 选另一套安全入口重新开始。

## 14. Moving Cut Window

主线一直在继续，原候选切点可能在互动音频准备完成前已经过去，因此切点不能在 Ticket 到达时锁死。

规则：根据预计 READY 时间选择未来切点；如果没赶上就顺延到下一个；只要未超过 max_wait_ms 和 ttl_ms 就继续寻找。

## 15. 标准回接例子

原主线：identity → origin → raising → activity → feeding → meat → slaughter。

当前正在 activity，用户问“这个鸡平时吃什么？”

Monitor 发 P1 Ticket，主线继续。Interaction Builder 看到后续 feeding、meat、slaughter。

后台生成：

回答：平时活动的时候会自己吃一些小虫、小竹笋，也会搭配人工科学配比的食材。

回接尾巴：再往下看，你收到货以后鸡皮和肉质这一块也可以注意一下。

covered_topics = feeding，resume_unit = meat，resume_mode = FUSION_SKIP。

TTS READY 后，在 activity 的自然句尾切入 interaction.wav。回答播放完后，原 feeding 直接 SKIP，从 meat 继续。

最终听感：主线讲活动量 → 回答吃什么 → 顺手带到肉质 → 主线继续肉质。

## 16. 欢迎、成交、关注也走同一机制

WELCOME、成交庆祝、关注等事件也可以形成 Interrupt Ticket。Heat Controller 决定值不值得插；Interrupt Scheduler 决定什么时候插；Interaction Builder 决定怎么说；Resume Controller 决定怎么回来。

热场时低价值欢迎可以直接取消，冷场时才积极互动。

## 17. 播放状态必须是语义状态

不能只保存 current_time=47.3s。

还必须保存：plan_id、current_unit、current_topic、spoken_units、covered_by_interaction、skipped_units、next_unit、active_ticket。

系统以后不是“音频播放器”，而是“带语义位置的播放器”。

## 18. V1 新增模块

- Mainline Track Builder：长文案和连续母带。
- Text-Audio Aligner：原文与音频时间轴。
- Safe Point Analyzer：安全点和评分。
- Mainline Player：连续播放和语义位置。
- Interrupt Scheduler：Ticket、ETA、Moving Cut Window。
- Interaction Builder：回答、回接、覆盖主题。
- Interaction TTS：回答和回接一次合成。
- Coverage Resolver：判定哪些后续 Unit 已覆盖。
- Resume Controller：六种恢复模式。
- Playback State：语义播放状态。

## 19. 与当前测试系统的关系

现有 Qwen3.8-Flash、Qwen-Audio 3.0 TTS Plus、Redis、Core SSE、Monitor/Control、Speech Bank 全部保留。

本阶段主要新增设计的是 Mainline Track、Interrupt Scheduler、Coverage Resolver 和 Resume Controller，不推倒现有架构。

## 20. 第一轮验证顺序

测试 A：生成 60～90 秒连续主线母带，验证声音连续性。

测试 B：建立文字/音频一一对应 Timeline，验证 Safe Point。

测试 C：人工触发问题，主线不停，后台回答和 TTS，READY 后再切入。

测试 D：短回答 DIRECT 恢复。

测试 E：问题覆盖下一段，验证 FUSION_SKIP。

测试 F：中等中断，验证 answer + resume_tail 自然桥接。

测试 G：连续互动超过 30 秒，验证 SWITCH_PLAN。

## 21. 成功标准

1. 等模型和 TTS 时主线不空场。
2. 插话发生在自然句尾。
3. 回答像主播现场回应，而不是外挂音频。
4. 回答结束后不机械说“回到正题”。
5. 回答已经讲过的内容，主线不重复。
6. 主线重新进入时语义自然。
7. 长互动以后不会硬接几十秒前的旧话题。
8. 整体听起来像一个主播在边讲边回应。

## 22. 当前设计结论

这套系统以后统一理解为：

Semantic Mainline + Asynchronous Interaction Preparation + Safe Interrupt Scheduling + Semantic Resume。

中文就是：主线不断、后台准备、自然插话、语义回接。

# 23. 2026-09-23 母带时间轴实测结论

本轮已基于现有测试台完成第一轮“长母带 + 时间戳 + SRT + Safe Point”实测。

## 23.1 Qwen-Audio 可直接提供字/词级时间戳

Qwen-Audio 3.0 TTS Plus 的流式合成可以开启 word_timestamp_enabled。

本轮使用“杨鸭子”Qwen-Audio 3.0 TTS Plus 克隆音色，直接对完整主线做一次连续 TTS，并从 TTS 事件流获得完整时间戳。

实测：

- 主线文本：579 字符
- 连续母带：约 87.9 秒
- Qwen 时间戳 token：529 个
- 自动生成句级 SRT：16 条
- 母带按切点物理分成 16 段后重新无损拼接
- PCM SHA256 与原母带完全一致

结论：

**现阶段不需要先用 ASR 把自己的 TTS 音频重新识别一遍。可以优先直接利用 Qwen TTS 原生时间戳生成 SRT 和 Timeline。**

## 23.2 原始时间戳不能简单把每个句尾直接当切点

实测发现，Qwen 的部分时间戳 token 会把标点和下一个字放在同一个时间 token 中，因此直接按句子首尾取时间会出现小范围重叠。

当前测试解决方式：

1. 根据 token 对完整 normalized_text 的字符位置做边界插值。
2. 再在预测边界附近约 ±220ms 范围扫描 PCM 能量。
3. 如果发现明显低能量谷值，优先把真实切点吸附到该位置。
4. 再基于语义结构给 Safe Point 评分。

因此正式设计不要只依赖“字幕条 start/end”，而应保存：

SRT + 原生 word timestamp + Safe Point。

## 23.3 两级 Safe Point 已有实测数据

当前 87.9 秒母带：

### 普通互动：A级切点

仅使用完整句结束/高质量边界。

- 可用切点：16 个
- 平均等到下一个安全点：约 3.23 秒
- P50：约 2.80 秒
- P90：约 6.65 秒
- P95：约 7.85 秒
- 最坏：约 10.85 秒

这对普通欢迎、低优先问答可以接受，但对购买问题偏慢。

### 高优互动：A级 + B级短语切点

在完整句之外，允许部分语义完整的逗号/短语边界。

- 可用切点：31 个
- 平均等待：约 1.66 秒
- P50：约 1.43 秒
- P90：约 3.44 秒
- P95：约 4.08 秒
- 最坏：约 5.86 秒

因此后续 Interrupt Scheduler 可以正式采用：

- 普通互动优先 A 级
- 高价值问题允许 A+B
- 极紧急事件再设计更强抢占策略

# 24. Monitor / Interaction 策略外置与权限分级（Policy V1.3）

当前已把“是否回答”和“怎么回答”从主程序硬编码中拆开，形成独立策略层。

运行时策略目录：

E:\webcodex\policies

源码镜像：

E:\直播伴播\系统设计\直播伴播_POC\policies

文件：

- monitor_policy.md：Monitor Agent 调度权限、P1/P2/P3、热度规则、何时允许延后。
- interaction_policy.md：Answer Agent 回答权限、推理边界、动态信息、特殊人群、回接风格。
- policy_config.json：Safe Point 阈值、等待时间、动态意图、烹饪意图、高风险关键词等程序参数。
- regression_cases.json：策略回归测试题库。

策略文件在每次请求时重新读取，后续修改 Monitor / Interaction Prompt 时原则上不需要再改主程序。

当前回答权限分为：

1. VERIFIED_FACTS：已确认事实，直接回答。
2. REASONED_ASSIST：事实库没有完整答案时，允许“已确认资料 + 一般常识 + 非绝对推理”。
3. COOKING_ASSIST：做法/炖/蒸/煮等问题，允许给实用做法建议，但不推导“更香、更嫩、营养更高、不柴”等未确认结果。
4. DYNAMIC_CAUTION：价格、库存、券、赠品、包邮、快递、当日发货等实时信息，不猜具体值，但必须给有用的确认路径。
5. GENERAL_CHAT：普通互动和一般常识，不因资料库未命中就机械推诿。

特殊人群规则：

- “老人、小孩、孕妇能不能吃”不自动转医生。
- 正常做法是先说明要看个人情况，再给做熟、做软等低风险建议。
- 只有明确过敏、疾病、用药、症状、治疗、诊断等问题才提高医疗谨慎等级。

程序层继续保留确定性保护：

- 绝对化词语软化。
- 已知事实措辞纠偏，例如“不圈养”不能自动改成“散养”。
- 普通问题自动去除无必要的“咨询医生/专业人士”。
- 烹饪回答出现“汤更香、营养更高、不柴”等越界结果时，回退到安全但仍有用的烹饪回答。
- 动态库存回答不假设页面一定展示具体剩余数量。
- 回接尾巴出现“因为/所以/跟……有关”等强因果桥接时，自动改成指向式桥接。
- 回答/桥接与恢复主线高度重复时自动跳过重复主线句。
