# 直播伴播三层策略服务端落地 V2

更新时间：2026-09-23

## 一、权威业务定义

运行时规则关系：

L1 系统强制边界
+
L2 行业默认业务规则（可被 L3 做业务差异覆盖）
+
L3 当前终端 / 当前直播间差异规则
=
Effective Policy

固定原则：

- L1：平台系统级强制规则，只允许超级系统管理员维护和发布。
- L2：行业默认规则，由有权限的管理人员维护。
- L3：终端 / 直播间差异策略，只允许对应终端账号维护。
- L3 可以 add、replace、disable L2。
- L3 永远不能新增、替换、关闭或复用 L1 的规则 key。
- L3 只保存与行业默认不同的地方，不复制完整 L2。
- 没有冲突的 L2 与 L3 同时生效。

表达模式：

- verbatim：固定原话，必须保存 fixed_text，运行时逐字使用。
- intent：按意思灵活生成，必须保留事实、意思与边界，可以变化表达。
- 固定原话若与 L1 冲突，不允许偷偷改写后继续标记为固定原话，必须阻止发布。

## 二、数据库

### live_policy_industries

行业目录。当前默认包含：

- general / 通用
- food / 食品餐饮
- agriculture / 农产品生鲜
- apparel / 服装鞋包
- beauty / 美妆个护
- local_life / 本地生活

### live_policy_tenant_industries

终端与行业绑定。

- 一个终端当前绑定一个主要行业。
- 未绑定时回退 general。
- 管理端终端列表可直接修改行业。
- 每次绑定记录旧行业、新行业与操作人。
- 直播运行中改变行业会立即刷新 Effective Policy。

### live_policy_scopes

策略作用域：

- L1:global
- L2:<industry_code>
- L3:<tenant_id>:<room_id>

current_version_id 指向当前正式生效版本。

### live_policy_versions

不可变版本记录。

包含：

- draft / active / archived
- source_text
- rules_json
- overrides_json
- conflicts_json
- source_version_id
- 创建人 / 发布人
- 创建时间 / 发布时间

回滚不会重新激活旧记录，而是从历史版本复制生成一个新的 active 版本，保证审计链不断裂。

### live_policy_audit_logs

记录：

- 草稿生成
- 发布
- 回滚
- 终端行业绑定

### live_runtime_policy_snapshots

保存每个 Runtime Session 当前最新的：

- 行业
- L1 version id
- L2 version id
- L3 version id
- Effective Policy JSON

### live_runtime_policy_revisions

保存同一场直播全过程中的策略版本切换历史。

revision_key 由 industry_code + L1 version + L2 version + L3 version 组成。

同一 session 的相同组合只记录一次。

以下动作会立即刷新所有正在运行会话：

- L1 发布 / 回滚
- L2 发布 / 回滚
- L3 发布 / 回滚
- 终端行业绑定变化

只有实际版本组合发生变化时才追加 revision，并写入 POLICY_REVISION_APPLIED Runtime Event。

这样同时满足：

- 当前实际生效策略可查
- 直播过程中策略切换时间可追
- 后续可以复盘某场直播当时使用的具体版本

## 三、服务端合并算法

实现位置：

management-service/internal/policy/merge.go

顺序：

1. 加载 L1 active，全部作为 locked 规则。
2. 加载终端所属行业 L2 active。
3. 行业没有 L2 时回退 general。
4. L2 与 L1 使用同一 key 时，L1 胜出并产生冲突。
5. 加载 tenant + room 对应 L3 active。
6. L3 add：新增业务规则。
7. L3 replace：替换 L2 同 key。
8. L3 disable：关闭 L2 同 key。
9. L3 触碰或复用 L1 key：拒绝并产生冲突。
10. 输出带 source_layer 与 source_version_id 的 Effective Policy。
11. 生成 Runtime PromptText。

## 四、权限

管理端：

- L1：仅 platform_admin。
- L2：platform_admin 或 livepolicy.manage_l2。
- L1/L2 查看：platform_admin 或 livepolicy.view。
- 管理端 Agent 不能读取、展示或编辑任何客户直播间 L3。

终端：

- L3 仅 role=customer。
- 必须校验 room 属于当前 tenant。
- 平台管理员和内部员工不能走终端 L3 API 替客户改规则。

## 五、Agent 工作流

自然语言
→ Agent 判断 EXPLAIN / DRAFT
→ 输出结构化规则
→ 服务端确定性 ValidateDraft
→ 保存 draft
→ 查看冲突
→ 显式发布
→ active version 更新
→ 正在运行的直播自动刷新 Effective Policy

Agent 不能直接写正式配置。

服务端永远不相信模型自己声称“没有冲突”，发布前必须重新使用当前 L1 做确定性检查。

## 六、管理端 UI

管理端直播策略：

- 左侧只显示第一层系统规则、第二层行业规则和行业目录。
- 禁止出现客户直播间列表。
- Agent 只作用于当前 L1 / L2 scope。
- 草稿与正式版本分开显示。
- 有冲突时禁止发布。

终端列表：

- 增加“行业 / L2”字段。
- 有 livepolicy.manage_l2 权限的人员可以直接修改终端行业。
- 修改行业后直播运行时自动切换对应 L2。

## 七、终端 UI

终端直播策略：

- 用户可以选择自己的直播间。
- “策略调教”写新的 L3 差异策略。
- L3 可以覆盖 L2 业务默认，但不能突破 L1。
- 主播训练、声音、媒体素材等仍使用原有配置体系。

## 八、旧配置兼容

旧 live_agent_config_versions 暂不删除，继续承载：

- persona
- model config
- speech config
- style profile
- 声音
- 媒体
- 主播训练相关配置

新的直播业务规则不得继续写回旧 layer1_json / layer2_json / layer3_json。

新的 live_policy_* 表是 L1 / L2 / L3 业务策略的唯一权威来源。
