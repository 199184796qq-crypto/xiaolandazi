# 直播伴播系统：扩展性、伸缩性、鲁棒性后续待办

更新时间：2026-09-23

> 本文只记录已经确认需要继续建设、但当前尚未完全落地的架构工作。
> 已经完成并验证的能力仅作为现状基线，后续开发不得倒退。

---

## 一、当前已经完成的基础能力

以下能力已经落地，不再列为待办：

- Core 房间 Redis Lease。
- Fencing Token，防止旧 Core 恢复后形成双采集。
- Core 租约续租与丢租主动停止。
- Management -> Core 的安全故障切换。
- 非幂等 POST 禁止跨 Core 自动重放。
- Core / Management 优雅停机。
- Management Reconciler Leader Lease。
- 管理审计 MySQL 权威账本，Redis Stream 作为实时镜像。
- Core / Management 基础 metrics。
- Collector Provider Registry。
- Collector Capability 抽象：events / preview / media_stream / push_ingress。
- Push Ingress 统一 Envelope / Result 契约。
- Chrome / Playwright 已降级为普通 Provider，不再是 Core 主架构。
- collector_mode=auto 已具备按 Provider 优先级选择和创建失败 fallback 的基础能力。

## 二、P0：正式生产前必须完成

### 1. 真正的多 Core 故障演练

当前 Lease/Fencing 已经单机重启验证，但还需要：

- 同时启动至少 2 个真实 Core。
- 同一批房间分布在不同 Core。
- 人工强杀其中一台 Core。
- 验证其他 Core 在 Lease TTL 后自动接管。
- 验证 Management 的 SSE / Preview / Media 路由同步切换。
- 验证旧 Core 恢复后不会抢回过期 Fence。
- 记录实际恢复时间、事件丢失窗口和重复事件情况。

验收目标：

- 不产生双采集。
- 单 Core 故障不影响其他节点房间。
- 故障房间可自动恢复，无需人工点击“连接”。

### 2. 30 / 50 / 100 房真实压力测试

当前 5 worker × 20 room = 100 room/Core 只是配置容量，不是生产结论。

必须采集：

- CPU。
- 内存。
- Chrome worker RSS。
- 每房事件速率。
- WebSocket 数。
- frame drop。
- reconnect 次数。
- Redis latency / used_memory。
- MySQL pool wait。
- Agent 调用并发。
- FFmpeg active sessions。
- 网络上行/下行。

分阶段：10 房基线 -> 30 房 -> 50 房 -> 100 房。

最终给出：

- 单 Core 推荐安全房间数。
- 60%～70% 常态容量线。
- 80% 告警线。
- 扩容触发指标。

### 3. 服务端 Agent Runtime 独立化

不要做成“一直播间一个 Agent 进程”。

目标结构：

    Management
        ↓
    Agent Runtime / Worker Pool
        ├─ MySQL：L1/L2/L3、策略版本、主播画像
        ├─ Redis：Room State、短期上下文、任务状态
        ├─ LLM Provider
        ├─ TTS Provider
        └─ 输出 Speech / Decision Task
                ↓
               Core

要求：

- Agent Worker 无状态化。
- 多实例横向扩展。
- 单个 Agent Worker 挂掉，任务可由其他 Worker 接手。
- 房间上下文不能只存在进程内存。
- 对 LLM/TTS 做超时、限流、熔断、重试边界。
- 任务必须带 tenant_id / room_id / task_id / config_version。
- 关键业务事实只能来自后端数据和规则层，不能让模型自由编造。

### 4. Production Readiness / Liveness 分离

当前已有 /healthz 和 /metrics，后续增加：

- /livez：进程是否存活。
- /readyz：是否真的可以接业务。

Readiness 至少检查 MySQL、Redis、Core Registry、Lease 状态、Agent Runtime 依赖。
部署滚动升级时，先摘流量再停进程。

## 三、P1：采集层扩展

### 5. Douyin Official Provider

建议目录：core-service/internal/collector/douyin/official/

目标能力：

- 官方评论、点赞、礼物、进房/关注等授权事件。
- 官方任务启动/停止/状态管理。
- webhook 签名验证。
- msg_id 幂等。
- 重放保护。

建议参数：id=douyin.official，platform=douyin，mode=official，priority=10。

### 6. Douyin Companion Provider

接抖音直播伴侣插件 / SDK。

目标：

- 客户端轻量桥接。
- 评论/点赞/礼物等转成统一 Push Ingress。
- 本地插件只负责采集和转发，不承载核心业务规则。
- 断线自动重连。
- 设备身份鉴权。

建议 priority=20。

### 7. 真正的 Lightweight Provider

当前 lightweight 仍是 Browser Provider 的兼容 alias。

未来真正实现：HTTP bootstrap -> WebSocket -> Frame/Protobuf decode -> 标准 RoomEvent。

要求：

- 与 Browser Provider 完全隔离。
- 独立限流和重连。
- 协议变化不能拖垮 Core。
- 失败可 fallback 到 Browser。

建议 id=douyin.lightweight，priority=30。

### 8. 其他平台 Provider

以后新增平台时，不允许再修改 Core Manager 主流程。

例如：kuaishou.official / kuaishou.companion / kuaishou.lightweight / kuaishou.browser，以及 xiaohongshu.* / shipinhao.*。

统一实现 Provider / Capability 契约。

## 四、P1：文件与媒体架构

### 9. 头像等剩余本地文件全部进入统一 Storage

目前媒体层已支持 Local/OSS Registry，但仍有部分本地文件路径。

目标：头像、语音克隆样本、主播学习素材、商品素材、视频、文档、长期生成音频都通过统一 Storage 管理。

ECS 本地磁盘只保存 cache、temp、可重建数据。

### 10. 大文件浏览器直传 OSS

当前大文件仍可能经过 Management。

最终流程：Web 请求上传凭证 -> Management 下发 STS/signed upload -> Web 直传 OSS -> 回写 object_key / sha256 / metadata。

避免 1～2GB 视频占用 Management 带宽和连接。

### 11. Media Worker 独立化

当大量房间需要实时视频/HLS/FFmpeg 时，将媒体处理从 Core 拆开。

Collector Core -> Media Job -> Media Worker Pool -> FFmpeg / HLS / ASR preprocessing。

原因：采集容量和转码容量是两个不同资源模型；当前 MEDIA_MAX_SESSIONS=8 不代表 Core 只能监控 8 房；不允许 FFmpeg 高负载拖死评论采集。

## 五、P1：调度与伸缩

### 12. 从 % shardCount 逐步升级到稳定节点调度

当前静态 Shard 只作为首选节点，Lease 才是真实所有权。

后续考虑：

- Rendezvous Hash / Highest Random Weight。
- 节点注册表。
- 节点权重。
- 节点容量上报。
- Drain 状态。

目标：增减 Core 节点时尽量少迁移房间；不要求所有节点同时修改 shard_count；支持不同规格 Core 混跑。

### 13. 自动扩容判定

不要只使用 CPU。

重点指标：active_rooms / collector_capacity、browser worker occupancy、Agent queue depth、event lag、DB pool wait、Redis latency、FFmpeg utilization。

推荐区间：60%～70% 正常，70%～80% 准备扩容，>80% 高风险。最终阈值以压力测试为准。

## 六、P1：Redis / MySQL / 事件可靠性

### 14. Redis 容量模型与扩容阈值

当前房间事件默认每房最多保留约 500 条。

后续按 100 / 500 / 1000 房真实测：used_memory、fragmentation、latency、evicted_keys、connected_clients、stream 长度。

当前 1GB Tair 不能直接假设能稳定承载 1000 个高活跃房。

### 15. 事件幂等和去重统一层

不同 Provider 可能重复推送同一事件。

统一使用 provider_id + platform + external_room_id + provider_event_id + occurred_at 形成 dedupe key。

官方 Push、Browser、Companion 切换时尤其重要。

### 16. 异步任务失败处理

未来 Agent/TTS/媒体任务量增加后需要：retry policy、backoff、dead-letter、poison message 隔离、task timeout、manual replay。

是否引入 RocketMQ / Kafka / Redis Streams Consumer Group，应按真实规模决定，不提前过度微服务化。

## 七、P2：可观测性与运维

### 17. Prometheus + Dashboard

当前 /metrics 只是第一层。

后续至少建立 Core、Management、Agent、MySQL、Redis、Collector Provider Dashboard，并支持每租户/每直播间问题定位。

### 18. 告警

需要覆盖：Core 节点死亡、Lease 大量转移、Browser worker 连续崩溃、Provider 错误率突增、Agent queue 堆积、LLM/TTS 延迟异常、Redis memory 超阈值、MySQL pool wait、FFmpeg capacity 满、单房间反复重连。

### 19. 一键链路追踪

长期目标：tenant -> room -> event -> agent decision -> llm -> tts -> speech task -> device playback。

统一 trace_id / task_id。后台可从某条评论一路看到最终播出的语音。

## 八、P2：部署与灾备

### 20. ECS 正式部署

最终结构：SLB/Nginx -> Web + Management -> Agent Runtime Pool -> Core Pool；共享 RDS + Tair + OSS。

要求：开机自启、异常自动重启、滚动发布、日志轮转、配置不进代码仓库、优先 RAM Role / STS，避免长期 AccessKey。

### 21. 数据库备份和恢复演练

需要真正做 RDS 自动备份策略、Point-in-Time Restore 验证、Redis/Tair 持久化和恢复策略确认、OSS 生命周期、配置版本恢复、定期恢复演练。

### 22. 灾难场景演练

至少模拟：Core 整机掉线、Management Leader 掉线、Redis 短时不可用、MySQL 短时不可用、OSS 不可用、LLM Provider 超时、TTS Provider 超时、Chrome worker 连续崩溃、网络抖动。

每一种情况都要明确：系统行为、用户看到的状态、是否自动恢复、是否需要人工介入、数据是否丢失。

## 十、架构底线

后续所有开发遵守以下约束：

- 不把某个平台协议写进 Core 主流程。
- 不把 Chrome 当成唯一采集方案。
- 不做“一房间一个 Agent 进程”。
- 不把永久业务数据只放 Redis。
- 不把媒体永久保存在 ECS 本地盘。
- 不让非幂等业务因为故障切换被自动重复执行。
- 不把一个客户永久绑定到某台 Core 或 Agent Worker。
- 所有重要状态必须可以恢复、追溯和重新调度。
- 优先保持简单架构，真实规模需要时再拆服务，不为了“看起来高级”提前引入复杂中间件。
