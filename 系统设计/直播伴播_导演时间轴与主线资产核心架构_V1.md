# 直播伴播 V1：导演时间轴、主线资产与实时策略系统详细设计

> 状态：V1 核心架构定稿 / 核心纯状态模块已开始落地  
> 日期：2026-09-25  
> 项目：小蓝直播伴播  
> 当前默认 Agent：qwen3.8-flash（通过 Agent Gateway）  
> 当前默认 TTS：qwen-audio-3.0-tts-plus（通过 TTS Gateway）  
> 核心原则：Timeline 是直播间记忆，Strategy Pin 是行为记录，Director 是决策者，Agent 是话术创作者，Scheduler 是执行者。

---

## 1. 目标

系统不再被理解为“收到问题 -> 大模型回答 -> TTS 播放”。

正式目标是：

1. 开播即建立唯一直播节目时间轴。
2. 主线音频不是普通 WAV，而是带语义地图的可调度资产。
3. Core 持续扫描公屏，把大量原始事件压缩成“房间状态 + 语义桶 + 短期记忆”。
4. Director 根据直播进度、房间氛围、主播风格、仿真人行为、回接策略联合决策。
5. Agent 负责把 DirectorPlan 写成自然话术，不直接控制播放器。
6. TTS 只负责把最终话术变成声音，厂商通过 Gateway 隔离。
7. Scheduler 只执行已经确认的播放计划，不理解 Qwen、不理解销售策略。
8. 所有行为写回 Runtime Timeline，后续生成前回溯，防止机械重复。
9. 主线尽可能资产化、缓存化，昂贵的大模型/TTS实时调用只用于真正需要变化的部分。

# 3. 开播即建立 Session Timeline

每次直播开始必须创建一个唯一：

- room_id
- session_id
- timeline_id
- started_at

此 Timeline 一直到直播结束。

Timeline 分两层。

## 3.1 Planned Timeline：计划时间轴

表示“这场直播原本准备怎么讲”。

例如：

~~~text
开场
-> 产品身份
-> 产地
-> 饲养
-> 肉质
-> 吃法
-> 物流
-> FAQ
-> 轻CTA
-> 转成交节点
-> 收口
~~~

这里不是简单的秒数，而是 Semantic Node。

每个节点至少有：

- node_id
- topic
- semantic_goal
- asset_candidates
- allowed_entry
- allowed_exit
- fact_ids
- strategy_tags
- next_candidates
- priority

Director 可以正常顺序走，也可以通过 Bridge 跳到另一个节点。

例如：

~~~text
当前：肉质介绍
Director判断：现在成交势能高
-> 等下一个 Safe Exit
-> 生成 Bridge
-> 跳 conversion_02 Safe Entry
~~~

## 3.2 Runtime Timeline：真实运行时间轴

记录实际发生的一切：

- 主线播到了哪里
- 哪个问题被回答
- 哪个 Topic Bucket 被聚合回答
- 哪次点赞 CTA 已经说过
- 哪次强成交已经执行
- 哪次开玩笑
- 哪次咳嗽/清嗓/重复
- 哪次桥接
- 哪种 Resume Strategy 被采用
- 跳到了哪个主线节点
- 房间从 WARM 进入 HOT 等

Runtime Timeline 是 Director 的真实记忆来源。

# 4. Strategy Pin：策略钉

每次有意义的导演行为都写入时间轴。

示例：

~~~json
{
  "at": "12:33:18",
  "kind": "CTA",
  "strategy": "conversion.push",
  "topic": "PRICE",
  "mainline_unit": "meat_03",
  "text_digest": "...",
  "metadata": {
    "room_heat": "HOT",
    "reason": "conversion_debt_high"
  }
}
~~~

典型 Pin：

- STRATEGY
- QUESTION
- ANSWER
- CTA
- HUMOR
- HUMANIZATION
- BRIDGE
- RESUME
- NODE_JUMP
- MAINLINE_TOPIC

生成新话术之前，Director 必须先读取 Timeline View。

目的：

1. 防止一分钟内重复要点赞。
2. 防止刚开完玩笑又开。
3. 防止重复回答刚回答的问题。
4. 防止连续强逼单。
5. 知道哪些产品主题已经讲过。
6. 知道刚才用了哪种仿真人行为。
7. 知道当前观众是否已经换了一批，某些核心信息是否可以重新讲。

# 5. 动态 Hot Window

不把几小时直播原文全部塞给 Agent。

采用：

## 5.1 Hot Window：完整短期记忆

默认：

- HOT / OVERHEATED：3 分钟
- BUSY：5 分钟
- WARM：8 分钟
- COLD：10 分钟

第一版接受“普通房间约 5 分钟”的业务直觉，但做成动态。

原因：

高热直播间观众流动快，3分钟前的听众可能已经大量更换；冷房间同一批观众留得更久，短时间重复反而明显。

## 5.2 Compressed Memory：超过窗口的摘要

超过 Hot Window 的 Pin 不删除，而是压缩：

- 各种行为累计次数
- 最近一次发生时间
- 某 Topic 本场讲过几次
- 最近一次强 CTA
- 最近一次回答价格
- 最近一次玩笑
- 最近一次 Humanization
- 主线哪些主题已覆盖

Agent 不需要看到旧原文，只需要摘要。

---

# 6. Audience Turnover：观众换血率

重复控制不能只依赖“5分钟之前讲过”。

重要指标：

~~~text
AudienceTurnover5m
= 最近5分钟进房量 / 当前在线人数
~~~

例如：

当前在线 1000，最近5分钟进房 3000。

说明观众换血非常快。

这时：

- 核心卖点可更快重新开放。
- 价格/物流/购买方法可以再次统一说明。
- 但不能机械复读同一句话。

因此正式规则：

**事实可以重复，话术不能机械重复。**

重复容忍度由：

- 观众换血率
- 主题重要度
- 距离上次讲述时间
- 近期重复次数
- 当前房间状态

共同决定。

# 7. Topic Bucket Pool：公屏语义桶

原始弹幕不能逐条送给 Agent。

先进入 Topic Bucket Pool。

例如：

~~~text
“多少钱”
“什么价格”
“一只好多钱”
“有没有优惠”
~~~

被聚成：

~~~json
{
  "topic": "PRICE",
  "count": 27,
  "unique_users": 19,
  "last_seen_at": "...",
  "last_answered_at": "...",
  "sample_questions": ["多少钱", "今天什么价格"]
}
~~~

建议初始 Topic：

- PRICE
- SHIPPING
- HOW_TO_EAT
- SPEC
- ORIGIN
- STORAGE
- AFTER_SALE
- QUALITY
- COUPON
- ORDERING
- GENERAL_CHAT
- NEGATIVE / DOUBT

后续可以通过语义分类器动态扩展，不应该硬写死全部分类。

# 9. 大房间和小房间的问答策略

不简单用在线人数，而主要用 Question Pressure。

~~~text
QuestionPressure
= 有效问题速度 / 系统合理回答能力
~~~

## 9.1 低压力 / 小房间

Director 偏向：

- 一对一回应
- 可点昵称
- 增加轻互动
- 适当追问
- 更重视留人

## 9.2 高压力 / 高热房间

Director 偏向：

- 不逐个问题回答
- Topic Bucket 聚合
- 只回答 Top N 高频问题
- 1 次回答覆盖一个问题簇
- 尽快回到主线
- 保留成交节奏

示例话术：

“我看大家现在问得最多的就是发货和怎么吃，这两个我一起给大家说一下。”

# 10. Strategy Debt：策略需求积累

禁止用固定定时器实现：

- 每5分钟要点赞
- 每10分钟逼单
- 每3分钟互动

改成 Strategy Debt。

初始 Debt：

- INTERACTION
- LIKE_CTA
- FOLLOW_CTA
- CONVERSION
- QUESTION

Debt 随房间状态积累。

例如：

- 冷场 -> Interaction Debt 增加
- 进房很多但点赞弱 -> Like Debt 增加
- 产品核心价值已覆盖、成交势能上升、很久未 CTA -> Conversion Debt 增加
- 高频问题持续增长 -> Question Debt 增加

执行一次后：

~~~text
Spend Debt
-> debt = 0
-> 进入 cooldown
~~~

Cooldown 内即使 Debt 又开始积累也不能马上再次触发。

正式思想：

**需求积累 -> 条件成熟 -> 策略释放 -> Strategy Pin -> 冷却。**

# 11. Director 五路策略

Director 最终不直接生成音频，而是生成 DirectorPlan。

五类策略：

## 11.1 Progress Strategy：直播进度

决定：

- 继续主线
- 暂停推进优先答疑
- 聚合回答
- 热场
- 推进成交
- 切新主题
- 放弃旧计划重新选安全入口

## 11.2 Atmosphere Strategy：节奏/氛围

决定：

- NEUTRAL
- WARM_UP
- CELEBRATE
- LIGHT_HUMOR
- CALM_AND_FOCUS

例如：

- 冷房间 -> 提高互动
- 连续下单 -> 轻庆祝
- 负面/投诉 -> 收稳
- 太躁 -> 降节奏
- 高热 -> 减少低价值互动

## 11.3 Style Strategy：主播风格

长期学习的内容：

- tone
- sentence rhythm
- fillers
- repetition style
- CTA style
- humor ceiling
- transition style

Style 只决定“怎么说”。

不得携带样本中的产品事实。

## 11.4 Humanization Strategy：仿真人行为

独立于 Style。

行为：

- PAUSE
- FILLER
- REPEAT_FRAGMENT
- SELF_CORRECTION
- INVERSION
- REHOOK
- THROAT_CLEAR
- COUGH

必须：

- 低频
- 冷却
- 每分钟数量上限
- 投诉/售后/价格争议/高意向成交时抑制
- 不得引入新商品事实

非语言事件：

1. TTS Provider 支持 paralinguistic mark -> Provider 表达。
2. Provider 不支持但有预录资产 -> 插 Humanization Micro Segment。
3. 都不支持 -> 降级为自然 pause。

禁止让 Agent 文本直接写“咳咳”。

## 11.5 Resume Strategy：语义回接

当前内置：

1. DIRECT
2. BRIDGE
3. FUSION_SKIP
4. CROSS_RESUME
5. RE_ANCHOR
6. SWITCH_PLAN

采用 Registry。

以后新增第 7、第 8 种：

只实现 Strategy 并 Register。

Scheduler 不需要修改。

# 13. Interaction Builder

收到值得回应的事件后，主线继续播放。

Interaction Builder 同时看到：

- 当前主线 Unit
- 当前 Topic
- 当前 Safe Point
- 后续 2～4 个 Unit
- DirectorPlan
- Topic Bucket
- 最近 Hot Pins
- 全场压缩摘要

Agent 一次产出：

~~~json
{
  "reply_core": "...",
  "resume_tail": "...",
  "covered_topics": [],
  "covered_fact_ids": [],
  "suggested_skip_units": [],
  "suggested_resume_unit": "",
  "suggested_resume_mode": "BRIDGE"
}
~~~

关键原则：

**Bridge 必须在进入 TTS 前已经写好。**

不能回答播完再临时生成一句“接回去”。

推荐：

~~~text
final_interaction_text
= reply_core + resume_tail
~~~

一次 TTS，保证回答和桥接语气连续。

程序再将 Agent 的 Resume 建议交给 Resume Registry 校验。

# 14. 主线不是 WAV，而是 Schedulable Semantic Audio Asset

任何进入主线资产库的音频都必须有 Semantic Manifest。

Asset：

- asset_id
- role
- pool
- quality
- final_text
- audio_uri
- duration_ms
- semantic_units
- alignment
- safe_entry_points
- safe_exit_points
- strategy_nodes
- fact_ids
- cache_key
- voice/model/style version
- play_count / last_played_at

没有语义地图的音频：

**只能算普通音频文件，不算可调度主线资产。**

# 16. Safe Exit / Safe Entry

不能只检测“静音”。

需要：

**语义完整性 + 声学停顿 + 后续可接性**

等级：

- A：HARD SAFE
- B：SOFT SAFE
- C：仅高优事件使用
- FORBIDDEN：禁止切

禁止位置：

- 数字中间
- 价格中间
- 商品名中间
- 否定关系中间
- 因果关系未结束
- 半句话
- CTA 说到一半

Safe Entry 与 Safe Exit 同等重要。

因为：

~~~text
主线 -> Safe Exit
-> Bridge TTS
-> 另一个主线节点 Safe Entry
~~~

这样才能自然跳到逼单、FAQ、吃法等节点。

# 17. 新主线资产生成：通常只调用一次 LLM

最优流程：

~~~text
LLM
-> 最终文本 + Semantic Manifest

TTS
-> 最终声音 + Provider timestamp（如果有）

Alignment
-> Unit 映射到真实毫秒

Safe Point Analyzer
-> Safe Entry / Exit

Asset Validator
-> 合格后入库
~~~

职责：

- LLM：语义
- TTS：声音
- Alignment：时间
- Safe Point Analyzer：切点
- Director：什么时候使用

新生成文本时已经知道语义，因此音频生成后通常不需要再调用大模型分析一次。

只有：

- 真人历史录音
- 没有 Manifest 的旧资产
- 外部导入音频

才需要：

ASR + Semantic Parser 补结构。

# 18. 主线资产池与成本控制

四个 Pool：

## 18.1 Evergreen Pool

长期复用资产。

例如：

- 产品身份
- 产地
- 工艺
- 肉质
- 吃法
- 品牌故事

这些内容变化少，应最大化复用。

## 18.2 Session Pool

本场直播生成一次，本场复用。

例如：

- 今日活动解释
- 今日发货安排
- 今日主推方向
- 今日成交话术

直播结束后表现好可以升级到 Evergreen。

## 18.3 Dynamic Pool

实时生成。

只用于：

- 问答
- bridge
- 聚合问题
- 房间热场
- 突发事件
- 少量动态成交桥接

## 18.4 Humanization Pool

极短微音频：

- 轻咳
- 清嗓
- 呼吸/停顿资产（如需要）

# 19. 主线版本不随机轮换

每个语义节点可以有 2～5 个 Variant。

但不能 random(A/B/C)。

Director 根据：

- 最近 5 分钟播过哪个版本
- 当前观众换血率
- 本 Topic 最近讲过几次
- 当前房间状态
- 当前前后节点
- 资产质量等级
- play_count
- last_played_at

选择版本。

目标：

**业务核心稳定，表达看起来有变化。**

# 20. Asset Quality

建议：

- GOLD：人工确认，高优使用
- SILVER：自动检测通过，可正常使用
- EXPERIMENTAL：新生成，本场低频试播
- RETIRED：过期或表现差，不再使用

直播运行数据可以逐步升级/降级资产。

# 21. TTS Cache

缓存键至少：

~~~text
normalized_text_hash
+ voice_id
+ tts_provider
+ tts_model
+ style_version
+ prosody_version
+ speed
~~~

只要 Key 不变：

**不允许重新请求 TTS。**

这会成为后期主要成本控制手段之一。

# 23. 音频调度

房间保持：

**双音频准备，单音频输出。**

~~~text
Slot A
Slot B
~~~

A/B 是 buffer，不是永久角色。

例如：

~~~text
A = 主线
B = Interaction READY

Safe Exit
A -> B

B 播 reply_core + resume_tail
A 同时准备 Resume Mainline

B 完成
B -> A
~~~

外部设备只看到一条房间连续声音。

# 24. Strategy Pin 写回闭环

一次 Director 决策完成后，不是结束。

必须写回：

1. 选择了什么策略。
2. 实际生成了什么话术 digest。
3. 播了什么资产。
4. 回接到哪。
5. 使用了什么 Humanization。
6. Topic Bucket 哪些被标记 answered。
7. 对应 Strategy Debt 被 Spend。
8. 运行结果。

因此形成：

~~~text
Observe
-> Decide
-> Generate
-> Play
-> Pin
-> Learn next decision
~~~

# 26. 落地阶段

不建议一次把所有能力接到真实直播。

目标：

- roomintel
- timeline
- director

- resume

全部纯 Go 单测跑通。

不接真实 TTS。

## Phase 2：Timeline + 公屏实时输入

把 Core 当前：

- chat

- Heat
- Question Pressure
- Audience Turnover
- Top Topic Buckets
- Hot Window
- Strategy Pins
- Strategy Debts

此阶段不自动说话。

## Phase 3：主线 Asset Builder

从现有母带测试升级：

输入：

~~~text
最终文本 + Semantic Manifest
~~~

生成：

~~~text
Qwen TTS
+ word_timestamp
+ alignment
+ Safe Entry/Exit
+ strategy nodes
~~~

最终输出一个标准 Mainline Asset。

测试 3～5 个 Variant。

## Phase 4：Director Shadow Mode

Director 实时运行，但不控制声音。

页面显示：

~~~text
如果现在让我决定：
Progress = ...
Atmosphere = ...
Humanization = ...
Resume = ...
建议回答 = ...
建议跳转节点 = ...
~~~

和真人场控判断对照。

这是非常重要的一步。

## Phase 5：真实 Interaction + TTS

人工输入问题。

完整链路：

~~~text
Topic / Question
-> DirectorPlan
-> Agent reply_core + resume_tail

-> READY

-> Interaction
-> Safe Entry
-> Resume
~~~

## Phase 6：自动房间策略

逐步开放：

1. 自动聚合问题。
2. 自动低流量互动。
3. 自动点赞/关注 CTA。
4. 自动成交推进。
5. 自动 Humanization。
6. 自动主线节点跳转。

每类策略可独立开关。

# 27. 测试总方案

## Test A：主线资产解析

准备 60～120 秒母带。

检查：

- Units 是否完整
- 时间戳是否正确
- Safe Point 是否落在自然位置
- Entry/Exit 是否都可用
- 不允许在数字/价格/半句中切

成功标准：

人工听 30 个随机切点，明显突兀率低于预设阈值。

## Test B：主线 Variant

同一个 Topic 准备 3 个版本。

连续播 30 分钟。

验证：

- 不机械随机
- 近期不重复同版本
- 换血率高时允许核心内容重新开放
- 资产选择可解释

## Test C：低流量房间

模拟：

~~~text
在线 20
30秒进房 2
30秒聊天 1
~~~

预期：

- Heat = COLD/WARM
- PreferOneToOneQNA = true
- Interaction Debt 上升
- Director 增加互动
- 不频繁逼单

## Test D：高热房间

模拟：

~~~text
在线 1000
30秒进房 100
30秒弹幕 60
问题 40
~~~

预期：

- HOT / OVERHEATED
- PreferAggregateQNA = true
- Topic Bucket 排名
- Director 不逐个点名
- 一次回答 Top Topic
- 主线占比明显提高

## Test E：5分钟时间钉

连续模拟 20 分钟。

检查：

- Hot Window 只保存动态窗口内完整 Pins
- 超过窗口进入 Summary
- Agent 输入大小不随直播时长线性增长
- 老主题统计仍可用

## Test F：Strategy Debt

验证：

- 冷场 Interaction Debt 上升
- 执行互动后清零
- cooldown 内不能马上再次触发
- CTA 同理

## Test G：Humanization

运行 1 小时模拟。

验证：

- 不会每句话重复/咳嗽
- cooldown 生效
- 每分钟上限生效
- 投诉场景强制关闭
- 不引入商品新事实

## Test H：六种 Resume

分别人工构造：

- DIRECT
- BRIDGE
- FUSION_SKIP
- CROSS_RESUME
- RE_ANCHOR
- SWITCH_PLAN

重点听：

- 是否重复刚回答过的主线
- Bridge 是否自然
- 是否硬接旧话题
- 是否跳到可独立进入 Unit

## Test I：真实 Agent + TTS

网页：

- 输入问题
- 目标 10s / 20s
- Agent provider/model
- TTS provider/model
- voice_id

页面显示：

- DirectorPlan
- reply_core
- resume_tail
- selected resume strategy
- Agent latency
- TTS latency
- actual WAV duration
- selected Safe Exit
- selected Safe Entry

## Test J：双浏览器

A/B 浏览器同时接房间。

验证：

- 主线一致
- 晚加入追当前房间时间轴
- Interaction 同时切入
- Resume 同时切回
- 设备不能改变房间主时钟

## Test K：长稳态

至少运行 2～4 小时。

验证：

- Segment Sequence 连续
- A/B 槽轮换正常
- Strategy Pin 不无限增长
- Topic Bucket 自动过期
- Agent Context 大小稳定
- 内存无持续增长
- 不出现同一个 CTA 高频重复
- 不出现 Humanization 越播越密

## Test L：成本

记录每小时：

- Agent 请求次数
- Agent input/output token
- TTS 请求次数
- TTS 字符数
- Cache Hit Rate
- Evergreen 使用比例
- Session Asset 使用比例
- Dynamic TTS 比例

目标趋势：

随着资产库成熟，单小时生成成本持续下降。

# 29. V1 验收标准

系统通过 V1 的标准：

1. 主线连续数小时，不因 Agent/TTS 等待而空场。
2. 主线资产具备语义位置，不依赖裸 currentTime。
3. 公屏大量问题可以聚合，不逐条轰炸 Agent。
4. 小房间明显更互动，大房间明显更克制。
5. 5分钟左右短记忆能抑制机械重复，同时不会无限吃 Token。
6. 核心卖点可以在高换血房间自然重复，但不是复读旧话术。
7. CTA/点赞/关注由 Debt + cooldown 控制，不固定定时。
8. Humanization 是低频自然行为，不成为“AI故意装人”。
9. 回答生成时已经有 Bridge，播放完不会临时硬接。
10. Resume 是语义回接，不是简单回原毫秒。
11. Agent/TTS 供应商可以替换，不改 Director/Scheduler。
12. 主线缓存命中率逐渐升高，单小时生成成本逐渐下降。
13. 两个或多个接收端听到的始终是一条权威房间声音。

# 30. 最终架构定义

以后整个系统统一理解为：

**Semantic Mainline Asset Library  
+ Room Intelligence  
+ Session Timeline / Strategy Memory  
+ Live Director  
+ Agent Speech Builder  
+ TTS Gateway  
+ Semantic Resume  
+ Single Authoritative Room Audio Scheduler**

中文：

**“有主线资产、有房间感知、有短期记忆、有导演决策、有自然话术、有语义回接、最后只有一条房间声音。”**

这是后续所有开发的核心边界。
