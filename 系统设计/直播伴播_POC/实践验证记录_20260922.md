# 直播伴播第一次实践验证记录

日期：2026-09-22

## 1. 验证目的

不是验证某个大模型“回答得好不好”，而是先验证系统架构最关键的五件事：

- 是否真的能减少 Agent Token。
- 主线是否能被自然打断。
- 打断后是否能恢复。
- 旧任务是否会迟到播放。
- 两个 Agent 是否可以保持职责分离。

## 2. 本次场景

### 场景 1：主线播放 + 低价值事件

输入普通用户进房和低阈值点赞。

结果：两个事件都被 Event Engine 规则层直接处理，Agent 调用 0，Token 0。

结论：所有事件可以进入监控体系，但绝不能等于所有事件都调用监控大模型。

### 场景 2：用户问价格

主线播放时用户问“这个多少钱？”。

结果：Event Engine 本地命中 PRICE_QUERY，Monitor Agent 和 Control Agent 均未调用；使用价格模板生成文本；当前主线短句播完后 SOFT_INTERRUPT；回答价格后从下一完整主线句恢复。

结论：高频标准问题应该尽可能在 Agent 前截断。

### 场景 3：复杂用户问题

用户问“这个给家里老人吃合适吗？”。

结果：规则不能直接确定完整动作，调用 Monitor Agent；再调用 Control Agent 生成自然口语；当前短句播完后插入互动；互动后使用模板桥接语，再从下一完整主线句恢复。

结论：两个 Agent 的职责拆分可工作；桥接语无需每次让模型生成。

### 场景 4：逼单任务产生后商品切换

近期加购 12、成交 2，系统触发 TIMER_SALES_PUSH_DUE。Monitor Agent 判断需要轻逼单，场控层生成逼单模板，但逼单尚未播放时商品切换。

结果：product_context_version 从 1 升级到 2；旧逼单任务版本失效；Audio Focus 执行前丢弃旧任务；原商品主线也停止。

结论：SpeechTask 必须绑定 product_context_version / room_context_version。只有 TTL 不够，版本控制是防止“迟到话术”的关键。

### 场景 5：重复事件

同一个 event_id 连续进入两次。

结果：第二次直接去重，Agent 调用 0。

## 4. 已证明可行的设计

### 4.1 Token Gate 必须保留

实践验证链路合理：

~~~text
原始事件
→ 规则过滤
→ Monitor Agent（必要时）
→ 模板/缓存
→ Control Agent（必要时）
~~~

不能改回“事件 → Agent → Agent → TTS”。

### 4.2 SOFT_INTERRUPT 作为默认策略

本次 POC 中，用户问题到达后没有切断正在说的半句话，而是在当前 Segment 结束后切入互动。

HARD_INTERRUPT 保留给人工停止、风险内容、商品/上下文彻底失效和设备异常。

### 4.3 Resume Point 必须是语义/句子级

当前恢复位置保存为“下一完整 Segment”。

~~~text
mid_sentence_resume_count=0
~~~

这个指标后续必须长期保持为 0。

### 4.4 版本失效比单纯优先级更重要

一个优先级很高的旧商品任务，在商品切换后也必须立即失效。

后续至少需要：

~~~text
product_context_version
room_context_version
config_version
~~~

其中前两个进入 SpeechTask。

## 5. POC 暴露出的下一批问题

### 问题 1：单个 pending_interrupt 不够

正式实现需要 Priority Queue、同类 Action 合并、新事件覆盖旧事件规则、每类 Action 独立 TTL。

### 问题 2：Audio Focus 需要独立状态机

正式实现必须明确：

~~~text
IDLE
PLAYING_MAIN
INTERRUPT_PENDING
PLAYING_INTERACTION
RECOVERING
PAUSED_BY_HUMAN
~~~

不能长期靠零散 if/else 维护。

### 问题 3：需要真实 TTS 测听感

逻辑正确不代表听起来自然。第二阶段必须实际测试 Segment 多长最自然、软打断等待多久仍可接受、桥接语是否啰嗦、TTS 首包延迟以及句间停顿。

### 问题 4：需要真实并发测试

本次是单房间。后续至少跑 3 房间、20 房间，重点验证 Room State、Agent Session、Audio Queue、Token 计量不串，以及单房间慢请求不阻塞其他房间。

## 6. 本轮结论

第一轮实践没有发现需要推翻整体架构的问题。

目前更有把握的核心原则是：

> 事件一直监听，但大模型按需调用；  
> 主线可以被打断，但默认在完整短句处打断；  
> 恢复的是语义，不是音频毫秒位置；  
> 所有待播内容在真正执行前必须再做一次有效性检查；  
> 商品/房间上下文版本发生变化时，旧任务宁可丢弃，也不能迟到播放。

下一轮应从“纯逻辑 POC”进入“真实声音 POC”。
