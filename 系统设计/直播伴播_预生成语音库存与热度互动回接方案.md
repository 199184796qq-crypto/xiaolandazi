# 直播伴播：预生成语音库存、热度互动与语义回接方案

> 状态：方案定稿草案（仅落盘，不进入代码实现）
>
> 日期：2026-09-22
>
> 目标：把直播伴播从“边播边调用模型生成”调整为“预生成高质量内容与音频为主、实时互动调用模型为辅”的运行架构，降低模型/TTS成本、减少延迟、提高稳定性，并解决直播语音被互动打断后的自然回接问题。

---

## 1. 核心决策

当商品、活动、价格、优惠、主播风格、合规规则等关键条件未变化时，不再持续实时生成主线口播。

系统改为：

1. 一次生成多套不同表达的主线文案。
2. 文案按自然语义切段。
3. 每段提前完成 TTS。
4. 文案、段落状态、播放游标、断点信息存 Redis。
5. 音频文件存 OSS，终端按版本下载到本地缓存。
6. 直播过程中以“本地播放预生成音频”为主。
7. 只有真正需要实时互动、复杂问答、异常事件时才调用模型。
8. 互动频率由直播间热度控制，不由大模型自由决定。
9. 被打断时不在句中硬切，使用“语义书签 + 回接桥”恢复主线。
10. 长时间中断后不强行续接旧稿，直接切到新一套内容的安全入口。

最终目标：

**正常直播 80%～95% 的时间不需要实时调用大模型生成主线内容。**

---

## 2. 总体运行架构

主流程：

商品/活动/事实配置
→ 计算 Content Fingerprint
→ Speech Bank 内容库存
→ 多套文案生成
→ 语义切段
→ 提前 TTS
→ 音频上传 OSS
→ Redis 保存索引与播放状态
→ 终端下载本地缓存
→ 本地连续播放

实时事件流程：

直播间事件
→ Heat Controller 判断当前热度
→ Event Priority 判断事件价值
→ FAQ/缓存回答优先
→ 必要时调用模型
→ 播放互动回答
→ Semantic Bookmark 恢复
→ Resume Bridge 回接
→ 继续本地 Speech Bank

## 3. Content Fingerprint：内容版本指纹

Speech Bank 是否可以继续使用，不看“时间”，而看内容条件是否变化。

建议指纹至少由以下内容共同决定：

- 商品事实版本
- SKU/规格版本
- 活动版本
- 当前价格版本
- 优惠/券版本
- 库存策略版本
- 赠品版本
- 物流信息版本
- 主播风格版本
- 合规规则版本
- 口播 Prompt Kernel 版本
- TTS 模型
- 音色 ID
- 语速/情绪/指令版本

只要上述关键条件未变，则 fingerprint 不变。

Fingerprint 不变：
- 继续复用 Speech Bank
- 不重复生成主线文案
- 不重复 TTS
- 终端无需重新下载

Fingerprint 变化：
- 创建新 Speech Bank 版本
- 后台生成新文案
- 生成新音频
- OSS 发布新版本
- 终端增量更新
- 老版本进入可回收状态

这样可以保证：
**商品和活动不变，就尽量一次生成、反复使用。**

## 4. Speech Bank：主线文案/语音库存

### 4.1 目的

Speech Bank 不是一篇循环稿，而是一批“同一商品、同一事实、同一活动下的不同表达”。

每个 Bank 维持多套独立口播计划，例如：

- A：商品身份 + 产地 + 养殖重点
- B：活动量 + 鸡皮 + 肉质重点
- C：饲喂 + 现杀 + 内脏重点
- D：规格 + 原切重点
- E：物流 + 做法重点
- F：消费者常见疑虑导入
- G：细节观察型表达
- H：问题式开场
- I：产品故事型表达
- J：轻 CTA 型收口

骨架可以稳定，但开场、重点、过渡、收口、句式需要变化。

当前已经验证的“稳定骨架 + 动态表达”继续保留，只是从“直播时生成”迁移到“后台批量生成”。

### 4.2 库存水位

建议初始参数：

- 目标库存：12 套
- 低水位：4 套
- 低于 4 套时后台补充 6 套
- 单套可由 8～16 个语义段组成
- 最近播放过的内容进入冷却窗口，避免短时间重复

以后可根据直播时长与重复率动态调整。

### 4.3 去重

Speech Bank 新增内容时，不仅检查全文相似度，还需要检查：

- 开场相似度
- 连续长短语相似度
- 转场句相似度
- 收口相似度
- 核心卖点排列方式

事实可以重复，表达不能机械重复。

## 5. 语义切段原则

不能再按“固定 7 段”理解主线。

切段必须以自然语义为边界，例如：

- chunk_01 商品身份
- chunk_02 皖南来源
- chunk_03 养殖方式
- chunk_04 活动量
- chunk_05 鸡皮/肉质
- chunk_06 饲喂
- chunk_07 现杀
- chunk_08 鸡胗/鸡肝/鸡心
- chunk_09 原切定义
- chunk_10 规格
- chunk_11 物流
- chunk_12 做法
- chunk_13 收口/轻 CTA

每个 chunk 应满足：

1. 自己听起来是一个完整意思。
2. 可以自然作为“停止点”。
3. 下一个 chunk 可以被自然恢复。
4. 尽量避免一句话被拆成两个音频。
5. 单段不应太长，以免无法及时响应关键互动。
6. 单段也不应太短，避免播放碎片化。

目标是：
**可打断，但听起来不是“分段播放”。**

## 6. 音频存储策略

### 6.1 Redis 不存大音频

Redis 只保存：

- speech_bank_id
- fingerprint
- plan_id
- chunk_id
- 文案文本
- 音频 URL/路径
- 音频时长
- TTS 模型
- voice_id
- 播放次数
- 最近播放时间
- 冷却状态
- 当前播放游标
- 断点
- 热度状态
- 待回答队列
- resume bridge 索引

不建议把 WAV/MP3 二进制长期塞进 Redis。

### 6.2 OSS

OSS 保存正式音频资产。

建议路径逻辑：

room/customer
→ fingerprint
→ plan
→ chunk
→ audio

OSS 作为：
- 中央音频源
- 多终端分发源
- 新版本同步源
- 灾备源

### 6.3 终端本地缓存

盒子/终端拿到新的 fingerprint 后：

1. 比较本地版本。
2. 只下载新增或变化的音频。
3. 下载完成后校验。
4. 更新本地 manifest。
5. 播放时优先使用本地文件。
6. OSS 只负责首次下载和版本更新。

正常播放不反复访问 OSS。

### 6.4 音频格式

开发和质量校验阶段可以保留 WAV。

正式长期分发优先考虑较高质量压缩音频，例如 MP3/AAC/Opus，具体格式根据播放器稳定性和听感测试决定。

原则：
- TTS 原始高质量版本可以留存。
- 终端分发版本尽量降低带宽和磁盘占用。
- 不以牺牲直播听感为前提。

## 7. Heat Controller：直播间热度控制

大模型不直接决定“要不要互动”。

由确定性的 Heat Controller 先判断直播间状态。

建议分级：

- COLD：冷场
- WARM：正常
- HOT：热场
- VERY_HOT：高热

### 7.1 热度输入

可以综合以下时间窗口：

最近 30 秒、2 分钟、5 分钟：

- 在线人数
- 在线人数变化率
- 进房速度
- 评论速度
- 有效问题数量
- 点赞速度
- 商品点击
- 加购
- 下单/成交
- 粉丝团/关注
- 礼物等平台事件
- 当前主播/AI 是否连续发声
- 最近是否已回答过问题

不要只看在线人数绝对值。

不同体量直播间需要按“自身基线”做判断。

### 7.2 热度对应互动策略

#### COLD

目标：增加互动，避免单向念稿。

策略：
- 更积极挑问题回答
- 可以主动调用历史 FAQ
- 可以适当欢迎/互动
- 主线允许较频繁软打断
- 可以用观众问题带回商品

#### WARM

目标：主线和互动平衡。

策略：
- 有价值问题回答
- 重复问题合并
- 一般问题进入短队列
- 控制打断频率

#### HOT

目标：保护主线节奏。

策略：
- 减少普通问答
- 只回答高价值问题
- 重复问题走缓存
- 尽量不打断高转化主线
- 普通问题延迟到自然窗口

#### VERY_HOT

目标：最大限度保护高热主线。

策略：
- 普通问题基本不即时回答
- 高优先级问题才插入
- 优先继续产品塑造/活动说明/转化
- 大量重复问题进入 FAQ 统计，不逐条回应

核心原则：

**直播间越热，越少打断；直播间越冷，越需要互动。**

## 8. 问题回答的成本分层

所有观众问题不应直接进入大模型。

优先级：

### L0：忽略

包括：
- 无意义刷屏
- 已处理重复事件
- 与当前场景无关低价值文本

不调用模型，不播放回答。

### L1：预制 FAQ 音频

例如：
- 多重
- 生的还是熟的
- 发什么快递
- 几天到
- 怎么做
- 原切是什么
- 小母鸡几个月

命中标准 FAQ：
直接播放已缓存回答。

大模型调用：0
TTS 调用：0

### L2：事实模板回答

问题可以从结构化事实直接回答，但没有对应预制音频。

使用确定性模板组装文本。

大模型调用：0
TTS：必要时实时生成，后续可进入缓存。

### L3：复杂问答

需要理解上下文、重组信息、解释或自然回应。

才调用 Qwen3.8-Flash 等语言模型。

回答生成后：
- 通过事实约束
- 合规检查
- TTS
- 如果属于高频问题，可以沉淀成 FAQ 缓存

### L4：事实不足/高风险

现有资料不能确认：
- 不猜
- 不自动补事实
- 转人工/客服
- 或简短说明现有信息不足

## 9. Semantic Bookmark：语义书签

这是新架构里最关键的播放器能力之一。

每次播放必须知道：

- 当前 plan_id
- 当前 chunk_id
- 当前 chunk 是否已完整播放
- next_chunk
- 当前语义主题
- 当前计划剩余长度
- 最近已讲过哪些主题

当出现允许打断的事件时：

**原则上不在一句话或一个语义段中间硬切。**

正常过程：

正在播放 chunk_05
→ 收到值得回答的问题
→ 标记 pending_interrupt
→ 当前 chunk_05 播完
→ 写 bookmark
→ 播放互动回答
→ 根据中断长度和上下文选择回接方式

Bookmark 至少包含：

- bank_id
- plan_id
- current_chunk
- next_chunk
- current_topic
- resume_topic
- interrupted_at
- interrupt_reason
- interruption_duration
- resume_mode

## 10. Resume Bridge：自然回接机制

不能每次都说：

- “回到正题”
- “继续刚才的话题”
- “接着聊”
- “刚才说到”

这些重复会非常像机器人。

### 10.1 DIRECT：直接续播

适用：
- 回答很短
- 中断约 3～6 秒
- 下一个 chunk 自身可以自然开头

处理：
互动回答结束
→ 直接 next_chunk

不增加额外模型调用。

### 10.2 BRIDGE：回接桥

适用：
- 中断约 6～20 秒
- 下一个 chunk 直接播放略显突兀
- 需要一句自然铺垫

每个语义节点提前准备多个 Resume Bridge，并提前 TTS。

例如：

原顺播：

“它平时活动量比较大，再说到平时吃的这一块……”

被打断后可选择：

“鸡本身咱们再往下说，它平时怎么吃这一块也可以看一下……”

或者：

“前面养殖环境咱们讲到了，接下来其实饲喂这块也很关键……”

桥接句也要动态多样，不固定一个句式。

### 10.3 SWITCH_PLAN：切换新稿

适用：
- 中断超过约 20～30 秒
- 连续回答多个问题
- 互动导致原主线语境已经丢失
- 当前 plan 剩余内容不适合硬续

处理：
- 放弃当前 plan 剩余部分
- 标记已讲主题
- 从另一套 Speech Bank 中选择安全入口
- 避免重新讲刚刚说过的内容

这样比强行说“我们接着刚才讲”自然得多。

## 11. 打断优先级

不是所有事件都能打断。

可建立优先级：

P0：系统安全/人工接管/严重异常
→ 立即处理

P1：高价值购买问题
→ 根据热度决定是否当前 chunk 后打断

P2：高频真实疑问
→ COLD/WARM 可回答，HOT 延迟

P3：欢迎、普通互动
→ COLD 优先，HOT 基本不打断

P4：刷屏/重复/低价值
→ 忽略

转化阶段、重要活动说明、价格规则说明等可定义为“保护区”，只允许 P0/P1 打断。

## 12. 播放状态机

建议播放器状态至少包含：

- IDLE
- PRELOADING
- PLAYING_MAINLINE
- PENDING_INTERRUPT
- PLAYING_INTERRUPT
- RESUMING
- SWITCHING_PLAN
- ERROR_RECOVERY
- HUMAN_TAKEOVER

主要流程：

PLAYING_MAINLINE
→ 收到事件
→ 判断优先级和热度
→ 不值得处理：继续
→ 值得处理：PENDING_INTERRUPT
→ 当前语义段结束
→ 写 bookmark
→ PLAYING_INTERRUPT
→ 回答结束
→ 判断中断时长
→ DIRECT / BRIDGE / SWITCH_PLAN
→ 回到 PLAYING_MAINLINE

## 13. Redis 建议职责

Redis 负责“状态和索引”，不负责长期大文件。

建议逻辑对象：

### Speech Bank Meta
保存：
- fingerprint
- bank_id
- version
- status
- created_at
- available_plan_count

### Plan Index
保存：
- plan_id
- topics
- chunks
- last_played_at
- play_count
- cooldown_until

### Playback State
保存：
- current_plan
- current_chunk
- next_chunk
- state
- bookmark
- heat_level

### Question Queue
保存：
- normalized_intent
- question_text
- priority
- created_at
- expire_at
- repeat_count

### Heat State
保存：
- level
- score
- last_update
- source metrics

### FAQ Cache
保存：
- intent
- fact_version
- answer_text

- usage count

### Resume Bridge Index
保存：
- from_topic
- to_topic

- audio assets

## 14. OSS 与本地缓存生命周期

### 新版本发布

后台完成：
文案
→ 切段
→ TTS
→ 校验
→ 上传 OSS
→ 写 manifest
→ Redis 标记 READY

终端：
发现 fingerprint 更新
→ 下载 manifest
→ 下载缺失资源
→ 校验完整
→ 原子切换版本

### 老版本

不要立即删除。

保留一定时间用于：
- 回滚
- 网络异常
- 终端未完成更新

达到回收周期后：
- 删除 OSS 冗余音频
- Redis 元数据归档/清除
- 终端清理本地旧缓存

## 15. 失败降级

### 大模型失败

主线不受影响。

继续播放本地 Speech Bank。

### TTS 实时失败

互动回答：
- 尝试已有 FAQ 音频
- 或跳过该互动
- 主线继续

### Redis 短暂异常

终端继续使用当前本地 manifest 和播放队列。

### OSS 异常

只要本地缓存完整：
直播继续。

### 网络异常

本地主线照常播放。
实时互动能力降级。

这也是本方案相比“每句话云端生成”的核心优势。

---

## 16. 成本策略

新的成本逻辑：

### 主线内容

商品/活动不变时：
- LLM 批量生成一次
- TTS 批量生成一次
- OSS 保存
- 终端下载一次
- 后续重复播放几乎无新增 AI 成本

### 实时互动

只有：
- 复杂问题
- 新事实解释
- 极少量现场事件

才产生实时 LLM/TTS 成本。

### 预期效果

与“整场持续实时生成”相比：

- LLM 调用显著下降
- TTS 调用显著下降
- OSS/本地缓存成为主要分发链路
- 播放延迟趋近本地文件播放
- 云端抖动对直播影响明显降低

---

## 17. 质量控制

预生成并不等于固定录音循环。

必须同时解决重复问题。

建议：

- 最近 N 套不重复
- 同一开场冷却
- 同一 CTA 冷却
- 同一重点组合冷却
- 同一长句冷却
- 高频核心事实允许重复，但句式变化
- 一轮中已讲过的主题写入 recent_topics
- SWITCH_PLAN 时优先选未充分覆盖主题

系统追求的是：

**事实稳定，结构稳定，表达动态。**

---

## 18. 动态事实与静态事实分离

静态事实：
- 产地
- 品种
- 养殖方式
- 规格
- 原切定义
- 烹饪常识

可长期复用。

动态事实：
- 当前价格
- 券
- 库存
- 赠品
- 活动截止时间
- 实时销量
- 发货临时调整

必须有：
- 来源
- 更新时间
- TTL
- 生效时间
- 失效策略

Fingerprint 应纳入动态事实版本。

活动变化时，只失效受影响的 Speech Bank，不应无差别清空所有历史资产。

- 模型调用分层

第五阶段：
- OSS 发布与终端版本同步
- 本地缓存
- 回滚/容灾

第六阶段：
- 真实直播压测
- 重复率测试
- 中断回接测试
- 热场/冷场策略回归
- 成本统计

## 20. 当前确定的设计原则

1. 主线以预生成语音为主，而不是实时大模型为主。
2. 商品/活动不变，尽量不重复生成。
3. 音频不长期存 Redis。
4. OSS 做中央资产库，终端做本地缓存。
5. Redis 做索引、状态、游标、队列和热度。
6. 热度越高，越少回答普通问题。
7. 热度越低，越主动互动。
8. FAQ/缓存优先于大模型。
9. 不在自然语义中间粗暴打断。
10. 短中断直接续，中等中断桥接，长中断换稿。
11. 回接句提前准备并提前 TTS，尽量不临时调用模型。
12. 播放器必须知道“讲到哪、接下来讲什么、刚才为什么被打断”。
13. 已讲主题必须有记忆，避免切稿后重复。
14. 云端异常不能让直播主线停掉。
15. 商品事实与活动事实必须可追溯、可版本化。
16. 后续代码实现不得破坏现有事实约束和合规边界。

## 21. 架构命名

本方案后续统一使用以下模块名：

- **Speech Bank**：预生成文案/语音库存
- **Content Fingerprint**：内容版本指纹
- **Heat Controller**：直播热度控制器
- **Semantic Bookmark**：语义断点/书签
- **Resume Bridge**：回接桥
- **FAQ Cache**：高频问答缓存
- **Playback State Machine**：播放状态机
- **Local Audio Cache**：终端本地音频缓存

新主架构可概括为：

**Speech Bank + Heat Controller + Semantic Bookmark + Resume Bridge**

其目标不是让大模型“每秒都参与直播”，而是让大模型在后台生成高质量内容，在真正需要智能判断和实时回答的地方才参与。
